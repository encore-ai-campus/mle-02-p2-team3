# 카드 혜택 GraphRAG 과제 산출물 M0–M9

## 과제 범위

- **주제:** 하나·우리카드 상품설명서의 혜택·조건·한도·제외 규정을 구조화<br /> - GraphRAG 검색으로 원문 근거를 연결해 카드 혜택 질문에 답한다.
- **문서 범위:** 하나·우리카드 대표 상품설명서.<br /> - 사용자는 과제용 활용을 확인했고 원문 PDF를 저장소에 재배포하지 않기로 했다.
- **이용 조건:** 위 범위는 과제 범위에 대한 사용자 결정이다. <br /> -카드사의 별도 이용 허가를 확인했다는 뜻은 아니다.
- **질문 예:** 카드의 혜택과 연결된 조건·한도·대상은 무엇인가? <br /> - 특정 대상에 적용되거나 제외되는 혜택은 무엇인가?
- 문서 목록·버전·출처·쿼리  관련하여 아래사항 참고<br />  [하나 manifest](../src/data/hana_all/manifest.csv), [우리 manifest](../src/data/woori_all/manifest.csv),  [그래프 질의 파일](../src/card_benefit/payment_card/file_pipeline/graph/queries.cypher)

## M1 



### 전처리 전

```text
[가상 카드 안내 PDF 1쪽]
가상 카드 안내
예시 혜택
```

### 전처리 후

```json
{
  "doc_id": "0123456789abcdef",
  "chunks": [
    {
      "chunk_id": "0123456789abcdef-p0001-c01",
      "page_no": 1,
      "start_pos": 1,
      "end_pos": 14,
      "text": "가상 카드 안내\n예시 혜택"
    }
  ]
}
```

   -실제 구현은 에서 페이지 텍스트·위치를 추적 [traceability.py](../src/card_benefit/payment_card/file_pipeline/doc_index/traceability.py) 및 청크는 다음과 같음 [chunking/build.py](../src/card_benefit/payment_card/file_pipeline/chunking/build.py). <br /> -위치는 페이지 텍스트 기준 1부터 시작하며 끝 위치를 포함

## M2 — 온톨로지 유형과 관계

### 정의 전

개체 종류와 관계 방향을 제한하지 않으면 추출기마다 연결이 달라질 수 있음

### 정의 후

| 개체 유형 | 의미 |
|---|---|
| `Benefit` | 혜택 |
| `Condition` | 이용 조건 |
| `Limit` | 혜택 한도 |
| `Target` | 적용·제외 대상 |

| 관계 | 허용 방향 |
|---|---|
| `HAS_CONDITION` | Benefit → Condition |
| `HAS_LIMIT` | Benefit → Limit |
| `APPLIES_TO` | Benefit → Target |
| `EXCLUDES` | Benefit → Target |
| `MUTUALLY_EXCLUSIVE` | Benefit → Benefit |

이 정의는 [추출 스키마](../src/card_benefit/payment_card/file_pipeline/extraction/schema.py)와 [온톨로지 v1 기록](작업이력/02-스키마-온톨로지/온톨로지-v1.md) <br /> - `Card → Benefit`의 `OFFERS` 관계는 추출 JSON이 아니라 상품 인덱스 기반 그래프 조립에서 추가

## M3 — 실제 프롬프트

-다음은 실제 사용 프롬프트 생성 함수 [extraction/prompt.py의 `build_prompt(chunk)`](../src/card_benefit/payment_card/file_pipeline/extraction/prompt.py). <br /> -프롬프트는 스키마 필드·enum·허용 관계·예시 JSON을 코드에서 삽입하고, 청크별 `page_no`, `start_pos`, 원문 텍스트를 덧붙인다. <br /> -실제 실행 시에는 청크마다 원문 부분이 달라진다.

핵심 지시에는 원문에 없는 관계 추측 금지, 허용된 S-P-O 유형만 사용, 엔티티·관계별 원문 인용 근거 필수, JSON만 출력, 반복 인용문의 위치는 임의 확정하지 않기가 포함. <br /> -금액·한도·제외·표 관계 규칙도 프롬프트에 존재<br /> -`Condition.min_amount`는 원 단위 실적·결제 기준 금액이고 `Condition.text`는 조건 원문을 보존.

## M5 — 중복 개체 정규화

-실행 코드는 [graph/entity_resolution.py의 `transform()`](../src/card_benefit/payment_card/file_pipeline/graph/entity_resolution.py). <br /> -사람 승인 mapping에 따라 대표 ID를 정하고, 노드 ID·관계 endpoint·근거 대상을 갱신하며 중복 관계를 접고 audit 파일을 생성.

| 구분 | 그래프 |
|---|---|
| 변환 전 노드 | `card-1`; `benefit-1: Coffee`; `benefit-2: Coffee discount` |
| 변환 전 관계 | `offers-1: card-1 → benefit-1`; `offers-2: card-1 → benefit-2` |
| 사람 승인 mapping | 같은 카드 내 `benefit-2`를 대표 ID `benefit-1`에 병합 |
| 변환 후 노드 | `card-1`; `benefit-1` |
| 변환 후 관계 | 중복 `OFFERS`를 접어 `offers-1: card-1 → benefit-1` 하나 유지 |
| 근거 | `benefit-2`의 노드 근거와 `offers-2`의 관계 근거를 대표 ID로 재연결 |

-코드 검증은 30개 통과했고, 테스트는 다음과 같음 [test_file_pipeline_graph_entity_resolution.py](../src/card_benefit/payment_card/tests/test_file_pipeline_graph_entity_resolution.py).

## M6 — 스키마 매핑과 Neo4j 적재

### 매핑

| 그래프 개체·관계 | Neo4j 라벨·관계 |
|---|---|
| Card / Benefit / Condition / Limit / Target | `FpCard` / `FpBenefit` / `FpCondition` / `FpLimit` / `FpTarget` |
| Evidence | `FpEvidence` |
| Card → Benefit (`OFFERS`) | `FP_OFFERS` |
| Benefit → Condition (`HAS_CONDITION`) | `FP_HAS_CONDITION` |
| Benefit → Limit (`HAS_LIMIT`) | `FP_HAS_LIMIT` |
| Benefit → Target (`APPLIES_TO`, `EXCLUDES`) | `FP_APPLIES_TO`, `FP_EXCLUDES` |
| Benefit → Benefit (`MUTUALLY_EXCLUSIVE`) | `FP_MUTUALLY_EXCLUSIVE` |

-노드 근거는 `(FpNode)-[:FP_HAS_EVIDENCE]->(FpEvidence)`로 연결하며,<br /> -관계 근거는 `FpEvidence.edge_id`로 식별한다.

### 코드

- [graph/export.py](../src/card_benefit/payment_card/file_pipeline/graph/export.py)는 추출 결과를 네 그래프 CSV로 변환한다.
- [graph/cypher_export.py](../src/card_benefit/payment_card/file_pipeline/graph/cypher_export.py)는 고유 제약과 `MERGE`를 사용하는 Neo4j Browser용 Cypher 파일을 만든다.
- [graph/load.py](../src/card_benefit/payment_card/file_pipeline/graph/load.py)는 Neo4j가 아니라 Supabase `public.fp_*` 적재용이다.

-2026-11-06 사용자 실행 기록은 Neo4j에서 도메인 노드 12,144개, 관계 15,697개, `FpEvidence` 23,970개를 확인.<br /> -CSV 근거 24,066행과 Neo4j 근거 수 사이 96건 차이의 원인은 미확인.<br /> -현재 DB를 재조회한 값은 아니다. 상세는 [지식그래프 설계](설계/지식그래프.md#5-저장과-챗봇-읽기)와 [적재 작업 이력](작업이력/06-챗봇연결-골든셋/2026-11-06-PPT요구사항대조-Neo4j적재-README3개-laptop.md)을 참고.

## M7 — Cypher 조회와 시각화

실제 질의 모음은 [graph/cypher/queries.cypher](../src/card_benefit/payment_card/file_pipeline/graph/cypher/queries.cypher)이며. 카드 ID를 넣어 해당 카드의 혜택과 조건·한도·대상을 화면에 펼치는 예시는 다음과 같다.
<img width="1905" height="1001" alt="image" src="https://github.com/user-attachments/assets/d94e1ac9-25f6-4cb8-b085-4f59e49ea5d6" />

```cypher
MATCH path=(c:FpCard {id: $card_id})-[:FP_OFFERS]->(b:FpBenefit)
OPTIONAL MATCH (b)-[:FP_HAS_CONDITION|FP_HAS_LIMIT|FP_APPLIES_TO|FP_EXCLUDES]->
  (detail:FpCondition|FpLimit|FpTarget)
RETURN path, detail
LIMIT 100;
```

```mermaid
graph LR
  C["FpCard 카드"] -->|FP_OFFERS(제공)| B["FpBenefit 혜택"]
  B -->|FP_HAS_CONDITION(조건)| CO["FpCondition 조건"]
  B -->|FP_HAS_LIMIT(한도)| L["FpLimit 한도"]
  B -->|FP_APPLIES_TO(적용대상)| T["FpTarget 적용 대상"]
  B -->|FP_EXCLUDES(제외대상)| X["FpTarget 제외 대상"]
```


-화살표는 저장된 방향을 나타낸다. `OPTIONAL MATCH`는 상세 노드가 없는 혜택도 결과에서 유지.<br /> -`LIMIT 100`으로 결과가 잘렸는지 확인해야 하며, 스키마에는 Condition과 Limit을 직접 잇는 관계가 없으므로 각각의 대응을 추정하면 안 된다.

## M9 — 통합 시연과 회고

시연에서는 한 문서와 한 질문을 고정해 아래 연결을 보여준다.

1. 문서와 출처·버전·활용 범위
2. 문서 ID → 페이지·청크 ID와 원문 위치
3. 프롬프트·스키마 → 추출 트리플과 근거
4. 사람 승인 mapping → 정규화 노드·관계·근거
5. Neo4j 적재 → 실제 Cypher 결과·화면
6. 원문 대조 결과, 오류·수정·재확인


### KPT 회고 양식

| 항목 | 회고 내용 |
|---|---|
