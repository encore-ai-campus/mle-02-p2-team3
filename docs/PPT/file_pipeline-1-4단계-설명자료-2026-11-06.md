### 청크가 없는 대표 문서 57개 (질문받기 쉬운 부분)
인덱스 대표 문서 263개의 전체 해시와 청크 파일의 해시를 대조하면, 청크가 있는 문서가 206개, 없는 문서가 57개다. 57개는 인덱스의 메타 열(문서 종류·카드 종류·OCR 필요 표시)로 분류할 수 있다. **다만 메타 열만으로 "왜 산출물이 없는지"를 확정한 것은 아니다.**

- **결정 문서로 뒷받침되는 제외는 10개**(약관 3 + 체크카드 7)다. 나머지 47개는 OCR 필요 표시가 붙은 문서이고, 처리 대기일 가능성이 높지만 의도적 제외인지는 결정 문서에서 확인하지 못했다.
- 우리 OCR 필요 대표 문서 45개 = 상품설명서 25 + 브랜드 서비스 19 + 분류 미정 1이다. 이 45개가 앞서 말한 "우리 이미지 문서 45개"와 같은 집합이다. 전체 인덱스 행으로 보면 OCR 필요가 우리 75개이므로 분모를 항상 같이 말한다.

### 문서에 적힌 옛 값과 다른 곳
- 작업이력과 프로젝트 지도에는 **"4단계: 213개 문서(하나 97·우리 116)"**로 적혀 있다. 2026-11-02 시점 기록이고, 현재 로컬 청크 산출물은 **206개 문서(하나 95·우리 111)**다. 하나 2개, 우리 5개가 줄었는데 **어떤 문서가 빠졌는지는 당시 문서별 목록이 없어 확인하지 못했다.** (줄어든 7개와 체크카드 7개의 개수가 같지만 같은 문서라는 증거는 없다.)
- 이전에 정리한 요약에는 "대표 253문서·1,028쪽"도 있었는데, 인덱스 파일에서 직접 세면 **263문서·1,061쪽**이다. 이전 요약의 계산 기준을 확인하지 못해 차이 원인은 모른다. 설명에는 직접 센 값을 쓴다.

## 2. 이 방식의 특징 (왜 이렇게 했나)

1. **청크가 생성된 206개 문서에서는 "어느 문서 몇 쪽 몇 번째 글자"가 따라붙는다.** 청크와 추출 결과는 `doc_sha256 + 쪽 + 시작/끝 위치`로 원문을 가리킨다. 그래서 답이 틀려도 원문에서 대조할 수 있다(청크가 없는 57개 문서에는 해당하지 않는다).
2. **청킹 단계에는 만들 때마다 자동 검사가 들어 있다.** 청크를 이어 붙이면 쪽 원문과 같은지, 해시가 인덱스와 같은지, id가 겹치지 않는지를 검사하고 어긋나면 오류로 중단한다(코드와 테스트로 확인). 오늘 밤 별도로 다시 검사한 결과도 불일치 0건이었다.
3. **팀 `db_pipeline`과 섞이지 않는 독립 구현이다.** 같은 원천 문서를 다른 방식으로 처리하므로 코드와 입력 경로가 분리돼 있고, 결과 계약을 정하면 서로 비교할 수 있다(비교는 아직 하지 않았다). `docs/프로젝트-지도.md` 1절에도 "서로를 입력으로 쓰지 않는다"고 적혀 있다.
4. **결정과 이력이 문서로 남아 있다.** `docs/결정/README.md`(결정 14건), `docs/작업이력/`(단계별 폴더)에 무엇을 왜 정했는지 기록돼 있다.

## 3. 시연 (3~5분, 화면 순서)

한 상품을 정해 PDF 한 쪽이 청크가 되기까지를 따라간다. **시연 전에 선택한 문서의 일치 검사를 한 번 돌려 확인해 둔다.** 기존 자료를 그대로 쓸 수 있다: `docs/프로젝트-코드흐름-한건따라가기.md`(에너지 더블 카드), `docs/프로젝트-코드흐름-01-04.md`의 "발표용 2분 설명문".

1. 인덱스 한 줄: `documents.csv`에서 그 상품의 문서 행(해시, 대표 여부, 쪽수).
2. 원문 추적: 같은 해시의 쪽별 원문과 글자 위치.
3. 청크: 같은 쪽의 청크 id, 시작/끝 위치, "원문[시작:끝] == 청크 본문"이 같다는 확인.
4. (선택) 이어지는 5~11단계를 한 줄로: 이 청크가 추출 결과, 그래프, 챗봇 답변의 출처로 이어진다.

## 4. 이어서 한 일 (5~11단계, 보조 한 장)

- **(아래 5~11단계 수치는 작업 기록의 값이며, 실행 날짜와 평가 방식을 함께 말한다.)**
- **추출:** 청크 1,032개를 LLM으로 추출(성공 998·실패 34).
- **그래프 적재:** 하나·우리 결과를 Supabase `public.fp_*`에 적재(하나 노드 5,748, 우리 4,561).
- **챗봇 평가:** 골든셋 80문항, dev 3회 평균 82.9%(자동·AI 판정). **사람이 확정한 정확도는 아직 0건이다.**
- **추출 재현율(정답 라벨 124개 기준):** Benefit 58%·Condition 45%·Limit 54%·Target 45% (라벨이 표본이라 참고용).

## 5. 솔직하게 먼저 말할 한계

1. 사람이 확정한 정확도는 없다. 점수는 자동·AI 판정이다.
2. OCR 필요 표시 대표 문서 47개(하나 2·우리 45)와 실패 청크 34개는 그래프에 없다.
3. 3·4단계 산출물이 로컬 폴더라 팀이 바로 재현하기 어렵다(이식 브랜치 `port/file-pipeline-onto-main`은 코드·문서만 포함).
4. 개발 과정에서 Claude와 Codex를 구현 보조 도구로 썼다. 결정과 실행 기록은 `docs/결정/README.md`와 `docs/작업이력/`에 남아 있다. (역할 분담은 본인이 설명하는 내용이고, 커밋 기록만으로 입증되는 것은 아니다.)
5. 결과 A(`file_pipeline`)와 결과 B(`db_pipeline`) 비교(8단계)는 아직 하지 않았다.

### 팀 안에서의 위치를 설명하는 문장 (중립)
- file_pipeline은 문서 수집부터 쪽별 원문 추적, 청킹, 추출 결과 검증까지 파일 단위로 이어지는 처리 흐름이다.
- 문서와 청크의 위치 메타데이터를 유지해 결과를 원문 쪽과 연결할 수 있다.
- 모호하거나 찾지 못한 근거를 별도 상태로 남겨, 자동 결과와 사람이 볼 대상을 구분한다.
- 결과 계약을 정하면 데이터베이스 중심 방식과 같은 문서에서 독립적으로 결과를 비교할 수 있다.
