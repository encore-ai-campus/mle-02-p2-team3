### 3페이지. 프로젝트의 도입 목적

**제목**

정확한 안내를 위해 혜택·조건·근거를 함께 구조화했습니다

**화면 핵심 문구**

**정확한 고객 안내**
- 혜택, 한도, 조건, 제외 대상을 함께 제공
- 답변마다 원문 쪽·위치 근거 확인

**구조화된 비교 기반**
- 카드·혜택·조건·한도·대상을 같은 모델로 표현
- 하나·우리 두 카드사를 같은 구조에 적재

**검증 가능한 품질 관리**
- 자동 검증 + 사람 확인을 분리해 기록
- 답변 시험 결과를 반복 측정

**발표 스크립트**

저희가 우선한 목표는 두 가지입니다.

첫째, 고객 질문에 혜택만 답하지 않고 한도와 조건, 제외 대상을 함께 답하는 것입니다.

둘째, 모든 답이 상품설명서의 어느 쪽, 어느 위치에서 왔는지 확인할 수 있게 하는 것입니다.

비교·분석 기능은 이 구조화가 바탕이 되어야 가능해서, 현재는 구조화를 마치고 검증을 진행하는 중이며 비교 기능 자체는 다음 단계입니다.

### 4페이지. 카드 혜택정보의 복잡성

**제목**

하나의 카드 혜택에도 여러 적용 조건이 연결되어 있습니다

**화면 핵심 문구**

SHINSEGAE by JADE HanaCard — 디지털 컨텐츠 청구 할인

- 혜택에 조건 3개, 한도 1개, 근거 2곳이 연결
- 자동납부 결제 건만 서비스 제공
- 포인트·캐시·머니충전·컨텐츠 개별 결제·간편결제 등은 제외
- 지난달 실적 50만원 이상, 월 할인 한도 1만원 `[확인 필요: 발표 전 PDF 7쪽 재확인]`

**발표 스크립트**

하나카드 SHINSEGAE by JADE의 디지털 컨텐츠 할인을 사례로 보겠습니다.

그래프에서 이 혜택에는 조건 세 개와 한도 한 개가 연결되어 있고, 각각 상품설명서 근거 위치가 붙어 있습니다. 직접 그래프를 조회해 확인한 구조입니다.

할인율만 보면 이 혜택을 받을 수 있는지 알 수 없습니다. 자동납부 결제만 인정되고, 간편결제나 앱스토어 결제 등은 제외된다는 조건이 함께 있어야 정확한 안내가 됩니다.

저희는 이런 혜택과 조건, 근거의 관계를 데이터로 표현했습니다.

### 5페이지. 상품설명서 데이터의 구조화 과제

**제목**

상품설명서의 혜택과 조건을 비교 가능한 형태로 정리할 때 어려웠던 점

**화면 핵심 문구**

- 한도가 여러 개인 혜택: 하나 102개, 우리 208개 `[이력 기재 수치, 집계 정의 재확인 필요]`
- 같은 문구라도 어느 혜택·구간의 조건인지 연결 필요
- 우리카드 이미지 문서 45개(126쪽): 그래프 미반영, OCR 결과 검수·반영 대기
- 인용문 위치 실패: 20개 청크 시범에서 38건 → 0건

**발표 스크립트**

PDF에서 문장만 뽑으면 끝나지 않았습니다.

한도가 여러 개 있는 혜택이 많아서, 각 한도가 어느 실적 구간에 해당하는지 연결이 필요했습니다. 작업 기록상 이런 혜택이 하나카드에서 102개, 우리카드에서 208개였습니다. 다만 이 수치는 기록된 값이고 집계 기준은 다시 확인해야 합니다. 그래서 혜택에 한도·실적 조건의 원문 구간을 함께 붙였습니다.

우리카드에는 이미지로만 된 문서 45개, 126쪽이 있습니다. OCR은 진행했지만 결과의 검수와 반영이 남아 있어서, 현재 이 문서들은 그래프에 반영되지 않았습니다. 따라서 해당 상품의 혜택은 비어 있을 수 있습니다.

또 추출한 문장이 원문의 정확히 어디인지 찾는 과정에서, 프롬프트를 보강하며 위치를 찾지 못한 건수를 38건에서 0건으로 줄였습니다. 이는 20개 청크 시범에서의 결과입니다.

### 6페이지. GraphRAG 기반 데이터 구성

**제목**

혜택과 조건의 관계를 원문 근거와 함께 관리하는 구조를 구현했습니다

**화면 핵심 문구**

공식 상품설명서 PDF (하나·우리)

→ 문서 인덱스 · 쪽별 원문 · 청킹 (청킹 검증 213개 문서)

→ LLM 혜택·조건 추출 + 근거 위치 부여

→ 자동 검증 · 사람 확인

→ PostgreSQL `public.fp_*` 적재 (노드 · 엣지 · 근거)

→ 챗봇 그래프 탐색 / Neo4j 로컬 시각화

**발표 스크립트**

상품설명서를 쪽별로 읽어 청크로 나누고, 청크마다 혜택·조건·한도·대상을 추출합니다. 추출한 모든 항목에는 원문 쪽과 글자 위치를 부여하고 자동 검증을 거칩니다.

그래프 모델은 스키마상 노드 여섯 종류, 관계 여섯 종류를 허용하고, 실제 적재에서 만들어지는 노드는 카드·혜택·조건·한도·대상 다섯 종류입니다. 카드가 혜택을 제공하고, 혜택에 조건과 한도, 적용 대상과 제외 대상이 연결됩니다.

프로젝트 기록 기준으로 하나카드 전체는 노드 5,748개, 엣지 7,956개, 근거 11,287건이고, 우리카드는 현재 추출분이 노드 4,561개, 엣지 5,173개, 근거 9,266건입니다. 모두 PostgreSQL에 적재했습니다. `[확인 필요: 발표 직전 재조회]`

Neo4j는 구조를 눈으로 확인하는 로컬 시각화 용도로만 사용합니다.

### 7페이지. 활용 방안 ① 정확한 고객 안내

**제목**

그래프에서 찾은 혜택·조건·근거로 답하는 챗봇을 시험했습니다

**화면 핵심 문구**

**질문 예시**

신세계 by JADE 디지털 콘텐츠 할인 받으려면 결제는 어떻게 해야 돼요?

**그래프에 있는 정답 정보**

- 자동납부 결제 건만 서비스 제공
- 포인트·캐시·간편결제·앱스토어 결제 등 제외
- 상품설명서 7쪽 근거 위치

**그래프에서 만든 질문의 자동 판정 시험 (24문항, 하나 12·우리 12)**

- 개선 규칙: 하나 10/12, 우리 7/12
- 원문 구간 부착 후 재시험: 하나 8/12, 우리 6/12
- 사람 확정 점수가 아님, 표본이 작아 변동이 큼

**발표 스크립트**

챗봇은 질문에서 관련 노드를 찾고, 그 주변 그래프를 읽어 답합니다.

24문항 자동 판정에서 정답을 모두 포함한 문항은 하나카드 10개, 우리카드 7개였습니다. 원문 구간을 붙인 뒤 재시험에서는 8개와 6개로 달라졌습니다.

이 숫자는 사람이 확정한 점수가 아니고, 질문이 추출 결과에서 만들어져 낙관적일 수 있으며, 문항이 24개뿐이라 변동 폭이 큽니다. 그래서 사람이 PDF 원문에서 직접 쓴 골든셋으로 다시 측정하고 있습니다.

### 9페이지. 활용 방안 ③ 상품 품질 개선 지원

**제목**

추출 검증 과정에서 드러난 문서의 모호함을 개선 후보로 쓸 수 있습니다 `[예정]`

**화면 핵심 문구**

**검증 중 확인한 사례**

- 한도가 여러 개일 때 구간 연결이 문서에 불분명한 경우
- 같은 표현이 문서마다 다른 범위를 가리키는 경우
- 이미지 문서에만 있는 정보

**활용 흐름**

구조화 → 검증 중 모호 항목 식별 → 개선 후보 → 담당자 검토

**발표 스크립트**

구조화와 검증을 하는 과정에서 사람이 읽기에도 모호한 조건이 드러났습니다. 예를 들어 한도가 여러 개일 때 어느 실적 구간에 해당하는지가 명확하지 않은 경우입니다.

이런 항목을 개선 후보로 모아 담당자에게 넘기는 활용을 생각할 수 있지만, 분석 결과만으로 상품의 품질을 단정하지는 않고 최종 판단은 담당자가 합니다. 현재는 방향만 제시하는 단계입니다.

### 10페이지. 활용 방안 ④ 조건 변경 영향 분석

**제목**

조건과 연결된 혜택을 따라가며 영향 범위를 확인하는 방향입니다 `[예정]`

**화면 핵심 문구**

**그래프에서 가능한 탐색**

특정 조건 → 연결된 혜택 → 혜택을 제공하는 카드 → 원문 근거

**현재 상태**

- 관계를 따라가는 구조만 확인함(영향 분석 기능은 아님)
- 변경 영향 분석 기능 `[예정]`, 자동 처리 아님

**발표 스크립트**

그래프에서는 조건 하나에서 출발해 그 조건이 붙은 혜택과 카드, 원문 근거까지 따라갈 수 있습니다.

변경 영향 분석은 이 탐색을 활용하는 방향이지만 아직 구현하지 않았습니다. 정책 변경을 자동으로 처리하는 기능이 아니며, 담당자가 검토할 후보를 보여 주는 용도입니다.

### 11페이지. 서비스 활용 구조

**제목**

공통 데이터 계약을 팀 DB 파이프라인과 맞추는 것이 다음 과제입니다

**화면 핵심 문구**

**두 갈래 파이프라인**

- 결과 A: 파일 기반(`file_pipeline`) — 추출·그래프·챗봇 시험
- 결과 B: DB 기반(`db_pipeline`) — 팀 DB 처리

**현재 상태**

- 그래프는 격리된 `public.fp_*`에 적재, 팀 스키마에는 쓰지 않음
- 팀 장부 스키마와의 공통 계약: 합의 대기
- 내부 API / MCP 연동 `[예정, 미구현]`

**발표 스크립트**

저희 팀은 같은 상품설명서를 두 방식으로 처리했습니다. 하나는 파일 기반이고, 하나는 DB 기반입니다.

두 결과를 같은 위치 기준으로 비교하고, 공통 데이터 계약으로 맞추는 작업이 다음 단계입니다. 현재 그래프는 팀 스키마와 분리된 공간에 적재했고, 팀 장부로 옮기는 기준은 팀 합의를 기다리고 있습니다.

API나 MCP로 다른 서비스와 연결하는 방안은 아직 구현하지 않았습니다.

## 부록. 팀원 초안과의 비교 — 팀원 초안 vs file_pipeline(결과 A) 기준

- 비교 대상 A: 팀원 초안 `src/card_benefit/docs/presentation/ppt스크립트초안.md` (원격 `main`, 커밋 6b5b937, 작성자 KimByungJoo, 2026-11-05)
- 비교 대상 B: 이 문서의 위쪽 본문 (file_pipeline 작업에서 확인한 수치만 사용)
- 기준일: 2026-11-05
- 한계: 팀원 초안의 근거 코드와 데이터(`db_pipeline`)는 읽지 않았다(프로젝트 지도 규칙). A의 사실 주장은 문서에 적힌 대로만 대조했고, 맞고 틀림을 판정하지 않았다. B의 정확도 수치는 자동·AI 판정이며 사람이 확정한 값이 아니다.

### 1. 한 줄 결론

두 문서는 **같은 13쪽 뼈대**(소개 → 업계 → 목적 → 복잡성 → 구조화 과제 → 데이터 구성 → 활용 ①~④ → 서비스 구조 → 검증 방향 → 결론)를 쓰지만, A는 **앞으로 할 활용 방안을 제안하는 문서**이고 B는 **이미 구현하고 측정한 것과 아직 아닌 것을 나눠 보이는 문서**다. 합치면 A의 활용 스토리에 B의 실측 수치와 상태 표시를 넣는 것이 가장 강하다.

### 4. A가 더 나은 점, B가 더 나은 점

- **A가 나은 점**: 활용 시나리오가 구체적이다(변경 영향 분석 흐름, 비교 항목 목록). 상품권 제외 규칙 같은 비교 사례가 있다. 청중이 "왜 필요한가"를 따라가기 쉽다.
- **B가 나은 점**: 숫자와 상태가 있다. 완료·진행·예정을 구분하고, 자동 판정 수치에 한계를 같이 적었다. 두 카드사를 같은 구조로 적재한 점을 보여 준다.

### 6. 합칠 때 제안

1. **뼈대는 A의 13쪽을 유지**한다(청중이 이해하기 쉬움). 이미 같은 틀이라 쪽 단위로 교체하기 쉽다.
2. **6쪽(데이터 구성)·7쪽(활용①)·12쪽(검증)은 B로 교체**한다. 건수와 시험 점수가 필요한 쪽이다.
3. **4쪽 사례는 둘 중 하나로 통일**한다. B 사례는 데이터 직접 조회로 뒷받침되고, A 사례는 데이터 출처를 확인해야 한다. A 사례를 쓰려면 먼저 5절 상 항목을 해소한다.
4. **8·10쪽은 A의 시나리오를 유지**하되 "구현 전"을 B처럼 명시한다.
5. **11쪽은 결과 A/B 구성과 합의 대기 항목**(B 내용)을 반영한다.
6. 수치 옆에는 **자동 판정인지 사람 판정인지**를 항상 붙인다.
7. 발표 직전에 B 문서 맨 아래 「수치 근거와 확인 상태」 표를 다시 대조한다. 골든셋 사람 판정이 끝나면 7쪽·12쪽 수치를 갱신한다.

### 7. 이 비교에서 하지 않은 것

- A의 근거 코드(`db_pipeline`)와 데이터는 열지 않았다. A의 주장이 맞는지는 판정하지 않았다.
- B의 수치는 프로젝트 지도·품질 문서·직접 조회에서 가져왔다. 지도 기재 수치는 이번에 원본 결과 파일로 다시 계산하지 않았다.
- 슬라이드 디자인과 분량(시간)은 비교하지 않았다.
