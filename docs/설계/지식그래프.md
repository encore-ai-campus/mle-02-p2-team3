# 지식 그래프 설계

## 1. 목적과 범위

이 그래프는 `file_pipeline`이 추출한 카드 혜택·조건·한도·대상을 노드와 관계로 저장하고, 챗봇이 질문에 관련된 부분 그래프를 읽게 한다. 추출 원문 전문을 저장하는 장부가 아니라, 식별 가능한 근거 위치와 구조화 결과를 연결한다. 현재 챗봇 시험 저장소는 사용자 관리 Supabase `public.fp_*`와 `fp_chat`이다. 팀 `file_pipeline` 장부로 이관·통합하는 일은 합의 대기다.

## 2. 현재 모델

SQL은 여섯 노드 종류와 여섯 관계 종류를 허용한다. 추출 모델이 정의하는 관계는 다섯 종류이고, `OFFERS`는 상품 인덱스와 혜택을 연결하도록 export가 추가한다. `Issuer`는 스키마·검증기·Neo4j 내보내기에는 허용되지만, 현재 `export.py`의 노드 생성 그룹에는 없다. 따라서 일반 file-pipeline 적재에서 생성되지 않는 것으로 코드상 확인된다.

| 관계 | 허용 출발 → 도착 | 용도 |
|---|---|---|
| `OFFERS` | Card → Benefit | 상품 인덱스의 상품-혜택 연결 |
| `HAS_CONDITION` | Benefit → Condition | 혜택 이용 조건 |
| `HAS_LIMIT` | Benefit → Limit | 혜택 한도 |
| `APPLIES_TO` | Benefit → Target | 적용 대상 |
| `EXCLUDES` | Benefit → Target | 제외 대상 |
| `MUTUALLY_EXCLUSIVE` | Benefit → Benefit | 함께 제공되지 않는 혜택 쌍 |

| 노드 | export가 넣는 기본 속성 |
|---|---|
| Card | `issuer`, `product_name`, `card_type` |
| Benefit | `name`, `method`, `rate`, `amount` |
| Condition | `text`, `kind`, `min_amount` |
| Limit | `text`, `period`, `amount`, `unlimited`, `shared` |
| Target | `text`, `kind` |
| Issuer | 기본 export 생성 없음 |

열거형은 추출 스키마 기준이다. Benefit.method는 `DISCOUNT`, `CASHBACK`, `POINT`; Condition.kind는 `SPEND_REQ`, `EXCLUDE`, `USAGE`, `PAYMENT`, `MERCHANT`, `OTHER`; Limit.period는 `TXN`, `DAY`, `MONTH`, `YEAR`, `UNKNOWN`; Target.kind는 `MERCHANT`, `INDUSTRY`, `CHANNEL`, `SERVICE`, `OTHER`다. `MUTUALLY_EXCLUSIVE`는 자기 자신을 연결할 수 없으며 추출기·export·SQL 적재 검증이 끝점 종류를 검사한다.

## 3. 식별자 규칙

Benefit·Condition·Limit·Target 노드 ID는 `{chunk_id}:{추출 item id}`이고, 엣지는 청크 ID와 관계 순번으로 만든다. Card ID는 `card:{issuer}:{product_key}`다. product_key 우선순위는 `CD_ID`, `PC_SEQ`, `디자인코드`, `모바일_CD_NO`, `product_code` 순으로 첫 유효값을 선택한다. 우리카드의 `product_code`는 숫자 상품 코드로 쓰이는 사례가 확인됐다. 다른 노드 ID의 역사적 표기 `{doc_id_prefix}-p{page}-c{chunk}:{item}`은 과거 파일·청크 명명 규약을 설명하는 예이며, 현재 export 구현은 전달된 `chunk_id` 전체를 접두부로 사용한다. 실제 입력 ID가 이 형태인지 일반화할 수 없어 미확인이다.

## 4. 근거 모델

`fp_evidence` 열은 `node_id`, `edge_id`, `doc_sha256`, `page_no`, `start_pos`, `end_pos`, `quote_status`다. 대상 노드 또는 엣지 중 정확히 하나에 연결한다. `located`는 위치를 찾았다는 뜻이며 쪽 번호와 시작·끝 위치가 있어야 한다. `ambiguous`는 같은 문구의 위치가 모호해 임의 선택하지 않은 상태, `missing`은 위치를 찾지 못한 상태다. 두 상태는 위치 열을 비운다. 좌표는 페이지 텍스트 기준 1부터 시작하고 끝 위치를 포함한다. 인용 본문이나 청크 본문은 이 테이블에 저장하지 않는다.

## 5. 저장과 챗봇 읽기

Supabase SQL은 `fp_load_runs`, `fp_nodes`, `fp_edges`, `fp_evidence` 네 테이블을 정의한다. PK/FK, 비어 있지 않은 ID, 중복 방지, 해시 형식, 근거 대상 하나, 상태별 위치 규칙 및 엣지 끝점 종류 트리거가 있다. 네 테이블 모두 RLS 활성화 SQL이 코드에 있다. 스키마 주석은 정책을 만들지 않는다고 적는다. 실제 프로젝트 상태는 아래 2026-11-06 사용자 실행 기록을 참고한다. 이번 갱신에서 DB에 직접 접속하지 않았다.

`fp_chat.nodes`는 원 노드 ID를 `md5(id)::uuid`로 바꾸고, 이름은 `name`, `text`, `product_name`, ID 순으로 선택해 공백을 정리하고 80자로 자른다. 근거 문서마다 Document 노드를 만들며 이름은 해시 앞 8자리로 표시한다. `fp_chat.edges`는 원 엣지와 `SUPPORTED_BY`를 제공한다. 노드별 문서 링크는 최대 3개이며 located 근거를 우선한다. SQL은 뷰에 `security_invoker`를 지정하지 않아 기본 뷰 소유자 권한을 사용하고, `service_role`에 조회를 허용한다. 실제 뷰 소유자와 챗봇 연결 역할은 확인되지 않았다.

2026-11-06 프로젝트 지도와 사용자 실행 작업이력에는 전체 Supabase 그래프가 노드 12,144개·엣지 15,697개로 적재됐다고 기록돼 있다. 같은 수의 도메인 노드·관계를 로컬 Neo4j에서 확인했고 Neo4j 근거 노드는 23,970개다. 내보내기 원본 CSV의 근거 24,066행과의 차이 96개는 원인 미확인이다. 이 값은 DB를 이번에 직접 조회한 결과가 아니다. Neo4j는 로컬 시각화 경로이며, `FpEvidence` 노드까지 생성하는 점에서 Supabase의 근거 행 모델과 표현이 다르다.

한 번의 적재 및 삭제는 `run_id`로 구분된다. `load.py`는 기본 dry-run, `--execute` 명시 시 쓰며, CSV의 단일 run 일치·개수·ID·끝점·근거 상태를 검증한다. 삭제는 run 단위로 evidence, edges, nodes, load run 순서다.

## 6. 보강 변형

`source_text.py`는 Benefit에 `source_text`, `source_text_pages`, `source_text_truncated` 세 속성을 덧붙인다. 한도 근거 위치를 우선 anchor로 삼고, 조건 근거와 혜택 근거 창을 예산 내에서 더한다. 기본 상한은 700자이며 초과 구간은 생략 표식 ` … `으로 연결하거나 잘림 표시를 남긴다. 측정 결과(이력에 기록된 최신 재계산)는 서로 다른 금액 한도가 2개 이상 연결된 Benefit을 분모로 할 때 하나 86/88(97.7%), 우리 180/190(94.7%)에서 모든 한도 금액이 포함됐다. 이 수치는 실행 결과를 기록한 이력의 직접 계산값이다. 이전 전달값 하나 81/88, 우리 73/88(약 83%)은 기준·분모가 달라 최신값과 섞지 않는다.

`normalize_values.py`에는 금액·비율·조건 파서가 있지만 현재 `export.py`의 표준 경로에서 호출하지 않는다. `export.py`는 허용 속성을 추출 JSON에서 복사한다. 따라서 이 파서가 그래프 CSV 속성을 정규화한다고 보아서는 안 된다.

`cypher_export.py --lang ko`는 `kind_ko`, `cond_kind_ko`, `target_kind_ko`, `method_ko`, `period_ko`, `caption_ko`, 관계 `label_ko` 등을 보탠다. 코드상 기본 영어 출력 경로는 한국어 속성을 추가하지 않는다. 이력은 기본 출력의 바이트 단위 동일성을 주장하지만, 여기서는 모든 입력 CSV의 전후 출력물을 비교하지 않았으므로 바이트 동일성은 미확인이다.

## 7. 알려진 한계

| 한계 | 영향·근거 |
|---|---|
| 한도와 조건 사이 직접 연결 없음 | Limit은 Benefit에, Condition도 Benefit에 각각 연결된다. 복수 한도의 조건별 대응을 명시하지 못하며 source_text가 문맥을 보완한다. Hana 102·Woori 208 같은 복수 한도 사례 수는 미확인(이력 기재 수치). |
| 중복·동일 이름 | 같은 발급사 안에서 이름(공백·부호 정규화)이 같은 노드 그룹은 하나 917(2,827노드)·우리 595(2,036노드), 발급사 간 겹치는 이름은 178 그룹(CSV 기준 Codex 분석 2026-11-05; 정규화 전 문자열 비교는 159). 그 중 속성까지 모두 같은 쌍은 약 73%. 이름 시드는 여러 노드로 확장될 수 있다. 다만 24문항 시험에서 LLM이 고른 시드 중 발급사 간 공통 이름은 없었고, woori-04의 카드사 혼동은 '후보 목록에 카드사 정보가 없어서' 생긴 것이다. |
| 발급사 구분 미흡 | Issuer 노드 및 발급사 관계가 없고 Card의 `issuer` 속성만 있다. 발급사를 말하지 않은 질문에서 동명 노드 혼동 가능성은 추정이며, 후보 목록이 발급사 정보를 노출하는지 코드 경로에 따라 다르다. |
| 추출 누락·불확실 | `UNKNOWN` 월 한도 기간 등 원천 추출의 결손이 그래프에 남을 수 있다. hana-04('월 이용 횟수 한도')는 그래프에 호텔 발레파킹 한도가 '무제한/10회/5회'로만 있고 기간이 UNKNOWN이라 기대 정답 3(월 3회)을 낼 수 없는 추출 데이터 부족 사례(결과 파일 직접 확인). 한도가 둘 이상이고 금액이 서로 다른 혜택은 하나 102개·우리 208개, 그중 실적 조건이 둘 이상인 구간형은 하나 44개·우리 82개(CSV 직접 계산). |
| 우리 이미지 문서 OCR 품질 | 2026-11-06 OCR 실행 결과 117청크 중 깨끗한 성공 47(40.2%), 인용 위치 문제 42(35.9%), 빈 결과 27(23.1%), 재시도 실패 1이다. OCR 그래프는 Supabase에 적재된 최신 run에 포함되지만, 이 수치는 추출 정확성에 대한 사람 검수가 아니다. OCR 위치는 PDF 텍스트가 아니라 OCR 추적 텍스트 기준이며, 남은 실패 청크와 숫자 대조도 확인이 필요하다. |
| Neo4j 근거 행 차이 | 사용자가 확인한 Neo4j 근거 노드 23,970개와 export 원본 CSV 근거 24,066행 사이 96개 차이가 작업이력에 기록돼 있다. 원인은 미확인이다. |
| 범위 밖 | 텍스트 PDF인데도 추출·청킹에서 빠진 문서가 있다: 하나 약관 3개(부속약관·표준약관·체크카드 약관), 우리 체크카드 상품설명서 7개. 장부 드라이런이 '쪽·청크 JSON 없음'으로 보고한 문서가 이 10개이며(직접 확인) 의도된 범위 제외로 보이나 제외 결정 기록은 확인하지 못했다(추정). |

## 8. 팀 V7 초안과의 대응

| 그래프 개념 | V7 초안의 유사 개념 | 차이 |
|---|---|---|
| Benefit + 조건·대상·수치 | `card_bnft.rule_list`, `cond_expr`, `relation_list` | V7은 카드 중심 JSON 규칙 구조, 그래프는 분리 노드·엣지 |
| Condition | 카드/혜택/규칙 `cond_expr` JSON | V7은 AND/OR/NOT 표현 가능; 그래프 추출 Condition 노드와 일대일 대응 미정 |
| Limit | `bnft_limit_txt` 등의 원문 TEXT | 그래프는 Limit 노드와 `HAS_LIMIT`; V7 draft는 별도 한도 풀 및 규칙-한도 연결을 두지 않는다고 명시 |
| Evidence | `fp_evidence`의 위치·상태 | `card_source_evidence`는 quote 및 승인·문서/staging 참조가 중심. `quote_status` 대응 열은 확인되지 않음 |
| 실행/호출 이력 | `card_ai_run`, `card_ai_call` | `fp_load_runs`는 그래프 적재 실행 단위여서 AI 호출 이력과 다름 |
| 적재 전 후보 | `card_extr_stg` | staging raw JSON·상태·후보 종류를 보관. PK의 `stg_item_seq` 부재 문제는 V7 변경 보고서의 지적이며 draft 현행 확인은 미확인 |

V7 `STG_KIND`가 `BENEFIT`, `CONDITION`만 쓴다는 항목은 참조 파일의 관련 코드 정의를 직접 대조하지 못해 미확인으로 남긴다. 별도 [카드 혜택 적용 규칙 데이터 모델 제안](../자료조사/김병주/2026-10-31/카드혜택_적용규칙_데이터모델_설계결정안.md)은 `BenefitRule`, 조건식, `LimitPool`·tier를 제안하지만 문서에서 신규 테이블·컬럼은 현재 DB에 없다고 명시한다. 현재 GraphRAG 스키마와 합쳐진 구현으로 취급하지 않는다. 대응과 결정이 필요한 사항은 [결정 기록](../결정/README.md)의 지식그래프·장부 경계를 참조한다.

## 9. 설계 선택의 근거

청크별 ID 접두부는 추출 ID 충돌을 막고, 별도 근거 행은 본문 저장 없이 위치를 추적한다. `run_id`는 한 차례 적재를 검증·정리하는 단위다. `SUPPORTED_BY` 문서 노드는 기존 챗봇 그래프 인터페이스가 문서 근거까지 순회하도록 연결한다. 팀 V7과 저장 책임·조건 표현·증거 승인 흐름을 맞출 결정은 [결정 기록](../결정/README.md)에 연결한다.
