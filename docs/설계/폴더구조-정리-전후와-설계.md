## 1. 왜 정리했나

- `chat/`에는 챗봇 진입점, DB 연결, 답변 판정, 검색 보조, 평가 도구, 사람 검수 도구가 한 폴더에 섞여 있었다. 파일 이름만으로는 "서비스 코드"와 "평가용 도구"를 구분할 수 없었다.
- `extraction/`에는 LLM 추출 코드와, 추출 결과를 집계·검토·평가하는 도구가 섞여 있었다.
- 목표는 **폴더만 보고 "이 모듈이 흐름의 어느 단계에서, 어떤 역할로 쓰이는지"를 알 수 있게 하는 것**이다.

## 3. 어떻게 설계했나

### 3.1 흐름 순서가 기준이다

프로젝트는 수집부터 챗봇까지 11단계 흐름을 가진다. `file_pipeline` 안의 폴더가 그 단계와 대응하도록 했다.

| 단계 | 하는 일 | 폴더 |
|---|---|---|
| 1 수집 | PDF와 manifest | `src/data/*_all` (이 폴더 밖) |
| 2 분류·인덱스 | 대표 문서 선정, 상품 연결 | `doc_index/` |
| 3 원문 추적 | 쪽별 원문과 위치 JSON | `doc_index/`(`batch`, `traceability`) |
| 4 청킹 | 쪽 원문을 청크로 | `chunking/` |
| 5 추출 계약 | 온톨로지와 스키마 | `extraction/schema.py` |
| 6 LLM 추출 | 프롬프트, 실행기, 근거 위치 | `extraction/` 직속 |
| 7 검증 | 집계·검토·평가 | `extraction/report`, `review`, `eval` |
| 9~10 정규화·그래프 | 그래프 변환과 적재 | `graph/` |
| 11 질의·챗봇 | 검색, 답변, 화면, 평가 | `chat/` |

- 3단계 원문 추적을 최상위에 두지 않고 `doc_index/`에 둔 것은, 실제 호출 순서가 `doc_index/batch → traceability → chunking`이기 때문이다.
- 8단계(결과 A·B 비교)는 아직 구현이 없다.

### 3.2 `chat/`은 "무엇을 하는가"로 나눴다

| 폴더 | 기준 | 이유 |
|---|---|---|
| `answer/` | 답변을 만들고 점검 | 형식 지침, 판정, 숫자 근거 확인. 런타임과 평가가 함께 쓴다 |
| `retrieval/` | 검색 결과를 다듬음 | 중복 병합, 시드 보완, 출처 라벨 |
| `ui/` | 화면 | v2 화면과 화면 독립 도우미 |
| `eval/` | 오프라인 평가 도구 | 질문 생성, 골든셋, 검색·답변 평가 |
| `review/` | 사람 검수 자료 | HTML·CSV 대조 자료 |
| 직속 6개 | 진입점과 연결부 | 아래 참고 |

- **직속에 남긴 것**: `run_fp_chat`, `run_fp_chat_v2`(실행 진입점), `fp_chat_patch`, `openai_llm_patch`, `db_pool`(GraphRAG·OpenAI·PostgreSQL 연결부), `qa_log`(런타임 기록). 실행 명령과 여러 모듈이 함께 부르는 연결부라서, 옮기면 임포트 경로가 한꺼번에 흔들린다.
- `answer_eval`은 이름이 "평가"지만 런타임 Q/A 기록과 숫자 확인에서도 쓰이므로 `eval/`이 아니라 `answer/`에 두었다.
- `value_conflicts`는 질문과 그래프를 조사하는 오프라인 분석 도구라 `eval/`에 두었다.

### 3.3 확인한 호출 관계 (코드를 읽어 확인)

- `fp_chat_patch`가 `answer/`, `retrieval/`의 모듈을 부른다.
- `qa_log`와 `ui/app_v2`가 `answer/`를 부른다.
- `eval/`의 도구들이 `answer/`, `retrieval/`을 부른다.
- 반대로 `answer/`, `retrieval/`, `ui/`가 `eval/`을 부르지는 않는다(예외: `retrieval/seed_union`이 `eval/seed_matcher`의 함수를 하나 쓴다).

### 3.4 변경 원칙

1. **로직 불변**: 파일 이동과 임포트·경로 수정만 한다.
2. **단계당 15개 이하, 한 단계 = 한 커밋**: 문제가 생기면 그 단계만 되돌린다.
3. **임포트 규칙**: 패키지 경로(`payment_card.file_pipeline.chat.answer.answer_eval`)를 우선하고, 스크립트로 직접 실행하는 경우를 위해 같은 폴더 기준 fallback을 남긴 곳이 있다.
4. **폴더마다 README**: 모듈 표와 역할을 적어 폴더가 스스로 설명하게 했다. 이동할 때 표와 개수를 같이 고쳤다.
5. **참조 전부 갱신**: 코드 임포트, 테스트의 모듈 찾기, 노트북 셀, README, 점검 목록을 같은 단계에서 고쳤다.

## 4. 어떻게 안전하게 진행했나

1. 단계마다 별도 작업 폴더와 브랜치에서 이동을 적용했다.
2. 컴파일, 관련 테스트, 이동 모듈의 `--help`, 옛 경로 검색(작업이력 제외)이 통과한 것만 병합했다.
3. 병합 직전 커밋을 기록해 되돌릴 수 있게 했다.
4. 일부 단계는 별도 도구로 읽기 전용 독립 검토를 했고, 지적(임포트 단순화, README 개수 등)을 반영했다.

## 5. 한계와 남은 일

- 챗봇 화면은 자동 테스트로 실행하지 않았다. 정리 후 사용자가 서버를 띄워 정상 동작을 확인했다(서버 기동 시각 2026-11-06 23:34).
- A 단계의 독립 검토는 시간 초과로 끝나지 않아, 임포트·옛 경로·내부 경로·`--help`를 직접 확인하는 것으로 대체했다.
- 이동 도구는 `from ..모듈 import`형 임포트, 노트북 셀, 테스트 로더를 처리하지 못해 단계마다 수동 수정이 필요했다. 도구 보강은 다음 이동 때로 미뤘다.
- 팀원 쪽 `db_pipeline`은 이 정리에 포함하지 않았고 읽지 않았다.
- 이 정리는 구조만 바꾼 것이며, 추출·검색·답변의 품질은 이번 작업의 범위가 아니다.
