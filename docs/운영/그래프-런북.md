# 하나·우리카드 지식그래프 런북

- 이 문서의 목적: 그래프 CSV 준비·적재·교체·복구와 챗봇 검수를 안전하게 안내한다.
- 마지막 확인일: 2026-11-05
- 상태: 코드·이력에서 직접 확인한 사실과 전달된 DB 상태·절차상 추정을 구분해 표시한다.

## 1. 범위와 안전 경계

| 규칙 | 적용 |
|---|---|
| DB 변경 | 실제 DB 적재·삭제는 사용자만 실행한다. AI는 `.env`나 접속 값을 열지 않는다. 환경 변수 이름만 다룬다. |
| 대상 | 적재 코드의 허용 테이블은 `public.fp_load_runs`, `fp_nodes`, `fp_edges`, `fp_evidence`뿐이다. 팀 `db_pipeline`·`file_pipeline` 스키마에는 쓰지 않는다. |
| 순서 | 드라이런 → CSV와 출력 건수 대조 → (교체면 삭제 드라이런·건수 확인·삭제) → 적재 → SQL 확인. 한 단계라도 불일치하면 멈춘다. |
| 출력 보호 | 적재기 오류는 예외 클래스 이름과 SQLSTATE만 출력한다. 오류 한 줄에 비밀이 포함될 수 있으므로 공유 전에도 값이 없는지 확인한다. |

## 2. 기준 상태 (2026-11-05)

아래 DB 상태는 요청에 제공된 스냅샷이며 이 작업에서 DB 접속으로 재확인하지 않았다.

| 카드사 | run_id | 노드 | 엣지 | 근거 | 버전 |
|---|---|---:|---:|---:|---|
| 하나 | `full_hana-20261104T080526Z-st2` | 5,748 | 7,956 | 11,287 | 원문 구간 부착 |
| 우리 | `full_woori-20261104T080527Z-st2` | 4,561 | 5,173 | 9,266 | 원문 구간 부착 |

전달된 DB 크기 약 50~60MB, 한도 500MB. `fp_chat.nodes`·`fp_chat.edges` 읽기 뷰가 존재한다고 전달받았다. 실제 용량·한도·뷰 접근 권한은 미검증이다. 뷰는 문서 노드와 `SUPPORTED_BY` 링크를 더해 원본 테이블 행 수와 달라질 수 있다.

## 3. CSV 계보와 생성

| 폴더 | 용도 | 판단 |
|---|---|---|
| `/tmp/fp-check-hana`, `/tmp/fp-check-woori` | 원본 export | 구 버전 |
| `/tmp/fp-check-hana-st`, `/tmp/fp-check-woori-st` | 이전 구간 부착 | 낡거나 잘린 버전. 한도 금액 누락 사례가 있어 적재 금지 |
| `/tmp/fp-check-hana-st2`, `/tmp/fp-check-woori-st2` | 현재 전달된 적재본 | 각각 5,748/7,956/11,287 및 4,561/5,173/9,266 건 |

CSV는 `/tmp`에 있고 임시이며 재생성 가능하다. 적재 직전에 네 CSV 파일의 수정 시각과 내용이 고정됐는지 사용자 확인한다. 아래는 코드에서 확인한 CLI 모양이다. 경로 인자는 실제 경로로 바꾼다.

```bash
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit uv run --locked --no-sync python -m payment_card.file_pipeline.graph.export --result-dir <RESULT_DIR> --chunk-dir <CHUNK_DIR> --index-dir <INDEX_DIR> --model-name <MODEL> --output-dir /tmp/fp-check-hana --run-id full_hana-20261104T080526Z
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit uv run --locked --no-sync python -m payment_card.file_pipeline.graph.source_text --csv-dir /tmp/fp-check-hana --issuer hana --documents <DOCUMENTS_DIR> --output-dir /tmp/fp-check-hana-st2 --run-id-suffix -st2
```

우리카드도 같은 인자에 해당 우리 입력 경로와 `--issuer woori`, 출력 `/tmp/fp-check-woori-st2`를 쓴다. 생성 이력의 정확한 전체 입력 경로·명령은 미확인. `<…>`는 자리표시자이며 그대로 입력하지 않는다. 출력 표에서 노드·엣지·근거 건수 및 run_id를 대조한다.

## 4. 표준 절차

공통 실행기(아래 명령은 적재·삭제 전후에 사용):

```bash
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit uv run --locked --no-sync python -m payment_card.file_pipeline.graph.load --csv-dir <CSV_DIR>
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit uv run --locked --no-sync python -m payment_card.file_pipeline.graph.load --csv-dir <CSV_DIR> --execute
```

| 작업 | 순서와 성공 판정 |
|---|---|
| 새 카드사·새 run | 입력 CSV의 네 파일과 CSV 디렉터리 외부 항목 없음 확인 → 드라이런. 성공 출력 예: `{"counts":{"fp_edges":7956,"fp_evidence":11287,"fp_load_runs":1,"fp_nodes":5748},"mode":"dry_run"}` (순서는 정렬 출력 기준) → 예상 건수와 비교 → 사용자 실행. 성공은 `mode=execute`와 같은 counts. |
| 기존 run 교체 | 노드 ID는 전역 PK이므로 같은 카드 데이터의 새 run을 바로 넣으면 충돌 가능. 삭제 드라이런 후 네 테이블 건수를 확인하고 사용자 판단으로 삭제 실행 → 새 CSV 드라이런·대조 → 적재 → SQL 확인. 삭제 명령: `...graph.load --delete-run <RUN_ID>` 후 `...graph.load --delete-run <RUN_ID> --execute`. 삭제 후 적재 전 실패하면 해당 run이 비어 있다. |
| 복구 | 삭제 전 CSV 보존본의 run_id·개수·수정 시각을 대조한 후 드라이런·건수 비교·실행. 백업이 없으면 자동 복구 불가. 현재 `/tmp` CSV는 임시이므로 장기 백업으로 간주하지 않는다. |
| 챗봇 시험 | 질문 JSON을 `/tmp`에 준비. 기본은 dry-run이며 실제 OpenAI 호출은 `--execute`, 키는 `OPENAI_API_KEY`, DB 읽기는 코드상 `DB_URL`이 필요하다(`FP_DATABASE_URL`과 자동 연결되지 않음). 출력·요약은 `/tmp` 기본값. 비용 상한 `--max-cost-usd` 지정. 실행 종료 후 결과 파일을 확인하고 재채점·검수 시트를 만든다. |

SQL은 컬럼명을 `schema.sql`에서 확인했다. 실행 후 사용자 SQL 도구에서 다음을 조회한다.

```sql
select run_id, count(*) from public.fp_nodes group by run_id order by run_id;
select run_id, count(*) from public.fp_edges group by run_id order by run_id;
select count(*) from public.fp_evidence e where e.node_id in (select id from public.fp_nodes where run_id = '<RUN_ID>') or e.edge_id in (select id from public.fp_edges where run_id = '<RUN_ID>');
select run_id, node_count, edge_count from public.fp_load_runs order by run_id;
select count(*) from fp_chat.nodes;
select count(*) from fp_chat.edges;
```

예상 SQL 결과는 위 표의 run별 노드·엣지·근거 행 수와 `fp_load_runs`의 node_count/edge_count가 일치하는 것이다. 뷰 전체 수는 문서·근거 링크 추가로 다를 수 있다. 실패하면 재실행하지 말고 오류 한 줄과 현재 SQL 건수를 확인한다. DB 비밀을 출력하거나 복사하지 않는다. 환경 변수 설정 여부 확인은 값 대신 `설정됨(길이 N)`만 표시한다.

시험 CLI (인자는 `run_eval.py`, `answer_eval.py`, `review_sheet.py`에서 확인):

```bash
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit uv run --locked --no-sync python -m payment_card.file_pipeline.chat.eval.run_eval /tmp/questions.json --mode answer --source db --execute --max-cost-usd 0.04 --output /tmp/fp-chat-eval.jsonl --summary /tmp/fp-chat-summary.json
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit uv run --locked --no-sync python -m payment_card.file_pipeline.chat.answer_eval --results /tmp/fp-chat-eval.jsonl --questions /tmp/questions.json --output /tmp/fp-chat-rejudged.jsonl
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit uv run --locked --no-sync python -m payment_card.file_pipeline.chat.review.review_sheet --results /tmp/fp-chat-eval.jsonl --questions /tmp/questions.json --csv-dir <CSV_DIR> --documents <DOCUMENTS_DIR> --output /tmp/fp-review.html
```

명령 모양은 확인했으나 시험 모듈들의 정확한 인자 조합·질문 JSON 스키마·DB_URL 설정 절차는 미확인이다. 출력 결과 JSONL에 문항이 기록됐는지 확인한 뒤 검수 시트를 만든다. 모든 `/tmp` 결과는 “재생성 가능 산출물; 위치는 임시”다.

## 5. 흔한 실수와 대응

| 증상 | 대응 |
|---|---|
| run 삭제 후 적재가 실행되지 않아 하나 그래프가 비어 있는 상태로 시험됨 | 시험 전에 `fp_load_runs`와 노드 run별 SQL 확인 |
| 새 터미널에서 `OPENAI_API_KEY` 또는 `FP_DATABASE_URL` 미설정 | 값은 출력하지 말고 변수 설정 여부만 확인. 챗봇 DB 읽기는 `DB_URL`을 코드가 요구하므로 별도 확인 |
| `<카드 id>` 같은 자리표시자를 그대로 입력 | 실제 값을 대입. 미확인 ID를 임의로 만들지 않는다 |
| `.env` CRLF가 DB 이름에 붙어 `database "postgres\r" does not exist` | 사용자가 로컬에서 줄 끝을 정리할 수 있다: `tr -d '\r'`; `.env`는 열어 공유하지 않는다 |
| 오래된 CSV 적재 | 파일 수정 시각, run_id, 한도 포함 개선 이력 확인. `-st`는 사용하지 말고 `-st2` 계보 대조 |
| Neo4j Browser에 큰 Cypher를 붙여 넣어 정지 | 로컬 컨테이너로 파일 복사 후 `cypher-shell -f` 사용. 정확한 컨테이너 실행 인자는 미확인 |
| `OperationalError`만 출력 | 오류 클래스만 출력하도록 설계됨. 사용자 환경에서 접속 주소·포트·TLS·DB명 존재 여부를 비밀 없이 확인하고, 반복 실행은 보류 |
| `CheckViolation` | 과거 빈 CSV 칸이 빈 문자열로 적재되던 버그. 현 코드는 관련 키를 NULL로 변환. 계속 발생하면 중단 |
| 결과 파일이 비어 있음 | 실행 중인 시험이 끝나기 전에 검수 시트를 만들지 않는다. 종료 코드·결과 행 수 확인 |
| 같은 시험 점수가 ±2 변동 | 비결정성 가능. 동일 질문 세트를 3회 반복하고 평균·범위로 비교 |

## 6. 로컬 Neo4j: 시각화 전용

**2026-11-06 실제 적재 절차(사용자 실행, 건수 확인됨).** 현재 Supabase 그래프(5개 run)를 로컬 Neo4j(`graphrag-neo4j`, `Fp` 라벨 전용)에 올렸다. `cypher_export.py` 는 CSV 폴더 하나만 받으므로 run 별로 Cypher 를 하나씩 만들어 순서대로 실행한다(같은 ID 의 카드는 `MERGE` 로 합쳐진다).

1. 입력: 5개 CSV 폴더 `graph-csv/hana-st2`, `graph-csv/woori-st2`, `ocr-graph-full/ready-full_woori_ocr-…-st2`, `retry-export2/ready-hana`, `retry-export2/ready-woori`(저장소 밖 `~/pilot_work/eval-assets/`, 각 폴더에 `fp_nodes.csv`·`fp_edges.csv`·`fp_evidence.csv`).
2. 생성: 폴더마다 `cypher_export --csv-dir <폴더> --output ~/pilot_work/neo4j/NN-….cypher --lang ko`(영구 위치에 저장, `/tmp` 사용 안 함).
3. 적재: 컨테이너로 복사해 `cypher-shell -f` 로 실행(파일이 커서 Browser 붙여넣기는 피한다). 비밀번호는 입력창으로만 받고 명령줄·파일에 남기지 않는다. 하나카드 파일(약 11MB)이 가장 오래 걸려 약 3분, 전체 약 8분.
4. 확인(적재 직후 기대 값): 도메인 노드 `FpIssuer·FpCard·FpBenefit·FpCondition·FpLimit·FpTarget` 합계 **12,144**, 데이터 관계 6종(`FP_OFFERS`, `FP_HAS_CONDITION`, `FP_HAS_LIMIT`, `FP_APPLIES_TO`, `FP_EXCLUDES`, `FP_MUTUALLY_EXCLUSIVE`) 합계 **15,697**. 라벨별 Benefit 2,841·Card 244·Condition 3,756·Limit 1,511·Target 3,792, 근거 노드 `FpEvidence` 23,970(CSV 24,066행에서 변환 중 96 감소, 원인 미확인). 근거는 엣지가 아니라 `edge_id` 속성으로 연결되고 문서 해시·쪽·글자 위치만 있다(인용문 본문 없음).
5. 주의: Browser 의 옛 결과 화면(샘플 시절 167노드/210관계)이 남아 있을 수 있다. 건수는 새로 실행한 쿼리로만 확인한다. 전체를 한 번에 펼치면 느리므로 카드 1장을 혜택 8개로 제한해 시각화한다.

`cypher_export.py`는 CSV를 Neo4j Cypher 샘플로 변환한다. `--lang ko`는 한국어 속성을 추가하고 `--backfill-ko-out`은 기존 로컬 그래프의 한국어 보정용 파일을 생성한다. 기본 영어 스키마는 유지한다. 데이터 라벨은 `Fp` 접두사, 관계는 생성된 `FP_` 관계 계열만 관리한다. 컨테이너 이름은 `graphrag-neo4j`. 팀 Aura에는 적재·정리하지 않는다.

```bash
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit uv run --locked --no-sync python -m payment_card.file_pipeline.graph.cypher_export --csv-dir <CSV_DIR> --output /tmp/fp-graph.cypher --lang ko --backfill-ko-out /tmp/fp-backfill-ko.cypher
```

정리 전 로컬 연결과 대상 라벨을 확인하고 `MATCH (n) WHERE any(label IN labels(n) WHERE label STARTS WITH 'Fp') DETACH DELETE n` 범위로 한정한다. `Fp` 외 라벨·관계는 건드리지 않는다. 삭제 전 라벨과 건수를 확인한다.

## 7. 롤백·비상

실패한 적재는 한 트랜잭션에서 롤백된다. 성공한 run은 `--delete-run`으로 근거→엣지→노드→run 기록을 삭제할 수 있으나 원문 CSV가 없으면 데이터 복원은 보장되지 않는다. 새 run 적재 후 이전 run 삭제는 별도 사용자 결정이다. 스키마/뷰 변경은 이 적재기로 되돌릴 수 없다. 오류 발생 시 재시도·추가 삭제를 멈추고 오류 클래스와 run별 SQL 건수만 기록한다.
