# 미래 생활계획 카드 GraphRAG — 토스 차별화 실증 검증

| 항목 | 내용 |
|---|---|
| 작성자 | Claude (Opus 5.5, Claude Code) |
| 작성일·확인일 | 2026-10-28 (모든 URL 확인일 동일) |
| 문서 버전 | v1 |
| 조사 방법 | 토스 카드라운지 공개 페이지의 **서버 HTML**(브라우저가 받는 원본)을 내려받아 필터 정의, 카드 목록 데이터, 상세 페이지 본문을 직접 파싱했다. 토스 공식 서비스 소개 페이지는 웹 조회로 읽었다. 카드사 상품설명서 PDF는 같은 날 이미 원문을 대조한 6종(이전 Claude 보고서)을 기준으로 삼았다 |
| 확인하지 못한 것 | **토스 앱**(로그인, 마이데이터 연결 후 카드홈·추천), 카드라운지에서 **브라우저로 실제 클릭하는 동작**(필터 다중 선택, 비교함 화면). 서버 HTML로는 데이터와 문구만 보이고 클라이언트 동작은 보이지 않는다 |
| 표기 | **[V]** 직접 확인한 사실 / **[I]** 확인된 사실에서 추론 / **[H]** 가설·미검증 |
| 독립성 | 다른 AI 보고서와 노션은 읽지 않았다. 이전 Claude 보고서는 PDF 사실 확인용으로만 썼다 |

## 1. 한 페이지 결론

**판정**

| 평가 축 | 판정 |
|---|---|
| 토스와의 차별화 | **B** (차별화 가능성은 있으나 기능 범위를 좁혀야 함) |
| GraphRAG 기술 적용 | **B** (교육용으로 타당, SQL·일반 RAG 대비 이점은 제한적) |
| 결론 | **REFINE** |

**"토스는 미래 계획을 다루지 않는다"는 주장은 그대로 쓰면 틀린다.**

- [V] 토스 앱의 추천은 공식 페이지 문구상 **과거 소비 기반**이다. "지난 한 달 동안 내 카드로 쓴 금액과 사용처를 분석", "내 소비 내역을 바탕으로 할인과 적립이 가장 많이 되는 카드부터".
- [V] 그러나 **토스 카드라운지는 로그인이나 소비내역 없이** "내 취향에 맞게 검색하기"를 제공한다. 사용자는 앞으로 필요한 혜택을 직접 고를 수 있다.
  - 혜택 카테고리 11종: 여행·생활비·**통신비**·식비·**온라인**·주유/충전·교통·전가맹점·카페·**문화**·오프라인
  - 혜택 형태, 카드사 10곳, 연회비 6구간, 전월실적 4구간
- 따라서 "앞으로 통신비·온라인 혜택이 필요하다"는 수준의 미래 계획은 **토스에서도 처리할 수 있다.** 자연어 입력창만으로는 차별화가 되지 않는다.

**토스에 실제로 있는 것과 없는 것**

| 구분 | 내용 |
|---|---|
| [V] 있음 | 카드라운지 상세 페이지가 혜택별 결제 조건 문구를 **거의 원문 그대로** 싣는다. 예: WE:SH All+ "쇼핑 멤버십/OTT는 공식 홈페이지를 통한 정기 결제 건에 한함 (간편결제 및 인앱결제 등은 할인 제외)", "이동통신 할인은 인터넷/IPTV 등 결합상품 할인 제외". **혜택별 적용 범위 정보 자체는 토스에도 있다** |
| [V] 없음(공개 페이지) | ① 전월실적 제외 항목: 상세 5건 모두 표시 없음 ② `/search`의 1,737종 카드 목록에 체크카드 없음 ③ 검색 필터에 '결제방식(간편결제·인앱)'과 'OTT' 없음(OTT는 별도 랭킹 페이지에만 있음) ④ 여러 카드의 조건을 결합한 자동 판정, 원문 PDF 링크 ⑤ 우리 핵심 카드 6종 중 4종(NEED Pay, KB ALL, Youth Club, 첵첵)은 공개 목록에서 찾지 못함 |

**차별화가 성립하는 곳**

차별화는 "미래 계획 입력"이 아니라 아래에서만 성립한다.

1. **결제방식 관점의 교차 판정.** 예: "간편결제를 계속 쓰면 어느 카드의 어느 혜택이 빠지고, 어느 혜택은 오히려 Pay가 조건인가."
2. **선택 제약 자동 탐지.** 예: Youth Club은 A팩·B팩 중 매달 하나만 고를 수 있다.
3. **할인 적용분의 전월실적 제외 범위 비교.**
4. **신용·체크를 한 번에 비교**하고 PDF 쪽수로 근거를 단다.

이 네 가지도 토스 앱 화면을 확인하지 못했으므로 **"공개 자료에서 확인되지 않음"** 단계다.

**REFINE 방향**

- '미래 생활계획'은 **입력 방식(사용자 경험)으로만** 유지한다.
- 발표의 핵심 차별점은 다음으로 좁힌다.
  - "계획한 결제방식·관심 혜택을 기준으로 카드별 **제외·선택충돌·실적제외를 자동 판정**하고 PDF 근거를 단다"

## 3. 검증되지 않은 기능 목록

1. 토스 앱 카드홈의 보유 카드 실적 현황, 카드별 실적 제외 안내 (로그인 필요)
2. 토스 앱 추천 화면에서 소비내역 없이 관심 혜택을 지정하는 기능이 있는지
3. 카드라운지 필터의 다중 선택과 조합 결과 (클라이언트 동작)
4. 카드라운지 비교함이 무엇을 나란히 보여주는지, 신용·체크를 섞어 담을 수 있는지
5. NEED Pay, KB ALL, Youth Club, 첵첵의 카드라운지 상세 페이지 존재 여부와 표시 내용
6. Youth Club A/B팩 택1, NEED Pay의 '간편결제 제외의 예외' 같은 조건을 토스가 어떻게 표시하는지 (해당 카드 페이지를 찾지 못함)
7. 토스 앱 내 AI·대화형 카드 탐색 기능 (공개 자료에 없을 뿐, 앱에 없다는 반대 근거도 없음)

## 4. 세 가지 미래 생활계획 질문 — 토스 대비 수행 과정

### 질문 1 — 구독 시작

> "다음 달부터 넷플릭스와 유튜브를 구독하고 통신비를 카드로 자동납부하려고 해. 간편결제도 계속 사용하고 싶은데 어떤 카드의 조건이 맞을까?"

| 항목 | 내용 |
|---|---|
| 토스에서의 과정 [V+I] | ① 카드라운지 `/search`에서 '통신비' 선택(OTT 필터는 없음) 또는 `/ranking/ott-subscription` 열람 ② 후보 카드 상세를 하나씩 열기 ③ 혜택 문단의 조건 문구 읽기 ④ 비교함에 담기(최대 3장) ⑤ 체크카드는 `/ranking/check`에서 따로 반복 |
| 토스로 얻는 정보 | 카드별 OTT·통신 혜택 존재 여부. WE:SH All+는 "OTT 간편결제·인앱 제외, 통신 결합상품 제외, 통합 5천원" 문구까지 확인 가능 [V] |
| 사용자가 직접 판단할 것 | ① 두 혜택을 **같은 달에 함께** 받을 수 있는지 ② "간편결제 제외"가 OTT에만 걸리는지 카드 전체에 걸리는지 ③ 여러 카드 사이의 같은 조건을 맞춰 보기 ④ 전월실적에서 할인분이 빠지는지(토스 상세에 없음) |
| 우리가 자동화할 수 있는 것 | 카드 6종을 대상으로 다음을 표 하나로 판정 [V: PDF 근거] |
| 근거 부족으로 판단 불가 | 사용자가 쓰는 '간편결제'가 어떤 Pay인지 모르면 NEED Pay의 Pay 택1이나 Youth Club 편의점(KB Pay 조건)은 확정할 수 없다. 문서에 없는 조건은 '미기재'로만 표시 |
| 절약되는 노력·새 가치 | 카드 상세 4~6개를 열어 문구를 대조하는 수고. **같은 달 동시 가능 여부의 자동 판정**이 새로 생긴다. 토스 공개 화면에서는 이 판정을 보지 못했다 |

**질문 1에서 자동 판정할 내용**

| 카드 | 판정 | 근거 |
|---|---|---|
| WE:SH All+, KB ALL | OTT·통신 동시 가능. 통합 한도를 공유하고, OTT는 간편결제 결제 시 제외 | p1 |
| Youth Club | OTT(A팩)와 통신(B팩) **동시 불가** | p1·p2 |
| NEED Pay | 통신 혜택 없음. 디지털콘텐츠는 간편결제 시 제외지만 멤버십 3종–지정 Pay는 예외 | p1 |
| JADE Classic | 통신 혜택 없음. 디지털 적립은 간편결제·인앱 제외 | p4 |

### 질문 2 — 카드 유형 전환

> "앞으로 신용카드 사용을 줄이고 체크카드 중심으로 생활하려고 해. OTT와 온라인쇼핑 혜택을 함께 고려하면 어떤 제약이 있을까?"

| 항목 | 내용 |
|---|---|
| 토스에서의 과정 | 신용카드는 `/search`, 체크카드는 `/ranking/check`. 검색 화면이 다르다. 체크카드 상세를 하나씩 열어 OTT·온라인쇼핑 조건을 확인한다 |
| 토스로 얻는 정보 | 체크카드 상세의 혜택 문구(노출된 카드에 한함) |
| 사용자가 직접 판단할 것 | 신용과 체크의 같은 혜택을 서로 맞춰 보기, 팩·택1 제약, 할인 방식 차이(청구할인 vs 환급할인) |
| 자동화 | Youth Club: OTT(A팩)와 쇼핑멤버십·온라인몰(B팩) **같은 달 택1**(p1·p2). 첵첵: OTT 없음, 온라인 간편결제·텐바이텐 할인(p1). 신용 쪽(WE:SH All+·NEED Pay·JADE)과 결제 경로 조건 비교 |
| 판단 불가 | 사용자의 현재 신용카드를 모르므로 "무엇이 유지되는지"는 확정하지 않는다. **확보한 체크카드가 2종(KB만)이라 결과의 대표성이 낮다** |
| 새 가치 | 신용·체크를 한 화면에서 같은 기준으로 비교. 다만 데이터 범위가 작아 시연 설득력은 중간 |

### 질문 3 — 결제 습관 변경

| 항목 | 내용 |
|---|---|
| 토스에서의 과정 | '온라인' 필터 → 카드 상세 → 각 혜택 문단에서 '간편결제'·'인앱'·'공식 홈페이지' 문구를 찾아 읽는다. **결제방식 필터는 없다** [V] |
| 토스로 얻는 정보 | 카드별·혜택별 결제 조건 문구(카드 중심 보기) |

| 판단 불가 | 가맹점 등록 업종 분류(문서가 "가맹점 업종코드 기준"이라고만 적음), 특정 Pay의 실제 처리 방식 |
| 새 가치 | **세 질문 중 토스와 가장 뚜렷하게 다르다.** 토스는 카드 → 혜택 → 문구 순서로만 보여주고, 결제방식에서 출발하는 보기는 공개 화면에서 찾지 못했다 |

## 6. GraphRAG vs SQL vs 일반 RAG

| 질문 | 일반 PDF RAG | 정규화 SQL | Neo4j GraphRAG |
|---|---|---|---|
| 질문 1 동시 가능 판정 | Youth Club p1(혜택 표)과 p2(택1 조항)가 다른 청크에 있으면 "동시 가능"으로 오답할 위험이 크다 [I] | `choice_option` 자기조인으로 **동일 결과** | `(b1)-[:OPTION_OF]->(ch)<-[:OPTION_OF]-(b2)` 경로로 **동일 결과**. 경로가 그대로 설명 문장이 된다 |
| 질문 3 결제방식 역조회 | 키워드 검색으로 문구는 찾는다. 제외·조건·대상의 구분은 LLM에 맡겨야 해 불안정 | `rule` + `rule_payment` + `rule_scope` 조인으로 **동일 결과** | `PaymentMethod` 공유 노드에서 들어오는 간선 종류(TARGETS의 kind)로 분류. **동일 결과** |
| 예외의 예외(NEED Pay) | 한 청크 안에 있어 의외로 잘 찾을 수 있다 | `rule_exception` 테이블 하나 추가 | 간선 하나 추가 |
| 실적 제외 범위 | '미기재'를 '인정'으로 말할 위험 | 행 유무로 처리 | 간선 유무로 처리 |

**공정한 결론**

- **SQL로 같은 결과를 만들 수 있다.** 6종 규모에서 성능이나 정확도 차이는 없다.
- GraphRAG의 실제 이점은 세 가지다.
  - ① 결제방식·서비스를 **공유 노드**로 두면, "간편결제에서 출발하는 역조회"(질문 3)를 질의 하나로 표현할 수 있다.
  - ② 택1·범위·예외가 **경로**로 반환되어 설명과 시각화에 바로 쓸 수 있다.
  - ③ 사람이 승인하는 단위(관계 1건)와 저장 단위가 같다.
- **GraphRAG 전용 기능처럼 보이지만 SQL·일반 RAG로 충분한 것**
  - PDF 쪽수 근거 표시(SQL 행에 저장 가능)
  - 자연어 입력 해석(LLM의 일)
  - 단순 필터 검색(토스 필터 수준)
  - 실적 기준 금액 비교(속성 비교)
  - 혜택 존재 여부 조회
- 이것들을 "그래프 덕분"이라고 발표하면 안 된다.

| 보조 2 | **판정 근거 경로 표시**(혜택–택1–혜택, 규칙–범위–결제방식) + PDF 원문 | GraphRAG를 쓰는 이유를 시연으로 보여준다 |
| 제외 | 자연어 대화 고도화, 카드 10종 확장, 필터 검색 화면(토스와 중복), 금액 계산, 결제 배분 | 차별화가 약하거나 범위 밖 |

**2인 역할 분담 [H]**

- 1인: 추출·검수·데이터
- 1인: 그래프·질의·화면

데이터 범위는 이렇게 잡는다.

- 텍스트 레이어가 양호한 4종(NEED Pay, JADE, Youth Club, 첵첵)을 우선한다.
- 이미지 PDF인 WE:SH All+는 사람이 전사해 넣는다. 질문 1의 "동시 가능" 사례에 필요하다.

## 8. 실패 가능성과 차별화가 무너지는 조건

1. **토스 앱(로그인)에 결합 판정이 있는 경우.** 앱 카드홈이나 추천 화면이 "이 카드는 팩 선택이 필요해요" 같은 판정이나 실적 제외 안내를 이미 제공하면 #4와 '추가' 항목의 차별화가 사라진다. **확인하지 못했다.**
2. **카드라운지 필터가 다중 선택과 결제방식 조건까지 지원하는 경우.** 클라이언트 동작을 확인하지 못했다.
3. **데이터 범위가 너무 작은 경우.** 체크카드가 KB 2종뿐이다. "체크카드 중 OTT·통신 동시 가능 카드 없음" 같은 결론이 시장 전체 결론처럼 보일 수 있다. 화면에 "확보 문서 N종 기준"을 반드시 표시해야 한다.
4. **추출 정확도.** LLM이 '간편결제 제외'의 범위(카드 전체 vs 혜택)를 틀리면 핵심 기능이 오답을 낸다. 범위 판정은 사람 승인 필수.
5. **우리 카드가 토스에 없는 점의 해석.** NEED Pay 등이 카드라운지 목록에 없다는 사실은 차별화 근거가 아니라 데이터 범위 차이다. "토스에 없는 카드를 다룬다"를 차별점으로 주장하면 안 된다.
6. **사용자 가치 미검증.** "판정표가 상세 페이지를 여러 개 읽는 것보다 낫다"는 것은 가설이다. 5명 내외의 간단한 비교 관찰이라도 없으면 주장 강도를 낮춰야 한다.

## 10. 강사 발표용 차별화 설명 5문장

1. 토스는 소비내역 기반 추천(토스 앱)뿐 아니라, 카드라운지에서 로그인 없이 통신비·온라인 같은 원하는 혜택을 골라 검색하는 기능도 제공합니다. 그래서 '앞으로 필요한 혜택을 고른다'는 것 자체는 우리의 차별점이 아닙니다.
2. 카드라운지 상세 페이지는 "쇼핑 멤버십/OTT는 … 간편결제 및 인앱결제 등은 할인 제외"처럼 혜택별 조건을 원문 수준으로 보여줍니다. 다만 그 조건들을 여러 카드에 걸쳐 결합해 판정해 주지는 않습니다(2026-10-28 공개 화면 기준).
3. 우리 서비스는 사용자가 계획한 결제방식과 관심 혜택을 입력받아, 카드별로 같은 달에 함께 받을 수 있는지, 선택 충돌이 있는지(KB Youth Club A/B팩), 간편결제가 제외 사유인지 조건인지를 자동으로 판정합니다.
4. 같은 '간편결제'라도 Youth Club에서는 카드 전체 할인의 제외 사유이고, KB ALL에서는 쇼핑멤버십·OTT에만 걸리며, NEED Pay에서는 할인 대상입니다. 이 차이를 공식 상품설명서 쪽수와 함께 경로로 보여주는 데 그래프를 씁니다.
5. 같은 결과를 SQL로도 만들 수 있다는 점을 인정하며, 토스 앱 로그인 화면은 확인하지 못했습니다. 그래서 차별화는 '공개 화면에서 확인되지 않은 결합 판정'으로 한정해 말씀드립니다.
