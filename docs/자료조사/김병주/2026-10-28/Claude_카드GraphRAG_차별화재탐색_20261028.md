## 1. 결론 요약

**최종 결정: PIVOT** (카드 주제의 차별성이 부족하므로 다른 주제로 전환 권장)

**최우선 질문:** "일반 ChatGPT가 복잡한 카드 조건을 설명하는데, 사용자가 별도 GraphRAG 서비스를 써야 할 실질적 이유는 무엇인가?"

**답: 사용자 입장에서 설득력 있는 이유를 찾지 못했다.**

남은 차이는 두 가지뿐이다.

- **닫힌 문서 집합 안에서의 전수성.** 정해진 카드 집합 전체를 빠짐없이 같은 기준으로 판정한다.
- **판정의 검증 가능성.** 규칙의 적용 범위를 구분하고, 확인할 수 없으면 '확인 불가'로 돌려주며, 조항 원문을 인용한다.

그러나 두 가지 모두 약점이 있다.

1. **사용자가 체감하기 어렵다.** 틀린 답을 받아 본 뒤에야 느끼는 품질 속성이다. 기능으로 보이지 않는다.
2. **아직 측정하지 않았다.** 일반 ChatGPT가 이 부분에서 실제로 얼마나 틀리는지 실험한 적이 없다. 사용자 실험에서 과잉 일반화 의심 사례가 1건 있을 뿐이다(§2.2).
3. **카드 수가 4~6종이면 전수성의 실익이 작다.** 6종 안에서 다 찾아 주는 것은 사용자에게 큰 의미가 없다.
4. **GraphRAG가 아니어도 된다.** 두 가지 모두 SQL 조건 테이블과 Python 판정으로 똑같이 구현할 수 있다.

**평가표 결과**

- 새로 발굴한 카드 후보 6개 중 **70점 이상은 0개**다. 최고점은 C2 "결제계획 기준 역방향 전수 판정"의 **63점(추정)** 이다.
- 지시문 기준에 따라 **핵심 차별화로 쓰기 어렵다.**

**전환 방향 (조건부)**

- 1순위 후보는 저장소에 이미 실데이터 검증이 된 **DART 재건축·재개발 현장–조합–PF 보증 GraphRAG**다(§8).
- 단, 이 후보도 같은 기준으로 **68점(추정)** 이라 70점에 못 미친다. 카드보다 나은 이유는 두 가지다.
  - 일반 ChatGPT가 잘한다는 반증이 아직 없다.
  - 문서 간 개체 결합(조합명 정규화, 표 간 연결)이 질문의 본질이다.
- 그래서 **착수 전에 2시간짜리 "일반 ChatGPT 기준선 시험"을 반드시 먼저 하라고 권한다**(§8.3). 이 시험에서 ChatGPT가 대부분 맞히면 전환 근거도 약해진다. 그때는 강사님 평가 기준(§9)으로 결정한다.

## 2. 현재 카드 기획의 약점

### 2.1 일반 ChatGPT가 이미 수행한 것 [U]

사용자 실험에서 일반 ChatGPT는 신한카드 공식 상품 페이지를 참조해 다음을 답했다.

1. OTT 할인 카드 추천
2. 전월실적, 할인율, 통합 한도
3. 앱스토어 인앱결제 제외
4. 간편결제의 가맹점명 조건
5. 공식 홈페이지 정기결제로 바꿀 때 풀리는 제약
6. 바꾼 뒤에도 남는 조건
7. 공식 URL과 해당 항목명

이 결과를 인정하면 기존 기획의 다음 요소는 **차별점에서 빠진다.**

| 기존 기획 요소 | 판정 | 근거 |
|---|---|---|
| 자연어 질문, 대화 맥락 유지 | **탈락** | 일반 ChatGPT [U], 신한 × ChatGPT for Kakao 발표 [V] |
| 카드 혜택 추천 | **탈락** | 토스 카드라운지 [V], 신한 발표 [V], 일반 ChatGPT [U] |
| 단일 카드의 2~3-Hop 조건 설명 | **탈락** | 일반 ChatGPT [U] |
| 인앱결제 제외 설명 | **탈락** | 토스 상세 페이지에 원문 수준으로 게시 [V], 일반 ChatGPT [U] |
| 결제방식 변경 전후 비교 (단일 카드) | **탈락** | 일반 ChatGPT [U] |
| "미래 생활계획" 입력 | **탈락** | 토스 카드라운지는 로그인 없이 앞으로 필요한 혜택 카테고리를 고르게 한다 [V]. 입력 방식의 차이일 뿐이다 |
| 단일 카드의 택1(A/B팩) 판정 | **약함** | 원문 한 장에 적힌 규칙이다. 단일 문서를 읽는 LLM이 처리할 수 있는 범위로 본다 [H] |

### 2.2 일반 ChatGPT의 약점으로 확인된 것

**과잉 일반화 의심 1건.** 사용자 보고에 따르면 ChatGPT가 "공식 홈페이지 정기결제" 조건을 "공식 앱 결제"까지 넓혀 허용한 것으로 의심된다 [U].

원문 [V]은 다음과 같다(신한 구독 좋아요, 공식 상품 페이지, 2026-10-28 수집).

> "서비스 대상 가맹점 공식 홈페이지에 직접 접속/신청하여 정기결제(자동이체)를 이용하는 경우에 한하여 서비스 적용됩니다. (1회성 일반구매 결제, 구글 플레이/애플 앱스토어 등 앱마켓을 통한 인앱결제, 통신요금 포함(합산) 결제인 경우 서비스 적용 제외)"

- 넷플릭스 앱 안에서 앱마켓을 거치지 않고 카드를 직접 등록해 결제하는 경우는 **원문에 없다.**
- 따라서 원문 기준의 올바른 답은 **"허용"이 아니라 "확인 불가"** 다. 사용자 보고가 맞다면 ChatGPT의 답은 원문 범위를 넘었다.
- 다만 이것은 **1건의 사례**다. 오류율이나 재현성은 측정하지 않았다.

**PDF 쪽 번호 미제공.** 신한카드는 카드별 혜택을 HTML 상품 페이지에 싣는다. 카드별 PDF가 확인되지 않으므로 ChatGPT가 쪽 번호를 못 준 것은 정상이다. 약점으로 보기 어렵다.

### 2.3 남는 질문

일반 ChatGPT는 **사용자가 카드를 지정한 단일 카드 질문**에는 강하다. 차이가 생길 수 있는 곳은 아래 세 가지뿐이다. 세 가지 모두 **측정 전**이다.

- 카드를 지정하지 않고 **여러 카드에 걸쳐 전수**로 묻는 질문
- 규칙의 **적용 범위**가 카드마다 다른 질문
- **원문에 없는 것**을 묻는 질문

## 3. 새롭게 발굴한 차별화 후보

**공통 사항**

- 쪽 번호는 PDF 실제 페이지다.
- 원문 ID(N, W, L, J, Y, C)는 `Claude_카드GraphRAG_기술적용타당성_20261028.md` §2.2 관계표의 ID다. 이 관계표는 PDF 6종을 2026-10-28에 내려받아 텍스트 추출과 페이지 이미지로 대조한 것이다.
- R은 신한 구독 좋아요 공식 페이지 조항이다(`Claude_신한카드ChatGPTforKakao_1to3Hop_실증검증_20261028.md` §2.2).

### C1. 규칙 적용 범위 구분과 '확인 불가' 반환

- **사용자 문제:** 같은 "간편결제 제외"라도 카드 전체에 걸리는 경우와 특정 혜택에만 걸리는 경우가 있다. 이를 섞으면 혜택을 잘못 포기하거나 잘못 기대한다.
- **시연 질문:** "KB WE:SH All+로 휴대폰 요금을 카카오페이로 한 번 결제하면, 간편결제라서 할인이 빠져?"

| 단계 | 내용 |
|---|---|
| Entity | Card(WE:SH All+), Benefit(이동통신 5%), Rule(W2 간편결제·인앱 제외), Rule(W1 자동납부 요건), PaymentMethod(간편결제, 자동납부) |
| 경로 | `Card→OFFERS→Benefit(이동통신)` / `Card→HAS_RULE→Rule(W2)→SCOPED_TO→{쇼핑멤버십, OTT}` (이동통신 간선 없음) / `Benefit(이동통신)←SCOPED_TO←Rule(W1 자동납부 요건)→TARGETS→PaymentMethod(자동납부)` |
| 적용 규칙 | W2는 쇼핑멤버십·OTT에만 걸린다. 이동통신에 걸리는 것은 W1(자동납부 묶음)과 W3(결합상품 제외)이다 |
| 예상 판정 | "간편결제 제외 조항(W2)은 이동통신 혜택에 적용되지 않는다. 다만 이 혜택은 **자동납부 결제 건**을 전제로 하므로, 카카오페이 1회 결제는 자동납부 요건 미충족으로 할인 대상이 아닐 가능성이 높다. 자동납부를 카카오페이로 등록한 경우는 **문서상 확인 불가**" |
| 근거 | WE:SH All+ PDF p1 (W1·W2·W3, 이미지 판독) |

- **ChatGPT가 이미 잘 답한다면 추가 가치는?**
  - 이 카드 하나를 지정해 물으면 ChatGPT도 W2의 범위를 읽어낼 수 있다 [H].
  - 남는 가치는 범위 구분이 **데이터 구조로 고정돼 매번 같은 답이 나온다**는 점이다. 확인 불가도 규칙으로 반환된다.
  - 이 가치는 **품질 속성**이다. 사용자가 고를 만한 기능이 아니다.
  - 차별성은 **ChatGPT 기준선 실측으로 오류가 확인돼야만** 성립한다.

### C2. 결제계획 기준 역방향 전수 판정 (카드사 교차)

- **사용자 문제:** 사용자는 카드명이 아니라 자기 결제 습관(앱스토어 구독, 간편결제 위주)에서 출발한다. "내 습관이면 어느 카드 혜택이 다 무너지는가"를 한 번에 알고 싶어 한다.
- **시연 질문:** "넷플릭스를 아이폰 앱스토어 구독으로 계속 낼 거야. 등록된 카드 중 어느 카드의 어떤 혜택이 어떤 조항 때문에 빠지는지 전부 알려줘."

| 단계 | 내용 |
|---|---|
| Entity | Service(넷플릭스), PaymentMethod(인앱결제), Benefit(카드별 OTT·디지털콘텐츠), Rule(카드별 제외 규칙), Card |
| 경로 | `Service(넷플릭스)←APPLIES_TO←Benefit→OFFERED_BY→Card` 그리고 `Benefit←SCOPED_TO←Rule→TARGETS→PaymentMethod(인앱결제)` (카드 쪽으로 2-Hop, 규칙 쪽으로 2-Hop) |
| 적용 규칙 | W2(WE:SH All+), L1(KB ALL), N4(NEED Pay), J1(JADE Classic, 적립), Y3(Youth Club, A팩), R2(구독 좋아요) |
| 예상 판정 | OTT 혜택이 있는 6종 **모두 인앱결제 시 제외**(명시적 제외). 첵첵은 OTT 혜택 자체가 없음(C3). "앱스토어 결제를 유지하면 등록 카드 중 OTT 혜택을 받을 수 있는 카드: 0종" |
| 근거 | 각 PDF p1(J1은 p4), 구독 좋아요 공식 페이지 '디지털 구독 할인 서비스 유의사항' |

- **ChatGPT가 이미 잘 답한다면 추가 가치는?**
  - ChatGPT도 "OTT 카드 대부분은 인앱결제를 제외한다"고 일반론으로 답할 가능성이 높다 [H].
  - 추가 가치는 두 가지다.
    1. **정해진 카드 집합 전체를 카드별 조항과 함께 빠짐없이** 돌려준다.
    2. "제외 / 조건부 제외 / 미기재 / 혜택 없음"을 **같은 기준으로 분류**한다.
  - 그러나 집합이 6~7종이면 실익이 작다. SQL로도 같은 결과가 나온다(§6).
  - 6개 후보 중 차별성이 가장 덜 약할 뿐이다. 강하지는 않다.

### C3. 할인 적용과 전월실적 인정의 분리 판정

- **사용자 문제:** 할인받은 결제가 다음 달 실적에서 빠지는 카드가 있다. 그러면 실적 구간이 내려가 다음 달 혜택이 줄어든다. 언론도 혼란 사례로 다뤘다(뉴스토마토 2024-06-25, 이전 보고서 P3).
- **시연 질문:** "NEED Pay, WE:SH All+, 구독 좋아요 중에서 넷플릭스 할인받은 금액이 다음 달 전월실적에 들어가는 카드는?"

| 단계 | 내용 |
|---|---|
| Entity | Card, Benefit(OTT·디지털), Rule(실적 제외), Rule(할인 제외) |
| 경로 | `Card→HAS_RULE→Rule(실적 제외)→SCOPED_TO→Benefit` (scope='card'면 간선 없이 카드 전체) |
| 적용 규칙 | N8: NEED Pay는 할인 적용 매출 **전체**를 실적에서 제외. W4: WE:SH All+는 **자동납부 할인분만** 제외. R6: 구독 좋아요의 실적 제외 목록에는 할인 적용분이 **없음** |
| 예상 판정 | NEED Pay: 불포함(명시). WE:SH All+: 불포함(OTT는 자동납부 묶음이므로 명시). 구독 좋아요: 문서상 실적 제외 사유 없음 → 포함으로 판단. JADE·Youth Club·첵첵: 실적 제외 목록에 미기재 → **확인 불가** |
| 근거 | NEED Pay p2, WE:SH All+ p2, 구독 좋아요 '전월 이용금액 산정기준' |

- **함정:** 구독 좋아요의 '할인 제외 대상'에는 포인트 사용분이 있지만, '실적 제외 대상'에는 없다. 반대로 연회비·수수료는 실적 제외에만 있다. **두 목록은 다르다.**
- **ChatGPT가 이미 잘 답한다면 추가 가치는?**
  - 카드별로 물으면 ChatGPT도 목록을 읽을 수 있다 [H].
  - 뱅크샐러드는 보유 카드의 **결제 건별 실적 인정 여부를 이미 제공**한다(KPI뉴스 2026-04-30, 이전 보고서) [V]. 단, 할인분 실적 제외까지 반영하는지는 공개 자료상 확인 불가다.
  - 다음 달 구간 하락 계산은 Python 산술이다. **그래프의 몫이 거의 없다.**

### C4. 복수 제약의 충돌·예외 판정

- **사용자 문제:** 택1 제약, 통합 한도, 예외의 예외가 겹치면 사용자가 문서를 여러 번 읽어야 한다.
- **시연 질문:** "네이버플러스를 네이버페이로 결제하면서 OTT랑 통신 할인도 같은 달에 받고 싶어. Youth Club, NEED Pay, WE:SH All+ 중 뭐가 되고 뭐가 막혀?"

| 단계 | 내용 |
|---|---|
| Entity | Benefit, Choice(택1), Rule(간편결제 제외), Rule(예외 허용), Rule(중복 허용), Service, PaymentMethod |
| 경로 | `Benefit(OTT)→OPTION_OF→Choice←OPTION_OF←Benefit(통신)` (Youth Club, 2-Hop) / `Rule(N4 간편결제 제외)→HAS_EXCEPTION→Rule(예외 허용)→FOR_SERVICE→Service(네이버플러스)`, `…→TARGETS→PaymentMethod(네이버페이)` (NEED Pay, 3-Hop) |
| 적용 규칙 | Y1·Y2 (A팩 OTT vs B팩 통신, 월 1개 선택). N5 (네이버플러스–네이버페이는 간편결제여도 혜택). N6 (네이버페이 간편결제 할인과 중복 가능). W1·W2 (통합 월 한도 5천원, 쇼핑멤버십·OTT는 간편결제 제외) |
| 예상 판정 | Youth Club: OTT와 통신은 같은 달 **동시 불가**. NEED Pay: 네이버플러스를 네이버페이로 결제해도 **혜택**, 간편결제 할인과 **중복 가능**. NEED Pay에는 통신 혜택이 없다. WE:SH All+: 네이버플러스를 네이버페이로 결제하면 쇼핑멤버십 **제외**. OTT·통신은 자동납부 시 통합 한도 5천원 안에서 함께 가능 |
| 근거 | Youth Club p1·p2, NEED Pay p1, WE:SH All+ p1 |

- **ChatGPT가 이미 잘 답한다면 추가 가치는?**
  - 이 규칙들은 대부분 카드 한 장 안의 규칙이다. ChatGPT가 카드별 문서를 읽으면 처리할 수 있다고 본다 [H].
  - 추가 가치는 세 카드를 동시에 놓고 판정하는 데만 있다. 이는 C2와 같은 종류의 가치다.

### C5. 은행 적금·대출 우대조건 × 카드 실적 규칙 (문서 간 위임)

- **사용자 문제:** 은행 상품의 우대금리가 카드 실적을 요구한다. 그런데 은행 문서가 실적 기준을 **카드 상품설명서에 위임**한다. 두 문서를 이어야 판정할 수 있다.
  - 케이뱅크 주거래우대 자유적금: "해당 체크카드 상품설명서 상의 실적 인정 기준을 준용" [V, 이전 보고서]
  - 금감원은 이 혼선을 공식 인정했다(2026-07-22) [V].
- **시연 질문:** "케이뱅크 적금 우대금리를 받으면서 OTT 할인도 받고 싶어. 체크카드로 넷플릭스를 결제하면 적금 실적에도 들어가?"

| 단계 | 내용 |
|---|---|
| Entity | SavingsProduct, PreferentialCondition, Rule(실적 산정 위임), Card, Rule(실적 제외), Benefit |
| 경로 | `Savings→HAS_CONDITION→Condition(카드실적)→DELEGATES_TO→Card(Rule 실적 기준)→EXCLUDES→거래유형` (3-Hop, 문서 경계를 넘는다) |
| 예상 판정 | 위임 대상 체크카드가 특정되지 않으면 **확인 불가**. 특정되면 카드 실적 규칙으로 판정 |
| 근거 | 케이뱅크 상품 페이지 [V]. 적금 상품설명서 PDF 실물은 **미확보** |

- **약화 요인 [V]:** 금감원 개선안으로 **은행 대출 금리감면**의 카드 실적 제외항목이 4~8개에서 1개 수준으로 줄어든다. 체크카드도 신용카드와 같은 기준으로 인정한다. 2026년 9~10월 신규 대출부터 적용한다. 대출 쪽 복잡성은 제도적으로 줄어드는 중이다. 적금 쪽은 개선안에 포함됐는지 확인하지 못했다.
- **ChatGPT가 이미 잘 답한다면 추가 가치는?**
  - 문서 간 위임을 따라가야 하는 질문이다. 그래서 6개 후보 중 그래프 필요성이 가장 크다.
  - 그러나 다음이 걸린다.
    - 적금 PDF가 미확보다.
    - 문서 종류가 새로 늘어난다.
    - 대출 쪽 문제는 제도가 해소하고 있다.
  - 3일 일정에는 맞지 않는다.

### C6. 상품설명서 개정 전후 규칙 변경 추적

- **시연 질문:** "KB Youth Club 상품설명서가 개정되면서 OTT 결제 조건이 바뀌었어?"
- **판정: 탈락.**
  - KB PDF 파일명에 날짜가 있다(예: `04124__prdctOpmn_20260330.pdf`). 그러나 **이전 판 PDF를 구할 수 있는지 확인하지 못했다.**
  - 개정 이력이 없으면 시연할 수 없다. 지시문 제외 기준에 해당한다.

## 6. 최우선 후보 1개 심층 분석 — C2

### 6.1 대표 질문과 경로

- **질문:** "넷플릭스는 앱스토어 구독, 쇼핑은 대부분 네이버페이로 할 거야. 등록 카드 중에서 내 결제 습관 때문에 빠지는 혜택과 그 조항을 전부 보여주고, 습관을 하나만 바꾼다면 뭘 바꾸는 게 제일 많이 살아나는지 알려줘."

**경로**

1. `(:Service {넷플릭스})<-[:APPLIES_TO]-(:Benefit)<-[:OFFERS]-(:Card)`: 대상 혜택을 찾는다 (2-Hop)
2. `(:Benefit)<-[:SCOPED_TO]-(:Rule {kind:'결제수단 제외'})-[:TARGETS]->(:PaymentMethod {인앱결제})`: 각 혜택에 걸린 제외 규칙을 찾는다 (2-Hop)
3. 범위가 카드 전체인 규칙: `(:Card)-[:HAS_RULE]->(:Rule {scope:'card'})-[:TARGETS]->(:PaymentMethod {간편결제(일반)})`. 예: Youth Club의 Y4
4. 예외: `(:Rule)-[:HAS_EXCEPTION]->(:Rule {kind:'예외 허용'})-[:FOR_SERVICE]->(:Service)`, `-[:TARGETS]->(:PaymentMethod {네이버페이})`. 예: NEED Pay의 N5 (3-Hop)

**판정**

- Python이 각 (카드, 혜택)에 대해 다음 넷 중 하나로 분류한다: 명시 제외 / 예외로 허용 / 범위 밖 / 미기재(확인 불가)
- "습관 1개 변경" 비교는 결제방식 노드 하나를 바꿔 다시 판정하고, 살아나는 혜택 수를 센다.

### 6.2 일반 ChatGPT 대비 추가 가치 (정직한 평가)

| 항목 | 일반 ChatGPT | C2 |
|---|---|---|
| 단일 카드 해석 | 잘함 [U] | 동등 (추가 가치 없음) |
| 카드 집합 전체를 빠짐없이 | 웹 검색 결과에 좌우됨 [H] | 등록된 집합 전체를 반환. **단, 집합이 6~7종뿐** |
| 같은 단어, 다른 범위 (Y4 vs W2) | 미측정 | 데이터 구조로 고정 |
| 원문에 없을 때 | 과잉 일반화 의심 1건 [U] | '확인 불가'를 규칙으로 반환 |
| 습관 변경 시 살아나는 혜택 수 | 미측정 | 결정적 계산 |
| 사용자가 이 차이를 체감하는가 | — | **낮음.** 틀린 답을 경험해야 체감한다 |

**결론:** C2의 추가 가치는 "같은 기준으로, 빠짐없이, 재현되게"다. 이 가치는 **골든 테스트에서 ChatGPT 기준선보다 낫다는 측정치**가 있어야만 발표에서 차별화로 쓸 수 있다. 측정치 없이 쓰면 "ChatGPT로 되는데?"라는 질문에 답하지 못한다.

## 7. 3일 MVP 가능성

> 카드 주제를 REFINE으로 유지하기로 결정할 경우에만 쓰는 설계다. C2 하나로 시연한다.

### 7.1 범위

| 구분 | 내용 |
|---|---|
| 필수 | 카드 5종: NEED Pay, WE:SH All+, Youth Club, JADE Classic, 구독 좋아요 (첵첵은 '혜택 없음' 대조용 선택). Service 3개: 넷플릭스, 유튜브프리미엄, 네이버플러스. PaymentMethod 5개: 인앱결제, 간편결제(일반), 네이버페이, 공식 홈페이지 정기결제, 자동납부. 판정 4분류. 원문 인용 |
| 제외 | 금액 계산, 실적 구간 연쇄, 적금 연계, 개정 추적, 10종 전체 구축, 범용 규칙 엔진, 다중 에이전트 |
| 데이터 주의 | 구독 좋아요는 **신규 발급 중단** 상품이다 [V]. 근거도 PDF가 아니라 HTML이다. 대신 KB ALL로 바꿀 수 있다. KB ALL은 이미지 PDF라 사람 전사가 필요하다 |

### 7.2 노드·관계

- 노드: `Card`, `Document`, `Benefit`, `Service`, `PaymentMethod`, `Rule`(속성 `kind`, `scope`, `certainty`), `Choice`
- 관계: `OFFERS`, `APPLIES_TO`, `HAS_RULE`, `SCOPED_TO`, `TARGETS`, `HAS_EXCEPTION`, `FOR_SERVICE`, `DESCRIBED_IN`
- 모든 간선에 다음 속성을 붙인다: `{doc_id, page, quote, status:'approved'}`
- 이 스키마는 기존 설계와 같다(`Claude_카드GraphRAG_기술적용타당성_20261028.md` §4).

### 7.3 LangGraph State

```
user_query, parsed_plan{services[], payment_methods[]},
candidate_paths[], verdicts[{card, benefit, class, rule_id, quote, page}],
what_if{changed_method, revived_count}, unknowns[]
```

**Python 판정 책임**

- 4분류 우선순위: 예외 허용 > 명시 제외 > 범위 밖 > 미기재
- 카드 전체 규칙과 혜택 규칙을 함께 적용한다.
- 습관 1개 변경 시 다시 판정한다.
- LLM은 질의 파싱과 결과 문장화만 맡는다.

### 7.4 Streamlit

- 왼쪽: 결제 습관 선택(칩) + 자유 질문
- 가운데: 카드×혜택 판정 표(4색)
- 오른쪽: 선택한 칸의 경로 그래프와 원문 인용(쪽 포함)
- 아래: "습관 하나 바꾸기" 비교

### 7.5 골든 테스트 질문과 판정 기준

| # | 질문 | 정답 | 근거 |
|---|---|---|---|
| G1 | 앱스토어로 넷플릭스를 내면 어떤 카드 혜택이 빠지나 | 5종 모두 명시 제외 | W2, N4, J1, Y3, R2 |
| G2 | 네이버플러스를 네이버페이로 내면 | NEED Pay: 예외로 허용 + 중복 가능. WE:SH All+: 제외. Youth Club: 쇼핑멤버십은 B팩이고 카드 전체 간편결제 전용 가맹점 제외(Y4)가 걸릴 수 있음 → 조건부 | N5, N6, W2, Y1, Y4 |
| G3 | 넷플릭스 앱에서 카드를 직접 등록해 결제하면(앱마켓 아님) | 구독 좋아요: **확인 불가**(원문은 '공식 홈페이지 직접 접속/신청'만 명시). 다른 카드도 각 원문 표현으로 판정 | R2, N4, Y3 |

- **정답:** 4분류와 조항 ID가 모두 일치
- **오답:** 분류가 하나라도 틀림. 특히 확인 불가를 허용·제외로 단정하면 오답
- **근거 부족:** 분류는 맞지만 인용 쪽이나 문구가 틀림
- **필수 대조군:** 같은 3문항을 일반 ChatGPT에 같은 날 묻고 기록한다. 이 대조가 없으면 발표에서 차별화를 주장하지 않는다.

### 7.6 역할과 일정

## 8. 주제 유지 vs 변경

### 8.1 카드 유지(REFINE)의 근거

- 원문 PDF 6종, 관계표, 스키마, Cypher가 이미 있다 [V]. 3일 일정 위험이 가장 낮다.
- GraphRAG **교육 목적**의 장점이 실재한다. "같은 단어, 다른 범위"와 예외의 예외는 관계 추출 → 사람 승인 → 근거 추적을 보여주기 좋은 소재다 [V].

### 8.2 카드 변경(PIVOT)의 근거

- 사용자 실험에서 일반 ChatGPT가 기존 기획의 거의 모든 기능을 수행했다 [U].
- 새 후보의 최고점은 63점(추정)이다. 70점에 못 미친다.
- 남은 가치(전수성·재현성)는 측정 전이다. 사용자가 체감하기 어렵다. SQL로도 같은 결과가 나온다.
- 강사님은 이미 "토스가 비슷한 서비스를 한다"고 지적했다(이전 보고서). 같은 유형의 질문 "ChatGPT로 되는데?"에 답할 준비가 안 돼 있다.

### 8.3 서비스 경쟁 우위와 교육적 장점을 분리한 평가

| 구분 | 카드 GraphRAG |
|---|---|
| 서비스 경쟁 우위 | **약함** (§5, 최고 63점) |
| GraphRAG 교육적 장점 | **보통 이상** (범위가 다른 규칙, 예외의 예외, 사람 승인 흐름) |

### 8.4 구현 방식 비교 (§6 요구)

| 비교 항목 | ① LLM + 웹 검색 | ② RAG + PDF 청크 | ③ Neo4j + Python 판정 + LLM 설명 |
|---|---|---|---|
| 충돌·예외 처리 | 단일 카드는 처리 [U]. 여러 카드는 미측정 | 청크가 쪼개지면 예외 문구를 놓칠 위험 [H] | 승인된 관계 범위 안에서는 결정적. 관계를 잘못 추출하면 그대로 틀림 |
| 카드사 간 교차 비교 | 검색 결과에 좌우 [H] | 검색된 청크만큼 | 등록 집합 전체. **SQL로도 동일** |
| 근거 추적 | URL·항목명 [U] | 청크 위치 | 간선마다 쪽·인용 |
| 오답 검증 수단 | 사람이 매번 확인 | 검색 청크 확인 | 골든 테스트 + 승인 이력 |
| 구현 복잡도 | 낮음 | 중 | 중~상 (추출·승인·적재) |
| 3일 가능성 | 가능 (서비스가 아님) | 가능 | 가능 (범위를 C2 하나로 줄일 때) |
| 속도·정확도 우위 | **실험 안 함** | **실험 안 함** | **실험 안 함.** 우위를 주장하지 않는다 |

**SQL로 가능한 것:** C2·C1·C3·C4의 판정은 `card`, `benefit`, `rule`, `rule_scope`, `rule_target`, `rule_exception`, `choice_option` 테이블 조인으로 모두 가능하다. 그래프가 나은 점은 **경로 자체가 설명이 된다**는 표현상의 이점과 교육적 이점뿐이다.

### 8.5 전환 후보 비교 (§10 요구)

| 후보 | 공식 문서 확보 | 의미 있는 2~3-Hop | 일반 LLM과 구분되는 검증 가능한 기능 | 2인·3일 | 판정 |
|---|---|---|---|---|---|
| **P1. DART 재건축·재개발 현장→조합→PF 보증→조건** | **확보** (저장소 보고서: 현대건설·삼성물산 사업보고서 2건 + 계약 공시 2건, 현장 11개, 자동 확정 가능한 3-Hop 5개, 방화6은 사람 승인 필요) | 실재 (`현장→조합→PF 행→신용보강 조건`). 다만 조건 노드까지 가는 3-Hop은 일부 각주 행에만 있음 | **[H]** DART 뷰어의 표 두 개(수주 표, 우발부채 표)를 조합명 정규화로 이어야 한다. 웹 검색 LLM이 이를 안정적으로 하는지는 **미측정** | 가능 (보고서 결론. 이번 세션 재검증 안 함) | **추정 68점. 1순위** |
| P2. 삼성전자 보증·수리 판단 (DART + 보증 페이지) | 확보 (저장소 보고서) | 실재 (제품→구매형태→증빙규칙→예외) | 약함. 보증 정책은 공개 웹 페이지라 ChatGPT가 잘 읽을 가능성이 높음 [H]. 카드와 같은 약점 | 가능 | 추정 55점 |
| P3. 화장품 제품→원료→효능 (OpenDART) | 확보 (저장소 보고서: 3-Hop 하한 3건) | 약함 (데이터의 약 80%가 한 회사, 효능은 기업 주장) | 약함 | 가능 | 추정 50점 |
| P4. 사내 업무규정·협력사 준수기준·승인 예외 | **이번 세션에서 공식 문서 미확보** (ALIO 내부규정, 법령정보센터 원문 수집 시도 실패) | 미검증 | 미검증 | 미검증 | **추천 불가** (지시문 기준) |

**P1 점수 이유 (추정)**

| 항목 | 점수 | 이유 |
|---|---:|---|
| 차별성 | 13/25 | 반증은 없지만 측정도 없음 |
| 가치 | 11/20 | 조합원·투자자 관심. 단 위험 판정을 하지 않아 효용이 제한됨 |
| 그래프 필요성 | 16/20 | 문서 간 개체 결합과 동일성 확인이 본질 |
| 원문 확보 | 14/20 | 기존 검증 완료 |
| 구현 | 14/20 | XML 파서 재사용 언급이 있으나 이번 세션 미확인 |
| **합계** | **68** | P1도 **70점 미만**이다 |

**P1의 반증 가능성**

- P1은 "카드보다 확실히 낫다"가 아니라 **"아직 반증되지 않았다"** 수준이다.
- 그래서 착수 전 **Day 0 기준선 시험(2시간)** 을 권한다. 기존 Q&A 보고서의 Q05~Q08과 Q14를 일반 ChatGPT에 그대로 묻는다.
- **대부분 맞히면** P1의 전환 근거도 사라진다. 그때는 강사님의 평가 기준(§9 Q1)에 따라 카드 REFINE 또는 P1 중 데이터 준비가 된 쪽을 고른다.
- **틀리거나 표 결합을 못 하면** P1의 차별성이 실측으로 뒷받침된다.

**레시피 프로젝트 재사용**

- Neo4j 적재·라벨 규칙, Streamlit MVP 골격(`wip/graphrag-mvp-20261023` 브랜치)은 카드와 DART 어느 쪽에도 재사용할 수 있다.
- 도메인 ETL은 새로 짜야 한다.

## 10. 최종 결정

## **PIVOT**

**근거 (검증된 사실·실현 가능성·약점 순)**

1. **[U] 일반 ChatGPT가 기존 기획의 핵심 기능을 대부분 수행했다.** 1~3-Hop 조건 설명, 인앱결제 제외, 결제방식 변경 전후 비교가 여기에 들어간다.
2. **[V] 남은 차이(전수성·범위 구분·확인 불가)는 SQL로도 같게 구현된다.** 사용자가 체감하기 어렵다.
3. **[H] 그 차이가 실제로 존재하는지는 측정하지 않았다.** 근거는 과잉 일반화 의심 1건뿐이다.
4. **새 카드 후보 6개 모두 70점 미만이다.** 최고는 C2의 63점(추정)이다.
5. **실현 가능성 자체는 카드가 가장 높다.** 그래서 이 결정의 비용도 크다. 이를 줄이기 위해 다음 조건을 둔다.
