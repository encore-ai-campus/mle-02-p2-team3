## 0. 결론 요약

**판정: 조건부 가능.** 수작업 검수와 문서별 처리가 반드시 필요하다.

| 질문 | 답 | 근거 |
|---|---|---|
| 공식 PDF를 안정적으로 확보할 수 있는가 | **발급사에 따라 다르다.** KB국민·하나카드는 상품 페이지 HTML에 PDF 직링크가 있다. curl만으로 받을 수 있다. 신한·우리카드는 JS를 실행해야 링크가 생겨 확보하지 못했다. NH농협은 PDF를 받았지만 상세 페이지 버튼과의 연결은 확인하지 못했다 | 7종 다운로드 성공(3개 발급사). 2개 발급사는 실패. §A |
| 텍스트 추출이 쉬운가 | **대부분 쉽다.** 7종 중 6종은 텍스트 레이어가 있고 한글 깨짐이 0건이다. 1종(KB WE:SH All+)은 본문이 통째로 이미지라 OCR 없이는 혜택을 읽을 수 없다 | §B 실행 결과 |
| 혜택을 구조화하기 쉬운가 | **어렵다.** 텍스트가 나와도 병합셀, 2단 배치, 신용·체크 공용 문서, 다른 페이지 주석이 적용 범위를 바꾸는 문제가 있다. 이 때문에 '어느 조건이 어느 혜택에 붙는지'를 정하는 데 해석이 필요하다 | §C, §D 실제 사례 |
| 2인 팀의 현실적인 자동화 범위 | 다운로드 → 텍스트·표 추출 → LLM 후보 추출까지는 자동화할 수 있다. **혜택·조건·제외 연결의 최종 확정은 사람이 원문 페이지를 보며 검수해야 한다.** 카드 10종 안팎이 현실적이다 | §F |
| 가장 큰 기술 위험 | 값 자체가 아니라 **적용 범위**(어느 혜택·카드 종류·결제 방식에 조건이 걸리는지)를 잘못 연결하는 것. 추출 결과는 그럴듯해 보이므로 오류가 눈에 띄지 않는다 | §D-3, §E |

### B-2. 원문 구조와 추출상 문제 (실제 관찰)

1. **띄어쓰기 소실 (KB 2종).** 공백/한글 비율이 KB 첵첵 0.06이다. 하나·NH는 0.34~0.39다. 예: `전월30만원이상이용시`, `상품권및선불카드구입(충전)금액`. 화면에서는 띄어 쓰여 있다(페이지 이미지 확인). PowerPoint에서 PDF로 바꿀 때 공백 글리프가 빠진 것으로 보인다(추정). 정규식에 `\s*`를 넣어야 하고, 임베딩·키워드 검색 품질에도 영향이 있다.
2. **표의 세로 병합셀 (KB 첵첵 1쪽).** pdfplumber가 13×7 표를 뽑았다. 그러나 '건당 1천원 / 영역당 2천원 / 건당 2천원 / 영역당 4천원'은 첫 행에만 있고 **나머지 8개 영역은 None 32칸**이다. 원본은 9개 영역에 한 셀이 병합된 구조다. "위 행 값으로 채우기"는 이 표에서는 맞지만, 병합이 아닌 진짜 빈칸에서는 틀린 값을 만든다.
3. **2단 배치를 섞는 추출 (NH).** `pdfplumber.extract_text()`는 신용·체크 두 단을 한 줄로 이어 붙였다. 예: `□ 이 동통신요금 5% 청구할인(월 1회)`와 체크 단의 `- GS25/CU`가 같은 영역에 뒤섞인다. PyMuPDF는 단을 블록 단위로 내놓아 순서가 맞았다. 다만 상단 제목 `체크카드 주요 서비스`가 `신용카드 주요 서비스`보다 **먼저** 나온다(화면과 반대). 제목 텍스트로 단을 나누는 방식은 실패한다.
4. **글자 사이 공백·제어문자 (NH).** pdfplumber는 `버 스`, `이 동통신요금`처럼 글자 사이에 공백을 넣었다. PyMuPDF는 `\x07`(BEL) 52개를 섞었다. 정제 단계가 필요하다.
5. **펼침면·인쇄 쪽번호 불일치 (하나).** PDF 3쪽 안에 인쇄 쪽번호 '2', '3'이 함께 있다. 원문 근거는 **PDF 페이지 번호**로 저장하고 인쇄 쪽번호는 따로 둬야 한다. 하나 원더카드 3쪽 표 하나에 왼쪽(연회비)과 오른쪽(서비스 개요) 내용이 함께 잡혔다.
6. **상품명과 문서의 불일치 (하나).** 페이지 상품명은 "원더카드 2.0 FREE+"이지만 PDF 텍스트 어디에도 "FREE"가 없다. PDF는 원더카드 2.0 전체 설명서다. 상품 유형명('범용형/혼합형/특화형')은 4쪽의 **도형(이미지) 안 글자**라 텍스트로도 나오지 않는다. 상품과 문서 범위를 연결하려면 사람이 판단해야 한다.
7. **문서 유형 명칭 불일치 (하나).** 버튼은 '상품약관보기', PDF 메타 제목은 '…약관', 본문은 "상품설명서"라고 말한다. 파일명 날짜(20260708)와 PDF 작성일(2026-08-04)도 다르다. **URL 날짜를 문서 버전으로 쓰면 안 된다.**
8. **신용·체크 공용 문서 (NH).** 한 PDF에 두 상품이 있다. 연회비·혜택·한도·해외수수료가 카드 종류마다 다르다(예: 해외서비스수수료 신용 0.25%, 체크 건당 $0.5). "카드 1종 = PDF 1개" 가정이 깨진다.
9. **혜택 조건이 여러 페이지에 흩어짐.** 혜택 표는 1쪽, 전월실적 산정 기준·제외 대상·입점매장 제외·PG 제외·중복 제한은 2쪽에 있다(KB 첵첵, NH 모두 같은 구조). 하나 원더카드는 서비스 영역 기준이 6~8쪽, 제공 기준이 9~11쪽, 유의사항이 13~16쪽에 있다.

### B-3. 페이지 번호·원문 위치 보존

- 두 라이브러리 모두 페이지 단위로 열기 때문에 **PDF 페이지 번호 보존은 쉽다.** 이번 테스트의 모든 추출값에 page를 붙였다.
- **쪽 안의 위치**(블록 좌표)도 PyMuPDF `get_text("dict")`로 얻을 수 있다. 다만 이번에는 페이지 + 원문 문구 수준까지만 저장했다.
- **조항 번호 보존은 문서마다 다르다.** KB는 `[전월이용실적제외대상]` 같은 대괄호 소제목이 있다. NH는 `•`, `※`, `□` 기호만 있다. 하나는 `2. 원더 서비스 > 2) … > ② …` 계층이 있다. 일관된 조항 ID는 만들 수 없고, 문서별 규칙이 필요하다.

### C-3. 방식 A 결과 채점 (정답 셋 대비, 수동 대조)

| 항목 | KB 첵첵 | NH 모두의카드 |
|---|---|---|
| 숫자 값(금액·%·한도) | 9개 영역 × 4칸 + 통합한도 모두 일치. 단 병합셀 채우기 가정 덕분 | 연회비 6칸, 혜택률 14개, 통합한도 3세트 일치 |
| 대상 가맹점 | 문자열은 맞음. '네이버/카카오/SSG페이' 분해 안 됨 | `\x07` 잡음이 붙은 상태로 추출 |
| 조건 귀속 | 영역별 조건은 표 열이라 맞음. 2쪽 제외조건과의 연결은 없음 | ※ 주석을 단 단위로만 귀속. **'스포츠·H&B 오프라인 한정'을 라이프(1)에 연결하지 못함.** '가족카드 발급 불가'와 페이지 하단 문구(심의필·상담센터)가 **체크카드 주석으로 오귀속** |
| 판단 불가 항목 | 대중교통 '건당 3만원' 의미를 구분 못 함(그대로 3만원 저장) | 라이프(1) 최소금액 없음을 표시하지 못함 |

→ **숫자 추출은 규칙으로 충분하다. 조건의 적용 범위는 규칙으로 맞추기 어렵다.** 게다가 규칙은 문서별로 직접 작성했다(KB 표 열 위치, NH '두 번째 모빌리티 서비스' 위치). 다른 카드에 그대로 재사용할 수 없다.

### D-2. 방식별 비교 (A~D)

| 방식 | 구현 난이도 | 자동화 가능성 | 사람 검수 지점 | 정확성 위험 | 예상 주요 오류 | 2인 팀 부담 |
|---|---|---|---|---|---|---|

### D-3. 요청된 다섯 질문에 대한 실제 예시

**1) 혜택 표는 Python만으로 추출할 수 있는가?**
**표 모양에 따라 다르다.**
- KB 첵첵 1쪽 표는 pdfplumber로 13×7을 그대로 얻었다. 그러나 할인금액 셀 32칸이 None이었다. 페이지 이미지를 보고 "세로 병합"임을 확인한 뒤에야 위 값으로 채울 수 있었다.
- NH는 pdfplumber 표 12개가 대부분 1~2행 조각이었다. 실제 값은 PyMuPDF 줄 순서(전월실적 → 구간1 → 구간2 → 할인한도 → 값1 → 값2)를 정규식으로 읽어 얻었다.
- 하나 원더카드는 펼침면 좌우 내용이 한 표로 묶였다.
- 즉 **값은 Python으로 뽑을 수 있지만, 표 구조가 맞는지는 사람이 페이지 이미지로 확인해야 했다.**

**2) 제외 조건을 정확하게 추출하기 어려운 이유는?**
- (a) **층위가 여러 개다.** NH는 '전월실적 산정 제외'(21개)와 '할인 서비스 제외'(22개, 무이자할부 추가)가 따로 있다. 이름이 비슷해 섞이기 쉽다.
- (b) **위치가 흩어져 있다.** KB 첵첵은 영역별 제외(1쪽 표 열), 일반 할인 제외(2쪽 본문), 실적 제외(2쪽 대괄호 소제목)가 세 곳에 있다.
- (c) **확정 여부가 불명확하다.** KB 2쪽 "…입점한 가맹점이나 상품권 구매 시 할인대상에서 **제외될 수 있습니다**".
- (d) **가맹점 분류에 의존한다.** NH "가맹점명이 '네이버페이'인 경우 편의점 가맹점이 아닌 '간편결제' 가맹점으로 분류" — 1쪽 편의점 혜택의 범위를 2쪽이 거래 단위로 바꾼다. PDF만으로는 어떤 거래가 해당하는지 알 수 없다.
- (e) **목록 끝이 "등"이다.** "…포인트 사용분 **등**의 이용금액" — 완전한 목록이 아니다.

**3) LLM이 할인 조건의 적용 범위를 잘못 해석할 위험이 있는가?**
**있다. 이번 문서에서 구체적인 함정을 확인했다.**
- NH 신용 단의 "※ 커피전문점/편의점/**스포츠/H&B** 할인 대상 가맹점은 오프라인 매장 현장 결제에 한함"은 '라이프 서비스(2)' 블록 아래에 있다. 그런데 스포츠·H&B는 '라이프 서비스(1)'의 혜택이다. 블록 단위로 읽으면 누락하고, 문장 단위로 읽으면 맞게 연결된다.
- NH 체크 단 주석은 "이동통신요금 **할인**"이라고 쓰지만 체크카드 혜택은 캐시백이다.
- "라이프 서비스는 이용 건당 1만원 이상"이 자동납부 통신요금에도 적용되는지 원문만으로는 알 수 없다.
- KB 대중교통 "이용금액 건당 3만원 이상"은 후불교통 청구 건과 고속버스 승차권 건 중 무엇을 뜻하는지 정해지지 않는다.

이런 문장에서 LLM은 **하나의 해석을 골라 확신 있게 출력**할 가능성이 높다(이번에 LLM 파이프라인을 실행해 측정한 것은 아니고, 문서 구조에서 예상한 위험이다). → 스키마에 `evidence_type`(명시/해석/조항연결/판단불가)과 원문 인용을 **필수 필드**로 두고, 해석 이상 항목은 사람 검수 대상으로 보내야 한다.

**4) 추출 결과를 관계형 테이블로 정리하기 쉬운가?**
**뼈대는 쉽고, 조건은 어렵다.**
- 쉬운 부분: `card`(발급사, 이름, 종류, 문서 버전) / `annual_fee` / `benefit`(영역, 가맹점, 방식, 율·금액) / `spend_tier`(구간 하한·상한) / `benefit_cap`(혜택×구간×한도). KB·NH 두 카드가 모두 이 틀에 들어갔다.
- 어려운 부분:
  - (a) NH처럼 **한 문서 = 두 상품**이면 `document`와 `card`를 N:M으로 둬야 한다.
  - (b) 한도가 세 층이다(건당 / 영역당 / 통합). 그룹 한도(NH '라이프서비스1 통합')는 혜택 묶음 테이블이 따로 필요하다.
  - (c) "월 2천원, 2회 한"처럼 **금액 한도와 횟수 한도가 한 문구**에 있다.
  - (d) 조건은 결국 `condition(text, scope, evidence)` 같은 반구조 컬럼으로 남는다.
  - (e) 하나 원더카드는 **사용자가 57개 영역과 율을 고르는 구조**라 고정 혜택 행으로 표현할 수 없다.

**5) Neo4j 관계로 바꿀 때 추가로 필요한 작업은?**
- (a) **엔티티 정규화 사전**: 'CU편의점', 'GS25/CU', '편의점'처럼 같은 대상이 문서마다 다르게 적힌다. 업종과 가맹점 노드를 통일하는 사전을 직접 만들어야 한다.
- (b) **조건을 노드로 할지 관계 속성으로 할지 결정**: 전월실적 구간은 혜택 × 구간마다 한도가 달라 관계 속성으로 넣기 어렵다.
- (c) **관계 방향과 범위 검증**: '오프라인 한정'이 혜택 노드에 붙는지 그룹에 붙는지 정해야 한다. 이는 §D-3 3)의 해석 문제가 그대로 그래프 오류가 된다.
- (d) **문서 버전 노드**: 같은 카드의 PDF가 갱신되면(파일명 날짜 ≠ 작성일) 이전 관계를 무효화해야 한다.
- (e) **출처 연결**: 모든 관계에 `(document, page, quote)`를 붙여야 원문 대조 검수가 가능하다.
- 관계형(C)에서 이미 해야 하는 정규화에 (a)·(c)가 더해진다. **추출 정확도는 저장소 선택으로 좋아지지 않는다.**

| 문제 | 이번에 관찰한 사례 | 영향 | 대응 방향 |
|---|---|---|---|
| **PDF 형식 차이** | KB=PowerPoint 변환(세로 3쪽), 하나=Illustrator 펼침면(가로/세로), NH=InDesign 2단 A4, KB WE:SH=전면 이미지 | 공통 파서가 불가능. 발급사·양식별 분기 필요 | 1단계에서 텍스트형/이미지형 자동 판별, 양식별 전처리 |
| **문서 확보 경로 차이** | KB·하나는 HTML 직링크, NH는 코드 경로, 신한·우리는 JS 렌더링 | 수집기 발급사별 구현. 신한·우리는 헤드리스 브라우저 필요 | 범위를 직링크 발급사로 제한하거나, 브라우저 자동화 시간을 따로 잡기 |

| **상품 ↔ 문서 매핑** | 원더카드 2.0 FREE+ 페이지 → 원더카드 2.0 전체 문서(FREE 표기 없음). NH 문서 하나 = 신용+체크 | 카드 단위 집계 오류 | `document`와 `card`를 분리 저장, 매핑은 사람이 확정 |

| **정규화** | 금액 표기(1천원/1,000원/1만원), 한도 층위(건당·영역당·통합·그룹), 횟수+금액 혼합 | 비교 질의 오류 | 단위 변환 함수 + 한도 유형 코드 |
| **텍스트 품질** | KB 띄어쓰기 소실, NH `\x07` 52개, pdfplumber 글자 사이 공백·단 혼합 | 검색·정규식·LLM 입력 품질 저하 | PyMuPDF 우선 사용, 제어문자 제거, 라이브러리 2종 교차 확인 |
| **이미지 PDF** | KB WE:SH All+ 텍스트 452자(본문 전부 이미지) | OCR 없이는 혜택 0건 | OCR 엔진 도입(이번 환경에 없음) 또는 비전 LLM. 둘 다 숫자 오인식 검수 필요 |
| **검수 비용** | KB 첵첵 3쪽·NH 2쪽 정답 셋 작성에 원문 텍스트 + 페이지 이미지 대조가 필요했다 | 카드 수에 비례해 증가 | 검수는 '해석·판단불가' 항목에만 집중. 숫자는 규칙과 LLM 교차 일치로 자동 통과 |

**검수 비용 추정(참고, 측정치 아님):** 2~3쪽짜리 단순 설명서는 카드당 30분~1시간, 하나 원더카드 같은 16쪽 선택형은 수 시간 수준으로 예상한다. 이번에 정답 셋 2종을 만든 경험에서 나온 추정이며, 사람 작업 시간을 실측하지는 않았다.

## F. 최종 판단

### 판정: **조건부 가능**

수집·텍스트 추출은 대부분 수월하다. 그러나 혜택-조건-제외의 정확한 연결에는 **사람 검수가 필수**이고, 일부 문서는 **별도 처리(OCR, 공용 문서 분리, 선택형 구조)**가 필요하다.

**근거(이번 검증에서 직접 확인한 것):**
1. 공식 PDF 7종(3개 발급사)을 실제로 받았다. 모두 `%PDF` 시그니처, 정상 쪽수, 암호화 없음.
2. 7종 중 6종은 텍스트 레이어가 있고 한글 깨짐 0건. 1종은 이미지 기반(452자)이다.
3. 규칙 기반 추출로 KB 첵첵·NH 모두의카드의 금액·율·한도·구간·제외 목록은 정답 셋과 일치했다. 그러나 조건 귀속 오류 2건(스포츠·H&B 오프라인 조건 누락, 가족카드·하단 문구 오귀속)과 판단 불가 항목 처리 실패가 나왔다.
4. 신한·우리카드는 JS 렌더링 때문에 정상적인 정적 방법으로 PDF를 확보하지 못했다.

### 질문별 답

**1. 공식 카드 PDF를 안정적으로 확보할 수 있는가?**
**발급사를 고르면 가능하다.** KB국민·하나카드는 상품 페이지 HTML에 직링크가 있어 curl만으로 반복 수집할 수 있다. NH농협은 공식 도메인 PDF를 받을 수 있지만, 상세 페이지 버튼과의 연결을 확인하지 못해 상품코드로 추정 매핑했다. 신한·우리카드는 브라우저 자동화 없이는 확보하지 못했다. 파일명 날짜가 문서 버전과 일치하지 않아 '최신본 여부'는 해시와 심의필로 따로 관리해야 한다.

**2. 실제 PDF에서 카드 혜택을 추출하고 구조화하기 쉬운가?**
**텍스트 추출은 쉽고, 구조화는 어렵다.** 숫자 값은 규칙으로 뽑힌다. 그러나 병합셀, 2단 배치, 신용·체크 공용 문서, 주석이 다른 블록의 혜택을 제한하는 구조 때문에 "어느 조건이 어느 혜택에 붙는가"는 해석이 필요하다. 정답 셋 기준으로 KB 첵첵 혜택 9행 전부가 '해석' 이상(병합셀)이었다. NH에서는 판단 불가 항목이 4건 나왔다.

**3. 카드 10종, 30종, 100종으로 늘리면 가장 큰 어려움은?**

| 규모 | 가장 큰 어려움 |
|---|---|
| 10종 | 검수 시간. 직링크 발급사(KB·하나)와 텍스트형 PDF로 제한하면 2인이 정답 셋 수준까지 검수할 수 있다 |
| 30종 | **양식 다양성과 엔티티 정규화.** 발급사가 늘면 규칙 재사용이 안 되고, 가맹점·업종 이름 통일 사전이 커진다. JS 렌더링 발급사 수집기와 이미지 PDF OCR이 필요해진다 |
| 100종 | **문서 갱신 추적과 검수 비용 선형 증가.** 문서 버전이 계속 바뀌어 재추출·재검수 파이프라인이 필요하다. 하나 원더카드 같은 선택형(57개 영역)은 고정 행으로 표현할 수 없어 별도 모델링이 필요하다 |

**4. 2인 교육 프로젝트에서 어디까지 자동화가 현실적인가?**
- **자동화:** 직링크 발급사 PDF 수집 → 무결성·텍스트형 판별 → PyMuPDF 페이지별 텍스트·표 추출 → 숫자 필드 규칙 추출 → LLM 후보 추출(evidence_type·원문 인용 필수) → 규칙과 LLM 결과 자동 비교.
- **사람:** 상품↔문서 매핑, '해석·조항연결·판단불가' 항목 확정, 엔티티 정규화 사전.
- **권장 범위:** KB·하나·NH 중심 **텍스트형 PDF 10종 안팎**. 이미지형(WE:SH All+)과 선택형(원더카드)은 '어려운 사례'로 따로 다루거나 제외한다.

**5. 실제 추출·정제 작업에서 가장 큰 기술적 위험은?**
**조건 적용 범위의 오연결이다.** 숫자 오류는 규칙과 LLM 결과를 비교하면 잡힌다. 반면 "오프라인 한정이 어느 혜택에 걸리는가", "건당 최소금액이 자동납부에도 적용되는가", "제외될 수 있다를 제외로 볼 것인가"는 두 방식이 같이 틀릴 수 있다. 결과도 그럴듯해 보여 눈에 띄지 않는다. 다음으로 큰 위험은 이미지 PDF(OCR 숫자 오인식)와 상품·문서 매핑 오류다.

### 미확인·한계 사항

- 신한·우리카드 PDF: 확보 실패. JS 렌더링 때문이며, 브라우저 도구가 꺼져 있었다.
- NH 모두의카드: 상세 페이지 버튼 → PDF 연결을 직접 확인하지 못했다. 상품코드 일치로 추정했다.
- 신규 발급 가능 여부: 신청 버튼이 있는지만 확인했다.
- 재배포 허용 여부: 홈페이지 이용약관을 확인하지 않았다.
- 실행하지 않은 것:
  - OCR — 엔진 미설치.
  - LLM API 기반 B~D 추출 — 실행 안 함. 정답 셋은 Claude의 수동 원문 대조 결과다.
- 하나 원더카드 2.0(16쪽): 구조 점검만 했고 정답 셋은 만들지 않았다.
