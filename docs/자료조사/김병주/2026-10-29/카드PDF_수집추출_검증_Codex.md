# 공식 카드 PDF 수집·추출 사전 검증

조사일: 2026-10-29. 목적은 공식 자료의 확보와 혜택 조건의 구조화 가능성을 확인하는 것이다. 실제 신청, LLM 호출, DB 저장은 수행하지 않았다. 결과는 **조건부 가능**이다. 하나카드의 실제 PDF 6개를 내려받아 열고 텍스트를 추출했지만 발급사 다양성, 최신 발급 상태, 자동 표 복원 및 의미 정확성은 검증이 충분하지 않다.

파일 위치는 `tmp/card_pdf_validation/codex/` 아래다. KB [ALL 카드](https://m.kbcard.com/cards/credit-cards/kb-all-card) 상세 페이지에서 상품설명서 다운로드 항목은 확인했지만 실제 직링크와 파일 확보는 하지 못했다. 신한카드는 공식 자료 검색을 했으나 개별 상품 혜택 PDF와 상세 페이지의 연결을 검증하지 못했다. 우리·농협·IBK는 이번 조사에서 확보·검증하지 못했다. 이 사실은 해당 기관에 PDF가 없다는 뜻이 아니다.

## B. 실제 PDF 분석

프로젝트 `.venv`의 PyMuPDF로 파일을 열고 페이지별 `get_text`와 `find_tables`를 실행했다. 표 탐지 개수는 정확한 표 수나 정확한 셀 복원을 보증하지 않는다. 페이지 번호는 PDF 파일 기준 1부터이고, 원문 텍스트 파일과 전체 탐지 결과·SHA-256은 임시 폴더의 `*_pN.txt`, `inspection.json`에 남겼다. 텍스트의 한글 글자 수가 충분하고 U+FFFD가 0개였으나, 이는 모든 글자의 의미 정확성을 보장하지 않는다. 6건 모두 텍스트 레이어가 존재하므로 전체 스캔 문서로 분류할 근거는 없으며 OCR은 실행하지 않았다. 일부 페이지는 이미지도 포함한다.

|PDF|페이지|페이지별 텍스트 글자 수|표 탐지 수|구조·난점|
|---|---:|---|---|---|
|BT|1|4659|4|혜택·공통조건이 한 큰 페이지에 다단 배치. 읽기 순서가 뒤섞이고 표 행이 합쳐짐|
|트래블로그 plus|2|3385, 4608|3, 1|통화표와 조건이 복수 페이지에 배치|
|PRESTIGE|2|4432, 3906|3, 3|통화·서비스 표와 조건이 혼재|
|ONE PICK STYLE|2|2420, 3169|0, 0|첫 페이지에 혜택표와 제외·실적 조건이 함께 있으나 표 미탐지; 다음 페이지에 공통 안내|
|VIVA G|1|5887|1|많은 문장이 한 페이지 다단 구성|
|MULTI Any|2|4853, 5120|0, 4|이미지와 텍스트 혼합, 표 탐지는 페이지별 편차|

BT의 `find_tables` 결과는 BIG TICKET 표를 찾았으나 4개 금액 구간과 4개 비율을 각각 하나의 셀에 줄바꿈으로 묶고, 월 한도도 `300만원 / 한도 없음`으로 합쳤다. 단순히 셀 하나를 한 레코드로 저장하면 잘못된다. 일반 텍스트 역시 표의 `없음`, `300만원` 등이 원래 행에서 떨어진다. ONE PICK STYLE은 표 탐지 0건이지만 텍스트에는 수치가 있으며, 표와 주석을 결합하는 별도 레이아웃 처리가 필요하다. 페이지별 텍스트 보존 자체는 성공했으나 사각형 좌표까지 검수한 것은 아니다. 원문은 파일 페이지 안에서도 다단이어서 순서와 범위 검수가 필요하다.

## C. 구조화 샘플 및 근거

두 카드의 수작업 검수 기반 JSON은 `tmp/card_pdf_validation/codex/samples.json`에 있다. 자동 LLM 추출 결과가 아니다. 모든 채워진 주요 항목에는 파일 및 페이지/원문 근거가 연결되며, 미확인 필드는 null로 두었다. 완전한 상품 데이터가 아니라 주요 혜택 각각 한 건을 뽑은 부분 샘플이다. 선택 및 중복 제한은 조사 범위에서 미확인이다.

## D. 자동화와 구현 부담

|방식|난이도 / 자동화|사람 검수·정확성 위험|2인 부담|
|---|---|---|---|
|A Python 규칙|어려움; 다운로드·페이지 추출·금액 후보 정규식은 가능|다단·병합 셀 복원, 부정·예외·적용 범위와 누락 확인 필요. 6건만으로 범용 규칙 성능 미측정|발급사·서식별 규칙 유지가 큼|
|B LLM→JSON|보통~어려움; 후보 생성 가능, 실제 모델 실험은 미수행|표와 제외 범위 오연결, 숫자 누락·환각; 근거 페이지와 원문 대조 필수|스키마·평가셋·검수 도구 필요|
|C LLM→PostgreSQL|어려움; JSON 후보 뒤 적재는 자동화 가능|카드 버전, 혜택, 조건, 한도, 제외, 근거를 분리하고 외래키·제약 검수|B에 스키마 및 이력 관리가 추가. 실제 DB 변경 없음|
|D LLM→Neo4j|어려움; 매핑은 자동화 가능|가맹점 동명이칭, 조건 범위, AND/OR, 한도 공유·시간 버전, 관계 방향 및 근거 검수|C의 정규화에 개체 식별·관계 모델링과 질의 검증 추가. 실제 DB 변경 없음|

Python은 PDF 유효성·페이지·문자·수치 후보를 처리하고 일부 표 위치를 탐지할 수 있다. 위 BT와 ONE PICK 결과는 표 전체를 정확하게 자동 구조화했다고 입증하지 않는다. LLM은 복잡한 문장의 범위 연결 후보에 도움을 줄 수 있지만 필수임을 실험으로 입증한 것은 아니며 정확성을 보증하지 않는다. 특히 BT의 BIG TICKET은 실적 없음인데 다른 서비스의 50만원 조건을 문서 전체에 적용하면 잘못된다. 실적 제외와 할인 제외는 같은 항목이 일부 겹치더라도 서로 다른 조건이다. 관계형 저장은 검수된 정형 데이터의 테이블화 자체는 가능하지만 여러 혜택에 걸친 공유 한도와 예외는 별도 테이블과 범위 표현이 필요하다. 그래프는 카드→혜택→조건·제외·가맹점 관계 외에도 조건 결합, 적용기간 및 문서 근거를 모델링해야 하므로 저장 형식만 바꿔 정확도가 개선되지는 않는다.

## E–F. 확대 시 문제와 최종 판단

1. **안정적 확보:** 하나카드 6개 URL은 이번에 정상 다운로드했다. 발급사 한 곳과 한 시점의 표본이므로 전체 시장에서 안정적으로 확보된다고 결론낼 수 없다. 메뉴 접근·발급 중단·링크 변경·접근제한 및 재배포 허가를 확인해야 한다.
2. **추출·구조화 난이도:** 텍스트 확보는 이 표본에서 쉬웠으나 정확한 조건 구조화는 어렵다. 표 미탐지와 병합, 다단 순서 및 별도 제외 조항 때문에 검수가 필요하다.
3. **10/30/100종 확대:** 10종은 출처·문서별 수작업 검수, 30종은 발급사별 레이아웃과 개정 이력 관리, 100종은 변경 감지·중복 및 대규모 품질 검수가 가장 큰 부담이 될 가능성이 있다. 이는 정량 벤치마크가 아닌 이 실험에 근거한 추정이다.
4. **2인 교육 프로젝트:** 소수 발급사·소수 혜택으로 범위를 한정하고 다운로드, 텍스트/페이지 추출, 후보 JSON과 검수 목록까지 자동화하는 수준이 현실적이다. 전수 자동 정확 추출이나 상시 최신성은 검증하지 못했다.
5. **가장 큰 기술적 위험:** 숫자 추출 자체보다 혜택별 조건·예외·공유 한도의 적용 범위를 잘못 연결하면서 그럴듯한 결과를 생성하는 것이다. 원문 페이지뿐 아니라 조항·범위까지 검수해야 한다.

재현: 저장소 루트에서 `.venv\Scripts\python.exe tmp/card_pdf_validation/codex/validate_pdfs.py`. 최초 실행에서 파일명을 `inspect.py`로 지정하여 표준 라이브러리와 충돌했으며, 이름 변경 후 위 명령으로 성공했다. 탐지 결과는 `inspection.json`; 해당 파일은 표 후보일 뿐 정답 데이터가 아니다. 네트워크 샌드박스에서 첫 다운로드는 연결 실패했으며 승인된 네트워크 접근으로 재시도해 성공했다.
