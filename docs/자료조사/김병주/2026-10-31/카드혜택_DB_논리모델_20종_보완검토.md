# 카드 20종 기반 PostgreSQL 논리 모델 보완 검토

작성 기준: 2026-10-31. **분석·제안 전용**이며 DB INSERT/UPDATE/DELETE/DDL, 기존 파일 수정, LLM API 호출, 커밋·푸시를 수행하지 않았다. PDF에서 확인한 사실, 현재 PostgreSQL 카탈로그 사실, 아직 구현하지 않은 논리 모델을 구분한다. 표의 `C01`~`D10`은 이 보고서의 **조사 식별자**이며 실제 `card_id`가 아니다.

## 1. 환경·증거·판정 방법

원천은 `src/card_benefit/data/raw/hana_all/credit|debit`의 실제 상품설명서 20개다. 같은 상품의 웹페이지 변환 PDF는 별도 상품으로 세지 않았다. 페이지는 PDF의 1부터 시작하는 쪽수다. 파일명의 끝 날짜는 **파일 식별용 표기**이고, 발급 가능 여부나 현재 유효한 약관의 확증이 아니다. `URL추정확인`은 로컬 파일·내용은 확인했지만 원본 URL은 이번 작업에서 재검증하지 않았음을 뜻한다. 다단 PDF는 텍스트 순서가 섞일 수 있어 표 제목·행·각주를 함께 대조했다. 이전 8종의 상세 근거는 [기존 검토 보고서](카드혜택_DB_모델링_컬럼행_설계검토.md)에 있으며, 이번 보고서는 추가 12종과 중요한 정정에 집중한다.

`.env`의 `DB_URL`을 프로세스 내에서만 사용해 Supabase PostgreSQL에 접속했다. `SET TRANSACTION READ ONLY` 및 `transaction_read_only=on`, 서버 17.11을 확인했다. 비밀값은 출력·보고서 기록하지 않았다. 현재 `db_pipeline`은 **11개 테이블, 187개 컬럼, 64개 제약, 40개 인덱스**다. 최신으로 확인된 백업은 `src/data/backup/dump-postgres-202610311136.sql`(파일 헤더 시작 2026-10-31 11:36:11)이다. 이전 보고서에서 현재 DB와 이 백업의 테이블·컬럼·타입·제약·인덱스·COMMENT 대상 대조가 완료됐다. 이번 재조회에서 구조적 수치와 11개 테이블 존재를 재확인했다. `card_benefit` 스키마 및 `card_benefit.card_product`는 현재 접속 DB에서 `to_regnamespace`/`to_regclass`가 모두 NULL이었다. `src/card_benefit/sql/schema.sql`은 별도 정의 파일일 뿐 현재 테이블의 증거는 아니다. 두 관리 DDL(`db_pipeline_schema.sql`, `db_pipeline_schemaV2.sql`)은 여전히 10개 `CREATE TABLE`을 포함하므로 **현재 DB·최신 백업을 기준**으로 한다. 과거 10/11 문제는 해결된 이력이며 이번 작업의 미해결 이슈가 아니다.

| `card_excl_item_als` | 제외 개념의 원문 표기 별칭 | `(card_excl_item_id,card_excl_item_als_id)` PK; 별칭 UNIQUE |

현재 `db_pipeline`에 물리 FK는 없다. `card_cond`는 `SPEND_EXCL`과 `BNFT_EXCL`에 `card_excl_item_id`·원문 표기를 요구하는 CHECK가 있다. 두 조건은 같은 상품권 개념 ID를 공유할 수 있어도 **정책·적용 범위는 다른 행**이어야 한다. `card_bnft`는 `DISCOUNT/CASHBACK/POINT/FEE_WAIVER/SERVICE/INSTALLMENT/ETC` 유형을 CHECK한다. `card_cond`는 `SPEND_REQ/SPEND_EXCL/BNFT_EXCL/LIMIT/TIER/USAGE_REQ/GRACE/MERCHANT_RULE/ETC`를 CHECK한다. `cond_rule_json`에 계산식을 보존할 수 있으나 JSON을 넣었다는 사실만으로 관계·경계·단위가 SQL에서 검증되지는 않는다.

`card_cond.card_bnft_id`는 BENEFIT 범위 조건의 **기존 앵커**이고 `card_bnft_cond`는 N:M 적용 관계다. 두 컬럼이 공존하는 이유는 단일 혜택 조건과 공유 조건을 모두 다루려는 구조로 해석된다. 다만 현재 CHECK상 여러 혜택이 공유하는 조건은 CARD로 올리거나 한 혜택을 앵커로 둬야 하므로, 원문의 '카드 공통'과 '특정 여러 혜택 공유'가 구별되지 않을 수 있다. 최종 적용 관계는 `card_bnft_cond`에서 관리하고, `card_bnft_id`는 이행 기간의 앵커로 유지하며 링크 불일치를 SQL로 검출한다. 삭제 결정은 실제 적재·조회 코드 점검 후로 보류한다. `bnft_rate`와 `cond_rate`도 충돌하지 않게 **단일 고정률은 혜택, 구간/대상별 변동률은 규칙 행이 우선**이라는 해석 우선순위가 필요하다.

## 6. 식별·경계·관계의 최소 의미 규칙

1. **상품/문서/버전:** 상품은 여러 문서판을 갖는다. `card_doc.card_id`는 상품의 안정 ID, `card_doc_id`는 특정 원문판, `doc_sha256`은 파일 내용이다. C01/D01은 같은 K-패스 계열이지만 다른 상품 ID·정책이다. 현재 접속 DB에 상품 마스터가 없어 20종을 다른 문서판·브랜드 변형과 안전하게 구분할 수 없다. 별도 배포 위치의 권위 있는 상품 마스터가 확인되지 않는다면 최소 `card_product` 논리 엔티티(발급사·공식 상품명·신용/체크·상품 식별 코드·상태)가 필요하다. 기존 `schema.sql`은 출발점이나 실제 DB 테이블로 간주하지 않는다.
2. **혜택 경계:** 고객에게 독립적으로 설명·적용·한도/우선순위 판단되는 서비스는 별도 `card_bnft` 행. 같은 공과금 혜택의 세 대상, 동일 10%에 구간별 한도 변화는 혜택 하나+대상/구간 행. C06의 커피와 쇼핑은 대상·예외·영역 한도가 별개이므로 별도 혜택, 공유 통합 한도만 공동 연결. C04의 기본/특별, D03의 ONE PICK/교통/놀이공원은 별도 혜택. 같은 이름이 다른 문서판에 나와도 문서별 행이다. 현재 `(card_doc_id,bnft_nm)` UNIQUE 때문에 같은 인쇄 명칭의 두 세부 서비스가 독립 혜택인 경우 이름에 승인된 구분자를 넣거나 키 정책 조정을 검토한다.
3. **대상 경계:** `bnft_target_txt`는 원문 설명을 보존하고, 검색·대상별 적립률·예외가 필요한 경우 대상별 행을 추가한다. D05의 쇼핑 영역처럼 하위 가맹점별 예외는 대상 행에 조건을 연결해야 한다. 대상 자체가 가맹점인지 업종인지 결제 채널인지 `target_type_cd`로 분리한다.
4. **구간 경계:** 최소값 포함, 최대값 미포함 `[min,max)`으로 수치화한다. `40만원 미만`은 `[0,400000)`, `40만원 이상`은 `[400000,∞)`이다. PDF의 `이상/초과/미만/이하`를 원문 근거에 보존하고, 모호하면 정규화 승인 보류. C05에는 두 TIER의 `cond_rate=1,2`; C09에는 `cond_limit_cnt=10,20,30`; C03에는 계절 구분별 `cond_limit_amt`. `cond_rate`의 단위는 퍼센트 숫자(예: 2는 2%)로 계약한다. C10의 45 UniMile/1500원은 이 `cond_rate`로 환산하지 않는다.
5. **공유 한도:** `card_cond`의 하나의 LIMIT 행을 여러 혜택에 `card_bnft_cond`로 연결하면 공유 가능하다. C06/D05처럼 실적 구간마다 한도가 다른 경우 각 TIER/LIMIT 행을 같은 **한도 풀 식별자**로 묶고 소진 집계 범위·기간·단위를 명시해야 한다. `cond_policy_cand_key`는 그 식별자가 아니다. 동일 금액의 독립 한도들은 풀 식별자를 공유하지 않는다. C04 라운지의 연 3회와 월 10만 포인트는 단위도 풀이 다르다.
6. **AND/OR/NOT:** 기본 논리 연결만으로는 연산자를 알 수 없다. D02 자동이체 AND 건당 기준, D05 공식 홈페이지 OR 공식 앱, 매장 대상 AND 대형시설 입점 아님을 표현해야 한다. 단순한 1층 식은 검증된 `cond_rule_json`의 그룹 연산자·자식 조건 ID로 시작하고, 중첩/재사용이 늘면 그룹 엔티티를 도입한다. `card_bnft_cond`에 단순히 여러 행이 있다는 사실을 무조건 AND로 해석하지 않는다.
7. **혜택 간 순서:** C04/C07의 `HIGHER_VALUE_WINS`, `MUTUALLY_EXCLUSIVE`, `FALLBACK_AFTER_CAP`은 조건이 아니라 혜택 사이 정책이다. 방향·트리거·우선순위·원문 근거를 별도 논리 관계로 보존한다. 한 거래에 적용할 혜택이 둘 이상인지는 대상·조건 평가 후 이 관계로 판정한다.
8. **검증된 없음:** D03 ONE PICK, D08 기본 적립은 문구상 `VERIFIED_NONE`인 전월 실적 조건이다. 아직 추출하지 않은 혜택은 `PENDING_REVIEW`; 조건 행 부재를 `NONE`으로 추론하지 않는다. 원문 문장·쪽·검수자·시각이 확인된 뒤만 상태를 확정한다.

| **보류** | 별도 조건 그룹 테이블 | 단순 AND/OR/NOT은 검증된 `cond_rule_json`으로 가능. 중첩·공유 논리식·부분 수정이 늘면 정규화 | JSON 스키마/참조 검증으로 시작; 그래프 변환 시 그룹 노드 선택 가능 |
| **보류** | `card_cond.card_bnft_id` 삭제, EAV 전환, 기존 11개 테이블 폐기 | 실제 적재·조회 코드 영향 미조사. 현재 N:M과 중복되는 문제는 검증으로 통제 가능 | 마이그레이션 부담을 당장 지지 않음 |

**최소 변경안**은 기존 11개를 유지하면서 대상·대상조건·혜택관계 3개 논리 테이블, `card_cond` 공유/풀 식별, `card_bnft` 전달/검증 상태, 연속 월 코드, 상품 ID 공급을 추가하는 것이다. **확장안**은 적재 중 깊은 조건식이나 복잡한 한도 버전이 실제로 누적되면 조건 그룹·한도 풀을 독립 엔티티로 승격한다. 제안은 DDL이 아니며 컬럼 타입/길이·제약의 최종안은 적재 시험 후 확정한다.

## 9. 관계형 샘플 행: PDF 값과 임의 키를 분리

다음 `DOC-C05`, `B-C05-WIDE`, `K-C05-LOW` 등은 **설명용 임의 논리 키**다. 실제 DB ID·삽입값이 아니다. `p1`/`p4`는 2절 PDF의 원문 쪽을 뜻한다. 표에 생략된 `card_extr_stg_id`, 근거 오프셋, 감사 컬럼 등은 실제 적재 시 승인 후보로부터 채워야 한다. 한 원문 문구가 여러 조건 행을 낳으면 후보→확정 1:1 UNIQUE 제약과 충돌할 수 있으므로 실제 적재 전 후보 분할·키 전략을 검증한다.

## 10. 조회·정합성 SQL 예시 (모두 SELECT, 실행/적재 없음)

아래 SQL은 **논리 모델 검증 예시**다. `card_bnft_target`, `card_bnft_target_cond`, `card_bnft_rel`, `limit_pool_key` 등은 현재 DB에 존재하지 않으므로 해당 쿼리는 보완 후의 설계 참고용이다. 실제 스키마에 실행했다고 주장하지 않는다.

```sql
-- 현재 스키마에서 실행 가능한 혜택↔조건/앵커 불일치 조회
SELECT bc.card_doc_id, bc.card_bnft_id, bc.card_cond_id,
       CASE WHEN b.card_bnft_id IS NULL THEN 'BENEFIT_MISSING'
            WHEN c.card_cond_id IS NULL THEN 'CONDITION_MISSING'
            WHEN b.card_id <> c.card_id THEN 'CARD_MISMATCH'
            WHEN c.card_bnft_id IS NOT NULL
             AND c.card_bnft_id <> bc.card_bnft_id THEN 'ANCHOR_MISMATCH'
       END AS issue
FROM db_pipeline.card_bnft_cond bc
LEFT JOIN db_pipeline.card_bnft b
  ON (b.card_doc_id,b.card_bnft_id)=(bc.card_doc_id,bc.card_bnft_id)
LEFT JOIN db_pipeline.card_cond c
  ON (c.card_doc_id,c.card_cond_id)=(bc.card_doc_id,bc.card_cond_id)
WHERE b.card_bnft_id IS NULL OR c.card_cond_id IS NULL
   OR b.card_id <> c.card_id
   OR (c.card_bnft_id IS NOT NULL AND c.card_bnft_id <> bc.card_bnft_id);
```

```sql
-- 보완 후: 한 문서의 실효 혜택 조건과 대상별 조건 조회
SELECT b.card_doc_id, b.card_bnft_id, b.bnft_nm, b.delivery_cd,
       c.card_cond_id, c.cond_type_cd, c.cond_min_amt, c.cond_max_amt,
       c.cond_rate, c.cond_limit_amt, c.cond_limit_cnt,
       t.target_id, t.target_nm, tc.card_cond_id AS target_cond_id
FROM db_pipeline.card_bnft b
LEFT JOIN db_pipeline.card_bnft_cond bc
  ON (bc.card_doc_id,bc.card_bnft_id)=(b.card_doc_id,b.card_bnft_id)
LEFT JOIN db_pipeline.card_cond c
  ON (c.card_doc_id,c.card_cond_id)=(bc.card_doc_id,bc.card_cond_id)
LEFT JOIN db_pipeline.card_bnft_target t
  ON (t.card_doc_id,t.card_bnft_id)=(b.card_doc_id,b.card_bnft_id)
LEFT JOIN db_pipeline.card_bnft_target_cond tc
  ON (tc.card_doc_id,tc.target_id)=(t.card_doc_id,t.target_id)
WHERE b.card_doc_id = :doc_id AND b.bnft_status='CONFIRMED';
```

```sql
-- 보완 후: C05형 [min,max) 구간 겹침 후보. 적용 월/채널도 같은 경우만 오류 확정.
SELECT a.card_doc_id, a.card_bnft_id, a.card_cond_id AS a_id,
       z.card_cond_id AS z_id
FROM db_pipeline.card_cond a
JOIN db_pipeline.card_cond z
  ON (z.card_doc_id,z.card_bnft_id)=(a.card_doc_id,a.card_bnft_id)
 AND z.card_cond_id>a.card_cond_id
WHERE a.cond_type_cd='TIER' AND z.cond_type_cd='TIER'
  AND a.cond_min_amt < COALESCE(z.cond_max_amt,1e30)
  AND z.cond_min_amt < COALESCE(a.cond_max_amt,1e30)
  AND COALESCE(a.cond_rule_json->>'month_set','ALL')
      = COALESCE(z.cond_rule_json->>'month_set','ALL');
```

추가 게이트: `[min,max)`의 경계 누락/겹침, C03 계절 월 집합의 상호 배타·전체 커버리지, `limit_pool_key`별 동일 단위/기간·혜택 구성원, `SPEND_EXCL`/`BNFT_EXCL` 용도 혼동, 혜택·대상·조건의 문서/상품 ID 동일성, `card_bnft_rel` 순환·자기 참조·상충하는 우선순위, `spend_review_cd=VERIFIED_NONE`인데 SPEND_REQ 링크가 있는 행, 후보의 페이지·청크 오프셋과 확정 근거 불일치를 SELECT로 검사한다. 물리 FK 없이도 승인 전 차단·적재 후 감사가 가능하지만 검사 누락 위험은 운영 절차가 담당해야 한다.

## 11. Neo4j 변환과 SQL 역할

| PostgreSQL 확정 키/행 | Neo4j 노드·관계 | 의미 보존 규칙 |
|---|---|---|
| 상품 ID, `card_doc` | `(:Card)-[:HAS_DOCUMENT]->(:Document)` | `doc_sha256`·버전·출처로 동일 상품의 판 구분 |
| `card_bnft` | `(:Card)-[:OFFERS]->(:Benefit)` | 혜택은 문서판별 ID, 유형·전달 방식 분리 |
| `card_bnft_target` | `(:Benefit)-[:APPLIES_TO]->(:Target)` | 대상별 비율·금액을 관계/대상 속성에 보존 |
| `card_bnft_cond`, `card_bnft_target_cond` | `(:Benefit|:Target)-[:REQUIRES|EXCLUDES]->(:Condition)` | SPEND_EXCL은 실적 계산 경로, BNFT_EXCL은 혜택 적용 경로로 분기 |
| 공유 `card_cond`+`limit_pool_key` | 여러 `Benefit`→`LimitPool` | 같은 금액이라는 이유만으로 풀 병합하지 않음; 구간·기간·단위 포함 |
| `card_bnft_rel` | `(:Benefit)-[:OVERRIDES|FALLS_BACK_TO|MUTUALLY_EXCLUSIVE_WITH]->(:Benefit)` | 방향·트리거·우선순위·원문 쪽 유지 |
| 원문 청크/후보/확정 근거 | `Benefit/Condition/Relation-[:SUPPORTED_BY]->DocumentChunk` | 승인된 근거만 그래프에 반영, 미검증을 `없음`으로 확정하지 않음 |

단일 카드의 40만 원 경계 할인율·월 한도·고아 관계 검사는 **SQL이 더 단순하고 확정적**이다. C04/C07의 한도 후 대체, C08의 일반↔우대, D05의 여러 영역↔공유 한도↔대상별 제외를 **여러 상품에 걸쳐 영향 탐색**할 때 Neo4j 경로 탐색이 유용하다. 같은 질문을 SQL 조인으로도 풀 수 있으며 그래프가 자동으로 더 정확해지는 것은 아니다. 원문 범위·우선순위·문서판을 PostgreSQL에서 먼저 검증해야 그래프 엣지도 정확하다.

## 12. 결론과 실제 적재 시 게이트

1. **현재 11개 그대로는 부족하다.** C05 구간률은 기존 TIER로 표현 가능하지만 C04/C07의 혜택 간 관계, D05의 대상별 제외, D03의 현장할인/무실적 검증 상태는 정형 의미가 부족하다.
2. **필수 보완:** 상품 안정 ID 공급, `card_bnft_target`, 대상–조건 연결, 혜택–혜택 관계, 공유 한도 풀 식별·SHARED 범위, 전달 방식·검증된 무실적 상태, 연속 3개월 규칙 코드/검증. 기존 `card_bnft_cond`는 유지한다.
3. **권장:** 정규식·수작업 후보 출처, 계산식·단위·반올림 규약, 혜택 이름/앵커 정합성 게이트.
4. **보류:** 독립 한도 풀·조건 그룹 테이블, `card_cond.card_bnft_id` 삭제, EAV 전환. 실제 20종 적재·질의 실패 사례가 생기면 재판정한다.
5. **적재 전 확인:** 6개 `URL추정확인`의 원본 URL·해시·현행성, 각 PDF의 전체 각주와 표, 문서판·상품 마스터 매핑, 후보→근거 오프셋→승인→확정의 추적, 타입/단위/구간/풀 구성원/혜택 우선순위의 SQL 검증. 미검증 문서는 Neo4j에 확정 규칙으로 보내지 않는다.

이 문서는 변경 제안만 포함한다. 실제 DDL 보완과 데이터 적재는 별도 사용자 검토 후 수행한다.
