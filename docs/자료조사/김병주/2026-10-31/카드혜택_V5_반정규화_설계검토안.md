# 카드 혜택 V5 — 반정규화 설계 검토안

**상태:** 사용자 검토용 초안. 현재 개발 DB의 V4는 변경하지 않았다. V5 DDL·DBML은 별도 파일이다.

**산출물:**

- DDL: [`db_pipeline_schemaV5_draft.sql`](../../../../src/card_benefit/sql/db_pipeline_schemaV5_draft.sql)
- ERD: [`db_pipeline_schemaV5_draft.dbml`](../../../../src/card_benefit/sql/db_pipeline_schemaV5_draft.dbml)

## 0. 결론

| 항목 | V4 | V5 제안 |
|---|---:|---:|
| 테이블 | 49 | **25** |
| 컬럼 | 416 | 285 |
| 시퀀스 | 25 | 16 |
| 물리 FK | 0 | 0 |
| 논리 관계선 | 72 | 38 |
| 조회 뷰 | 0 | 6 |

판정 결과는 유지 24개, 통합 24개, 제거 1개, 보류 0개다. 신규 테이블은 근거 연결용 `card_policy_evidence` 1개다.

**핵심 구조:** `card_product → card_policy_version → card_bnft → card_bnft_rule`의 PK 상속은 그대로 유지한다. 부모에 종속된 세부값(조건식, 대상, 한도 구간, 브랜드 선택지)은 부모 행의 JSONB로 옮긴다. 저장은 JSONB로 간결하게 하고, 검증은 CHECK 함수로, 조회는 뷰로 V4와 같은 행 구조를 제공한다.

```text
card_product (card_id)
  │  brand_opt_list          ← 브랜드 선택지
  └─ card_policy_version (card_id, policy_ver_id)
       │  policy_cond_expr   ← 카드 전체 조건
       ├─ card_bnft (card_id, policy_ver_id, card_bnft_id)
       │    │  bnft_cond_expr, bnft_brand_opt_cds
       │    ├─ card_bnft_rule (…, card_bnft_id, rule_id)
       │    │    cond_expr, target_list
       │    └─ card_bnft_common ─── card_common_policy_version
       ├─ card_limit_pool (card_id, policy_ver_id, pool_id)
       │    tier_list ── card_bnft_rule_pool ── card_bnft_rule
       └─ card_policy_evidence ── card_source_evidence ── card_doc_chunk

card_common_bnft (common_bnft_id)
  └─ card_common_policy_version (common_bnft_id, common_ver_id)
       └─ card_common_bnft_rule (…, common_rule_id)
            cond_expr, target_list, limit_list
```

**검증:** PostgreSQL 17.4 메모리 DB에서 전체 DDL과 조회 SQL을 실행했다. 잘못된 입력 15건은 거부됐고, 고아 데이터 12건은 게이트가 검출했다. 개발 Supabase에서는 실행하지 않았다(13절).

## 1. 2차 ERD와 실제 PDF에서 확인한 사실

**2차 ERD 표시 (V4 DDL과 대조):**

| 표시 | 대상 | 해석 |
|---|---|---|
| `(삭제예정대상)` | `card_product_variant`, `card_product_variant_doc` | 삭제 의도 명확 |
| `(통합 삭제 검토)` | `card_bnft_cond` | 통합 방향 |
| 머리글 노란색 | `card_cond` | 표시 의미가 불명확하다. 유지 의도일 수도 있어 쟁점 1로 올렸다 |

ERD의 PK·컬럼은 V4 DDL과 일치한다. 다만 `card_bnft_rule.expr_id → card_cond_expr`, `card_cond_expr_atom.card_cond_id → card_cond` 관계선은 이미지에 없다. 일부 영역 ERD이므로 이 차이를 오류로 보지 않고 V4 DDL을 기준으로 삼았다.

**발급형의 실제 필요성:**

| 확인 내용 | 근거 | 설계 영향 |
|---|---|---|
| 브랜드 선택 문구가 있는 공식 상품설명서는 123개 중 28개 | 텍스트 패턴 집계 | 브랜드 선택지는 흔하다 |
| 그중 브랜드별 서비스 유형이 갈리는 상품은 4개 | CLUB Primus Skypass, CLUB Signature SKYPASS, CLUB SK, JADE Classic | 혜택까지 달라지는 경우는 소수다 |
| JADE Classic은 브랜드별 유형이 모두 다름 | 5쪽: Visa Signature 02, Mastercard World 03, Amex Platinum 03, UPI Diamond 02 | 브랜드별 적용 사실은 **반드시 보존** |
| 국내전용 선택도 혜택을 가름 | JADE 3쪽 라운지: 국내전용카드 보유 회원 제외 | 국내전용도 선택지로 저장 |
| 상품 고유 혜택도 브랜드에 종속될 수 있음 | CLUB Signature SKYPASS: LoungeKey는 VISA | `COMMON_LINK`만으로는 부족, `LOCAL`에도 브랜드 범위 필요 |
| 같은 공통 정책에 상품별 조건이 붙음 | MP001 2쪽: CLUB SK 30만, 하나골드클럽멤버스Ⅱ 50만 | 상품별 조건은 `card_bnft`에 저장 |

**결론:** 브랜드 선택지는 업무 사실이지만, 독립 생명주기나 자식 데이터가 없다. V4처럼 4개 테이블로 분리할 실익은 없다. 선택지 목록은 상품으로, 적용 범위는 혜택과 문서 관계로 옮긴다.

**공통 혜택 PDF:**

| 확인 내용 | 근거 | 설계 영향 |
|---|---|---|
| `통합 월 N회`는 대부분 한 서비스의 대상 목록에 걸림 | AP003, MP001, VP001 등 2쪽: 호텔 통합, 공항 통합 | 대상을 한 규칙에 모으면 공유 관계가 규칙 안에서 끝난다 |
| 기간별 이중 한도가 있음 | VI001 `호텔 통합 월 8회/연 60회`, AP003 1쪽 `월 1회, 연 2회` | `limit_list` 배열 사용 |
| 개정판 사이 수치가 실제로 다름 | VP001 Booking.com: 2023판 10% 캐시백, 2026판 최대 7% 월렛포인트 | 공통 정책판 테이블 유지 |
| MP001·MP004는 정규화 후 텍스트 행의 약 60%가 같고 2쪽 대상이 다름 | 224행·217행 중 136행 동일 | PDF 공유나 등급 일치만으로 병합하지 않는다 |

**기존 V4 검토안 샘플과 PDF가 다른 부분 (V5 시험 데이터는 PDF 기준):**

- 달달 체크카드는 7개 영역이다. 간편결제 0.3%는 영역 한도가 없고, 구독은 10%다.
- JADE의 한도 소진 후 기본 적립은 특별 적립뿐 아니라 디지털컨텐츠·커피·택시까지 4종 모두에 적용된다(4쪽).

## 4. 영역별 결정 이유

**A. 상품 발급형 → 통합.** 1절 근거에 따라 4개 테이블을 없앴다. 카드 실물 단위 판정은 `brand_opt_cd`로 계속 가능하다. 시험 결과 JADE의 규칙 수는 AMEX 9개, VISA·Mastercard·UPI 8개, 국내전용 7개로 갈렸다.

**B. 혜택 조건 → JSONB 통합.** 적용 범위가 저장 위치로 드러나므로 모호해지지 않는다.

| 범위 | 위치 | 결합 |
|---|---|---|
| 카드 전체 | `card_policy_version.policy_cond_expr` | 실적 산정·실적 제외·유예 |
| 혜택 전체 | `card_bnft.bnft_cond_expr` | AND |
| 규칙별 | `card_bnft_rule.cond_expr` | AND |
| 공통 규칙 | `card_common_bnft_rule.cond_expr` | 상품의 혜택 조건과 AND |
| 한도 구간 | `tier_list[].cond_expr` | 구간 선택 |

JSONB가 원칙 7을 해치지 않도록 전월 실적 구간은 `spend_min_amt`, `spend_max_amt_excl` 생성 컬럼으로 노출했다. 값은 `cond_expr`에서만 파생되므로 원천은 한 곳이다. 단일 branch가 아니면 NULL이 되고, 그때는 `v_card_cond_atom`으로 조회한다.

**C. 혜택 대상 → JSONB 통합.** 대상에는 V4에서도 수치가 없고, 근거 연결도 없었다. 규칙에 내장해도 잃는 관계가 없다. 대상별 비율이 다르면 규칙을 나누는 V4 원칙은 유지한다. 대상 검색은 GIN 인덱스와 `target_list @> ...`로 처리한다.

**D. 공통 혜택 → 11개에서 4개로 축소.** 유지하는 것은 정체성, 정책판, 규칙, 적용 관계다. 8절에 적용 방식을 정리했다.

**E. 공유 한도 → 풀 유지, 구간만 통합.** 상품 측 한도는 사용자 원칙대로 독립 엔티티를 유지한다. 달달의 쇼핑 규칙은 `P-SHOP`과 `P-ALL`을 동시에 소비하고, JADE 특별 적립 3개 규칙은 `P-SPECIAL` 하나를 공유한다. 이 실제 N:M 때문에 `card_bnft_rule_pool`도 유지한다. `card_limit_tier`만 풀의 `tier_list`로 옮겼다. 구간에는 독립 식별이 필요 없고, 풀 하나당 1~3개이며, 풀을 통해서만 조회되기 때문이다.

**F. 원문 근거 → 연결 7개를 2개로.** 단순 다형 참조 대신, 대상 유형별로 타입 컬럼을 두고 CHECK로 조합을 고정했다. 이렇게 하면 유형별로 논리 FK 검사가 가능하다. `ev_subject_cd=RULE`이면 `card_bnft_id`, `rule_id`만 값이 있어야 한다. JSONB 항목의 근거는 `ev_item_cd`, `ev_item_key`로 연결하고, 키 존재 여부를 게이트가 검사한다. 공통 측은 부모 키가 달라 별도 테이블로 뒀다. V4 `card_common_rule_evidence`에 컬럼 2개를 더한 형태다.

**G. 원천·AI 파싱 → 변경 없음.** 확정 업무 데이터와 분리하는 원칙을 유지했다.

## 7. JSONB 계약과 중복 허용 범위

모든 JSONB 컬럼은 `fn_valid_*` 함수를 CHECK로 사용한다.

| 컬럼 | 위치 | 검증 함수 | 핵심 규칙 |
|---|---|---|---|
| `policy_cond_expr`, `bnft_cond_expr`, `cond_expr` | 정책, 혜택, 규칙, 공통 규칙 | `fn_valid_cond_expr` | branch는 OR, atom은 AND, `negate_yn`은 NOT. 키 중복·구간 역전·금액 문자열 거부 |
| `target_list` | 규칙, 공통 규칙 | `fn_valid_target_list` | 유형·키·이름 필수, `(유형, 키)` 중복 금지. `CONFIRMED` 규칙은 1개 이상 |
| `tier_list` | `card_limit_pool` | `fn_valid_tier_list` | `limit_num` 0 이상의 숫자, `CONDITIONAL`이면 `cond_expr` 필수 |
| `limit_list` | `card_common_bnft_rule` | `fn_valid_limit_list` | 기간·단위·집계 기준 필수. 같은 `pool_key`는 공유 한도 |
| `brand_opt_list` | `card_product` | `fn_valid_brand_opt_list` | 코드 중복 금지, 상태 코드 제한 |

**예시 1. Wide 규칙의 조건 (`cond_expr`)**

```json
{"expr_status_cd": "CONFIRMED",
 "branches": [{"branch_no": 1, "atoms": [
   {"atom_key": "SPEND_HIGH", "atom_seq": 1, "negate_yn": false,
    "cond_type_cd": "SPEND_REQ", "cond_basis_cd": "PREV_MONTH_SPEND",
    "cond_min_amt": 400000, "cond_max_amt_excl": null,
    "cond_status_cd": "CONFIRMED"}]}]}
```

이 행의 `spend_min_amt`는 자동으로 400000이 된다.

**예시 2. JADE 항공·면세 규칙의 OR + NOT (요약)**

```json
{"expr_status_cd": "CONFIRMED",
 "branches": [
   {"branch_no": 1, "atoms": [
     {"atom_key": "CH_OFFICIAL", "atom_seq": 1, "negate_yn": false,
      "cond_type_cd": "PAYMENT_METHOD", "cond_raw_txt": "공식 홈페이지(온라인/모바일앱)",
```

두 번째 branch의 `atoms` 배열은 지면상 줄인 표기다. 실제 값은 첫 번째 branch와 같은 객체 구조여야 한다.

```json
  "aggregation_key_cd": "CARD_MEMBER",
  "predicate_state_cd": "VERIFIED_UNCONDITIONAL", "limit_num": 2}]
```

**중복 허용 범위:**

| 허용 | 금지 |
|---|---|
| 같은 실적 조건을 여러 혜택의 `bnft_cond_expr`에 반복 (JADE 50만) | 계산값(`value_num`)을 혜택·조건·대상에 복제 |
| 서비스 제외 목록을 혜택마다 반복 | 공통 규칙값을 상품 규칙으로 복사 |
| 같은 대상을 여러 규칙의 `target_list`에 반복 (Wide 1%, 2%) | 공유 한도를 규칙별 한도로 복제 |
| 같은 원문 문장을 여러 근거 연결에서 참조 | `spend_min_amt`를 `cond_expr`과 별도로 입력 (생성 컬럼이라 불가) |
| 같은 금액의 영역 한도를 풀마다 저장 (달달 영역 6개) | 금액이 같다는 이유로 풀을 병합 |

## 8. 공통 혜택 적용 방식

```text
card_bnft (상품별 인스턴스, COMMON_LINK)
  ├ bnft_brand_opt_cds = 어떤 브랜드 선택지에 적용되는가
  ├ bnft_cond_expr     = 이 상품에만 붙는 조건 (AND)
  └ card_bnft_common ── card_common_policy_version ── card_common_bnft_rule
                                                      (값·대상·공통 조건·한도)
```

- 공통 규칙값은 한 곳에만 있다. 상품에는 복제하지 않는다.
- 상품별 차이는 `card_bnft`가 받는다. MP001의 30만·50만이 시험에서 같은 공통 정책판 아래 그대로 분리됐다.
- 공통 정책 개정은 새 `common_ver_id`와 새 링크로 표현한다. 상품 혜택을 다시 만들지 않아도 된다.
- 승인된 링크 중 기간이 겹치는 것은 게이트가 거부한다. V4의 "승인 링크 1개 제한"은 공통 정책이 연 단위로 갱신되면 맞지 않아, 기간 겹침 검사로 바꿨다.
- 공통 PDF를 참조한다는 사실만으로 공통 정책으로 묶지 않는다. 판단 기준은 쟁점 5다.

**검토 후 채택하지 않은 안:** 브랜드 서비스를 가상의 `card_product` 행으로 저장하면 `card_bnft_rule` 하나로 모든 규칙을 합칠 수 있다. 테이블은 더 줄지만 상품 마스터에 상품이 아닌 행이 섞이고, 모든 상품 조회에 필터가 필요하다. 공통 혜택의 독립 식별 요구와도 맞지 않는다.

## 9. 실제 카드별 표현 비교

수치는 PDF 원문 확인값이다. 키와 정책 시작일은 시험용 가상값이다.

## 10. Neo4j GraphRAG 영향

Neo4j 적재기는 아직 구현 전이다. 아래는 설계 대응표다. JSONB 때문에 노드가 줄어들지는 않는다. 뷰가 V4와 같은 행을 제공하기 때문이다.

| 그래프 요소 | V5 원천 | 키 |
|---|---|---|
| `(:Card)` | `card_product` | `card_id` |
| `(:BrandOption)` | `v_card_brand_opt` | `card_id + brand_opt_cd` |
| `(:Policy)` | `card_policy_version` | `card_id + policy_ver_id` |
| `(:Benefit)` | `card_bnft` | PK |
| `(:Rule)` | `v_card_bnft_rule_effective` | PK 또는 공통 규칙 PK |
| `(:Condition)` | `v_card_cond_atom` | 소유 PK + `atom_key` |
| `(:Target)` | `v_card_rule_target` | `target_type_cd + target_key` |
| `(:LimitPool)` | `card_limit_pool`, `v_card_common_limit` | PK 또는 `pool_key` |
| `(:CommonBenefit)` | `card_common_bnft` + 정책판 | PK |
| `(:Evidence)` | `card_source_evidence` | `evidence_id` |
| `[:APPLIES_TO_BRAND]` | `bnft_brand_opt_cds` | 혜택 → 선택지 |
| `[:USES_COMMON]` | `card_bnft_common` | 혜택 → 공통 |
| `[:CONSUMES]` | `card_bnft_rule_pool` | 규칙 → 풀 |
| `[:EXCLUSIVE_WITH]`, `[:FALLS_BACK_TO]` | `card_bnft_rel` | 혜택 → 혜택 |
| `[:SUPPORTED_BY]` | `card_policy_evidence` | 대상 → 근거 |

**바뀌는 점:**

- `Condition` 노드 ID는 조건 행 ID가 아니라 소유자 + `atom_key`다. 같은 50만 조건이 혜택마다 별도 노드가 된다. 실적 조건 공유 경로가 필요하면 `(cond_type_cd, cond_basis_cd, 구간)`으로 노드를 합치는 규칙을 적재기에 둔다.
- `Target`은 자연키로 합쳐지므로 그래프에서는 V4보다 오히려 공유가 쉽다.
- AND/OR 구조를 그래프에서 탐색하려면 branch를 중간 노드로 만들 수 있다. `branch_no`가 보존되어 있어 가능하다.

| # | 쟁점 | 제안 | 대안 | 판단 기준 |
|---:|---|---|---|---|
| 1 | `card_cond` | JSONB 통합 | 혜택에 종속된 단일 조건 테이블 1개 유지 (행 단위 관리, 테이블 +1) | 2차 ERD의 노란 표시가 유지 의도인지, 조건을 SQL 행으로 직접 관리하고 싶은지 |
| 2 | 브랜드 선택지 | `brand_opt_list` JSONB | `card_product_brand` 단일 테이블 (PK 보장, 테이블 +1) | 브랜드 코드를 PK로 검증해야 하는지 |
| 3 | 공통 규칙 저장 | 별도 `card_common_bnft_rule` | 브랜드 서비스를 가상 상품으로 저장 (8절) | 상품 마스터 순수성과 테이블 수 중 우선순위 |
| 4 | 공통 한도 | `limit_list` + `pool_key` | `card_common_limit_pool` 유지 (테이블 +1~2) | 현재 PDF의 통합 한도는 한 규칙 안에서 끝난다. 규칙을 넘는 공유가 늘면 대안 채택 |
| 5 | 공통 승인 기준 | **대상 상품 2개 이상이 같은 조항을 공유**할 때 공통 | 브랜드 문서 출처면 모두 공통 | AP003 2쪽 Amex Platinum 03의 대상은 JADE Classic 1개다. 제안 기준이면 `LOCAL` + `BRAND`이고, V5는 양쪽 모두 표현한다. 시험은 공통 경로 검증을 위해 `COMMON_LINK`로 넣었다 |
| 6 | 제외 목록 위치 | 실적 제외는 정책, 서비스 제외는 혜택별 반복 | 정책 단위 묶음 코드 도입 | 서비스 제외 목록이 카드 안에서 얼마나 다른지 |
| 7 | 추가 정책판 제거 | 상품 정책판 단일화 | `policy_scope_cd` 유지 | 브랜드만 개정되는 고유 혜택이 실제로 있는지 |
| 8 | 근거 연결 PK | `ev_link_id` + 자연키 UNIQUE | 대상별 연결 테이블 3~4개 유지 | 상속 PK 원칙을 근거 연결에도 엄격히 적용할지 |
| 9 | V5 적용 방식 | 확정 후 V4 스키마를 교체 | 별도 스키마 병행 | 초안은 빈 `db_pipeline` 전제다. 현재 스키마에 그대로 실행하면 `CREATE SCHEMA`에서 실패한다 |
| 10 | 감사 컬럼 | V4와 동일 (업무 테이블 일부 없음) | 업무 테이블 전체에 추가 | 승인 이력 추적 수준 |

## 12. 검증 SQL

아래 SQL은 시험 DB에서 그대로 실행한 원본이다. 리터럴 값과 ID는 시험 데이터 기준이므로 운영에서는 바인딩 값으로 바꾼다.

```sql
-- @Q1 상품 → 정책 → 혜택 → 계산 규칙 (JADE, AMEX 선택지, 2026-11-01)
WITH cur AS (
  SELECT v.card_id, v.policy_ver_id
  FROM db_pipeline.card_policy_version v
  WHERE v.card_id = 1 AND v.policy_status_cd = 'APPROVED'
    AND DATE '2026-11-01' >= v.valid_from
    AND (v.valid_to_excl IS NULL OR DATE '2026-11-01' < v.valid_to_excl)
)
SELECT e.bnft_nm, e.rule_source_cd, e.rule_key, e.calc_method_cd, e.value_num, e.value_unit_cd, e.payout_unit_cd
FROM cur
JOIN db_pipeline.v_card_bnft_rule_effective e USING (card_id, policy_ver_id)
WHERE e.rule_status_cd = 'CONFIRMED'
  AND (e.bnft_scope_cd = 'PRODUCT' OR 'AMEX_PLATINUM_03' = ANY (e.bnft_brand_opt_cds))
  AND (e.common_valid_from IS NULL
       OR (DATE '2026-11-01' >= e.common_valid_from
           AND (e.common_valid_to_excl IS NULL OR DATE '2026-11-01' < e.common_valid_to_excl)))
ORDER BY e.card_bnft_id, e.rule_key;

-- @Q1b 같은 조회의 브랜드별 혜택 수 (브랜드 선택지 차이)
SELECT o.brand_opt_cd, count(*) AS rule_cnt,
       count(*) FILTER (WHERE e.rule_source_cd = 'COMMON') AS common_rule_cnt
FROM db_pipeline.v_card_brand_opt o
JOIN db_pipeline.v_card_bnft_rule_effective e ON e.card_id = o.card_id
WHERE o.card_id = 1 AND (e.bnft_scope_cd = 'PRODUCT' OR o.brand_opt_cd = ANY (e.bnft_brand_opt_cds))
GROUP BY o.brand_opt_cd ORDER BY o.brand_opt_cd;

-- @Q2 전월 실적 구간별 규칙 (Wide, 399,999원과 400,000원)
SELECT s.prev_spend, r.rule_id, r.value_num AS percent, r.spend_min_amt, r.spend_max_amt_excl, t.limit_num AS monthly_cap
FROM (VALUES (399999), (400000)) AS s(prev_spend)
JOIN db_pipeline.card_bnft_rule r
  ON r.card_id = 2 AND s.prev_spend >= r.spend_min_amt
 AND (r.spend_max_amt_excl IS NULL OR s.prev_spend < r.spend_max_amt_excl)
JOIN db_pipeline.card_bnft_rule_pool rp
  ON (rp.card_id, rp.policy_ver_id, rp.card_bnft_id, rp.rule_id) = (r.card_id, r.policy_ver_id, r.card_bnft_id, r.rule_id)
JOIN db_pipeline.v_card_limit_tier t
  ON (t.card_id, t.policy_ver_id, t.pool_id) = (rp.card_id, rp.policy_ver_id, rp.pool_id)
ORDER BY s.prev_spend;

-- @Q3 공유 한도: 하나의 풀을 소비하는 규칙 (JADE 특별 적립)
SELECT p.pool_id, p.period_cd, p.cap_unit_cd, t.limit_num, string_agg(rp.rule_id, ', ' ORDER BY rp.rule_id) AS rules
FROM db_pipeline.card_limit_pool p
JOIN db_pipeline.v_card_limit_tier t ON (t.card_id, t.policy_ver_id, t.pool_id) = (p.card_id, p.policy_ver_id, p.pool_id)
JOIN db_pipeline.card_bnft_rule_pool rp ON (rp.card_id, rp.policy_ver_id, rp.pool_id) = (p.card_id, p.policy_ver_id, p.pool_id)
WHERE p.card_id = 1 AND p.pool_id = 'P-SPECIAL'
GROUP BY 1, 2, 3, 4;

-- @Q3b 영역 풀과 통합 풀 동시 소비 (달달, 쇼핑 백화점 규칙, 전월 실적 500,000원과 1,000,000원)
SELECT s.prev_spend, t.pool_id, t.pool_scope_cd, t.limit_num
FROM (VALUES (500000), (1000000)) AS s(prev_spend)
JOIN db_pipeline.card_bnft_rule_pool rp ON rp.card_id = 3 AND rp.rule_id = 'R-SHOP-DEPT'
JOIN db_pipeline.v_card_limit_tier t ON (t.card_id, t.policy_ver_id, t.pool_id) = (rp.card_id, rp.policy_ver_id, rp.pool_id)
WHERE s.prev_spend >= t.spend_min_amt AND (t.spend_max_amt_excl IS NULL OR s.prev_spend < t.spend_max_amt_excl)
ORDER BY s.prev_spend, t.pool_id;

-- @Q4 공통 혜택 적용 상품과 상품별 조건 (Mastercard Platinum 01 호텔 발렛, 2026-11-01)
SELECT x.common_bnft_id, x.common_ver_id, p.product_nm, b.bnft_brand_opt_cds, a.cond_min_amt AS product_spend_min
FROM db_pipeline.card_bnft_common x
JOIN db_pipeline.card_bnft b ON (b.card_id, b.policy_ver_id, b.card_bnft_id) = (x.card_id, x.policy_ver_id, x.card_bnft_id)
JOIN db_pipeline.card_product p ON p.card_id = x.card_id
JOIN db_pipeline.card_policy_version v ON (v.card_id, v.policy_ver_id) = (x.card_id, x.policy_ver_id)
JOIN db_pipeline.card_common_policy_version cv ON (cv.common_bnft_id, cv.common_ver_id) = (x.common_bnft_id, x.common_ver_id)
LEFT JOIN db_pipeline.v_card_cond_atom a
  ON a.owner_cd = 'BNFT' AND (a.card_id, a.policy_ver_id, a.card_bnft_id) = (b.card_id, b.policy_ver_id, b.card_bnft_id)
 AND a.cond_type_cd = 'SPEND_REQ'
WHERE x.common_bnft_id = 'C-MP01-VALET' AND x.apply_status_cd = 'APPROVED'
  AND v.policy_status_cd = 'APPROVED' AND cv.policy_status_cd = 'APPROVED'
  AND DATE '2026-11-01' >= v.valid_from AND (v.valid_to_excl IS NULL OR DATE '2026-11-01' < v.valid_to_excl)
```

## 13. 검증 결과와 미검증 항목

**실행 환경:** PGlite(WASM) PostgreSQL 17.4 메모리 DB. 임시 폴더에서 실행했고 프로세스 종료와 함께 사라진다. 개발 DB는 17.11이다. `.env`와 Supabase에는 접속하지 않았다.

| 검증 | 결과 |
|---|---|
| V4 DDL 실행 (기준선) | 성공. 49개 테이블 |
| V5 DDL 빈 스키마 실행 | 성공. 25개 테이블, 6개 뷰, 16개 시퀀스, 인덱스 67개 |
| 제약 | PK 25, UNIQUE 14, CHECK 81, **FK 0** |
| PK 없는 테이블, 주석 없는 컬럼 | 0개 |
| DBML 파싱 (`@dbml/core`) | 성공. 25개 테이블, 285개 컬럼, 관계 38개, 그룹 6개 |
| 조회 SQL Q1~Q9 | 모두 실행, 9절 결과와 일치 |
| 게이트 21종 (정상 데이터) | 전부 0건 |
| 잘못된 입력 거부 | 15건 전부 거부 |
| 고아 데이터 주입 | 12건 전부 검출 |

**시험 중 발견해 고친 결함:** `cardinality(NULL) > 0`이 NULL이 되어 브랜드 없는 `BRAND` 혜택이 CHECK를 통과했다. `coalesce`로 고치고 `card_product_doc`의 같은 패턴도 수정했다. `pool_key` 생략 항목의 NULL 처리도 명시했다.

**게이트 주입 시험에 포함되지 않은 항목:** 21종 중 12종만 음성 시험을 했다. 나머지 9종은 정상 데이터에서 0건이 나오는 것까지만 확인했다.

**미검증 항목:**

- Supabase 실서버 실행과 V4→V5 이행 절차. 이번 범위에서 제외했다.
- 대용량 성능. GIN 인덱스는 만들었지만 실행 계획은 보지 않았다.
- 196개 PDF 전체의 DNF 표현 가능성. 사례 카드와 공통 문서 일부만 시험했다.
- 브랜드 집계. 공식 상품설명서 123개의 텍스트 패턴 기준이라 이미지 영역은 누락될 수 있다.
- 정책 적용 시작일. PDF로 확정하지 못해 시험에서는 가상값을 썼다.
- AI 추출 결과를 JSONB로 변환하는 적재 코드. 아직 없고, `stg_normalized_item` 형식과 `cond_expr` 계약을 맞춰야 한다.
- `predicate_state_cd`, `apply_status_cd` 등 V4에서 값 목록이 없던 코드. V5 CHECK 값은 설계 문서의 사용례 기준이라 승인이 필요하다.
