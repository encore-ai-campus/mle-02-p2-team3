# 카드 혜택 V6 — 공통코드·반정규화 설계 검토안

**상태:** 사용자 검토용 초안. 개발 Supabase의 V5는 변경하지 않았다.

**산출물:**

- DDL: [`db_pipeline_schemaV6_draft.sql`](../../../../src/card_benefit/sql/db_pipeline_schemaV6_draft.sql)
- ERD: [`db_pipeline_schemaV6_draft.dbml`](../../../../src/card_benefit/sql/db_pipeline_schemaV6_draft.dbml)
- 공통코드 시드: [`db_pipeline_common_code_seedV6.sql`](../../../../src/card_benefit/sql/db_pipeline_common_code_seedV6.sql)

## 0. 결론

| 항목 | V5 | V6 |
|---|---:|---:|
| 테이블 | 25 | **21** |
| 컬럼 | 285 | 245 |
| PK / UNIQUE / CHECK | 25 / 14 / 81 | 21 / 13 / 40 |
| 물리 FK | 0 | 0 |
| 시퀀스 | 16 | 13 |
| 조회 뷰 | 6 | 13 |
| 검증 함수 | 7 | 10 |
| 논리 관계선 | 38 | 28 |
| 공통코드 | 없음 | 44개 그룹, 162개 코드 |

**구조 요약:** 혜택이 계산 규칙과 혜택 간 관계를 직접 품는다. 공유 한도만 독립 테이블로 남는다.

```text
common_code_grp ─ common_cd                      코드 값

card_product
  └─ card_policy_version       source_doc_list
       ├─ card_bnft            rule_list[ pool_refs[] ], relation_list[]
       │    └─ card_bnft_common ─── card_common_policy_version (rule_list)
       ├─ card_limit_pool      tier_list  ← pool_refs가 참조
       └─ card_policy_evidence ─── card_source_evidence ─── card_doc_chunk
```

**동등성 검증:** 같은 시험 데이터를 V5와 V6에 넣어 대조했다. 업무 질의 13개와 행 단위 복원 11종이 모두 일치했다. 규칙 → 한도 → 대체 혜택 → PDF 근거 조회도 양쪽에서 같은 결과가 나왔다.

**가장 큰 대가:** 코드 값을 나열해 막던 CHECK 27개가 사라졌다. 잘못된 코드는 입력 시점에 거부되지 않고, 승인 전 정합성 게이트에서 잡힌다. 공통코드와 CHECK의 이중 관리를 피하라는 요구에 따른 결과다(쟁점 2).

## 3. 삭제·통합·유지 사유

| V5 테이블 | 처리 | 사유 |
|---|---|---|
| `card_bnft_rule` | `card_bnft.rule_list` | 규칙은 혜택 밖에서 독립 식별되지 않고 공유되지도 않는다. 사례 카드 기준 혜택당 1~3개다 |
| `card_bnft_rule_pool` | `rule_list[].pool_refs[]` | N:M이지만 소유 쪽이 분명하다. 역방향 조회는 `v_card_rule_pool`이 제공한다. `pool_role_cd`를 보존하려고 문자열이 아닌 객체 배열로 했다 |
| `card_bnft_rel` | `card_bnft.relation_list` | 시작 혜택 행이 곧 시작점이다. 안정 키 `relation_key`로 근거 연결을 유지한다 |
| `card_common_bnft_rule` | 공통 정책판 `rule_list` | 규칙은 정책판과 생명주기가 같다. 공유는 정책판 단위로 일어나므로 공유 구조에 영향이 없다 |
| `card_policy_doc` | `source_doc_list` | 속성이 역할 코드 1개뿐이다. 항목 수준의 추적은 근거 연결이 맡고 있다 |
| `card_excl_item_als` | `excl_alias_nms` | 원문 표기 하나만 저장하며 다른 테이블이 참조하지 않는다. GIN 인덱스로 별칭 조회가 가능하다 |

**유지한 이유가 분명한 테이블:**

- `card_limit_pool`: 규칙 여러 개가 공유하고(JADE), 한 규칙이 풀 여러 개를 소비하며(달달), 소진 대체의 트리거가 된다.
- `card_bnft_common`: 여러 상품이 같은 공통 정책판을 쓴다. 승인 상태가 있고, "이 공통 혜택을 어떤 상품이 쓰는가"가 핵심 역방향 질의다.
- `card_product_doc`: 공통 문서를 여러 상품이 공유하고, 적용 기간과 승인 이력을 관계 자체가 가진다.

**`card_method_catalog` 분석:**

| 역할 | 위치 | 이유 |
|---|---|---|
| 방법 코드와 이름 | `common_cd` (`CALC_METHOD`, `PREDICATE_METHOD`) | 단순 분류 |
| `method_ver`, `param_schema`, `handler_key` | `card_method_catalog` | 코드 1개에 버전 N개가 있어 `common_cd` 1행으로 표현 불가. 공통코드에 컬럼을 추가하지 말라는 요구도 있다 |

V5의 카탈로그에는 이름 컬럼이 없었으므로 역할이 겹치지 않는다. 게이트가 양쪽 일치를 확인한다.

## 4. 신규 공통코드 그룹과 코드

**기존 구축 확인:** 저장소와 개발 DB를 읽기 전용으로 확인했다. `recipe` 스키마에 같은 구조의 `common_code_grp`, `common_cd`가 있다.

| 항목 | `recipe` | 판단 |
|---|---|---|
| 규모 | 1개 그룹, 6개 코드 | 다른 프로젝트 소유 |
| 코드값 | `000001` 같은 일련번호 | 카드 쪽은 기존 코드값 보존이 원칙 |
| 재사용 시 | 스키마 간 의존 발생 | recipe 재구축이 카드 도메인에 영향 |

따라서 재사용하지 않고 요청대로 `db_pipeline`에 별도로 만들었다. 구조와 명명 규칙은 같다.

**코드 길이:** `varchar(20)`을 넘는 코드가 3개 있다.

|---|---:|---|

## 8. 공유 한도 관계 유지 방식

`card_limit_pool`은 독립 테이블로 유지했다. 규칙은 `pool_refs`로 참조한다.

**달달 체크카드, 편의점 규칙:** 영역 한도와 통합 한도를 동시에 소비한다.

```json
{
  "rule_key": "R-SHOP-CVS",
  "value_num": "5.0000",
  "pool_refs": [
    {
      "pool_id": "P-SHOP",
      "pool_role_cd": "CONSUME"
    },
    {
      "pool_id": "P-ALL",
      "pool_role_cd": "SHARED"
    }
  ]
}
```

| 관계 | V6 표현 | 시험 결과 |
|---|---|---|
| 여러 규칙이 한 풀 공유 | 여러 규칙의 `pool_refs`가 같은 `pool_id` | JADE 3개 규칙이 `P-SPECIAL` 공유 |
| 한 규칙이 여러 풀 소비 | `pool_refs` 원소 2개 | 전월 실적 50만 원: 쇼핑 2천 + 통합 1만 |
| 역할 구분 | `pool_role_cd` | `CONSUME`, `SHARED` 보존 |
| 소진 후 대체 | `relation_list[].trigger_pool_id` | 4개 혜택 모두 기본 적립으로 연결 |
| 존재 검증 | `v_card_integrity_issue` | 없는 풀 참조 검출 확인 |

`tier_list`는 유지했다. 풀당 1~3개이고 풀을 통해서만 조회되며, 수치는 CHECK 함수와 뷰로 검증된다. 공통 혜택은 V5와 같이 `limit_list`의 `pool_key`를 쓴다.

## 9. 혜택 간 관계 표현 방식

**JADE Classic.** 시작 혜택은 `card_bnft` 행 자체다.

```json
[
  {
    "card_bnft_id": "B-SPECIAL",
    "relation_list": [
      {
        "to_bnft_id": "B-BASE",
        "rel_type_cd": "MUTUALLY_EXCLUSIVE",
        "relation_key": "REL001"
      },
      {
        "to_bnft_id": "B-BASE",
        "rel_type_cd": "FALLBACK_AFTER_CAP",
        "relation_key": "REL002",
        "trigger_pool_id": "P-SPECIAL"
      }
    ]
  },
  {
    "card_bnft_id": "B-TAXI",
    "relation_list": [
      {
        "to_bnft_id": "B-BASE",
        "rel_type_cd": "FALLBACK_AFTER_CAP",
        "relation_key": "REL001",
        "trigger_pool_id": "P-TAXI"
      }
    ]
  }
]
```

| 요구사항 | 구현 |
|---|---|
| 대상 혜택 | `to_bnft_id` |
| 관계 유형 | `rel_type_cd` (공통코드 `REL_TYPE`) |
| 한도 소진 조건 | `trigger_pool_id`. `FALLBACK_AFTER_CAP`이면 CHECK에서 필수 |
| 우선순위 | `rel_priority` |
| 원문 근거 | `card_policy_evidence.relation_key` |
| 대상·한도 존재 | 게이트 `rel_to_bnft_orphan`, `rel_trigger_pool_orphan` |
| 자기 참조, 같은 대상·유형 중복 | CHECK에서 거부 |
| 대체 순환 | 게이트 `rel_fallback_cycle`. V5에는 이 검사가 없었다 |

**`MUTUALLY_EXCLUSIVE`의 양방향 규칙:**

- 저장: 한쪽 행에만 저장한다. 양쪽에 저장하면 게이트 `rel_mutual_stored_twice`가 검출한다.
- 조회: `v_card_bnft_rel`이 `reverse_yn=true` 행을 더해 양방향으로 돌려준다. 기본 적립에서 조회해도 특별 적립과의 배타 관계가 나온다.
- 집계: 관계 건수를 셀 때는 `NOT reverse_yn`으로 저장 행만 센다.

독립 테이블로 남겨야 할 사례는 찾지 못했다. 시험한 혜택 관계는 모두 시작 혜택이 명확했다.

## 10. PDF 근거 추적 방식

```text
card_policy_evidence
  RULE   → card_bnft_id + rule_key
  REL    → card_bnft_id + relation_key
  POOL   → pool_id
  BNFT   → card_bnft_id
  POLICY → 정책판
  ev_item_cd + ev_item_key → JSONB 안의 조건·대상·구간
        │
        └─ card_source_evidence → card_doc_chunk → card_doc_page → card_doc
```

JSONB로 옮겨도 근거 대상의 식별이 약해지지 않는다. V5의 `rule_id`가 `rule_key`로, `(to_bnft_id, rel_type_cd)`가 `relation_key`로 바뀐 것이 전부다. 대상 유형별 컬럼 조합은 CHECK가 고정하고, 키 존재 여부는 게이트가 검사한다.

## 12. Neo4j GraphRAG 영향

**JSONB로 합쳐도 그래프 노드는 줄어들지 않는다.** 복원 뷰가 그대로 입력이 된다. 시험 데이터의 적재 원천 행 수는 V5와 같다(Card 6, Policy 7, Benefit 19, Rule 22, Condition 49, Target 45, LimitPool 14, Evidence 11).

| 그래프 요소 | V6 원천 | 노드·관계 키 |
|---|---|---|
| `(:Card)` | `card_product` | `card_id` |
| `(:BrandOption)` | `v_card_brand_opt` | `card_id + brand_opt_cd` |
| `(:Policy)` | `card_policy_version` | PK |
| `(:Benefit)` | `card_bnft` | PK |
| `(:Rule)` | `v_card_rule`, `v_card_common_rule` | 소유 PK + `rule_key` |
| `(:Condition)` | `v_card_cond_atom` | 소유 PK + `atom_key` |
| `(:Target)` | `v_card_rule_target` | `target_type_cd + target_key` |
| `(:LimitPool)` | `card_limit_pool`, `v_card_common_limit` | PK 또는 `pool_key` |
| `(:CommonBenefit)` | `card_common_bnft` + 정책판 | PK |
| `(:Evidence)` | `card_source_evidence` | `evidence_id` |
| `[:CONSUMES {role}]` | `v_card_rule_pool` | 규칙 → 풀 |
| `[:EXCLUSIVE_WITH]` | `v_card_bnft_rel` (`NOT reverse_yn`) | 혜택 → 혜택, 방향 없음 |
| `[:FALLS_BACK_TO {trigger_pool}]` | `v_card_bnft_rel` | 혜택 → 혜택 |
| `[:USES_COMMON]` | `card_bnft_common` | 혜택 → 공통 |
| `[:SUPPORTED_BY]` | `card_policy_evidence`, `card_common_rule_evidence` | 대상 → 근거 |

**주의 사항:**

- Neo4j 적재기는 아직 없다. 위 표는 설계이고 실제 적재는 시험하지 않았다.
- `rule_key`가 바뀌면 그래프 노드와 근거 연결이 함께 끊긴다. 키 안정성이 V6의 핵심 운영 규칙이다.
- `(:Rule)` 라벨 등은 공통코드의 `common_cd_nm`으로 표시명을 채울 수 있다.

## 13. V5 대비 장단점

| 관점 | 좋아진 점 | 나빠진 점 |
|---|---|---|
| ERD | 테이블 4개, 관계선 10개 감소. 혜택 중심으로 읽기 쉬움 | 규칙·관계가 ERD 선으로 보이지 않음. DBML 상단과 컬럼 노트로 설명 |
| 코드 관리 | 코드 추가에 DDL 불필요. 코드명 한글 제공 | **잘못된 코드가 입력 시점에 거부되지 않음** |
| 적재 | 혜택 하나를 한 행으로 저장. 부분 실패 없음 | 규칙 1개 수정도 `rule_list` 전체 또는 `jsonb_set` 필요 |
| 조회 | 혜택 단위 조회에 JOIN 불필요 | 규칙 단위 SQL은 뷰 경유. 실적 구간에 전용 인덱스 없음 |
| 무결성 | `COMMON_LINK` 로컬 규칙 금지가 게이트에서 CHECK로 승격. 대체 순환 검사 추가 | `pool_refs`, `to_bnft_id`는 V5의 조인 컬럼보다 게이트 의존이 큼 |
| 근거 | 규칙·관계에 안정 키 사용 | `rule_key` 변경 시 근거가 끊김. 게이트가 검출은 함 |
| 공통 혜택 | 정책판 한 행에 규칙까지 포함 | 공통 규칙별 승인 상태는 JSONB 안에만 존재 |
| 규모 | 현재 카드 수에서는 문제 없음 | 규칙별 잠금이 불가능. 여러 사용자가 같은 혜택을 동시에 수정하면 덮어쓸 수 있음 |

**판단:** 카드 데이터가 소량이고 적재기가 한 곳이라는 현재 조건에서는 V6의 장점이 크다. 규칙을 화면에서 개별 편집하거나 규칙별로 승인하는 기능이 생기면 `card_bnft_rule` 분리를 다시 검토해야 한다.

## 15. 검증 SQL

리터럴 값과 ID는 시험 데이터 기준이다. 정합성 게이트 본문은 DDL의 `v_card_integrity_issue` 뷰에 있다.

```sql
-- @Q1 상품 → 정책 → 혜택 → 계산 규칙 (JADE, AMEX 선택지, 2026-11-01)
WITH cur AS (
  SELECT v.card_id, v.policy_ver_id
  FROM db_pipeline.card_policy_version v
  WHERE v.card_id = 1 AND v.policy_status_cd = 'APPROVED'
    AND DATE '2026-11-01' >= v.valid_from
    AND (v.valid_to_excl IS NULL OR DATE '2026-11-01' < v.valid_to_excl)
)
SELECT e.bnft_nm, e.rule_source_cd, e.rule_key, e.calc_method_cd, e.value_num, e.value_unit_cd, e.payout_unit_cd
FROM cur
JOIN db_pipeline.v_card_bnft_rule_effective e USING (card_id, policy_ver_id)
WHERE e.rule_status_cd = 'CONFIRMED'
  AND (e.bnft_scope_cd = 'PRODUCT' OR 'AMEX_PLATINUM_03' = ANY (e.bnft_brand_opt_cds))
  AND (e.common_valid_from IS NULL
       OR (DATE '2026-11-01' >= e.common_valid_from
           AND (e.common_valid_to_excl IS NULL OR DATE '2026-11-01' < e.common_valid_to_excl)))
ORDER BY e.card_bnft_id, e.rule_key;

-- @Q1b 같은 조회의 브랜드별 혜택 수 (브랜드 선택지 차이)
SELECT o.brand_opt_cd, count(*) AS rule_cnt,
       count(*) FILTER (WHERE e.rule_source_cd = 'COMMON') AS common_rule_cnt
FROM db_pipeline.v_card_brand_opt o
JOIN db_pipeline.v_card_bnft_rule_effective e ON e.card_id = o.card_id
WHERE o.card_id = 1 AND (e.bnft_scope_cd = 'PRODUCT' OR o.brand_opt_cd = ANY (e.bnft_brand_opt_cds))
GROUP BY o.brand_opt_cd ORDER BY o.brand_opt_cd;

-- @Q2 전월 실적 구간별 규칙 (Wide, 399,999원과 400,000원)
SELECT s.prev_spend, r.rule_key, r.value_num AS percent, r.spend_min_amt, r.spend_max_amt_excl, t.limit_num AS monthly_cap
FROM (VALUES (399999), (400000)) AS s(prev_spend)
JOIN db_pipeline.v_card_rule r
  ON r.card_id = 2 AND s.prev_spend >= r.spend_min_amt
 AND (r.spend_max_amt_excl IS NULL OR s.prev_spend < r.spend_max_amt_excl)
JOIN db_pipeline.v_card_rule_pool rp
  ON (rp.card_id, rp.policy_ver_id, rp.card_bnft_id, rp.rule_key) = (r.card_id, r.policy_ver_id, r.card_bnft_id, r.rule_key)
JOIN db_pipeline.v_card_limit_tier t
  ON (t.card_id, t.policy_ver_id, t.pool_id) = (rp.card_id, rp.policy_ver_id, rp.pool_id)
ORDER BY s.prev_spend;

-- @Q3 공유 한도: 하나의 풀을 소비하는 규칙 (JADE 특별 적립)
SELECT p.pool_id, p.period_cd, p.cap_unit_cd, t.limit_num, string_agg(rp.rule_key, ', ' ORDER BY rp.rule_key) AS rules
FROM db_pipeline.card_limit_pool p
JOIN db_pipeline.v_card_limit_tier t ON (t.card_id, t.policy_ver_id, t.pool_id) = (p.card_id, p.policy_ver_id, p.pool_id)
JOIN db_pipeline.v_card_rule_pool rp ON (rp.card_id, rp.policy_ver_id, rp.pool_id) = (p.card_id, p.policy_ver_id, p.pool_id)
WHERE p.card_id = 1 AND p.pool_id = 'P-SPECIAL'
GROUP BY 1, 2, 3, 4;

-- @Q3b 영역 풀과 통합 풀 동시 소비 (달달, 쇼핑 백화점 규칙, 전월 실적 500,000원과 1,000,000원)
SELECT s.prev_spend, t.pool_id, t.pool_scope_cd, t.limit_num
FROM (VALUES (500000), (1000000)) AS s(prev_spend)
JOIN db_pipeline.v_card_rule_pool rp ON rp.card_id = 3 AND rp.rule_key = 'R-SHOP-DEPT'
JOIN db_pipeline.v_card_limit_tier t ON (t.card_id, t.policy_ver_id, t.pool_id) = (rp.card_id, rp.policy_ver_id, rp.pool_id)
WHERE s.prev_spend >= t.spend_min_amt AND (t.spend_max_amt_excl IS NULL OR s.prev_spend < t.spend_max_amt_excl)
ORDER BY s.prev_spend, t.pool_id;

-- @Q4 공통 혜택 적용 상품과 상품별 조건 (Mastercard Platinum 01 호텔 발렛, 2026-11-01)
SELECT x.common_bnft_id, x.common_ver_id, p.product_nm, b.bnft_brand_opt_cds, a.cond_min_amt AS product_spend_min
FROM db_pipeline.card_bnft_common x
JOIN db_pipeline.card_bnft b ON (b.card_id, b.policy_ver_id, b.card_bnft_id) = (x.card_id, x.policy_ver_id, x.card_bnft_id)
JOIN db_pipeline.card_product p ON p.card_id = x.card_id
JOIN db_pipeline.card_policy_version v ON (v.card_id, v.policy_ver_id) = (x.card_id, x.policy_ver_id)
JOIN db_pipeline.card_common_policy_version cv ON (cv.common_bnft_id, cv.common_ver_id) = (x.common_bnft_id, x.common_ver_id)
LEFT JOIN db_pipeline.v_card_cond_atom a
  ON a.owner_cd = 'BNFT' AND (a.card_id, a.policy_ver_id, a.card_bnft_id) = (b.card_id, b.policy_ver_id, b.card_bnft_id)
 AND a.cond_type_cd = 'SPEND_REQ'
WHERE x.common_bnft_id = 'C-MP01-VALET' AND x.apply_status_cd = 'APPROVED'
  AND v.policy_status_cd = 'APPROVED' AND cv.policy_status_cd = 'APPROVED'
  AND DATE '2026-11-01' >= v.valid_from AND (v.valid_to_excl IS NULL OR DATE '2026-11-01' < v.valid_to_excl)
  AND DATE '2026-11-01' >= cv.valid_from AND (cv.valid_to_excl IS NULL OR DATE '2026-11-01' < cv.valid_to_excl)
ORDER BY p.card_id;

-- @Q5 복합 조건 해석: AND / OR / NOT 복원
WITH b AS (
  SELECT rule_key, branch_no,
         string_agg(CASE WHEN negate_yn THEN 'NOT ' ELSE '' END || coalesce(cond_raw_txt, excl_raw_txt, atom_key),
                    ' AND ' ORDER BY atom_seq) AS branch_txt
  FROM db_pipeline.v_card_cond_atom
  WHERE owner_cd = 'RULE' AND card_id = 1 AND rule_key IN ('R-15-AIR', 'R-12-MART')
  GROUP BY rule_key, branch_no
)
SELECT rule_key, string_agg('(' || branch_txt || ')', ' OR ' ORDER BY branch_no) AS expr_txt
FROM b GROUP BY rule_key ORDER BY rule_key;

-- @Q5b 제외 조건 검색: NOT atom 또는 제외 유형 (달달)
SELECT a.card_bnft_id, a.rule_key, a.cond_type_cd, a.negate_yn, coalesce(a.cond_raw_txt, a.excl_raw_txt) AS cond_txt
FROM db_pipeline.v_card_cond_atom a
WHERE a.card_id = 3 AND (a.negate_yn OR a.cond_type_cd IN ('SPEND_EXCL', 'BNFT_EXCL'))
ORDER BY a.rule_key, a.atom_seq;

-- @Q6 혜택 규칙 → PDF 근거 (JADE 특별 적립과 Amex 공통 규칙)
SELECT 'LOCAL' AS src, l.ev_subject_cd, l.rule_key AS subject, l.ev_item_cd, l.ev_item_key,
       d.doc_title, s.page_no, c.card_doc_chunk_id, left(s.quote_txt, 40) AS quote
FROM db_pipeline.card_policy_evidence l
JOIN db_pipeline.card_source_evidence s ON s.evidence_id = l.evidence_id
JOIN db_pipeline.card_doc_chunk c ON (c.card_doc_id, c.page_no, c.card_doc_chunk_id) = (s.card_doc_id, s.page_no, s.card_doc_chunk_id)
JOIN db_pipeline.card_doc d ON d.card_doc_id = s.card_doc_id
WHERE l.card_id = 1 AND l.card_bnft_id = 'B-SPECIAL' AND s.approval_status_cd = 'APPROVED'
UNION ALL
SELECT 'COMMON', 'RULE', l.rule_key, l.ev_item_cd, l.ev_item_key,
       d.doc_title, s.page_no, c.card_doc_chunk_id, left(s.quote_txt, 40)
FROM db_pipeline.card_common_rule_evidence l
JOIN db_pipeline.card_source_evidence s ON s.evidence_id = l.evidence_id
JOIN db_pipeline.card_doc_chunk c ON (c.card_doc_id, c.page_no, c.card_doc_chunk_id) = (s.card_doc_id, s.page_no, s.card_doc_chunk_id)
JOIN db_pipeline.card_doc d ON d.card_doc_id = s.card_doc_id
WHERE l.common_bnft_id = 'C-AMEX03-VALET' AND s.approval_status_cd = 'APPROVED'
ORDER BY 1, 2, 3;

-- @Q7 개정 전후 비교 (VISA Platinum Booking.com, 2023-06-01과 2026-11-01)
SELECT d.as_of, v.policy_ver_id, e.common_ver_id, e.value_num, e.value_unit_cd, e.payout_unit_cd, e.calc_params
FROM (VALUES (DATE '2023-06-01'), (DATE '2026-11-01')) AS d(as_of)
JOIN db_pipeline.card_policy_version v
  ON v.card_id = 6 AND v.policy_status_cd = 'APPROVED' AND d.as_of >= v.valid_from
 AND (v.valid_to_excl IS NULL OR d.as_of < v.valid_to_excl)
JOIN db_pipeline.v_card_bnft_rule_effective e
  ON (e.card_id, e.policy_ver_id) = (v.card_id, v.policy_ver_id)
 AND d.as_of >= e.common_valid_from AND (e.common_valid_to_excl IS NULL OR d.as_of < e.common_valid_to_excl)
ORDER BY d.as_of;

-- @Q8 혜택 간 관계 (JADE 우선·대체)
SELECT r.from_bnft_id, r.to_bnft_id, r.rel_type_cd, r.trigger_pool_id
FROM db_pipeline.v_card_bnft_rel r WHERE r.card_id = 1 AND NOT r.reverse_yn ORDER BY r.rel_type_cd DESC, r.from_bnft_id;

-- @Q9 Neo4j 적재 원천 행 수
SELECT 'Card' AS node_or_rel, count(*) AS cnt FROM db_pipeline.card_product
UNION ALL SELECT 'PolicyVersion', count(*) FROM db_pipeline.card_policy_version
UNION ALL SELECT 'Benefit', count(*) FROM db_pipeline.card_bnft
UNION ALL SELECT 'Rule(LOCAL+COMMON)', (SELECT count(*) FROM db_pipeline.v_card_rule) + (SELECT count(*) FROM db_pipeline.v_card_common_rule)
UNION ALL SELECT 'CommonBenefit', count(*) FROM db_pipeline.card_common_bnft
UNION ALL SELECT 'LimitPool', count(*) FROM db_pipeline.card_limit_pool
UNION ALL SELECT 'Condition(atom)', count(*) FROM db_pipeline.v_card_cond_atom
UNION ALL SELECT 'Target(distinct)', count(DISTINCT (target_type_cd, target_key)) FROM db_pipeline.v_card_rule_target
UNION ALL SELECT 'Evidence', count(*) FROM db_pipeline.card_source_evidence;

-- @Q10 규칙 → 한도 → 대체 혜택 → PDF 근거 (JADE 특별 적립)
SELECT b.bnft_nm, rp.rule_key, rp.pool_id, t.limit_num, t.cap_unit_cd,
       tb.bnft_nm AS fallback_bnft, s.page_no, left(s.quote_txt, 30) AS quote
FROM db_pipeline.v_card_rule_pool rp
JOIN db_pipeline.card_bnft b ON (b.card_id, b.policy_ver_id, b.card_bnft_id) = (rp.card_id, rp.policy_ver_id, rp.card_bnft_id)
JOIN db_pipeline.v_card_limit_tier t ON (t.card_id, t.policy_ver_id, t.pool_id) = (rp.card_id, rp.policy_ver_id, rp.pool_id)
JOIN db_pipeline.v_card_bnft_rel r
  ON (r.card_id, r.policy_ver_id, r.from_bnft_id, r.trigger_pool_id) = (rp.card_id, rp.policy_ver_id, rp.card_bnft_id, rp.pool_id)
 AND r.rel_type_cd = 'FALLBACK_AFTER_CAP'
JOIN db_pipeline.card_bnft tb ON (tb.card_id, tb.policy_ver_id, tb.card_bnft_id) = (r.card_id, r.policy_ver_id, r.to_bnft_id)
JOIN db_pipeline.card_policy_evidence l
  ON (l.card_id, l.policy_ver_id, l.card_bnft_id, l.relation_key) = (r.card_id, r.policy_ver_id, r.from_bnft_id, r.relation_key)
 AND l.ev_subject_cd = 'REL'
JOIN db_pipeline.card_source_evidence s ON s.evidence_id = l.evidence_id
WHERE rp.card_id = 1 AND rp.card_bnft_id = 'B-SPECIAL'
ORDER BY rp.rule_key;

-- @GATE 정합성 게이트. 결과가 0행이어야 승인
SELECT gate_cd, count(*) AS issue_cnt FROM db_pipeline.v_card_integrity_issue GROUP BY 1 ORDER BY 1;

-- @CODE1 코드 누락: 업무 데이터에 있으나 해당 그룹에 없는 코드
SELECT u.source_nm, u.common_code_grp_id, u.cd_value
FROM db_pipeline.v_common_cd_usage u
WHERE NOT EXISTS (SELECT 1 FROM db_pipeline.common_cd c
                  WHERE (c.common_code_grp_id, c.common_cd) = (u.common_code_grp_id, u.cd_value));

-- @CODE2 코드 중복: 같은 코드값이 여러 그룹에 있는 경우(의도된 재사용 여부 검토)
SELECT common_cd, count(*) AS grp_cnt, string_agg(common_code_grp_id, ', ' ORDER BY common_code_grp_id) AS grp_list
FROM db_pipeline.common_cd GROUP BY 1 HAVING count(*) > 1 ORDER BY 2 DESC, 1;

-- @CODE3 코드 미사용: 시드에는 있으나 업무 데이터에 쓰이지 않은 코드 수(그룹별)
SELECT c.common_code_grp_id, count(*) FILTER (WHERE u.cd_value IS NULL) AS unused_cnt, count(*) FILTER (WHERE u.cd_value IS NOT NULL) AS used_cnt
FROM db_pipeline.common_cd c
LEFT JOIN (SELECT DISTINCT common_code_grp_id, cd_value FROM db_pipeline.v_common_cd_usage) u
  ON (u.common_code_grp_id, u.cd_value) = (c.common_code_grp_id, c.common_cd)
GROUP BY 1 HAVING count(*) FILTER (WHERE u.cd_value IS NULL) > 0 ORDER BY 1;

-- @KEY1 rule_key 중복 검사(같은 혜택 안). CHECK가 막지만 적재 후 재검증용
SELECT card_id, policy_ver_id, card_bnft_id, rule_key, count(*)

-- @KEY2 양방향 관계 조회: 기본 적립에서 본 배타 관계
SELECT from_bnft_id, to_bnft_id, rel_type_cd, reverse_yn
FROM db_pipeline.v_card_bnft_rel
WHERE card_id = 1 AND from_bnft_id = 'B-BASE' AND rel_type_cd = 'MUTUALLY_EXCLUSIVE';

-- @KEY3 대상 가맹점으로 규칙 찾기(JSONB 포함 검색)

WHERE b.rule_list @> '[{"target_list":[{"target_key":"스타벅스"}]}]'
  AND r.target_list @> '[{"target_key":"스타벅스"}]';
```

## 16. 검증 환경과 미검증 항목

**실행 환경:** PGlite(WASM) PostgreSQL 17.4 메모리 DB. 프로세스 종료와 함께 사라진다.

**개발 Supabase:** 공통코드 존재 여부 확인을 위해 읽기 전용 트랜잭션으로 조회만 했다. DROP, ALTER, CREATE, INSERT는 실행하지 않았다. V5 25개 테이블과 0행 상태는 그대로다.

| 검증 | 결과 |
|---|---|
| V6 DDL + 시드 실행 | 성공 |
| 생성 결과 | 테이블 21, 뷰 13, 시퀀스 13, 인덱스 61, 함수 10 |
| 제약 | PK 21, UNIQUE 13, CHECK 40, **FK 0** |
| 주석 없는 컬럼 | 0개 |
| DBML 파싱 | 성공. 테이블 21개, 컬럼 245개, 관계 28개 |
| 빈 DB 게이트 | 0건 |

**시험 중 고친 사항:** `v_card_rule`의 실적 구간 타입이 V5와 달라 `numeric(18,2)`로 맞췄다. 미사용 코드 SQL의 집계 오류도 수정했다.

**미검증 항목:**

- Supabase 실서버 실행과 V5→V6 이행. 이번 범위 밖이다.
- 196개 PDF 전체의 규칙 구조 적합성. 사례 카드와 공통 문서 일부만 시험했다.
- 실제 Neo4j 적재와 AI 추출 결과를 `rule_list`로 변환하는 적재 코드.
- 대용량 성능과 GIN 인덱스 실행 계획.
- 동시 수정 충돌.
- 시드 코드의 완전성. 전체 카드를 적재하면 코드가 추가될 수 있다.
