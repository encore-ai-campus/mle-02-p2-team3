# 카드 혜택 V6 — 테이블·컬럼 상세 설명

DB COMMENT는 ERD 가독성을 위해 짧은 업무 명칭만 둔다. 구조, 규칙, 이력 설명은 이 문서에서 관리한다.

| 항목 | 위치 |
|---|---|
| 짧은 명칭 원본 | `src/card_benefit/sql/db_pipeline_comment_v6.sql` |
| 변경 전 긴 COMMENT 복원 | `src/card_benefit/sql/db_pipeline_comment_v6_restore.sql` |
| 설계 판단과 검증 결과 | `카드혜택_V6_공통코드_반정규화_설계검토안.md` |
| 공통코드 값 | `src/card_benefit/sql/db_pipeline_common_code_seedV6.sql` |

## 1. 전체 구조

```text
common_code_grp ─ common_cd

card_product                         카드 상품
  ├─ card_product_doc                상품별 문서 관계  ─ card_doc
  └─ card_policy_version             카드 정책 버전
       ├─ card_bnft                  카드 혜택 (계산 규칙·혜택 관계 포함)
       │    └─ card_bnft_common      상품별 공통 혜택 관계 ─ card_common_policy_version
       ├─ card_limit_pool            혜택 공유 한도
       └─ card_policy_evidence       정책 근거 관계 ─ card_source_evidence

card_common_bnft                     공통 혜택
  └─ card_common_policy_version      공통 혜택 정책 버전 (공통 규칙 포함)
       └─ card_common_rule_evidence  공통 규칙 근거 관계 ─ card_source_evidence

card_doc ─ card_doc_page ─ card_doc_chunk ─ card_source_evidence
card_ai_run ─ card_ai_call ─ card_extr_stg
```

- 업무 데이터의 기준은 문서가 아니라 **상품 정책 버전**이다. PDF는 근거다.
- 부모·자식은 부모 PK 전체를 자식 PK가 상속한다.
- 물리 FK는 없다. 논리 관계는 `v_card_integrity_issue`로 승인 전에 검사한다.
- 문서판, 상품 정책판, 공통 정책판은 각각 독립적으로 개정된다.

## 2. 상품·정책

**`card_product`**: 상품 마스터. `product_cd`는 문서 파일명과 무관한 업무 코드다. 출시일과 중단일은 확인된 경우에만 넣는다.

**`card_policy_version`**: 상품 정책 개정판.

- 같은 시점에 승인된 정책은 상품당 1개다.
- 기간은 `[valid_from, valid_to_excl)`로 시작일 포함, 종료일 미포함이다.
- 문서 발행일, 정책 승인일, 혜택 적용일은 서로 다른 값이다.
- 개정할 때 기존 행을 덮어쓰지 않고 새 `policy_ver_id` 아래에 새 행을 만든다.
- `policy_cond_expr`에는 실적 산정 기준, 실적 제외, 유예처럼 특정 혜택에 속하지 않는 조건을 둔다.

**`card_product_doc`**: 상품과 문서판의 N:M. 적용 기간과 승인 이력을 관계 자체가 가진다.

- 기간은 `[effective_from, effective_to_excl)`이다.
- 승인 상태가 되려면 적용 시작일과 적용 근거가 필수다.
- 브랜드 서비스 문서는 `brand_opt_cds`가 필수다. NULL이면 상품 전체에 적용된다.

## 3. 혜택과 계산 규칙

**`card_bnft`**: 상품 정책에 속한 혜택 인스턴스.

| 항목 | 규칙 |
|---|---|
| `bnft_origin_cd` | `LOCAL`은 `rule_list` 사용, `COMMON_LINK`는 공통 규칙 사용 |
| `COMMON_LINK` | `rule_list`가 비어 있어야 한다. 상품에 공통 규칙값을 복제하지 않는다 |
| `bnft_scope_cd` | `PRODUCT`는 상품 전체, `BRAND`는 `bnft_brand_opt_cds`의 선택지에만 적용 |
| `rule_select_cd` | 한 혜택 안에서 규칙이 겹칠 때 선택 방식 |

**실제 적용 조건**은 세 단계의 AND다.

```text
카드 공통 조건(policy_cond_expr)
  AND 혜택 적용 조건(bnft_cond_expr)
  AND 규칙 조건(rule_list[].cond_expr 또는 공통 규칙의 cond_expr)
```

**`rule_list`**: 계산 규칙 목록. 혜택의 계산값은 여기에만 저장한다.

| 키 | 설명 |
|---|---|
| `rule_key` | 혜택 안에서 유일한 안정 키. 근거 연결과 Neo4j 노드 ID에 쓰므로 바꾸지 않는다 |
| `cond_expr` | 규칙 조건식 |
| `predicate_state_cd` | `CONDITIONAL`은 조건식 필수, `VERIFIED_UNCONDITIONAL`은 원문 확인된 무조건, `PENDING_REVIEW`는 검토 대기 |
| `target_list` | 적용 대상. 확정 규칙은 1개 이상 필요 |
| `calc_method_cd`, `method_ver` | 계산 방식과 버전 |
| `value_num` | 방법별로 의미가 고정된 값. `PERCENT_OF_TXN`의 1.5는 1.5% |
| `value_unit_cd`, `payout_unit_cd` | 값의 단위와 실제 보상 단위 |
| `basis_amt` | 기준 금액. 1,500원당 적립의 1500 |
| `calc_params` | 방법별 가변 파라미터 |
| `rule_priority` | 원문에 명시된 우선순위 |
| `rule_status_cd` | 규칙 상태 |
| `pool_refs[]` | 소비하는 한도 풀. `{pool_id, pool_role_cd}` |

대상별 비율이 다르면 대상에 비율을 넣지 않고 규칙을 나눈다. `cond_expr`가 NULL이라는 사실만으로 무조건으로 보지 않는다.

**`relation_list`**: 이 혜택에서 시작하는 혜택 간 관계.

| 키 | 설명 |
|---|---|
| `relation_key` | 혜택 안에서 유일한 안정 키. 근거 연결에 쓴다 |
| `to_bnft_id` | 대상 혜택 |
| `rel_type_cd` | 관계 유형 |
| `trigger_pool_id` | 소진 대체를 일으키는 한도 풀. `FALLBACK_AFTER_CAP`에서 필수 |
| `rel_priority` | 관계 우선순위 |

`MUTUALLY_EXCLUSIVE`는 양방향 의미지만 한쪽 행에만 저장한다. `v_card_bnft_rel`이 `reverse_yn=true` 행을 더해 양방향으로 돌려준다. 저장 행만 셀 때는 `NOT reverse_yn`을 쓴다.

## 4. 조건식 구조

정책, 혜택, 규칙, 한도 구간, 공통 규칙이 같은 구조를 쓴다.

```json
{"expr_status_cd": "CONFIRMED",
 "branches": [
   {"branch_no": 1, "atoms": [
     {"atom_key": "CH_OFFICIAL", "atom_seq": 1, "negate_yn": false,
      "cond_type_cd": "PAYMENT_METHOD", "cond_raw_txt": "공식 홈페이지",
      "cond_status_cd": "CONFIRMED"}]}]}
```

- 서로 다른 `branches`는 OR, 같은 branch의 `atoms`는 AND, `negate_yn=true`는 NOT이다.
- 금액 구간은 `[cond_min_amt, cond_max_amt_excl)`로 하한 포함, 상한 미포함이다.
- `atom_key`는 조건식 안에서 유일하다. 조건 근거 연결에 쓴다.
- `predicate_method_cd`와 `predicate_method_ver`는 짝으로 저장한다.
- `SPEND_EXCL`, `BNFT_EXCL`은 `card_excl_item_id` 또는 `excl_raw_txt`가 필요하다.

**선택 키:** `cond_basis_cd`, `cond_min_amt`, `cond_max_amt_excl`, `predicate_method_cd`, `predicate_method_ver`, `cond_params`, `card_excl_item_id`, `excl_raw_txt`, `cond_raw_txt`, `link_role_cd`

## 5. 공유 한도

**`card_limit_pool`**: 상품 정책판의 독립 한도. 여러 규칙이 공유하고 한 규칙이 여러 풀을 소비하므로 독립 테이블로 유지한다. 금액이 같다는 이유로 풀을 병합하지 않는다.

| 사례 | 표현 |
|---|---|
| 여러 규칙이 한 한도 공유 | 규칙들의 `pool_refs`가 같은 `pool_id` 참조 |
| 영역 한도와 통합 한도 동시 소비 | 규칙의 `pool_refs` 원소 2개 |
| 한도 소진 후 다른 혜택 적용 | `relation_list[].trigger_pool_id` |

**`tier_list`**: `{tier_key, tier_priority, predicate_state_cd, limit_num, cond_expr}`의 배열. `limit_num`은 0 이상의 숫자이고, `CONDITIONAL`이면 `cond_expr`가 필수다. 실제 사용 잔량은 저장하지 않으며 거래 데이터로 계산한다.

## 6. 공통 혜택

```text
card_bnft (상품별 인스턴스, COMMON_LINK)
  ├ bnft_brand_opt_cds  어떤 브랜드 선택지에 적용되는가
  ├ bnft_cond_expr      이 상품에만 붙는 조건, 공통 조건과 AND
  └ card_bnft_common ─ card_common_policy_version.rule_list
```

- `card_common_bnft`는 특정 카드에 속하지 않는 서비스 정체성이다. 이름이나 PDF가 같다는 이유로 병합하지 않는다.
- `card_common_policy_version.rule_list`가 공통 규칙값의 유일한 기준이다. `pool_refs` 대신 `limit_list`를 쓴다.
- `limit_list`는 `{limit_key, pool_key, period_cd, cap_unit_cd, aggregation_key_cd, predicate_state_cd, limit_num, cond_expr}`의 배열이다. 같은 정책판의 같은 `pool_key`는 공유 한도다.
- 공통 정책 개정은 새 `common_ver_id`와 새 링크로 표현한다. 승인된 링크의 공통 정책 기간은 겹치면 안 된다.

## 7. 브랜드 선택지

`card_product.brand_opt_list`는 `{brand_opt_cd, brand_opt_nm, brand_cd, service_grade_cd, service_type_cd, brand_opt_status_cd}`의 배열이다. 국내전용도 하나의 선택지로 저장한다. `card_bnft.bnft_brand_opt_cds`와 `card_product_doc.brand_opt_cds`가 `brand_opt_cd`를 참조한다.

## 8. PDF 원문 근거

```text
card_policy_evidence / card_common_rule_evidence
   → card_source_evidence → card_doc_chunk → card_doc_page → card_doc
```

**`card_source_evidence`**: 승인된 문장과 청크 근거. 문서 키를 업무 PK로 전파하지 않기 위해 독립 ID를 쓴다. 같은 문장을 여러 대상이 참조할 수 있다.

**`card_policy_evidence`**: `ev_subject_cd`에 따라 값이 있어야 하는 컬럼이 정해져 있다. CHECK가 이 조합을 고정한다.

| 대상 유형 | 필수 컬럼 |
|---|---|
| `POLICY` | 없음 |
| `BNFT` | `card_bnft_id` |
| `RULE` | `card_bnft_id`, `rule_key` |
| `REL` | `card_bnft_id`, `relation_key` |
| `POOL` | `pool_id` |

JSONB 안의 세부 항목 근거는 `ev_item_cd`, `ev_item_key`로 연결한다.

| `ev_item_cd` | `ev_item_key` |
|---|---|
| `SELF` | `-` (대상 전체) |
| `COND` | `atom_key` |
| `TARGET` | `target_key` |
| `TIER` | `tier_key` |
| `LIMIT` | `limit_key` (공통 규칙) |

**`card_common_rule_evidence`**: 공통 정책판의 `rule_key`를 참조한다. 조건, 대상, 한도 근거도 같은 방식으로 구분한다.

## 9. 원천 문서

| 테이블 | 설명 |
|---|---|
| `card_doc` | 원천 PDF 파일과 문서판. 같은 계열의 개정판은 `doc_family_cd`로 묶되 각 판은 별도 행이다 |
| `card_doc_page` | 페이지별 추출 원문. 적재 후 변경하지 않는다. `page_raw_txt`는 가공하지 않은 원문이다 |
| `card_doc_chunk` | 조항·표·안내 단위 청크. 페이지를 넘지 않는다. `chunk_raw_txt`는 페이지 원문의 부분 문자열이고 위치는 PostgreSQL `substr` 기준이다 |

- `card_doc.card_id`는 기존 파이프라인의 단일 상품 힌트다. 신규 문서는 NULL이고 적용 기준은 `card_product_doc`이다.
- `doc_release_date`는 기존 상품 출시일 기록이며, 공통 문서는 확인된 발행일만 넣는다. 관계 적용 시작일과 다르다.
- `doc_status`는 원천 문서 상태다. 상품별 현재 적용 여부는 승인된 문서 관계의 기간으로 판정한다.

## 10. AI 파싱

| 테이블 | 설명 |
|---|---|
| `card_ai_run` | 추출·검증 실행 회차. 여러 문서를 처리하면 `run_target_card_doc_id`는 NULL이다 |
| `card_ai_call` | 실행 안의 청크별 호출과 원 응답. 재시도하면 `call_seq`가 증가한다 |
| `card_extr_stg` | 추출한 혜택·조건 후보. 원본, 정제값, 검증과 승인 상태를 가진다 |

- 자동 또는 수동 승인에는 정제 항목, SQL 검증 `OK`, 근거 위치, 근거 문장이 필요하다.
- `stg_parent_card_extr_stg_id`는 조건이 걸린 혜택의 추출 항목이다. 카드 전체 조건이면 NULL이다.
- `card_extr_stg.card_id`는 추출 실행의 대상 상품이다. 공유 문서는 상품 연결 범위를 별도로 검증한다.

## 11. 계산 방법과 제외 항목

**`card_method_catalog`**: 코드와 이름은 공통코드에 있고, 이 테이블은 버전별 실행 계약만 관리한다. `method_kind_cd`가 `CALC`면 `CALC_METHOD`, `PREDICATE`면 `PREDICATE_METHOD` 그룹의 코드를 쓴다. `handler_key`는 애플리케이션 허용 목록의 키이며, 문자열을 코드로 실행하지 않는다.

**`card_excl_item`**: 표준 제외 항목 사전이다. 카드사 범위의 개념이고 정책이 아니다. 병합은 같은 카드사 안에서만 한다. `excl_concept_cd`는 분류용이며 정책이 같다는 뜻이 아니다. `excl_alias_nms`는 공백을 뺀 원문 표기 기준으로 비교하고, 의미가 불확실한 표기는 등록하지 않는다.

## 12. 정합성 검증

**JSONB 검증 함수** (CHECK에서 호출):

| 함수 | 대상 |
|---|---|
| `fn_valid_cond_expr` | 조건식 |
| `fn_valid_rule_list` | 계산 규칙 목록 (상품·공통) |
| `fn_valid_relation_list` | 혜택 관계 목록 |
| `fn_valid_target_list` | 대상 목록 |
| `fn_valid_tier_list` | 한도 구간 목록 |
| `fn_valid_limit_list` | 공통 한도 목록 |
| `fn_valid_brand_opt_list` | 브랜드 선택지 목록 |
| `fn_valid_doc_ref_list` | 근거 문서 목록 |

**승인 전 게이트:** 아래 결과가 0행이어야 한다.

```sql
SELECT gate_cd, count(*) FROM db_pipeline.v_card_integrity_issue GROUP BY 1;
```

게이트 29종은 부모 누락, `pool_refs`와 `relation_list` 참조, 대체 순환, 공통 링크, 정책 기간 겹침, 브랜드 코드, 계산 방식, 근거 대상과 항목 키, 공통코드 소속을 검사한다.

**공통코드 검증:** CHECK에 코드 목록을 두지 않는다. 공통코드와 이중으로 관리하지 않기 위해서다. 어떤 컬럼이 어떤 그룹을 쓰는지는 `v_common_cd_usage` 뷰가 정의한다. 잘못된 코드는 입력 시 거부되지 않고 게이트 `common_cd_invalid`에서 검출된다.

**조회 뷰:**

| 뷰 | 용도 |
|---|---|
| `v_card_rule`, `v_card_common_rule` | 계산 규칙을 행으로 복원 |
| `v_card_rule_pool` | 규칙↔한도 |
| `v_card_bnft_rel` | 혜택 관계 (양방향 복원) |
| `v_card_rule_target` | 규칙 대상 |
| `v_card_cond_atom` | 조건 atom과 소유자 |
| `v_card_limit_tier`, `v_card_common_limit` | 한도 구간 |
| `v_card_brand_opt`, `v_card_policy_doc` | 브랜드 선택지, 정책 문서 |
| `v_card_bnft_rule_effective` | 상품 고유 규칙과 공통 규칙의 단일 출력 |
| `v_common_cd_usage` | 공통코드 사용처 |
| `v_card_integrity_issue` | 정합성 게이트 |
