# 카드 혜택 적용 규칙 데이터 모델 — DDL 전 설계 결정안

기준: 2026-10-31. 앞선 [8종 검토](카드혜택_DB_모델링_컬럼행_설계검토.md), [20종 검토](카드혜택_DB_논리모델_20종_보완검토.md), 실제 `db_pipeline` 기준 백업 `src/data/backup/dump-postgres-202610311136.sql`을 읽었다. PDF 재조사나 DB 변경은 수행하지 않았다. **이 문서의 신규 테이블·컬럼·SQL은 제안이며 현재 DB에 존재하지 않는다.** 아래 `DOC-*`, `B-*`, `R-*` 등은 설명용 가상 키이고 C04·C05·D05·D10은 앞선 20종 보고서의 PDF ID다.

## 1. 최종 권장 모델

**B안: 독립 `card_bnft_rule`을 혜택 적용값의 유일한 기준으로 채택한다.** `Benefit`은 고객이 이해할 서비스의 정체성, `Target`은 적용 대상, `Condition`은 참/거짓을 판정할 원자 조건, `Benefit Rule`은 대상·조건의 조합과 **계산 방식·값**, `Limit Pool`은 별도 누적 한도, `Benefit Relation`은 우선·배타·대체 관계다. 이 구분은 현재의 `card_bnft`·`card_cond`·`card_bnft_cond`를 활용하면서 계산값의 중복 저장을 끝낸다.

```text
Card ─ Document ─ Benefit ─ BenefitRule ─ RuleTarget ─ Target
                      │            │
                      │            ├─ ConditionExpression ─ ExpressionAtom ─ Condition
                      │            └─ RulePool ─ LimitPool ─ LimitTier ─ ConditionExpression
                      └─ BenefitRelation ─ Benefit
BenefitRule / Condition ─ approved evidence ─ DocumentChunk
```

**A 기존 혜택+조건+대상만 활용:** C05는 `cond_rate=1/2`, C04는 대상별 `target_rate=1.5/1.2`, D05는 `cond_limit_amt`, D10은 `cond_rule_json`이 각각 계산값을 갖는다. 한 상품을 조회할 때 네 위치를 해석해야 하고 `bnft_rate`·`cond_rate`·`target_rate` 충돌에 일반적인 SQL 기준이 없다. **C 기존 구조 일부 조정:** `card_cond`를 적용 규칙까지 겸하게 하면 C04 같은 한 조건에 여러 대상별 적립률과 D05의 영역/전체 한도를 한 행 유형으로 표현해야 한다. 행은 늘릴 수 있지만 조건의 진리값과 혜택의 출력값이 뒤섞인다. **B**는 적용값을 한 행 유형으로 고정하므로 새 계산 방식이 생겨도 원칙적으로 방법 코드·파라미터·계산기 구현만 추가한다. 대가로 규칙/대상/조건/한도 조인이 늘고 적재 파이프라인이 더 엄격한 검증을 해야 한다. 테이블 수보다 의미와 검사 가능성을 우선했다.

## 2. 테이블별 책임과 현재 구조와의 차이

| 엔티티 | 관리하는 것 | 핵심 컬럼·논리 키(제안은 `+`) | 관리하지 않는 것 |
|---|---|---|---|
| `card_doc`, `card_doc_page`, `card_doc_chunk`, `card_extr_stg` | 문서판·페이지·원문·후보·승인 근거 | 기존 `card_doc_id`, `card_id`, 해시, 쪽/청크/오프셋 | 계산의 최종 적용값 |
| `card_bnft` | 혜택 정체성·유형·전달 방식·검증 상태·한 혜택 안의 규칙 선택 정책 | 기존 `(card_doc_id,card_bnft_id)`, `bnft_type_cd`; `+delivery_cd`, `+spend_review_cd`, `+rule_select_cd` | **새 확정 행의** 비율/금액. 기존 `bnft_rate`, `bnft_amt`는 이행 기간 호환 필드 |
| `card_bnft_target` **신규** | 문서판·혜택에 속한 가맹점/업종/채널 대상 | `(card_doc_id,target_id)`, `card_bnft_id`, `target_type_cd`, `target_key`, 원문 근거 | 비율·금액·한도. 이전 보고서의 `target_rate/amt` 제안은 **채택하지 않음** |
| `card_cond` | 재사용 가능한 **원자 술어**: 전월 실적, 자동납부, 매입월 집합, 적용 제외 등 | 기존 `(card_doc_id,card_cond_id)`, `cond_type_cd`, `cond_basis_cd`, `cond_min/max_amt`, `cond_rule_json` | 혜택 출력값·한도값. 기존 `cond_rate/amt/limit_*`는 이행 기간 호환 필드 |
| `card_cond_expr`, `card_cond_expr_atom` **신규** | 조건의 AND/OR/NOT 묶음 | `(card_doc_id,expr_id)`; atom `(expr_id,branch_no,card_cond_id,negate_yn)` | 혜택 계산값 |
| `card_bnft_rule` **신규** | 한 혜택의 적용 방식·**유일한 계산값 원천** | `(card_doc_id,rule_id)`, `card_bnft_id`, `expr_id`, `predicate_state_cd`, `calc_method_cd`, `method_ver`, `value_num numeric`, `value_unit_cd`, `payout_unit_cd`, `basis_amt numeric?`, `calc_params jsonb`, `rule_priority`, `target_scope_cd`, 근거/상태 | 누적 한도와 거래별 실제 결과 |
| `card_bnft_rule_target` **신규** | 규칙이 적용되는 대상 집합 | `(card_doc_id,rule_id,target_id)` | 대상별 비율. 비율이 다르면 **별도 규칙 행** |
| `card_limit_pool` **신규** | 독립적인 누적 한도 정체성·범위 | `(card_doc_id,pool_id)`, `pool_scope_cd`, `period_cd`, `cap_unit_cd`, `aggregation_key_cd`, `reset_basis_cd`, 원문 근거 | 구간별 한도값 |
| `card_limit_tier` **신규** | 풀의 조건별 한도값 | `(card_doc_id,pool_id,tier_id)`, `expr_id`, `predicate_state_cd`, `limit_num numeric`, `tier_priority` | 혜택 계산 방식. 조건식은 위 expr을 참조 |
| `card_bnft_rule_pool` **신규** | 규칙이 소비하는 영역별/카드 전체 한도 | `(card_doc_id,rule_id,pool_id)`, `pool_role_cd` | 한도를 같은 숫자만으로 병합하지 않음 |
| `card_bnft_rel` **신규** | 혜택 간 우선/배타/소진 후 대체 | 문서, 시작·도착 혜택 ID, 관계 코드, `trigger_pool_id?`, 근거 | 조건 원자·계산값 |
| `card_method_catalog` **신규** | 계산·술어 방법 코드, 버전, 필수 파라미터 스키마, 결과 단위, 승인된 Python 핸들러 키 | `(method_kind_cd,method_cd,method_ver)`, `param_schema jsonb`, `handler_key` | 임의 SQL/Python 문자열 실행. 핸들러는 애플리케이션의 허용 목록에서만 선택 |
| `card_bnft_cond` 기존 | 혜택↔조건 탐색용 **호환 투영** | 현재 복합 PK 유지 | 규칙 판정의 최종 기준 아님. 새 데이터는 규칙식에서 DISTINCT로 유도·대조 |

`card_cond.card_bnft_id`는 현행 CHECK상 BENEFIT 조건의 앵커다. 새 모델에서는 `card_bnft_rule.card_bnft_id`와 식의 atom 연결이 **실효 적용 기준**이며, `card_cond.card_bnft_id`는 이행 중 호환 앵커로 둔다. `CARD`·`SHARED` 원자 조건의 앵커는 NULL, `BENEFIT`이면 같은 혜택의 규칙식에서만 쓰도록 검사한다. 즉시 삭제하지 않는다. 기존 `card_bnft_cond`는 승인된 규칙식의 `(혜택,조건)` DISTINCT와 일치해야 한다. 조건이 한도 풀의 식에만 등장하는 경우에는 그 풀을 소비하는 규칙의 혜택으로 투영한다. 이 경로를 정의하지 않은 수동 링크를 새 확정 데이터에 넣지 않는다.

물리 FK를 사용하지 않는 현행 원칙을 유지하더라도, 복합 키에 **문서 ID**를 포함하고 같은 문서·상품 ID, 고아 행, 단위·코드, 중복·순환을 SQL 승인 게이트로 검사한다. `card_benefit.card_product`는 현재 접속 DB에 없다. 상품 ID의 권위 있는 공급처는 DDL 작업 전에 별도 결정한다.

## 3. 혜택 수치의 단일 기준과 적용 순서

**출력값은 오직 `card_bnft_rule`에 둔다.** 고정 할인율은 해당 혜택의 한 규칙 `value_num`(예: 10, `value_unit_cd=PERCENT`), 구간별 할인율은 **구간별 규칙 행**(C05의 1·2), 대상별 적립률도 **대상별 규칙 행**(C04의 1.5·1.2)에 둔다. 같은 비율·동일 조건으로 여러 대상에 적용되면 규칙 하나와 `card_bnft_rule_target` 여러 행을 사용한다. `card_bnft.bnft_rate/amt`, `card_cond.cond_rate/amt`, 대상 행의 수치는 새 확정 데이터에서 권위가 없다. 삭제 전까지 새 행에서는 NULL 또는 명시적인 기존 데이터 이행값으로만 허용하고, 호환 필드와 규칙값이 충돌하면 **자동 우선 선택하지 않고 승인 실패**시킨다.

`value_num`은 계산 방법별 의미가 고정된다: `PERCENT_OF_TXN`이면 퍼센트 수치 1.5(=1.5%), `FIXED_PER_TXN`이면 100원, `UNITS_PER_AMOUNT`이면 45 UniMile, `MULTIPLY_EXTERNAL_POINTS`이면 배수 2. `basis_amt`는 `UNITS_PER_AMOUNT`의 1,500원처럼 필요한 경우만 사용한다. `payout_unit_cd`는 KRW/HANAMONEY/UNIMILE 등 실제 보상 단위다. 새로운 방식이 이 공통 수치에 맞지 않으면 `value_num`을 NULL로 하고 **검증된 `calc_params`와 방법별 Python 핸들러**가 결과를 산출한다. 빈 JSON이나 자유 텍스트 계산식은 허용하지 않는다.

적용 순서: ① 문서판·혜택 승인 및 검증된 대상 선택 → ② 규칙 대상 집합과 조건식 참 여부 → ③ 하나의 혜택 안에서 `card_bnft.rule_select_cd`(`EXCLUSIVE_BY_SCOPE`, `PRIORITY`, `MAX_BENEFIT_VALUE`)와 원문에 명시된 `rule_priority`로 겹침 해소(근거 없으면 모호성 오류) → ④ 규칙의 방법 코드로 **한 거래의 후보 보상량** 산출 → ⑤ 연결된 개별·공유 풀의 활성 한도 tier를 모두 조회해 남은 잔량으로 제한 → ⑥ `card_bnft_rel`의 높은 혜택 우선·배타·소진 후 대체 적용. 이 순서는 계산 계약이며 실제 고객별 잔량·거래 입력이 없으면 **정책만 조회**할 수 있다. 한도 소진 후 대체는 소진 전 부분 적용과 소진 후 추가 거래의 처리 문구를 원문별로 검증해야 하며, C04는 `소진 후 발생하는 추가 매출`이라고 되어 있다(20종 보고서 C04 p4).

## 4. 정형 컬럼·행·JSONB 경계와 검증 계약

| 정보 | 위치와 원칙 |
|---|---|
| 상품·문서·혜택·대상·조건·규칙·한도 풀 ID | 정형 키·관계 행. JSON 안에 상대 ID 문자열만 두지 않음 |
| 자주 비교하는 비율·정액·기준금액·한도 | 규칙 `value_num/basis_amt`, 조건 `cond_min/max_amt`, 한도 tier `limit_num`의 numeric. 단위 코드 필수 |
| 새 가맹점, 새 실적 구간, 새 한도, 새 조건 조합 | 대상·규칙·조건·식·tier·연결 **행** 추가 |
| 가변 계산 파라미터 | 규칙 `calc_params jsonb`; 방법 코드·버전의 스키마와 Python validator가 검사 |
| 가변 술어 파라미터 | 조건 `cond_rule_json jsonb`; `predicate_method_cd`(제안)·버전별 스키마로 검사. 범주 `cond_type_cd`는 SPEND_REQ/USAGE_REQ/BNFT_EXCL 등 기존 넓은 코드 유지 |
| 원문·추출 | 기존 페이지→청크→후보→확정 근거. 새 규칙/풀/관계에도 문서·청크·승인 후보 키와 원문 위치 필요 |

예시 방법 계약(실제 DDL/코드 아님):

| `method_cd` | 필수 정형값 | 필수/허용 JSON 키 | 검증·실행 |
|---|---|---|---|
| `PERCENT_OF_TXN` v1 | `value_num` 0~100, unit=PERCENT, payout unit | `{}` 또는 반올림 코드 | 결제대상 금액×비율; 한도는 별도 풀 |
| `FIXED_PER_TXN` v1 | `value_num>=0`, unit=KRW | `{}` | 건당 정액 |
| `UNITS_PER_AMOUNT` v1 | `value_num>0`, `basis_amt>0`, payout=UNIMILE 등 | `rounding_cd`(FLOOR/CEIL 등) | C10의 1,500원당 45마일처럼 단위/반올림 명시 |
| `MULTIPLY_EXTERNAL_POINTS` v1 | `value_num=2`, unit=MULTIPLIER, payout=KRW | `input_metric_cd='CJONE_BASE_POINTS'`, `exclude_bonus=true` | 외부 기본 적립 포인트가 있어야 산출. 행사 추가 포인트 제외 |
| 술어 `EVERY_MONTH_MIN_SPEND` v1 | `cond_min_amt=100000`, basis=ROLLING_MONTHS | `window_months=3`, `month_basis_cd='APPROVAL'` | C08처럼 최근 3개월 **각각** 검사 |
| 술어 `MONTH_IN` v1 | 정형 월/기간 코드 | `months:[2,3,8,9]`, `month_basis_cd='ACQUISITION'` | C03 매입월 기준; 1~12 정수·중복 금지 |

`card_method_catalog.param_schema`에 필수 키·타입·범위·추가 키 허용 여부·단위/결과 단위·스키마 버전을 기록한다. 승인 시 Python의 JSON Schema/코드별 validator와 SQL의 `jsonb_typeof`, `?`/`@>`·숫자형/단위 검사로 이중 검증한다. 방법 코드는 정적 CHECK 열거보다 **카탈로그 참조와 승인 게이트**를 사용한다. 새 코드 INSERT만으로 정책 저장은 가능하지만 Python 핸들러가 미배포되면 `UNEXECUTABLE`로 두고 **확정 계산 가능** 상태로 승격하지 않는다. 문자열을 SQL/Python 코드로 실행하지 않는다. 정책 표현 가능성과 거래별 계산 실행 가능은 별개다.

술어 JSONB 예시는 `{"predicate_method_cd":"MONTH_IN","months":[2,3,8,9],"month_basis_cd":"ACQUISITION"}`(C03)와 `{"predicate_method_cd":"EVERY_MONTH_MIN_SPEND","window_months":3,"month_basis_cd":"APPROVAL"}`(C08)이다. C08의 최소 10만 원은 중복 JSON 숫자가 아닌 `card_cond.cond_min_amt`가 기준이다. JSON의 방법 코드는 `card_method_catalog`의 술어 행·버전과 일치해야 한다.

조건식은 DNF로 제한한다: **한 `branch_no`의 atom은 AND, 서로 다른 branch는 OR, `negate_yn=true`는 NOT**이다. 예를 들어 `전월 30만 AND 자동이체`는 같은 branch에 두 atom, `공식 홈페이지 OR 공식 앱`은 두 branch다. `대상 매장 AND NOT 대형시설 입점`도 같은 branch에 NOT atom을 둔다. 중첩된 임의 식을 JSON 문자열로 허용하지 않고, DNF로 풀기 어려운 복합식이 실제 나오면 식 모델을 재검토한다. `expr_id`가 NULL이면 자동 무조건 적용이 아니며, 규칙/한도 tier의 검증 상태가 `VERIFIED_UNCONDITIONAL`일 때만 참이다.

## 5. 필수 사례 4종의 관계형 샘플 행

다음은 **실제 PDF에서 확인한 값 + 가상 식별자**를 섞은 논리 샘플이다. `p1` 등은 앞선 20종 보고서의 원문 쪽. 표에 없는 감사·후보·오프셋 컬럼은 실제 적재 시 채워야 하며 아래 행은 INSERT 문이 아니다. `card_bnft_rule`의 `value_num`은 항상 출력값의 유일한 원천이다.

원문 파일은 C05 `credit/신용_토스뱅크하나카드Wide_상품설명서(공식PDF)_15024_20250703.pdf`, C04 `credit/신용_JADEClassic_상품설명서(공식PDF)_14955_20260609.pdf`, D05 `debit/체크_달달하나체크카드_상품설명서(공식PDF,URL추정확인)_15114_20260306.pdf`, D10 `debit/체크_CJONE체크카드_상품설명서(공식PDF,URL추정확인)_03687_20260128.pdf`다. D05·D10의 파일명에 있는 출처 확인 표시는 **아직 해소되지 않은 상태**다. 본 문서는 앞선 보고서의 페이지별 검증 결과를 재사용한다.

### A. C05 토스뱅크 하나카드 Wide (PDF p1)

| `card_bnft_rule` | `(R-WIDE-1,B-WIDE,E-LOW,PERCENT_OF_TXN,value_num=1,unit=PERCENT,payout=KRW)`; `(R-WIDE-2,B-WIDE,E-HIGH,PERCENT_OF_TXN,value_num=2,unit=PERCENT,payout=KRW)` |

40만 원은 하한 포함, 상한 미포함이다. 신규 실적 구간·가맹점은 `cond`/`expr`/`rule`/`target` 행만 추가한다. Python의 `PERCENT_OF_TXN` 계산기는 그대로다. Neo4j는 `Benefit→Rule(1%,2%)→Condition(구간)`, 두 Rule→Target, 두 Rule→동일 LimitPool이다.

대상별 1.5/1.2%를 target 행이나 condition 행에 복제하지 않는다. 특별 적립 월 통합 10만은 같은 풀을 **두 규칙이 함께 소진**한다. 소진 후 **추가 매출**에 기본 1% 적용은 혜택 관계다. 새로운 특별 적립 가맹점은 대상 행과 해당 규칙 연결 행만 추가한다. Python은 겹친 특별 규칙의 원문상 최대 보상 선택과 소진 후 대체를 구현해야 한다. Neo4j는 두 `Rule→LimitPool`과 `SpecialBenefit→BaseBenefit` 관계를 만든다.

### C. D05 달달 하나 체크카드 (PDF p1)

| 테이블 | 가상 키·행의 핵심 값 |
|---|---|
| `card_bnft`·대상 | `(B-DAL-SHOP,POINT)`·`T-DAL-DEPT(백화점)`, `T-DAL-CONV(편의점)`; `(B-DAL-DELIVERY,POINT)`·`T-DAL-DELIVERY(배달의민족·요기요)`; 다른 교통·커피·생활·구독 영역도 별도 혜택 |
| `card_bnft_rule`·대상 링크 | `(R-DAL-SHOP-DEPT,5%,T-DAL-DEPT)`, `(R-DAL-SHOP-CONV,5%,T-DAL-CONV)`, `(R-DAL-DELIVERY,5%,T-DAL-DELIVERY)` — 모두 `PERCENT_OF_TXN`, payout=HANAMONEY. 같은 비율이라도 **대상별 제외가 달라** 규칙이 갈림 |
| `card_cond`·식 | `(K-30,[300000,700000))`, `(K-70,[700000,1000000))`, `(K-100,[1000000,∞))`; 백화점 규칙식에 `NOT K-RENTAL_SHOP`, 딜리버리 규칙식에 `K-OFFICIAL_WEB OR K-OFFICIAL_APP` 등 원문 조건 적용. 구간식은 아래 한도 tier에 연결 |

| `card_limit_tier` | `P-DAL-SHOP`: K-30/70/100 조건식에 2000/4000/6000; `P-DAL-ALL`: 같은 구간식에 10000/20000/30000 |
| `card_bnft_rule_pool` | 쇼핑 규칙 2개→`P-DAL-SHOP` **및** `P-DAL-ALL`; 딜리버리 규칙→`P-DAL-ALL` 및 자체 영역 한도 풀(원문 표 기준) |

한 결제는 해당 영역 풀과 카드 전체 풀 **둘 다** 소진한다. 후보 보상은 남은 두 한도의 최소값으로 제한한다. `P-DAL-SHOP` 2천과 다른 영역의 2천은 같은 액수라도 같은 풀이 아니다. 대상별 결제 채널·제외는 규칙식에 귀속되므로 대상 행에 JSON 관계 ID를 넣지 않는다. 새 영역은 혜택·대상·규칙·영역 풀·공유 풀 연결 행을 추가한다. Python에는 기존 PERCENT 계산기와 복수 풀 차감 로직이 필요하다. Neo4j에서는 여러 Rule→영역 Pool 및 같은 카드 전체 Pool 경로가 남는다.

## 6. 공유 한도와 혜택 관계: 두 대안의 실제 행 비교

| 비교 | `card_cond` + `limit_pool_key` | 독립 `card_limit_pool` + `card_limit_tier` **선택** |
|---|---|---|
| D05 쇼핑 2/4/6천 + 전체 1/2/3만 | LIMIT 행 6개에 `SHOP`/`ALL` 문자열 키, 기간·단위·구성원을 행마다 반복. 공유 구성원은 `card_bnft_cond`로 추론 | 풀 2행과 tier 각 3행. `card_bnft_rule_pool`이 실제 소비 규칙의 범위를 명시 |
| C04 특별 적립 10만 + 기본 1% | LIMIT 행 1개와 여러 혜택 링크. 기본 적립까지 잘못 연결되면 오적용 | 특별 규칙만 풀에 연결. 기본 규칙에는 연결 없음. 소진 후 기본은 별도 `card_bnft_rel` |
| 구간·기간/소진 | 같은 키의 조건마다 `MONTH/HANAMONEY`가 불일치할 수 있고 소진 단위를 식별하기 어려움 | 풀 키가 누적 원장/잔량 조회의 단위, tier는 활성 한도값. **실제 잔량은 거래·집계 데이터에서 계산**하며 정책 tier에 잔량 저장 안 함 |
| 독립 한도 구분 | 같은 숫자라도 키가 다르면 구분 가능하나 문자열 계약에 의존 | 별도 풀 ID로 구분하고 기간·단위·집계 키를 한곳에 정의 |

독립 풀을 **최종 선택**한다. 이전 20종 보고서의 `limit_pool_key` 필수·독립 풀 보류 판단을 이 문서에서 **대체**한다. 이유는 D05의 영역+전체 이중 소진과 C03의 구간×매입월, C04의 소진 후 대체가 모두 풀 정체성·구성원·잔량 참조를 요구하기 때문이다. `card_cond`의 LIMIT는 기존 자료 호환으로 유지하되 신규 확정 한도의 권위 있는 수치는 `card_limit_tier.limit_num`이다. 숫자만 같은 조건을 같은 풀로 병합하지 않는다.

`card_bnft_rel`도 채택한다. 현재 `card_bnft_cond`는 Benefit–Condition이고 Benefit–Benefit은 없다. `MUTUALLY_EXCLUSIVE`는 방향 없는 관계라 ID 정렬·중복 금지, `FALLBACK_AFTER_CAP`/`OVERRIDES`는 방향과 `trigger_pool_id`·근거가 필수다. 그래프 변환 전 SQL에서 자기 참조·대체 순환·존재하지 않는 풀·충돌하는 관계를 거부한다. 같은 혜택 안에서 규칙이 겹치면 `card_bnft.rule_select_cd`에 선언된 `PRIORITY` 또는 `MAX_BENEFIT_VALUE`를 사용한다. 원문에 우선 규칙이 없으면 임의 우선순위를 만들지 않는다.

## 7. SQL 조회·정합성 검증 예시

아래는 **제안 스키마의 읽기 전용 설계 예시**이며 현재 DB에서는 실행할 수 없다. `:doc_id`, `:benefit_id` 등은 애플리케이션 바인딩 값이다. 정책 행이 존재한다고 실제 거래 입력·제휴 포인트·월 사용 잔량이 존재하는 것은 아니다.

```sql
-- C05: 한 거래의 전월 실적에 맞는 규칙의 단일 비율과 월 한도 정책 찾기.
-- 이 예시는 각 C05 구간식이 원자 조건 1개인 구조에 한정한다.
SELECT r.rule_id, r.calc_method_cd, r.value_num AS percent,
       p.pool_id, lt.limit_num AS monthly_cap_krw
FROM db_pipeline.card_bnft_rule r
JOIN db_pipeline.card_cond_expr_atom a
  ON (a.card_doc_id,a.expr_id)=(r.card_doc_id,r.expr_id)
JOIN db_pipeline.card_cond c
  ON (c.card_doc_id,c.card_cond_id)=(a.card_doc_id,a.card_cond_id)
JOIN db_pipeline.card_bnft_rule_pool rp
  ON (rp.card_doc_id,rp.rule_id)=(r.card_doc_id,r.rule_id)
JOIN db_pipeline.card_limit_pool p
  ON (p.card_doc_id,p.pool_id)=(rp.card_doc_id,rp.pool_id)
JOIN db_pipeline.card_limit_tier lt
  ON (lt.card_doc_id,lt.pool_id)=(p.card_doc_id,p.pool_id)
WHERE r.card_doc_id=:doc_id AND r.card_bnft_id=:benefit_id
  AND c.cond_basis_cd='PREV_MONTH_SPEND'
  AND :prev_spend >= c.cond_min_amt
  AND (c.cond_max_amt IS NULL OR :prev_spend<c.cond_max_amt)
  AND lt.expr_id IS NULL AND lt.predicate_state_cd='VERIFIED_UNCONDITIONAL';
-- 기대: 399999→1%, 400000→2%, 두 경우 모두 월 한도 100000원.
```

```sql
-- C04: 대상별 규칙값·공유 한도·기본 혜택 대체 관계의 정책 조회.
SELECT r.rule_id, t.target_id, r.value_num AS percent,
       p.pool_id, lt.limit_num AS monthly_hanamoney,
       rel.rel_type_cd, rel.to_bnft_id
FROM db_pipeline.card_bnft_rule r
JOIN db_pipeline.card_bnft_rule_target rt
  ON (rt.card_doc_id,rt.rule_id)=(r.card_doc_id,r.rule_id)
JOIN db_pipeline.card_bnft_target t
  ON (t.card_doc_id,t.target_id)=(rt.card_doc_id,rt.target_id)
JOIN db_pipeline.card_bnft_rule_pool rp
  ON (rp.card_doc_id,rp.rule_id)=(r.card_doc_id,r.rule_id)
JOIN db_pipeline.card_limit_pool p
  ON (p.card_doc_id,p.pool_id)=(rp.card_doc_id,rp.pool_id)
JOIN db_pipeline.card_limit_tier lt
  ON (lt.card_doc_id,lt.pool_id)=(p.card_doc_id,p.pool_id)
LEFT JOIN db_pipeline.card_bnft_rel rel
  ON (rel.card_doc_id,rel.from_bnft_id)=(r.card_doc_id,r.card_bnft_id)
 AND rel.rel_type_cd='FALLBACK_AFTER_CAP'
WHERE r.card_doc_id=:doc_id AND r.card_bnft_id=:special_benefit_id
  AND t.target_id=:target_id AND p.cap_unit_cd='HANAMONEY';
-- 대상에 따라 1.5% 또는 1.2%, 동일 100000 하나머니 풀과 기본 혜택 ID 반환.
```

```sql
-- D05: 선택된 쇼핑 규칙이 소비하는 서로 다른 두 풀의 활성 한도 확인.
-- tier 식의 실적 atom 1개라는 샘플 전제. 다중 AND/OR는 검증된 식 평가기를 사용.
SELECT r.rule_id, p.pool_id, p.pool_scope_cd, lt.limit_num
FROM db_pipeline.card_bnft_rule r
JOIN db_pipeline.card_bnft_rule_pool rp
  ON (rp.card_doc_id,rp.rule_id)=(r.card_doc_id,r.rule_id)
JOIN db_pipeline.card_limit_pool p
  ON (p.card_doc_id,p.pool_id)=(rp.card_doc_id,rp.pool_id)
JOIN db_pipeline.card_limit_tier lt
  ON (lt.card_doc_id,lt.pool_id)=(p.card_doc_id,p.pool_id)
JOIN db_pipeline.card_cond_expr_atom a
  ON (a.card_doc_id,a.expr_id)=(lt.card_doc_id,lt.expr_id)
JOIN db_pipeline.card_cond c
  ON (c.card_doc_id,c.card_cond_id)=(a.card_doc_id,a.card_cond_id)
WHERE r.card_doc_id=:doc_id AND r.rule_id=:shop_rule_id
  AND :prev_spend>=c.cond_min_amt
  AND (c.cond_max_amt IS NULL OR :prev_spend<c.cond_max_amt)
ORDER BY p.pool_id;
-- 30만~70만 예: SHOP 2000 + ALL 10000, 두 행을 모두 반환.
```

```sql
-- D10: 외부 포인트가 없어도 계산 정책은 단일 규칙 행으로 조회 가능.
SELECT r.rule_id, r.calc_method_cd, r.method_ver, r.value_num AS multiplier,
       r.calc_params, p.pool_id, lt.limit_num AS monthly_cap_krw
FROM db_pipeline.card_bnft_rule r

  ON (p.card_doc_id,p.pool_id)=(rp.card_doc_id,rp.pool_id)

  ON (lt.card_doc_id,lt.pool_id)=(p.card_doc_id,p.pool_id)
WHERE r.card_doc_id=:doc_id AND r.card_bnft_id=:benefit_id
  AND r.calc_method_cd='MULTIPLY_EXTERNAL_POINTS';
-- 2배·최대 10000원은 조회되지만 외부 CJ ONE 기본 포인트·월 잔량이 없으면 결과액은 미산출.
```

새로 승인할 규칙에서 기존 수치 컬럼이 동시에 채워지는지 확인하는 게이트 예시다. 과거 데이터 전체에 소급 적용하지 않는다.

```sql
SELECT r.card_doc_id, r.rule_id, 'BENEFIT_LEGACY_VALUE' AS issue
FROM db_pipeline.card_bnft_rule r
JOIN db_pipeline.card_bnft b
  ON (b.card_doc_id,b.card_bnft_id)=(r.card_doc_id,r.card_bnft_id)
WHERE b.bnft_rate IS NOT NULL OR b.bnft_amt IS NOT NULL
UNION ALL
SELECT DISTINCT r.card_doc_id, r.rule_id, 'CONDITION_LEGACY_OUTPUT' AS issue
FROM db_pipeline.card_bnft_rule r
JOIN db_pipeline.card_cond_expr_atom a
  ON (a.card_doc_id,a.expr_id)=(r.card_doc_id,r.expr_id)
JOIN db_pipeline.card_cond c
  ON (c.card_doc_id,c.card_cond_id)=(a.card_doc_id,a.card_cond_id)
WHERE c.cond_rate IS NOT NULL OR c.cond_amt IS NOT NULL
   OR c.cond_limit_amt IS NOT NULL OR c.cond_limit_cnt IS NOT NULL;
```

SQL 게이트는 (1) `card_bnft_rule`의 타입·단위·방법별 필수 필드, (2) 한 혜택+대상+**실효 기간**에서 규칙식의 구간 겹침/누락, (3) 풀 tier 식의 구간·월 집합 겹침/누락, (4) `card_bnft_rule_pool`의 풀 문서/단위 일치, (5) 혜택·대상·조건·식·관계의 고아/문서판 불일치, (6) 기존 `card_bnft_cond`와 규칙식 투영 불일치, (7) 근거 쪽·청크/후보 승인 상태를 검사한다. 기존처럼 `card_cond.card_bnft_id`만으로 구간을 비교하면 SHARED 원자와 대상별 규칙을 놓치므로 **rule_target × expression × 활성 기간 × pool** 단위로 비교해야 한다. 겹침의 SQL 후보만으로 실제 오류를 단정하지 않고 OR branch·NOT·월 집합의 식 평가까지 확인한다.

## 8. 새 혜택·계산 방식의 DDL 변경 여부

| 변화 | 정책 데이터 변경 | Python 변경 | ALTER TABLE? |
|---|---|---|---|
| 가맹점·대상 추가 | target + rule_target 행 | 기존 대상 매칭기 사용 | 없음 |
| 고정/대상별/구간별 비율·금액 변경 | 새 문서판의 rule·expr·target 연결 행 | 기존 PERCENT/FIXED 사용 | 없음 |
| 건/월/연 한도, 공유 풀, 실적 구간 추가 | pool/tier/expr/rule_pool 행 | 기존 풀 집계기 사용 | 없음 |
| 자동이체 AND 공식 앱, OR/NOT 조합 추가 | 조건 atom·expr branch 행 | 기존 술어라면 없음 | 없음 |
| 새 제휴 포인트 배수 같은 계산 방식 | catalog 코드·버전/JSON 계약 + rule 행 | **새 승인 핸들러·검증기 필요** | 없음 |
| 새로운 업무 개체/관계 자체 | 모델 검토 후 테이블 가능 | 해당 처리 구현 | 경우에 따라 필요 |

`INSERT만으로 확장`은 **DDL 수행 이후 운영 시나리오**를 뜻한다. 이번 작업에서 INSERT를 실행했다는 의미가 아니다. 새 방법 코드의 Python 핸들러가 없거나 외부 입력이 없으면 저장·조회는 가능해도 계산 결과는 보류된다. Neo4j에서는 Benefit→Rule→Target/ConditionExpression/LimitPool와 Benefit→BenefitRelation을 그대로 변환하고 각 노드/관계에 `card_doc_id`·근거 청크·방법 버전을 남긴다. 카드별 값·구간 검증은 SQL이 간단하고, 여러 혜택의 공유 풀·우선·대체 영향 탐색은 Neo4j가 유용하다.

## 9. DDL 작업 순서와 보류

| 분류 | 정확한 대상·결정 |
|---|---|
| **유지** | 기존 11개 테이블, 특히 문서·후보 추적과 `card_bnft_cond` 관계. 물리 FK를 새로 강제하지 않음 |
| **컬럼 변경/추가** | `card_bnft`에 전달 방식·검증된 실적 부재 상태·규칙 선택 정책; `card_cond`에 술어 방법 코드/버전, CARD/BENEFIT/SHARED 출처 범위 규약. 기존 `cond_basis_cd`/유형의 **고정 CHECK가 새 코드마다 DDL을 요구하지 않도록** 코드 카탈로그 또는 넓은 범주/방법 코드로 1회 전환. `card_bnft_rule`의 공통 numeric/단위/파라미터는 신규 테이블 정의에 포함 |
| **신규 테이블** | `card_method_catalog`, `card_bnft_target`, `card_cond_expr`, `card_cond_expr_atom`, `card_bnft_rule`, `card_bnft_rule_target`, `card_limit_pool`, `card_limit_tier`, `card_bnft_rule_pool`, `card_bnft_rel`의 논리 구조. 우선 catalog→target/expr→rule→pool/tier→관계 순으로 DDL 초안·이행 SQL 설계 |
| **삭제·통합 검토** | `card_bnft.bnft_rate/amt`, `card_cond.cond_rate/amt/limit_amt/limit_cnt`, `card_cond.card_bnft_id`는 **새 데이터에서 비권위/NULL**, 기존 데이터 이행·조회 코드 점검 후 폐기 여부 결정. `card_bnft_cond`는 규칙식 투영으로 검증·호환 유지; 물리 테이블을 뷰로 바꿀지는 별도 판단 |
| **실제 적재 후 결정** | 상품 마스터의 권위 있는 위치(현재 접속 DB의 `card_benefit.card_product` 없음), 복잡한 식의 DNF 한계, 규칙·풀의 고객별 사용량 집계 원장, C09/D10 외부 입력 공급·계산기 세부, 과거 후보 1:1 UNIQUE의 분할 전략 |

**DDL 착수 순서의 첫 단계는** 적용값 단일 원천·코드 계약·기존 컬럼 이행 정책을 확정하는 것이다. 그다음 위 신규 테이블과 논리 정합성 SELECT를 설계하고, 4개 필수 PDF 사례로 샘플 적재 시험을 한 뒤 20종으로 확대한다. 본 문서는 실제 DDL·DB·기존 소스나 보고서를 변경하지 않았다.
