# 2차 팀 프로젝트 — 신규 GraphRAG 주제 선정 규칙

> 기준일: 2026-10-28  
> 상태: **주제 미확정 / 후보 조사 진행 중**  
> 목적: 팀원들이 같은 기준으로 후보를 조사하고, 근거를 비교해 주제를 결정하기 위한 문서

## 0. 공식 가이드와 팀 선정 규칙의 적용 순서

공식 「사내 기술 문서 개체 추출기」 가이드의 데이터 선정 안내, 필수 과제와 산출물을 먼저 충족한다. 이 문서의 신규 주제·데이터 연결·차별성·협업 기준은 팀이 추가한 선정 규칙이다. 팀 규칙은 공식 요구사항이나 공식 평가 배점이 아니다.

- **공식 데이터 기준:** 기술 백서·시스템 매뉴얼 등에서 개체와 관계를 확인한다. 실제 사내 문서는 이용·공유가 허용된 자료를 사용하며, 확보가 어려우면 공개 기술 백서·매뉴얼의 활용 범위를 강사님과 협의한다.
- **공식 필수 흐름:** 문서 확보 → 전처리 → LLM 개체·관계 자동 추출 → 동일 개체 정규화·스키마 매핑 → Neo4j 적재 → Cypher 조회·시각화 → 원문 대조 검증.
- **공식 필수 산출물:** ① 실제 LLM 추출 프롬프트 및 코드, ② Neo4j 기반 지식 그래프 시각화 결과물 및 스키마. 실행 안내와 정규화·검증 기록을 연결한다.
- **팀 추가 조건:** 무료 공식 원천의 실제 확보·추출, 서로 다른 문서 또는 레코드 간 검증 가능한 연결, 사용자 문제와 비교 근거를 확인한다. 공시·규정·공공데이터가 과제의 기술 문서 범위에 해당하는지는 강사님 확인 전까지 보류한다.
- **기준 출처:** [MLE 2기 2단위 프로젝트 가이드](https://app.notion.com/p/playdatacademy/MLE-2-2-4e3d943bcac2822fa805014402e4d338?source=copy_link)의 사용자 제공 본문. 페이지의 현재 내용은 이 문서 수정에서 별도 열람하지 않았다.

## 1. 주제 선정 목표

2차 팀 프로젝트에서 **기존 구현의 재포장이 아닌 새로운 문제 영역**을 찾는다. 주제 이름의 신선함보다 다음을 우선한다.

1. 실제 사용자가 겪는 문제인가?
2. 일반 ChatGPT 및 기존 서비스와 비교해 설득력 있는 차별성이 있는가?
3. **관계 탐색**이 핵심 기능에 기여하여 GraphRAG를 쓸 이유가 명확한가?
4. **무료로 접근 가능한 공식 원문(PDF·공시·규정·표준) 또는 공공데이터를 실제로 내려받고 추출할 수 있는가?**
5. 원천자료에 **공통 식별자 또는 문서 간 관계를 검증할 근거**가 있는가?
6. 팀이 구현·시연·검증까지 완성할 수 있는 범위인가?

## 2. 이미 확정한 결정 (변경 전제로 논의하지 않음)

- **기존 카드 혜택 주제는 탈락 확정이다.** 이전에 추진했던 「미래 생활계획 기반 대화형 카드 혜택 제약 진단 및 행동 변경안 분석 GraphRAG」는 경쟁 서비스와 일반 ChatGPT 기능을 검토한 결과 차별성이 부족하다고 판단했다. 해당 주제를 살리거나 이름만 바꿔 다시 제안하지 않는다.
- **완전히 새로운 GraphRAG 프로젝트 소재를 찾는다.** 기존 개발물의 공통 구조·학습 경험은 재사용할 수 있으나, 신규 도메인과 모델은 별도로 설계한다.
- **GraphRAG라는 기술명 자체는 차별점이 아니다.** 실제 사용자 가치와 검증 가능한 근거가 필요하다.
- **기존 레시피 프로젝트는 참고 구현체다.** 새로운 주제의 업무 코드와 데이터 모델을 기존 레시피 코드에 섞지 않는다.
- **원본 근거를 확보할 수 있는 공식 데이터 중심으로 주제를 선정한다.** 무료 공개된 원문 PDF·공시·규정·표준문서 또는 공공데이터를 실제로 수집·추출할 수 있고, 출처와 관계 근거를 추적할 수 있어야 한다. PDF는 우선 검토 형식이지만, 모든 자료가 PDF여야 하는 것은 아니다.

## 3. 1차 탈락 기준

다음에 해당하면 원칙적으로 후보에서 제외한다. 근거가 아직 부족한 항목은 '추가 검증'으로 구분한다.

| 기준 | 탈락을 검토하는 상황 |
| --- | --- |
| 차별성 부족 | 이미 있는 서비스와 사용자 경험·결과물이 사실상 같다. |
| 일반 ChatGPT로 대체 가능 | 별도 관계 데이터와 근거 검증 없이 프롬프트만으로 핵심 결과를 충분히 재현할 수 있다. |
| 그래프 필요성 부족 | 일반 검색, 단순 SQL 조회, 벡터 검색 또는 일반 RAG만으로 충분하고 노드·관계 탐색이 형식적이다. |
| 데이터 확보 불가능 | 공식 원문 또는 공공데이터를 무료로 실제 다운로드·추출할 수 없거나, 활용 조건을 확인할 수 없다. |
| 데이터 연결 근거 없음 | 문서·레코드 사이에 공통 식별자, 명시적 참조 관계 또는 검증 가능한 연결 근거가 없다. |
| 구현 범위 과도 | 수집·전처리·외부 연동·검증 부담 때문에 프로젝트 기간에 완성하기 어렵다. |
| 검증 불가능 | 예상 답변, 근거 경로, 성공·실패 기준을 정의하기 어렵다. |

> **중요:** 아이디어 설명만으로 통과시키지 않는다. 관련 URL, 실제 질의 결과, 데이터 샘플, 그래프 모델 같은 **검증 자료**를 확보한다.

## 4. 후보별 평가 항목

| 평가 항목 | 핵심 질문 | 반드시 확보할 근거 |
| --- | --- | --- |
| 문제 가치 | 누가 어떤 상황에서 무엇을 해결하는가? | 대상 사용자, 입력·출력 사례 |
| 차별성 | ChatGPT와 경쟁 서비스 대비 어떤 점이 실질적으로 다른가? | 경쟁 서비스 URL, 직접 비교한 질문·결과 |
| GraphRAG 적합성 | 어떤 노드·관계를 어떻게 여러 단계 탐색하는가? | 노드/관계 초안, 핵심 탐색 경로 |
| 데이터 실현성 | 공식 원문·공공데이터를 무료로 실제 다운로드·추출할 수 있는가? | 제공기관, 원문 URL, PDF/API/파일 형식, 비용·이용 조건, 실제 샘플 |
| 데이터 연결 가능성 | 서로 다른 문서·레코드를 어떤 근거로 연결할 수 있는가? | 식별자/참조번호/조문번호, 연결된 샘플 1건 이상 |
| 구현 가능성 | 작은 MVP를 끝까지 구현할 수 있는가? | 필수 기능, 제외 기능, 위험 요소 |
| 검증 가능성 | 답과 근거가 맞는지 어떻게 판단하는가? | 시험 질문, 기대 결과, 검증 기준 |

### GraphRAG 적합성 체크

- 단순히 그래프 DB에 데이터를 넣는 것이 아니라 **관계 경로를 따라야** 의미 있는 답을 얻는가?
- 서로 다른 개체 간 제약, 연결, 영향, 의존성 등을 탐색할 수 있는가?
- 결과와 함께 **사용한 데이터·노드·관계의 근거**를 제시할 수 있는가?
- 그래프 검색을 제거하면 답의 품질·설명 가능성에 뚜렷한 손실이 생기는가?

**모든 기능을 넣을 필요는 없다.** 해당 주제에서 그래프가 필요한 핵심 이유를 구체적인 질의와 예시로 증명하면 된다. 또한 GraphRAG를 구현할 때 **벡터 임베딩을 반드시 사용해야 하는 것은 아니다.** 핵심은 그래프 기반 검색과 근거 활용이 실제 문제 해결에 기여하는지다.

## 5. 공식 원천 데이터 확보 규칙 (주제 선정 전 필수 검증)

### 5-1. 우선 사용할 자료

**주제 선정의 출발점은 '데이터가 실제로 확보되는가'이다.** 다음 범주를 우선 탐색한다.

1. **정부·공공기관·공식 공시기관에서 공개한 원본 PDF:** 고시, 공고, 공시, 지침, 보고서, 규정, 표준문서 등. 웹 페이지에서 읽히는 것만으로는 부족하며 실제 파일 다운로드 및 텍스트·표 추출 여부까지 확인한다.
2. **공식 원문을 제공하는 다른 형식:** XML, HTML, TXT, XBRL, HWP 등. PDF가 없더라도 출처·내용·식별자를 추적할 수 있고 활용 가능한 원본이라면 허용한다.
3. **공공데이터포털/기관 공식 API·파일:** CSV, Excel, JSON, XML 등. 공시/규정/원문과의 연결 또는 데이터 간 참조 관계를 만들 수 있어야 한다.
4. **기업이 공개한 기술 백서·제품/운영/정비 매뉴얼:** 직접 문서 URL과 버전, 기술 문서로서의 과제 적합성, 이용·팀 공유·외부 LLM 전송 범위를 확인한다. 자료가 공개되어 있다는 사실만으로 활용 권한을 확정하지 않는다.

**공통 필수 조건:** (a) 무료 접근, (b) 공식·공개 출처, (c) 실제 다운로드 또는 API 추출 성공, (d) 프로젝트 활용·인용·재배포 조건 확인, (e) 출처 추적 가능, (f) **식별자 또는 검증 가능한 연결 근거** 확보. 단순히 목록 화면이 있다는 사실만으로는 데이터 확보를 완료했다고 보지 않는다.

> **중요:** '모든 데이터를 PDF로 받아야 한다'는 규칙이 아니다. **원문 PDF를 받을 수 있으면 우선 검토**하되, 공식 공시 원문이나 구조화된 공공데이터로 동일한 근거성과 연결성을 충족해도 된다. PDF 문서 자체가 공개되어 있어도 자동 수집·대량 다운로드·재배포는 별도 제한이 있을 수 있으므로 이용 조건을 확인한다.

### 5-2. 이전에 논의한 우선 조사 사이트 (확정 주제 아님)

| 조사 순서(당시 검토안) | 공식 사이트 | 살펴볼 데이터·관계 | 현재 검증 상태 |
| --- | --- | --- | --- |
| 1 | [OpenDART](https://opendart.fss.or.kr/) | 기업 공시, 회사·공시·보증/관계 데이터. 공시 원문과 기업 식별자·접수번호 확인 | 후보. 필요한 공시 유형·관계 연결 미검증 |

- 다른 분야의 공식 무료 데이터도 같은 조건을 충족하면 후보가 될 수 있다. 위 사이트만 사용하도록 제한하지 않는다.
- 참고: 식약처 데이터활용서비스는 XML/JSON 및 파일형 데이터를 안내하고, OpenDART는 원문 공시·API·XBRL 등을 제공한다. **개별 PDF 제공 여부는 데이터셋별로 별도 확인**한다.

### 5-3. 데이터 확보 검증 체크리스트

조사자는 후보 주제를 제시할 때 아래를 **실제 자료 기준**으로 확인한다.

- [ ] **공식 출처**: 기관명, 서비스명, 원문/데이터셋 URL, 확인 날짜를 기록했다.
- [ ] **무료 접근**: 별도 구매 없이 사용할 수 있으며, 계정/API 키 필요 여부·호출 제한을 확인했다.
- [ ] **실제 확보**: PDF 원본 파일 또는 공식 API/CSV/Excel/XML 등 샘플을 다운로드·호출해 봤다.
- [ ] **내용 추출**: PDF 텍스트·표 또는 API 주요 필드를 실제로 파싱할 수 있다. 스캔 PDF라면 OCR 난이도도 평가했다.
- [ ] **연결 근거**: 문서/레코드 간 공통 키(예: 품목제조보고번호, 입찰공고번호, 공시 접수번호), 조문 인용, 명시적 참조 등 **연결 가능한 실제 사례**가 있다.
- [ ] **출처 추적**: 검색 결과에 원본 URL, 문서명, 문서 버전/게시일, 페이지·조항·레코드 식별자 등을 제시할 수 있다.
- [ ] **이용 조건**: 비상업적·상업적 사용, 재배포/가공 가능 여부, 개인정보·저작권·API 정책을 확인했다.

**판정:** 다운로드·추출·연결 중 하나라도 확인하지 못했으면 **'추가 검증'**으로 남긴다. 자료를 구할 수 없거나 관계 근거 자체가 없다면 **탈락**을 검토한다.

### 5-4. 소규모 확인(PoC) 방법 — 운영 제안

1. 원본 문서/데이터 샘플 몇 건을 **합법적으로** 확보하고 파일명 또는 API 응답을 기록한다.
2. 핵심 식별자를 추출해 **노드–관계–노드**의 구체적 연결 사례를 작성한다. 단순 같은 단어 등장만으로 관계를 확정하지 않는다.
3. 서로 다른 자료를 연결한 질의 2~3개를 만들어 원문에서 사실 여부를 확인한다.
4. 결과에 원본 파일/공시/레코드의 URL 및 페이지·조항·식별자를 표시할 수 있는지 점검한다.
5. 일반 ChatGPT·일반 RAG와 같은 질문·근거를 기준으로 비교해 그래프 관계 탐색의 검증 가능한 가치를 판단한다. SQL이나 일반 RAG로 같은 답을 만들 가능성을 인정하고, 실제 비교 없이 그래프만 가능하거나 더 빠르고 정확하다고 주장하지 않는다.

이 순서는 팀의 실무적 확인 절차 **제안**이며, 문서 개수나 평가 점수를 필수 숫자로 강제하는 규칙은 아니다.

## 7. 팀 공통 선정 절차

1. **개별 조사:** 각자 후보 주제를 조사하여 개인 폴더에 기록한다.
2. **차별성 검증:** 비슷한 서비스와 일반 ChatGPT를 실제로 비교해 본다.
3. **공식 데이터 확보 검증:** 5장의 우선 사이트 등을 확인해 무료 원본 PDF 또는 공식 공시·공공데이터의 **실제 다운로드/추출**에 성공한다.
4. **자료 연결 검증:** 공통 식별자나 참조 근거로 최소 한 건의 문서/레코드 연결을 설명한다.
5. **그래프 모델 검증:** 핵심 노드·관계와 다단계 질의 사례를 제시한다.
6. **1차 탈락:** 3장의 기준을 근거로 확인하고 탈락 이유도 남긴다.
7. **후보 비교:** 남은 후보를 공통 비교표에서 나란히 평가한다.
8. **필요시 소규모 PoC:** 실제 샘플로 핵심 질의가 작동하는지 검증한다.
9. **최종 합의:** 선정 이유, 다른 후보를 제외한 이유, 첫 MVP의 범위와 위험을 기록한다.

## 8. 문서 및 저장소 운영 규칙

### 8-1. 자료조사 파일 보관 위치 (팀 공통 규칙)

조사한 Markdown 문서는 **조사자 이름 → 조사 날짜(`YYYY-MM-DD`) → 주제별 `.md` 파일** 순서로 보관한다.

- **로컬 기준 폴더:** `C:\myproject\workspace\mle-02-p2-team3\docs\자료조사`
- **Git 저장소 기준 상대 경로:** `docs/자료조사/<조사자 이름>/<YYYY-MM-DD>/<주제명>.md`
- 날짜 폴더명은 반드시 `2026-10-28`처럼 **연도 4자리-월 2자리-일 2자리** 형식으로 작성한다.
- 팀원마다 동일한 날짜 폴더를 각자의 이름 아래에 별도로 만든다.

| 조사자 | 구분에 사용하는 이메일/이름 | 자료조사 저장 위치 |
| --- | --- | --- |
| 김병주 | `darkping1980@gmail.com` | `docs/자료조사/김병주/YYYY-MM-DD/` |
| 이현근 | `이현근` (이메일 미지정) | `docs/자료조사/이현근/YYYY-MM-DD/` |

**2026년 10월 28일 작성 예시**

```text
mle-02-p2-team3/

    TEAM_START_HERE.md
    자료조사/

      최종_주제선정.md         # 주제 확정 후 생성
```

**저장 규칙**

1. 각 팀원은 **자신의 이름 폴더** 아래 조사한 날짜의 폴더를 만들고 Markdown 파일을 저장한다.
2. **조사 주제 하나당 Markdown 파일 하나**를 원칙으로 한다. 같은 날 여러 주제를 조사하면 같은 날짜 폴더에 각각 파일을 만든다.
3. 새로운 날짜에 새롭게 조사한 자료는 해당 날짜 폴더에 저장한다. **기존 조사 문서의 단순 수정**은 원본 파일을 수정하고, 필요하면 문서 내부에 수정일을 기록하여 중복 사본을 만들지 않는다.
4. `darkping1980@gmail.com`은 **김병주 자료의 작성자 식별용 이메일**로 취급한다. 이현근 자료는 **이현근** 폴더에 넣으며, 이메일은 별도 확인 전까지 지정하지 않는다.
5. Git의 `user.email` 설정만으로 폴더가 자동 선택되지는 않는다. **작성자가 직접 위 경로에 파일을 생성·저장**해야 한다.
6. Windows 로컬 경로는 현재 작업 PC 기준 예시다. 다른 팀원 PC에서 상위 경로가 달라도 **저장소 내부의 `docs/자료조사/` 이하 구조**는 동일하게 유지한다.

### 8-2. 공통 문서 및 외부 자료 관리

- 개인별 날짜 폴더는 **초기 조사 및 검증 자료**를 위한 공간이다.
- `주제_선정_규칙.md`는 **공통 규칙**으로 `자료조사` 폴더 바로 아래에 둔다.
- 공통 비교표는 팀원이 같은 기준으로 의견을 모으는 용도다.
- 최종 선정 문서에는 **선정 이유뿐 아니라 탈락 사유**도 남긴다.
- 외부 자료는 **공식 원문 URL, 확인 날짜, 실제 다운로드/추출 여부, 데이터 간 연결 근거**를 기록하고 저작권·이용 조건을 확인한다.
- 원본 PDF나 API 응답을 저장소에 함께 커밋할지는 **용량·재배포 허용 여부**를 확인한 다음 결정한다. 배포가 불가하면 출처 URL과 재현 가능한 수집 절차만 기록한다.
- API 키, 비밀번호, 개인식별정보, 공개할 수 없는 원본 데이터는 커밋하지 않는다.

## 11. 후보 5개와 원문 검증 기준 — 팀 운영 규칙

- 비교 후보는 **최대 5개**다. 조건을 충족하는 후보가 부족하면 미검증 후보로 숫자를 채우지 않는다.
- 각 후보는 **대상 기업·제품/시스템 + 실제 기술 문서 + 추출할 관계 + 핵심 그래프 질문**으로 표현한다. 산업 분야는 제한하지 않는다.
- 후보별로 원문 트리플 **3개를 목표**로 확인한다. 각 트리플의 문서명·버전·페이지/절·문단 또는 표 행·원문 근거·관계 방향을 기록한다. 세 개는 팀 비교 목표이며 공식 필수 수치나 충분성 보장이 아니다.
- 표는 제목·열·행·단위·각주와 적용 조건을 함께 확인한다. 요청/응답, 예시/권고/금지, 적용 조건과 실제 상태를 구분한다. 같은 단어의 등장만으로 서로 다른 문서·레코드를 연결하지 않는다.
- 원문을 확인한 표기에서 동일 개체 통합 또는 다른 개체 분리 사례를 기록한다. 약어는 원문에서 동일 대상으로 확인할 때만 통합하고, 판단 근거가 부족하면 보류한다.
- 특정 자료의 과제 인정, 재배포·공유·외부 LLM 전송, API 비용·한도는 확인 전까지 미확인으로 기록한다. 이용이 허용된 범위에서만 사전 조사를 진행한다.

| 항목 | 미확인 | 확인 전, 접근·실행 실패 또는 답변 대기 |

| 후보 | 보류 / 추가 검증 | 유망하나 필수 사실이 미확인. 허용된 범위의 사전 조사 가능 |

## 12. 병목을 줄이는 조사·협업 방식 — 팀 운영 제안

1. **기준 공유:** 이 문서와 공식 가이드를 함께 읽고, document_id·chunk_id·entity_id와 후보 기록 형식을 합의한다.
2. **분담 조사:** 팀원이 서로 다른 후보를 담당해 각자 개인 폴더에 기록한다. 후보별 공식 원문 확보, 관계·정규화, 자료 간 연결, 이용 조건 확인은 독립적으로 진행한다.
3. **병목 분리:** 강사님 확인, 이용 조건, API 키 발급 등이 기다려지는 후보는 보류로 표시하고 다른 후보의 허용된 사전 조사를 계속한다. 확인 전 자료를 외부 LLM에 전송하지 않는다.
4. **공통 비교:** 취합 담당자 한 명이 조사 결과를 모아 비교표를 갱신한다. 공동 파일의 동시 수정을 줄이고, 각 후보의 근거·미확인·다음 조치를 유지한다.
5. **우선 후보의 작은 실행:** 허용된 대표 구간을 전처리해 LLM으로 추출하고 JSON 구조·유형·관계 방향·원문 근거 및 정규화 판단을 확인한다. 모델·입력량·호출 횟수·비용과 실패를 기록한다.
6. **전환 결정:** 한 문제가 30분 넘게 막히면 증상·시도·도움받을 지점을 공유한다. 30분 경과만으로 자동 탈락시키지 않고, 해결 가능성과 남은 필수 작업을 검토해 범위 축소 또는 예비 후보 전환을 결정한다.
7. **Git 협업:** main에 직접 push하지 않고 작업 브랜치·PR과 1명 이상의 리뷰를 사용한다. 서로 다른 후보 파일에 작업하고 공통 비교표의 담당자를 정한다. 기존 레시피 코드·데이터와 다른 팀원의 작업은 보존한다.

## 13. 실행·발표 상태 구분

- 웹에서 원문을 열람한 것은 실제 파일 다운로드, 파싱, LLM 자동 추출 또는 Neo4j 적재 성공을 뜻하지 않는다. 각 단계를 별도로 기록한다.
- 수동으로 정리한 트리플은 원문 검토 결과로 표시하며 LLM 자동 추출 성공으로 표현하지 않는다. 실행 전 그래프는 스키마 초안이다.
- 발표는 실제 확보한 원문 → 전처리 → 실제 LLM 결과 → 정규화 → Neo4j 조회·시각화 → 원문 대조의 대표 사례를 사용한다. 임의의 성공률이나 실행 결과를 만들지 않는다.
- 팀의 현재 계획은 2인·3일이며 실제 인원과 일정이 바뀌면 범위를 다시 조정한다. 확장 화면과 별도 검토 기능보다 필수 흐름의 완주를 우선한다.
