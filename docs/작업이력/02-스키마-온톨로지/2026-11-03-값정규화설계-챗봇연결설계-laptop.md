## Export 부착 제안 — 결정 대기

현재 export는 `Benefit`에서 `name`, `method`, `rate`, `amount`; `Condition`에서 `text`, `kind`, `min_amount`; `Limit`에서 `text`, `period`, `amount`, `unlimited`, `shared`를 `props` JSON에 보존한다. 다음 부착 방안을 검토한다.

| props 키 후보 | 값 / 위치 | 결정할 점 |
|---|---|---|
| `rate_normalized` | Benefit.rate를 분수율로 변환한 객체 (`value`, `unit`) | 비율 표기 단위와 값 타입을 고정할지 |
| `amount_normalized` | Benefit.amount의 금액 객체 (`value`, `unit`) | 조건성 접미사 포함 값을 명시적으로 구간으로 보관할지 |
| `rate_range_normalized` | 범위 율의 하한·상한 객체 | rate와 별도 키로 둘지 |
| `per_unit_normalized` | 단위당 값 객체 (`value`, `unit`, `per`) | Benefit.rate 안에 둘지 별도 키로 둘지 |
| `text_normalized` | Condition/Limit 텍스트에서 판독한 비교값·횟수 | 기존 `Condition.min_amount`, `Limit.amount`와 중복 저장할지 |

미해석 값은 raw 필드를 그대로 두고 `normalization_status`/사유를 추가하는 방안이 있다. 중첩 정규화 키는 현행 `props` JSONB 안에만 추가하면 테이블 열 추가는 필요하지 않을 것으로 보인다. 단, DB 제약 또는 생성 인덱스를 추가하기로 하면 `graph/schema.sql` 변경이 필요할 수 있다. 어떤 키도 아직 export에 연결하지 않았다.

## pf_ 그래프를 읽는 챗봇 흐름 — 결정 대기

현재 챗봇은 `graphrag.nodes(id, name, label, props)`와 `graphrag.edges(source, target, type)`를 사용한다. `rag.py`는 질문에서 엔티티를 선택하고 방향을 무시한 재귀 탐색으로 하위 그래프를 모은 뒤 LLM에 관계·속성 사실을 전달한다. `db.py`는 `DB_URL`로 연결하고 `llm.py`는 `ANTHROPIC_API_KEY` 및 선택적 `LLM_MODEL`을 사용한다. 출처 출력은 Document 노드 이름·summary 중심이다.

제안 흐름은 카드 식별 후 혜택 노드를 고르고, 구조화된 SQL로 관련 서브그래프 및 근거 위치를 읽고, 그 근거 범위 안에서 답을 작성하는 것이다.

| 단계 | 제안 작업 | 기존 graph/queries.sql 재사용성 | 남은 설계 / 노력 |
|---|---|---|---|
| 질문에서 카드·요구조건 추출 | 카드명과 의도(목록/조건 비교/한도 질의)를 분석 | 없음. 기존 챗봇의 엔티티 선택 방식은 재사용 가능 | 카드명이 동명이거나 빠진 경우의 선택 처리 / 중간 |
| 카드와 혜택 식별 | `OFFERS`를 따라 Benefit 및 이름 검색 | 첫 쿼리의 카드별 혜택·조건·한도·대상 조인이 재사용 후보 | 카드 이름 필드와 검색 인덱스 확인 / 중간 |
| 그래프 조회 | 조건·한도·대상·상호배타 관계를 함께 조회 | 첫 쿼리, shared-limit 쿼리, mutually-exclusive 쿼리, bounded traversal 쿼리 재사용 후보 | `Condition.min_amount` 또는 정규화 금액의 비교 필터 쿼리 부재. 정규화 rate/amount 필터 쿼리 부재 / 중간 |
| 근거 위치 조회 | 선택 노드와 관계에 연결된 `pf_evidence` 위치를 읽음 | Benefit node evidence 조회 쿼리는 재사용 가능 | edge evidence 조회 및 여러 노드/엣지 위치를 서브그래프 결과에 묶는 쿼리 보완 / 소 |
| 답변 및 출처 구성 | 혜택 값, 조건, 비교 결과와 문서 해시·쪽·위치를 반환 | 기존 근거 기반 답변 생성 흐름 일부 재사용 | Document 노드 출처 방식 대신 위치 링크·페이지 표시 규칙 결정 / 중간 |
| DB 연결 분리 | 기존 graphrag 연결과 pf_ 연결 중 선택 | 없음 | `DB_URL`은 현재 graphrag용. pf_ 접속 설정 이름 후보 `PF_DATABASE_URL` (이름만 제안, 값 취급 금지). 한 DB인지 별도 접속인지 결정 / 소 |

스키마 충돌: 기존 챗봇은 UUID 노드 ID와 `name`/`label`, `source`/`target`/`type` edge 열을 전제로 한다. pf_ 모델은 text ID, `node_type`, JSON `props`, `source_id`/`target_id`/`edge_type`이며 별도 `pf_evidence` 위치 테이블이 있다. 기존 RAG SQL을 테이블 상수만 바꿔 재사용하기 어렵다. 기존 `graphrag` 구조를 마이그레이션할지, 별도 pf_ repository/retriever를 둘지 결정이 필요하다.

## 직접 확인한 내용과 추론

**직접 확인:** 온톨로지의 Benefit.rate/amount는 raw string이고, Condition.min_amount와 Limit.amount는 선택 정수 필드다. export는 위 속성을 `props` JSON 객체에 기록한다. `queries.sql`에는 카드별 연결 조회, 노드 근거 위치, 상호배타, 공유 한도, 제한 홉 탐색 쿼리가 있다. 챗봇은 `graphrag` 스키마의 노드·엣지 형식과 `DB_URL`을 참조한다.

**추론:** `props`가 JSONB인 만큼 새 하위 키 추가만으로 테이블 변경을 피할 수 있다. 현행 챗봇 RAG는 pf_ 테이블과 열·근거 모델이 달라 별도 조회기가 필요할 가능성이 높다. 이 판단은 설계 제안이며 실제 연결·DB 접속으로 검증하지 않았다.

## 하지 않은 일

- export 연결, SQL/schema 변경, 챗봇 코드 수정 및 실제 데이터베이스 조회를 하지 않았다.
- 네트워크·LLM·DB 호출을 하지 않았다.
- 원문 문장이나 청크 텍스트를 문서·로그에 복사하지 않았다.
