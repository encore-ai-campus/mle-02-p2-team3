## 테이블 역할 및 대응

아래 대응은 직접 확인한 컬럼·코드·README 범위의 기능 비교다. 부분은 일부 필드나 개념이 그래프에 들어갈 수 있다는 뜻이며, 테이블 간 일대일 변환을 뜻하지 않는다. 완전 대응은 없다.

| 참고 명세 테이블 | 저장 내용 | `public.pf_*` 대응 |
|---|---|---|
| `card_doc` | 카드 문서의 식별자, 유형, 파일, 해시, 수집·상태 메타데이터 | 부분 — 문서 해시는 `pf_evidence`에서 참조하지만 문서 마스터는 없음 |
| `card_doc_page` | 문서 쪽별 추출 원문·길이·해시·추출기 정보 | 부분 — `pf_evidence`가 쪽 번호를 보유하나 쪽 원문은 없음 |
| `card_doc_chunk` | 쪽별 청크 원문·정제문·순서·분할 메타데이터 | 부분 — `pf_nodes.chunk_id`로 추적 단서를 보유하나 청크 레코드·원문은 없음 |
| `card_ai_run` | 모델·프롬프트·단계·상태·실행 시각 및 파라미터 | 부분 — `pf_load_runs`가 그래프 적재 단위와 모델·시각을 기록하나 프롬프트·호출 실행 로그는 아님 |
| `card_ai_call` | 청크별 AI 호출 입력 해시·응답·오류·토큰·지연시간 | 없음 |

| `card_product_doc` | 상품과 문서의 역할·적용성·승인 연결 | 부분 — 상품 Card와 혜택 Benefit 사이의 `OFFERS` 관계가 일부 연결 역할을 하지만 문서 연결은 없음 |
| `card_bnft` | 상품별 혜택, 규칙·조건·기간·검색용 임베딩 | 부분 — `pf_nodes`의 Benefit 및 `pf_edges`에 그래프 관계를 표현하나 컬럼·규칙 목록·임베딩 구조는 다름 |

| `card_common_bnft_apply` | 공통 혜택과 적용 상품의 연결 | 부분 — Card→Benefit `OFFERS` 연결이 일부 관계를 표현할 수 있음 |
| `card_common_doc` | 공통 항목과 문서 연결 | 없음 |

| `card_excl_item` | 제외 대상 표준 항목·별칭 마스터 | 부분 — `Target` 노드와 제외 관계가 개념 일부를 표현할 수 있으나 별칭 사전은 없음 |

| `common_cd` | 코드 그룹별 코드·명칭·설명 | 없음 |

대응 요약(참고 명세 18개 테이블 기준): **있음 0, 부분 13, 없음 5**. 여기서 ‘있음’은 테이블 역할이 직접 대응하는 경우로 정의했다. 그래프 초안의 네 테이블은 `pf_load_runs`(적재 실행), `pf_nodes`(유형별 노드와 속성), `pf_edges`(노드 간 관계), `pf_evidence`(노드 또는 간선의 문서 근거 위치)다.

## 겹치지 않는 범위

- **참고 명세에만 있는 기능:** 문서·쪽·청크 원문 및 메타데이터 저장, AI 전체 실행 및 개별 호출 로그, 추출 스테이징과 승인 흐름, 상품 마스터와 상품-문서 적용성, 벡터 임베딩(`card_bnft`, `card_common_bnft`), 공통 혜택과 공통 코드 관리.
- **그래프 설계에만 있는 표현:** 유형 제한이 있는 노드·간선 그래프, 간선 끝점 검증, 추출 엔터티/관계 중심 저장, 노드 또는 간선에 각각 연결되는 근거의 쪽·문자 위치와 `located`/`ambiguous`/`missing` 상태. 실제 쪽·청크 원문이나 인용문은 저장하지 않는다.
- **직접 확인:** `graph/export.py`는 결과 JSON과 문서 인덱스를 읽어 네 종류의 `pf_*` CSV를 만들며 문서 본문을 DB용 그래프에 싣지 않는다. 두 README와 SQL 주석은 두 DDL 모두 자동 적용 대상으로 설명하지 않는다.

## 충돌 및 사전 합의점

- **스키마 이름:** 참고안은 `file_pipeline`, 그래프안은 `public`을 쓴다.
- **접두사:** 그래프안 객체는 모두 `pf_` 규칙을 따르지만 참고안은 `card_`/`common_` 이름을 쓰며 접두사 규칙이 다르다.
- **단계 범위:** 프로젝트 지도 4절은 현재 2~7단계에서 DB를 쓰지 않고 새 테이블도 만들지 않는다고 한다. DB 사용을 이 단계에 포함할지 별도 단계로 미룰지 정리가 필요하다.
- **RLS:** 그래프안은 모든 테이블에 RLS를 켜고 정책을 만들지 않아 기본 거부를 유지한다. 참고 DDL에는 RLS 설정이 없다. 실제 DB 적용 전 테이블별 접근 원칙을 합의해야 한다.
- **pgvector:** 참고안은 `vector` 열을 두고 vector 확장이 미리 설치되어야 한다고 명시한다. 그래프안에는 벡터 열이 없다. 확장 설치 가능성과 소유 주체를 정해야 한다.
- **컬럼 명명:** 참고안은 `card_doc_id`, `create_date`, `bnft_*` 등 업무 약어와 `create_user_id`/`update_user_id` 감사 컬럼을 쓴다. 그래프안은 `run_id`, `node_type`, `started_at` 같은 일반화된 이름과 `props` JSON을 쓴다.
- **도메인 소유 경계:** 프로젝트 지도 5절은 상품 마스터 위치와 그래프 저장소를 열린 결정으로 둔다. 참고 명세의 상품/공통 혜택과 그래프 Card/Benefit 노드 소유권을 정해야 중복 관리가 생기지 않는다.

## 통합 선택지 — 결정 대기

1. **`pf_` 그래프안만 DB 적용 후보로 두고 참고 명세는 문서로 유지.** 그래프 모델이 작고 현재 CSV 출력 및 적재 설계와 일치한다. 문서·AI 호출 이력·상품 마스터·임베딩은 DB에서 조회할 수 없다.
2. **그래프안은 유지하고 AI 실행/호출 로그만 `pf_` 테이블로 이식.** 추출 관측성이 개선되고 적용 범위가 제한된다. `pf_` 네이밍/기존 `pf_load_runs`와 실행 로그의 의미가 겹칠 수 있으며, 본래 2~7단계 무테이블 방침을 바꾸는 결정이 필요하다.
3. **참고 명세 전체를 `pf_` 접두사로 이식해 그래프와 통합.** 문서부터 마스터·추출·그래프까지 한 DB에서 관리할 여지가 생긴다. 변환·키·중복 데이터·RLS 정책·pgvector·마이그레이션 범위가 커지고, 현재 파일 기반 처리 및 단계 방침과 충돌한다.

**검토 추천:** 지금은 1번을 임시 기준으로 두고 팀이 별도 DB 단계를 승인할 때까지 두 SQL 모두 적용하지 않는 편이 범위를 가장 적게 바꾸며 현재 단계 방침과 맞는다. 이는 비교자의 제안일 뿐 확정 사항이 아니다. 최종 선택은 팀 결정 대기다.

## 노트북 점검

- **직접 확인:** `nbformat` 4.5, 7개 셀로 `nbformat.validate`를 통과했다. 모든 코드 셀의 `outputs`는 비어 있고 실행 횟수도 미실행 상태다. 검증 시 셀 ID 관련 향후 호환성 경고가 출력되었다.
- 저장소 루트는 현재 작업 디렉터리부터 `src/card_benefit/payment_card/file_pipeline/extraction` 폴더를 찾으며, import 경로로 `src`와 `src/card_benefit`를 추가한다. 기본 입력은 `/tmp/pilot_followup_20261103_desktop/chunks/hana`, `/tmp/.../out5a`, `/tmp/.../out5b`; 결과 쓰기는 `/tmp/.../notebook_audit` 아래다. 저장소 안 쓰기 경로는 코드에서 발견하지 못했다.
- 원문 대조 셀은 선택한 결과 청크의 원문·인용문·추출 항목을 노트북 출력에 렌더링한다. 현재 셀 출력은 비어 있으나 실행 후 저장/공유 시 원문이 노트북에 포함될 수 있다.
- 외부 네트워크 호출, LLM 호출, 환경 변수·키 접근 코드는 발견하지 못했다. 입력은 JSON 결과/청크 파일 읽기, 자동 점검 모듈은 `/tmp` 지정 폴더에 결과 JSON을 쓴다.
- 정적 import 대조: `verify_results`는 `extraction/verify.py`, `compare_variance`는 `extraction/variance.py`에 존재한다. `review_tally` import는 노트북에 없으며 모듈 파일은 존재한다. 이름 불일치나 없는 import는 발견하지 못했다.
- **문제/주의 목록:** 기본 `/tmp` 입력은 특정 PC의 경로라 다른 환경에는 없을 수 있다. 원문 렌더 셀을 실행하면 원문이 출력에 노출된다. nbformat 검증에서 셀 ID 향후 호환성 경고가 있었지만 노트북은 수정하지 않았다.

## 검증

- 요청한 pytest 명령 실행 결과: `90 passed in 2.88s`.
- SQL 가드 테스트는 `graph/schema.sql`을 고정 경로로 읽는다. 새 `sql/card_benefit_schema.sql`을 자동 대상으로 삼지 않으므로 새 참고 DDL이 그래프 접두사 검사에 잘못 들어가지 않음을 정적으로 확인했다.
- SQL은 실행하지 않았다. 네트워크·LLM·DB 호출, `db_pipeline` 접근은 하지 않았다.

## 직접 확인한 사실과 판단

- **직접 확인:** 읽기 범위의 SQL, README, 프로젝트 지도 4·5절, 이력, 스키마 모델, 그래프 export 코드와 노트북의 실제 내용 및 정적 구조.
- **판단/추정:** 대응표의 ‘부분’ 분류와 통합 선택지의 장단점 및 1번 추천. 이는 데이터 이관 검증이나 팀의 설계 승인이 아니다.

## 못 한 것 및 다음 할 일

- 실제 DB 적용·pgvector 설치 여부·RLS 접근 시험은 하지 않았다. 팀이 통합 방향, DB 단계, 스키마/접두사, 테이블 소유권, 접근 정책, 확장 사용 여부를 결정해야 한다.
- 선택 이후에만 마이그레이션 설계와 컬럼·키 대응을 구체화한다. 노트북의 기본 임시 경로는 실행 환경에 맞춰 사용자가 설정해야 한다.
- 호스트 조건에 따라 이력 작성은 허용되었으며 hostname은 공개 문서에 넣지 않았다.
