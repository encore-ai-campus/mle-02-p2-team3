# 카드 혜택 지식그래프 스키마 초안 (PC: laptop)

날짜: 2026-11-03. 상태: 검토용 파일 초안이며 Supabase 적용 전이다.

## 직접 확인한 사실

- 장비 식별 확인: 호스트명 `LeeHG`, `/etc/machine-id` 처음 8자 `a6629f64`.
- `extraction/schema.py`는 Benefit, Condition, Limit, Target 및 `HAS_CONDITION`, `HAS_LIMIT`, `APPLIES_TO`, `EXCLUDES`, `MUTUALLY_EXCLUSIVE` 관계와 허용 엔티티 쌍을 정의한다.
- 온톨로지 문서는 Card와 Issuer를 공통 계약 범위로 두고 추출 v1에서 제외한다.
- 상품 문서 인덱스 CSV 헤더는 `issuer,product_name,product_ids,card_type,doc_id,file_path,relation`이다.
- 기존에 읽은 챗봇 SQL은 `graphrag` 스키마의 `nodes`, `edges`를 사용하며 이전 마이그레이션 SQL은 `public.nodes`, `public.edges`를 참조한다. 이번 설계의 `public.pf_*` 이름과 충돌하지 않는다.

## 설계 초안과 보수적 기본값

`src/card_benefit/payment_card/file_pipeline/graph/README.md`와 `schema.sql`에 `pf_load_runs`, `pf_nodes`, `pf_edges`, `pf_evidence` 모델을 적었다. 모든 DB 객체를 `pf_`로 명명하고, `OFFERS`를 Card→Benefit 상품 연결 관계로 추가했다. 노드 유형은 요청에 맞춰 Issuer와 Card를 포함한다. 여러 적재 시도 간 ID 중복 가능성을 고려해 엣지 중복 제약에 run을 포함했다. 외부 계정이나 공개 API 정책은 만들지 않고 모든 테이블에 RLS를 켜되 정책은 두지 않는 기본 거부를 택했다. CSV 정의와 향후 적재기의 dry-run 기본, `--execute` 필요, 코드 고정 allowlist, `PF_DATABASE_URL` 환경변수 이름 규칙도 README에 기록했다.

현재 CSV 인덱스 헤더만 확인했으므로 실제 Card/Benefit 연결 행의 의미와 ID 규칙은 미확인이다. `OFFERS`는 제안이며 팀 합의 전이다.

## 검증 및 하지 않은 일

- SQL의 CREATE 대상 이름을 정규식으로 검사하고, 금지 SQL 토큰과 Mermaid 구조를 정적으로 확인했다.
- CREATE 대상 15개 모두 `pf_` 접두사이며 DROP/TRUNCATE/DELETE 토큰은 없다.
- 지정된 extraction 테스트: 55개 통과 (0.09초).
- DB 접속, SQL 실행, `.env` 열람, 원문/인용문 저장, `db_pipeline` 열람, 기존 SQL 파일 수정, Git 쓰기 작업은 하지 않았다.
- 이력 파일은 새로 작성했으며 기존 이력 파일은 편집하지 않았다.

## 다음 결정

팀에서 `pf_` 이름 충돌, RLS 접근 주체/정책, 상품 마스터 위치, `OFFERS` 입력과 적재 시 ID 범위를 결정해야 한다. 그래프 저장소는 프로젝트 지도에서 후보로만 표시했다.

## Claude 검토에서 고친 것 (직접 확인)
- 이름 검사: `schema.sql`의 CREATE 대상(테이블 4, 인덱스 9, 함수 1, 트리거 1)이 모두 `pf_`로 시작하고, DROP/TRUNCATE/DELETE 구문과 접두사 없는 `nodes`·`edges` 참조가 없음을 정규식으로 확인했다. RLS는 4개 테이블에 켜고 정책은 0개다.
- 결함 1: `pf_evidence`의 `page_no`, `start_pos`, `end_pos`가 모두 NOT NULL이라 위치를 못 찾은 인용문(`missing`)을 저장할 수 없었다. 실행기는 그런 인용문의 위치를 null로 남긴다. `missing`일 때만 위치를 비울 수 있게 하고(`pf_evidence_position_by_status`), `located`/`ambiguous`는 필수로 했다.
- 결함 2: 추출기의 id(`benefit-1` 등)는 청크마다 겹치는데 `pf_nodes.id`는 전역 기본키다. 적재기가 `"<chunk_id>:<추출 id>"`로 바꾸고 관계의 source/target도 같게 바꾼다는 규칙을 README에 추가했다.
- 함수 정의를 `create or replace function`으로 바꿨다(재실행해도 최신 정의로 갱신, 삭제 없음, `pf_` 함수만 대상).
- 확인하지 못한 것: 실제 PostgreSQL로 SQL을 실행하지 않았다(`psql` 없음, DB 접속 금지). 문법은 눈으로만 검토했다. 개발용 DB에서 사용자가 실행해 보기 전에는 오류 여부를 모른다.
- 남은 결정: Issuer→Card 관계 유형(`ISSUES` 등) 추가 여부, RLS 접근 주체, 상품 마스터 위치, 팀과의 접두사 합의. 기존에 사용자가 임시로 만든 `public.nodes`, `public.edges`는 이 스키마와 무관하며 건드리지 않는다.
