# 적재 드라이런·우리카드 청킹·비용 추정

PC: laptop

## 한 일

- out7 CSV를 `/tmp/pf-graph-out7`로 export하고 `load.py` 기본 모드로 그래프 적재 드라이런을 확인했다.
- DB 용량을 20청크 CSV의 실측 행 바이트와 사용자가 확인한 DB 용량 정보를 바탕으로 추정했다.
- 우리카드 문서 인덱싱과 청킹 결과, 전체 LLM 실행의 토큰·시간 규모를 정리했다.

## 직접 확인한 사실 vs 추정

### 직접 확인한 사실

- 드라이런 결과: `pf_nodes` 208개(Benefit 34, Card 30, Condition 74, Limit 32, Target 38), `pf_edges` 251개(HAS_CONDITION 113, OFFERS 54, HAS_LIMIT 41, APPLIES_TO 29, EXCLUDES 13, MUTUALLY_EXCLUSIVE 1), `pf_evidence` 394개(located 381, ambiguous 13, missing 0), `pf_load_runs` 1개, 오류 0개.
- `load.py` 159~163행은 기본값 `execute=False`일 때 DB 접속 전에 반환한다.
- 실제 적재(`--execute`)는 실행하지 않았다. `.env`에는 `PF_DATABASE_URL`이 없고 `DB_URL` 이름은 있으나 어느 DB를 가리키는지 확인하지 않았다. `.env`는 변수 이름만 확인하고 값은 열지 않았다. 첫 시도에서 `RuntimeError`가 출력됐다.
- `load.py`가 실제 적재에 필요로 하는 접속 문자열이 없어서 발생했을 가능성이 있지만, 원인은 확정하지 않았다. 적재는 급하지 않아 보류했다. 방법 1은 접속 문자열을 준비해 `--execute`로 적재하는 것, 방법 2는 INSERT SQL 파일을 SQL Editor에 붙여 실행하는 것이다.
- DB 한도 500 MB와 현재 사용량 48 MB는 사용자가 확인했다.
- 20청크 CSV 행당 평균 크기 실측값은 노드 184바이트, 엣지 125바이트, 근거 109바이트다. 하나카드는 543청크(문서 95개, 4,000자 초과 18개)로 직접 측정했다.
- Codex 샌드박스에서 `~/pilot_work` 쓰기가 불가해 우리카드 작업은 실패했고, Claude가 직접 실행했다. `doc_index.batch --issuer woori` 결과는 done 111, OCR 필요로 skipped 44, failed 0이다. `chunking.cli --issuer woori` 결과는 문서 111개, 청크 489개, 4,000자 초과 12개, 200자 미만 36개, OCR 건너뜀 44개, failed 0이다. 결과물은 저장소 밖의 `~/pilot_work/trace/woori`, `~/pilot_work/chunks/woori`에 있으므로 커밋하지 않는다. 하나카드와 합쳐 1,032청크다.
- 청크 길이 실측: 하나카드 평균 1,369자, 중앙값 934자, 최장 5,160자. 우리카드 평균 1,780자, 중앙값 1,242자, 최장 9,540자.
- LLM 토큰 사용량은 실행 결과에 기록되지 않았다. 단가도 확인되지 않아 금액 비용은 산출할 수 없다.
- `cli run --help`에서 금액 한도 옵션은 없고 `--max-estimated-tokens`(기본 200,000)만 확인했다. 옵션 목록은 `--chunk-dir`, `--output-dir`, `--chunk-ids`, `--model`, `--temperature`, `--api-key-env`, `--max-chunks`, `--workers`, `--retries`, `--no-fail-fast`, `--max-estimated-tokens`, `--allow-large`, `--execute`다.
- Codex의 첫 용량 추정은 스키마와 CSV를 읽지 못해 계산에 실패했고, Claude가 직접 계산했다.

### 추정

- 노드·엣지·근거의 행당 평균 바이트를 합산한 기준으로 청크당 약 17 KB다. 인덱스와 저장소 오버헤드는 별도 가정이다.
- 데이터 용량 시나리오: 20청크 약 0.3 MB, 하나카드 전체 약 9 MB, 하나카드+우리카드 약 18 MB, 누적 3/5/10회 약 53/88/175 MB. 속성 크기를 1.5배로 보면 전체 두 카드 약 23 MB, 청크 본문을 추가하면 약 3 MB, 임베딩을 추가하면 약 12 MB로 추정한다.
- 현재 한도에서 용량 위험은 낮아 보인다. 실제 위험은 `run_id` 누적에 따른 중복 적재다. 시범 run은 삭제한다.
- Codex가 제시했던 삭제 SQL은 `pf_evidence`에 `run_id` 컬럼이 없어 오류가 났으므로 폐기했다. 올바른 삭제 순서는 `pf_evidence`에서 `node_id`/`edge_id` 서브쿼리로 대상 근거를 지운 뒤, `pf_edges` → `pf_nodes` → `pf_load_runs` 순이다.
- 전체 LLM 실행 추정 입력은 약 6.2M~12.4M 토큰, 출력은 약 5.4M~10.8M 토큰이다. 한글 1글자를 1~2토큰으로 가정했고, 출력은 out7의 청크당 평균 5,226자를 적용했다.
- 파일 mtime 기반이라 신뢰도는 낮지만, 4 workers 가정 시 전체 약 8시간, 16 workers 시 약 2시간으로 추정했다.

## 못 한 것

- `--execute` 실제 적재는 하지 않았다.
- 정확한 LLM 단가 및 실행 토큰 사용량은 확인하지 못해 금액 비용을 계산하지 못했다.
- 청크 결과의 의미 정확성을 점검하지 않았다.
- 4,000자 초과 청크를 어떻게 처리할지 결정하지 않았다.
