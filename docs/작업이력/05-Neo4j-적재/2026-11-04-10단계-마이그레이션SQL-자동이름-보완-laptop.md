# 10단계 마이그레이션 SQL 자동 이름 보완

- PC: laptop
- 상태: SQL·정적 테스트 보완, 커밋 전

## 확인한 사실과 추정

- 직접 확인: `schema.sql`의 네 테이블은 기본 키와 일부 외래 키·CHECK 제약 이름을 지정하지 않아 PostgreSQL 자동 이름에 의존한다. `fp_evidence`는 identity 컬럼을 사용한다. 마이그레이션에는 기존 명시적 제약 이름 9개와 비제약 인덱스 9개의 이름 변경이 있었다.
- 직접 확인: 기존 SQL은 자동 명명 제약과 `pf_evidence_id_seq`를 대상으로 하지 않았다.
- 추정: 과거 `pf_` 스키마를 만든 DB에서는 이 자동 이름이 `pf_`로 남아 새 `fp_` 스키마와 객체 이름이 달라질 수 있다. DB 카탈로그에서 확인하지 않았다.

## 수정

- 네 `fp_` 대상 테이블에서 `pf_`로 시작하는 모든 제약을 찾아 `fp_` 접두사로 변경하도록 일반화했다. 같은 테이블에 새 이름이 있으면 건너뛴다.
- 기존 9개 비제약 인덱스 이름 변경문을 유지했다. identity 시퀀스는 이전 이름이 있고 새 이름이 없을 때 rename을 시도하며, 실패는 블록 내부에서 처리한다.
- 마이그레이션 끝에 `pf_` 잔존 여부와 `fp_` 객체 수를 확인하는 주석 조회를 추가했다.
- DB 없이 마이그레이션의 금지 문장·트랜잭션·객체 이름·일반화 루프·시퀀스 문장을 검사하는 테스트를 추가했다.

## 검증

- 직접 실행: 저장소 표준 추출·그래프·노트북 커버리지 테스트 명령 결과 `204 passed in 3.04s`.
- 실제 PostgreSQL/Supabase DB 동작, identity 시퀀스 이름 변경 가능 여부 및 예외 경로는 확인하지 않았다.
- 이 SQL은 Supabase SQL Editor에서 사용자가 실행한다. Codex는 실행하지 않았다.

## 사용자 실행 절차

1. SQL Editor에서 마이그레이션 파일 상단의 실행 전 확인용 조회를 실행하고, 대상 테이블이 `pf_` 이름으로 있고 `fp_` 이름과 충돌하지 않는지 확인한다.
2. 검토 후 마이그레이션 SQL을 실행한다.
3. 실행 후 파일 하단의 검증용 조회 4개를 각각 실행한다. `pf_` 조회 세 개가 비어 있는지 보고, 마지막 조회에서 테이블·인덱스·제약의 `fp_` 개수를 확인한다.

커밋 전.
