## 한 일

1. 추출 스키마, 그래프 export, 값 파서, Supabase 스키마·적재기, `fp_chat` 뷰, GraphRAG 어댑터·검색 흐름을 대조했다.
2. 현재 기본 모델이 Benefit·Condition·Limit·Target에 청크 기준 ID를 붙이고, export가 상품 인덱스에서 Card와 `OFFERS`를 추가한다는 점을 문서화했다. Issuer는 스키마에서 허용하지만 일반 export 생성 대상은 아니다.
3. 노드/엣지 근거, run 단위 적재, `fp_chat`의 Document·`SUPPORTED_BY` 투영과 Neo4j의 `FpEvidence` 표현을 구분했다. 조건과 한도 사이 직접 관계가 없고, `source_text`가 제한된 원문 구간으로 문맥을 보완하는 설계 한계를 명시했다.
4. `normalize_values.py`에 파서 함수는 있지만 표준 `export.py` 경로에서 호출하지 않는 점, GraphRAG 후보가 이름 중심이며 부분 그래프가 40노드 상한을 갖는 점을 기록했다.
5. 2026-11-06 작업이력의 사용자 실행 기록에 맞춰 현재 Supabase 적재와 로컬 Neo4j 시각화 현황을 반영하고, 작업이력·프로젝트 지도·결정 기록·설계 문서·그래프 README의 모순된 상태 설명을 정리했다.

## 직접 확인한 사실

- 온톨로지는 추출 노드 4종과 5개 관계를 정의한다. 그래프 SQL·export는 Card와 `OFFERS`를 더해 6개 관계를 허용한다.
- `fp_evidence`는 대상 노드 또는 엣지 하나와 문서 해시·위치·`quote_status`를 저장한다. 인용 본문은 저장하지 않는다.
- `fp_chat`은 문서 노드와 `SUPPORTED_BY`를 생성하고 노드당 최대 3개 문서를 연결한다. 실제 뷰 소유자와 챗봇 연결 DB 역할은 미확인이다.
- 작업이력의 사용자 실행 기록에는 Supabase 그래프 노드 12,144개·엣지 15,697개, 로컬 Neo4j 도메인 노드·관계 같은 수가 기록돼 있다. Neo4j `FpEvidence`는 23,970개이며 원본 CSV 24,066행과의 차이 96개는 원인 미확인이다. 이번 작업에서 DB를 직접 조회하지 않았다.
- 팀 장부로의 통합은 합의 대기다. 2026-10-31 Rule·ConditionExpression·LimitPool/tier 설계안은 제안 문서이며 현재 DB 스키마가 아니다.
- 우리 OCR 작업이력은 117청크 추출, 34개 실패 청크 중 31개 복구와 3개 미해결을 기록한다. OCR 추출의 사람 정확성 검수는 제한적이다.

- 원격 refs는 갱신하지 않았다. 이 실행 환경에서 `.git`은 읽기 전용이므로 `git fetch`를 수행하지 못했고, 원격 차이 판단은 기존 로컬 캐시 기준이다.
