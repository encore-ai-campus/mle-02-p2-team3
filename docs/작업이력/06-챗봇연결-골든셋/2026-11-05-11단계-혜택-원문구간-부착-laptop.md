# 11단계 혜택 원문 구간 부착

- PC: laptop
- 목적: 구간별 한도 오답을 줄이기 위해 Benefit 노드에 근거 위치로 구성한 원문 구간을 부착한다. 한도 풀과 규칙-한도 연결을 별도 생성하지 않고 혜택 설명·한도를 원문 기반 TEXT 로 두는 V7 설계와 같은 방향이다.
- 동작: Benefit 본인 및 연결 Condition·Limit·Target 노드의 located 근거를 문서·쪽별로 병합하고, PDF의 1-based inclusive 위치를 슬라이스해 `source_text`, `source_text_pages`, `source_text_truncated`를 추가한다. 출력은 `/tmp` 아래로 제한한다.
- 뷰 확인: `graph/chat_views.sql`은 `coalesce(n.props, '{}'::jsonb)`에 뷰 메타 속성만 결합해 `props`로 내보낸다. `source_text`도 JSON props에 유지되므로 뷰 변경은 불필요하다.

한도 포함 판정은 Limit의 숫자형 amount를 source_text 안의 원/만원 표기와 비교했다. 컨텍스트 추정(부착 노드 40개): 기존 Benefit props 평균은 하나 69.5자, 우리 69.3자다. source_text 평균은 하나 244.9자, 우리 334.7자다. 하나는 약 9,796자(약 6,531~9,796 토큰), 기존 대비 약 +252%; 우리는 약 13,388자(약 8,925~13,388 토큰), 기존 대비 약 +383%다. 토큰 환산은 한글 1~1.5자/토큰 가정이다.

hana-03 (`01c44066b8df1688-p0001-c01:b1`): source_text 길이 700자, 12,000원 포함 false, 19,000원 포함 false, `30만원 이상 ~ 100만원 미만` 포함 true, `100만원 이상` 포함 true. 제한 길이에서 중앙부를 우선 보존해 두 한도값이 잘린 결과다. hana-02는 제공된 입력 파일에서 사례 ID/기대 문구를 확인할 수 없어 미측정이다.

## 위험과 한계

- 한 혜택의 근거가 여러 문서에 걸리면 문서 ID를 텍스트에 표시하지 않고 쪽 번호만 표시한다. 다문서 근거의 혼합 및 순서 왜곡을 막으려면 문서별 별도 속성이나 원문 선택 정책이 필요하다.
- PDF 표의 텍스트 추출 순서가 시각적 행/열 순서와 다를 수 있다. 한도-실적 연계는 추출 텍스트에 나란히 있어야 확인되며, 본 방식이 의미적 표 구조를 복구하지는 않는다.
- 긴 제외 목록 등은 700자에서 절단된다. 중앙부 우선 방식은 시작/끝의 값이나 조건이 빠질 수 있으며 hana-03에서 두 한도값이 실제로 빠졌다. 상한 조정이나 표 영역 우선 절단 정책을 검토해야 한다.
- 혜택별 위치가 없는/ambiguous 3건(하나), 8건(우리)은 부착하지 않았다. PDF 접근/슬라이스 실패도 사유별로 집계한다.
- 배경에서 전달된 다중 조건 표본(44/82)을 현 CSV 관계와 동일하게 재현하는 필터는 확정하지 못했다. 위 표의 조건 분모는 전체 연결 그룹으로 별도 표기했다.

## 사용 방법

1. graph CSV 내보내기 후 `source_text` 생성 명령을 실행한다.
2. 새 출력에 `python -m payment_card.file_pipeline.graph.load --csv-dir <출력 폴더>` 드라이런을 실행한다.
3. 사용자가 기존 run 삭제 후 새 run을 적재한다. 이 작업에서는 적재하지 않는다.
4. `fp_chat` 뷰가 props를 그대로 노출하므로 뷰 변경 없이 챗봇 시험을 재실행한다.

점검 목록의 `source_text` 등록과 프로젝트 인덱스 갱신은 사용자가 반영한다. 커밋 전이다.

## 개정: 한도·실적 앵커 중심 절단 (2026-11-05)

중앙부 우선 절단이 긴 구간에서 한도 금액을 누락하고, 보조 문구를 보존하는 문제가 확인되어 절단 정책을 수정했다. 연결된 Limit의 located 근거 창을 필수로 보존하고, SPEND_REQ Condition 근거 창을 다음 우선순위로 추가한 뒤, 남는 길이는 Benefit 근거 앞부분으로 채운다. 창 사이 생략은 ` … `로 표시하며 쪽별 `(p.N)` 접두어와 700자 공통 상한을 유지한다. Limit·SPEND_REQ 앵커가 없는 경우에는 기존 구간 추출을 앞부분 우선으로 절단한다.

| 카드사 | 다중 상이 한도 금액 전체 포함 | 절단 Benefit | 절단 비율 | 평균 source_text 길이 | 40노드 평균 추정 | 40노드 최대 상한 |
|---|---:|---:|---:|---:|---:|---:|
| 하나 | 86 / 88 (97.7%) | 563 / 1,471 | 38.3% | 288.1자 | 11,524자 | 28,000자 |
| 우리 | 180 / 190 (94.7%) | 574 / 882 | 65.1% | 395.9자 | 15,836자 | 28,000자 |

측정 분모는 Benefit에 연결된 Limit의 `amount`를 정수화하고 0·None을 제외한 뒤, 서로 다른 amount가 2개 이상인 Benefit이다. 한도 문구는 쉼표와 원·천원·만원·만 N천원 표기를 정규화하고, 100 미만 amount는 숫자 경계 일치로 판정했다. 전달받은 이전 비교값은 하나 81/88(약 92%), 우리 73/88(약 83%)이다. 이번 우리 분모는 190이며 전달받은 참고 분모 208과 다르다.

hana-03 대상 Benefit `01c44066b8df1688-p0001-c01:b1`의 source_text는 698자이며 12,000원·19,000원·30만원 이상·100만원 이상이 모두 포함됐다. 금액이 다른 한도 전체 포함률 목표(하나 90%, 우리 85%)를 양사 모두 넘었다.

새 CSV 출력은 `/tmp/fp-check-hana-st2`, `/tmp/fp-check-woori-st2`에 생성했다. 드라이런 건수는 하나 node/edge/evidence 5,748/7,956/11,287, 우리 4,561/5,173/9,266이다. `-st2` run 접미사를 사용했고 DB 적재는 하지 않았다.
