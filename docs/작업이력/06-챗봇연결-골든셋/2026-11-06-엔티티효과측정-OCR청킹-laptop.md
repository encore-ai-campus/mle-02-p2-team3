## 한 일

1. **엔티티 연결을 DB에 적용**(사용자 실행, 저장소 밖 실행기). 하나 227행·우리 103행, 뷰 330행. 실행기가 run_id 오입력(하나 자리에 우리 run)을 한 번 허용해 하나 연결이 빠졌고, 같은 run 거부와 멤버 소속 검증을 넣어 다시 적용했다. 실제 DB run 이름은 `full_hana-20261104T080526Z-st2`, `full_woori-20261104T080527Z-st2`로 평가용 CSV 이름(`eval_*`)과 달랐다.
2. **묶음 자동 판정**(규칙 기반, 사람 확정 아님). 1차 규칙은 혜택 묶음을 처리하지 못하고 부모 이름을 문자열 완전 일치로만 비교해 "안전 9묶음"으로 과소 판정했다. 규칙을 고친 2차 결과: 병합 안전 56묶음(줄어드는 노드 73), 위험 78묶음(91), 불확실 15묶음(17). 표본 점검에서 위험 판정은 타당했고 EL-0083은 관대했다.
3. **중복 시뮬레이션** `chat/entity_dup_probe.py`(DB·LLM 없음, 시작 노드를 결정적 매처로 근사, 깊이 2 고정). 골든셋 v2 80문항: 안전 연결표 기준 영향 질문 2개(2.5%), 평균 서브그래프 대비 감소 0.07%, 근거 수 보존 위반 0, 골든 근거 영향 0. 연결표 전체(181개)를 쓰면 영향 질문 7개(8.75%)로 늘어, 위험 묶음을 거른 효과가 확인됐다.
4. **결론(사전에 정한 기준 적용)**: 영향 질문 5% 미만 → 챗봇 적용은 기본 꺼짐 유지, 효과 미미. 챗봇용 연결표는 `entity_links_safe.csv`(56묶음, 매핑 73).
5. **챗봇 실제 로그 1건 비교**(끄기/켜기). 두 실행 모두 검색된 노드 중 연결표 멤버가 0개라 연결 기능의 영향은 없었다. 같은 질문인데 답의 수치가 달랐다(객실 15%/20% 대 10%/15%). 그래프와 원문을 확인한 결과 한 카드 문서에 서로 다른 두 혜택 프로그램(31쪽 멤버십 특전, 47쪽 특급호텔 객실 할인)이 있고 둘 다 정확히 추출돼 있었다. 챗봇은 프로그램을 구분하지 않고 실행마다 한쪽만 골랐고, 수치 검증은 둘 다 통과했다(그래프 어딘가에 있는 숫자인지만 보기 때문, `scope_unknown`).
6. **청킹 `--include-ocr` 옵션**(`chunking/cli.py`, +23/-3). 기본 동작 불변. 합성 테스트 3개. 실제 OCR 추적 JSON 45개로 실행: 44문서·117청크, 청크 본문과 쪽 원문 불일치 0. 1문서는 인덱스에서 `doc_role: unclassified`라 문서 선택 규칙에서 제외됐다. 4,000자 초과 청크 30개(최대 8,250자), 200자 미만 13개.
7. **추출 비용 추정**(dry-run): 117청크, 입력 약 43.7만 토큰. 모델 `gpt-6-luna`의 가격은 확인하지 못해 달러로 환산하지 않았다. 출력 토큰은 추정에 포함되지 않았다.

## 못 한 것과 남은 위험

- 시뮬레이션은 LLM 시작 노드 선택을 근사했고 깊이를 2로 고정했다. 실제 챗봇의 영향은 2.5%와 다를 수 있다. 실제 로그는 1건뿐이다.
- 자동 판정과 시트 섹션 1·2의 자동 판정은 사람 확정이 아니다(`judge_source=auto`). 사람 확정 정확도는 0건.

- 카드 사이 연결(914묶음)은 두 run에 걸쳐 현재 테이블 설계로 DB에 넣지 못해 CSV로만 보관.

- 질의응답 로그 경로는 설계상 `/tmp` 아래만 허용되어 질문 후 복사가 필요하다.
