# 작업 이력: 카드사 공통 문서 인덱스 (하나·우리)

- 작업일: 2026-11-02

## 1. 목적

하나카드와 우리카드의 수집 PDF를 같은 규칙으로 분류하고, 카드사가 늘어나도 어댑터 하나만 추가해 같은 형식의 인덱스를 얻는다.

## 2. 한 일

### 2-1. 현황 분석 (읽기 전용)

- `src/data/woori_all` 구조를 분석했다.
  - `common/` 29개, `credit/` 262개, `debit/` 비어 있음.
  - `credit/`은 기존 확보본 108개와 신규 수집본 154개로 이루어져 있고, 두 묶음은 출처가 다르다(기존본은 출처 미확인).
  - 기존 108개 중 107개는 신규 수집본과 SHA-256이 같다.
- 하나와 우리의 manifest 열 이름이 하나도 겹치지 않음을 확인했다(하나 한글 26열, 우리 영문 26열).
- 하나에는 웹페이지 변환 PDF가 54개 있고, 해당 카드 53개 중 38개는 공식 PDF도 있다.
- 우리 상품설명서에는 같은 내용을 여러 상품이 쓰는 경우가 있다(경로는 다르고 해시가 같음).

### 2-2. 폴더 정리

- `woori_all/credit/collection/credit/`에 있던 신규 상품설명서 154개를 `credit/`로 옮기고 빈 `collection/` 폴더를 삭제했다.
- `manifest.csv`, `manifest.json`의 `file_path`에서 `collection/credit/` 접두어를 제거하고, `collection_report.md`의 경로 설명을 고쳤다.
- 검증: manifest 318행의 파일 경로가 모두 존재한다.
- 기존 108개 PDF와 `common/`은 건드리지 않았다.
- manifest는 작업 시점에 이미 `woori_all/` 바로 아래에 있었다. `file_path`는 지금도 `credit/` 기준 상대경로다.

### 2-3. 규칙 설계

- 병목 10가지를 정리하고 대응 규칙을 정했다. 상세는 지시문 §1~§2.
- 범위는 신용카드와 `common`으로 하고 체크카드(`debit/`)는 2단계로 미뤘다.
- 공유 문서는 RAG에서 청크 1개와 상품 목록으로 처리하기로 했다.
- OCR 도구는 설치하지 않기로 했다. 이미지 PDF는 `ocr_needed` 표시만 한다.

### 2-4. 선행 확인

- uv 환경에서 PyMuPDF·pypdf가 정상 동작한다.
- 인덱스 저장 위치 `src/card_benefit/data/index/`는 `.gitignore`에 걸리지 않는다.
- 이미지 PDF(쪽당 평균 50자 미만): 하나 0개, 우리 `credit` 37개, 우리 `common` 27개.
- 하나 웹 변환본 샘플 3개: 텍스트는 추출되나 "비교함", "공유하기" 같은 화면 문구가 섞여 있다.

## 4. 계획과 달라진 점

- 상품 여러 개가 공유한다고 본 PDF는 같은 파일이 아니라 경로가 다르고 해시가 같은 파일들이었다. 그래서 공유 여부를 해시 기준으로 판정한다.
- `duplicate_of`에는 대표 파일의 경로를 적고, `doc_id`는 내용 기준이라 중복 파일끼리 같다.
- `product_docs.csv`에 `file_path` 열을 추가했다.
- 모든 파일이 웹 변환본인 해시 그룹은 "대표 1건" 검증에서 뺀다.

### 4단계 시작: 표 구조 확인과 표 보조본

- 샘플 5장(하나 2, 우리 3)으로 평문 추출과 표 추출(`find_tables`)을 비교했다.
  - 평문은 작은 표의 행·열 순서를 대체로 보존한다. 넓거나 병합 셀이 있는 표는 짝이 모호해진다.
  - 표 추출은 병합 셀을 빈칸으로 내고, 글자를 셀마다 쪼개기도 한다(예: "스" / "파이크(SPIKE) 서비스"). 그대로 쓰면 평문보다 나쁜 경우가 있다.
- 결정: 청크 원문은 평문 그대로 두고(추적성 유지), 표는 **보조본**으로만 붙인다. 평문과 맞는지 검사해서 통과한 표만 `usable=True`로 표시한다.
- `doc_index/tables.py`를 추가했다. 검사 기준: 행 2개 미만 또는 칸 4개 미만은 제외, 한 글자 셀이 10%를 넘으면 제외, 표 글자 수가 평문의 0.8~1.2배를 벗어나면 제외.
- 대표 상품설명서(텍스트 PDF, 신용) 전체 결과:

| | 문서 | 쓸 수 있는 표가 있는 문서 | 통과한 표 | 제외 (너무 작음 / 글자 수 다름 / 글자 쪼개짐) |
|---|---|---|---|---|
| 하나 | 79 | 48 | 130 | 143 / 27 / 0 |
| 우리 | 114 | 80 | 202 | 111 / 9 / 14 |

- 코드 단순화는 이번에는 하지 않았다(다음 단계에서 `core.py`를 고칠 때 그 부분만 정리한다).
- 개선 후보: 문서 단위 `ocr_needed`는 SPIKE처럼 일부 쪽만 이미지인 문서를 놓친다. 쪽별 글자 없음은 `traceability` JSON의 `NO_TEXT`에 이미 있다.

### 4단계: 청킹 기준 탐색 (노트북)

- 탐색용 노트북 `file_pipeline/notebooks/chunking_explore.ipynb`로 기준을 정했다. 대상은 대표 상품설명서(텍스트 PDF, 신용) 193개, 814쪽.
- 쪽 길이: 중앙값 약 1,300자, 4,000자 넘는 쪽 12%, 최대 9,539자, 글자 없는 쪽 37개.
- 제목은 글자 크기만으로 찾을 수 있다(본문 6.0pt, 제목 8.4pt). 굵기 규칙은 효과가 없어 뺐다.
- 결정: **혼합 방식(C)**. 쪽이 4,000자 이하면 쪽 하나가 청크 하나, 그보다 길면 제목 기준으로 쪼개고 400자보다 짧은 조각은 앞 조각에 붙인다.
- 기준값 비교 결과(24가지 조합 중 선택): 하나 485청크(중앙값 814자), 우리 506청크(중앙값 1,196자). 4,000자 초과 청크는 하나 13개, 우리 8개가 남는다(제목이 없는 긴 쪽).
- 아직 `.py`로 옮기지 않았다. 다음 작업은 이 기준을 `chunking.py`로 옮기고 `traceability` 청크(쪽 단위)와 연결하는 것이다.

### 코드 단순화와 폴더 정리

- `core.py`의 `build_index`(143줄)를 단계별 함수 일곱 개로 나누고 임시 키를 없앴다(`c3b00f1`). 설명과 흐름도는 `core-단순화-계획.md`. 인덱스 재생성 결과는 변하지 않았다.
- 우리 기존 확보본 manifest에서 '; '로 이어 붙은 상품 이름 4행을 상품별로 나눴다(`716ac19`). 연결 행 312 → 325, 공유 문서(`shared_guide`) 21 → 34, `documents.csv`는 변경 없음. 나누기 중 상품 이름이 빈 파일(AK 우리카드)이 인덱스에서 사라지는 버그를 만들었다가 확인 후 고쳤고 테스트를 추가했다.
- `file_pipeline/` 폴더를 정리했다. 노트북 두 개를 `notebooks/`로, 파일럿 기록을 `pilot_hana_15299/`로 모았다. `data_modify.ipynb`는 커밋 안 된 수정이 있어 그대로 두었다.
- `file_pipeline/README.md`를 폴더 지도로 새로 썼다(흐름도, 폴더 구성, 모듈 호출 관계, 읽는 순서, 결정 기록). 상위 문서(`card_benefit/README.md`, `docs/directory_structure.md`)의 "미구현", "README만" 문구도 고쳤다.
- 2단계(청킹 코드를 쓸 때 `traceability.py`, `doc_index/batch.py`를 단계별 폴더로 모을지)는 그때 정한다.

### 4단계 청킹 구현

- `file_pipeline/chunking/`(split, headings, build, cli)과 테스트 12개를 추가했다. 규칙: 쪽 4000자 이하는 쪽 하나가 청크, 초과는 글자 크기 제목 앞에서 자르되 400자 미만 조각은 앞에 붙이고, 감지된 표 안 제목에서는 자르지 않는다.
- 하나·우리 대표 문서 213개 실패 0건. 청크를 이어 붙이면 쪽 원문과 같은지 문서마다 검증하고 출력도 따로 다시 대조해 불일치 0건.
- 한계: 제목이 없는 긴 쪽은 쪼개지지 않아 4000자 초과 청크가 29개 남는다. 문단 규칙은 5단계에서 길이가 문제인지 본 뒤 정한다.
- 청크 JSON에는 상품 목록을 문서 수준에 한 번만 넣었다(계획서는 청크마다였으나 공유 문서에서 반복이 크다).

## 6. 아직 하지 않은 것

- 체크카드(`debit/`) 인덱싱: 하나 `debit` 70개, 우리 `debit`은 비어 있음. 하나 체크카드에는 웹 변환본만 있는 카드가 13개 있다.
- OCR: `uv sync --group ocr` 설치, 모델 폴더 준비, `RAPIDOCR_MODEL_DIR` 설정이 모두 필요하고 승인 전이다. 대상은 대표 문서 기준 우리 39개(전체 이미지 PDF 64개 중 중복 제외).
- 하나 웹 변환본 화면 문구("비교함" 등 4종)는 청크 원문에 그대로 남아 있다. LLM 추출 단계 입력에서 거를지 정한다.
- 4000자 넘는 청크 29개(제목 없는 긴 쪽)의 문단 규칙 여부: 5단계에서 길이가 문제인지 본 뒤 결정.
- 검토 대상 확인: 우리 64건, 하나 8건(우리는 자동 상품명 확인 실패 63건, g1/g1New 2건, 분류 불가 1건 중 겹침 제외).
- 인덱스를 훑어보는 보조 노트북(만든다면 `doc_index`를 import하는 얇은 셀만 두고, 커밋 전에 출력을 비운다).
- 원본 데이터 폴더(`src/data/*_all/`)는 `.gitignore` 대상이라 올라가지 않는다.
