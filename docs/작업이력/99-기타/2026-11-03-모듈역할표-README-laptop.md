# 작업 이력: file_pipeline 모듈 역할표 추가 (laptop)

- 작업일: 2026-11-03
- PC: laptop (`hostname`과 machine-id 앞 8자를 개인 지침 값과 대조해 확인함)
- 범위: 문서만 수정. 코드와 테스트는 변경·실행하지 않았다.

## 배경과 결정
- 모듈 이름이 영어 약어(`parallel`, `verify`, `relocate`, `variance` 등)라 처음 보는 사람이 역할을 알기 어렵다는 지적이 있었다.
- 이름을 바꾸는 안(동사로 시작하는 이름, 예: `check_extraction_quality.py`)을 제시했으나 **사용자가 C안을 선택**했다: 이름은 그대로 두고 README에 역할표를 추가한다.
- 이름을 바꾸지 않은 이유(제안 시 확인한 사실): 대부분 이미 푸시된 파일이고 다른 파일 1~5곳이 참조하며, `cli.py` 등은 데스크탑 PC와 공유하는 파일이라 이름 변경이 병합 충돌과 문서·명령어 수정을 크게 늘린다.

## 한 일
- `file_pipeline/README.md`에 **3-1절 "이 파일이 하는 일"**을 추가했다. `extraction/`과 `graph/`의 모듈 22개를 6개 묶음(추출 실행, 시범 보조, 점검·진단, 복구·내보내기, 사람 점검, 지식그래프)으로 나누고 각 파일이 하는 일과 입력·출력을 적었다. 설명은 각 모듈의 첫 docstring 문장을 읽고 풀어 썼다.
- LLM을 실제로 호출하는 것은 "추출 실행" 묶음뿐이고 나머지는 저장된 결과를 읽는 분석이라는 점, 사람이 읽는 결과(대조표 등)는 PDF 원문이 들어가므로 저장소 밖에 둔다는 점을 같은 절에 명시했다.
- 이름 읽는 법(`report`, `diagnose`, `relocate`, `verify`, `variance`, `review`)을 한 줄로 정리했다.

## 검증
- README의 파일 이름이 실제 `extraction/`과 `graph/`의 파일과 일치하도록 각 모듈의 docstring을 직접 읽어 확인했다. 테스트는 실행하지 않았다(문서 변경만).

## 못 한 것과 남은 위험
- 표의 "하는 일"은 docstring과 이력에 근거한 요약이라 모듈이 바뀌면 표를 같이 고쳐야 한다.
- `notebooks/extraction_audit.ipynb`와 `sql/` 안 파일은 이 표에 넣지 않았다(미추적 상태였던 파일이며 별도 README가 있다).
- 모듈 이름 변경(B안)은 하지 않았다. 필요해지면 푸시 후 데스크탑과 합의해 별도 커밋으로 진행한다.
