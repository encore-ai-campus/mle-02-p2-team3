## 1. 조사 목적 및 전제

**목적:** 카드 상품설명서·약관 기반 혜택·조건 분석 GraphRAG의 데이터 범위를 A안(한 카드사 여러 카드)과 B안(여러 카드사 여러 카드) 중에서 정한다.

**전제** (`과제_매핑표_10.29.md` 기준)

- 범위: 필수 과제 M0~M9 + MCP 도구 2~3개(컷라인: 도구 1개)
- 핵심 시연: **공유 조건 변경 → 영향받는 카드·혜택 추적(Cypher 경로)**
- M5 정규화: 카드 간 같은 제외 항목은 하나의 개체로 연결하되 **오병합 점검** 필요
- 데이터: 공개 상품설명서·약관만 사용. 고객정보·이용내역 사용 안 함
- 일정: 3일, 2인. 추출은 `file_pipeline/`(이현근)과 `db_pipeline/`(김병주)이 같은 원천 문서를 각자 처리해 비교

**방법**

## 2. A안 분석 — 한 카드사의 여러 상품

### 2-1. 도입 주체와 사용자 [가정]

- **도입 주체:** 카드사(예: 하나카드) 상품·부가서비스 관리 부서
- **사용자:** 상품기획·부가서비스 운영 담당, 준법·상품설명서 검토 담당, 상담 지원(상담원이 근거 조항을 찾는 용도)
- **고객 대면 아님.** 고객 추천·개인화는 범위 밖이다.

### 2-2. 질문별 검토

| 질문 | 판단 | 근거 |
|---|---|---|
| 1. 자사 여러 상품을 분석할 이유가 있는가 | **있다** | 하나카드 상품들은 실적 제외·혜택 제외·가맹점 분류 기준 문구를 공유한다 [확인]. 하나머니처럼 **자사 그룹이 운영하는 결제수단**이 여러 상품의 제외 조건에 들어 있다. 이 정책이 바뀌면 어느 상품이 영향을 받는지 내부에서 알아야 한다 [가정: 실제 업무 절차는 미확인] |
| 2. 기존 시스템과의 연결 | MCP·API로 조회 기능만 노출 | 매핑표의 MCP 도구(`get_card_benefits`, `find_affected_by_condition`)를 내부 상담·상품관리 화면이 호출하는 구조 [가정]. 실제 하나카드 시스템 구조는 [미확인] |
| 3. 공통 조건 변경의 영향 분석 필요성 | **원문상 근거 있음** | 모든 상품설명서에 "부가서비스는 출시 후 3년 이상 유지, 단 ①~③ 사유 시 변경 가능, 변경 시 고지" 조항이 있다 [확인]. 조건 변경은 상품별 고지 대상이므로 영향 상품 목록이 필요하다 [해석] |
| 4. 특정 카드사 내부 업무로 자연스러운가 | **자연스럽다** | 신한카드는 2026-09-09 "복합적인 조건이 누락", "정책이나 규정이 미반영" 문제를 해결하는 AI 엔진 개발을 발표했다 [확인]. 다만 발표문은 대상이 자사 상품으로 한정되는지 **명시하지 않는다** [확인] |
| 5. 자체 시스템과 외부 범용 AI의 역할 구분 | 자체: 조건·근거·변경 이력의 **정본 관리** / 외부 AI: 고객 접점 | 팀 기존 정리(`최종_카드사_자체AI혜택서비스_사업적개발명분_20261029.md`)와 같다. 자체 구축이 더 빠르거나 우수하다는 주장은 하지 않는다 |

### 2-3. A안의 약점

- 우리 팀은 하나카드가 아니다. 내부 시스템 시나리오는 **가상**이며, 내부 데이터(실제 변경 이력, 상품 운영 기준)는 없다.
- 하나카드 상품 사이에도 문구가 완전히 같지는 않다(§5-1). 오래된 상품(VIVA G, 2014 출시)은 다른 표현을 쓴다. "한 회사니까 다 같다"는 가정은 성립하지 않는다.

## 3. B안 분석 — 여러 카드사의 여러 상품

### 3-1. 도입 주체와 사용자

- **도입 주체:** 카드 비교·판매대리 플랫폼, 핀테크, 금융 정보 콘텐츠 운영사 [확인: 뱅크샐러드가 신한카드 상품의 '전월 이용금액 제외'와 '적립 서비스 제외' 목록을 상품 페이지에 게시. 판매대리 역할 명시]
- **사용자:** 플랫폼 콘텐츠·데이터 운영자, 그리고 그 결과를 보는 소비자
- **카드사 내부 시스템으로 설명하기는 어렵다.** 한 카드사가 경쟁사 약관을 정본으로 관리할 이유는 약하다 [해석].

### 3-2. 질문별 검토

| 질문 | 판단 | 근거 |
|---|---|---|
| 1. 통합 분석의 실제 업무 주체 | 비교·판매대리 플랫폼 | 위 3-1 |
| 2. 카드사 내부 시스템인가, 플랫폼인가 | **플랫폼에 적합** | 여신금융협회 비교공시는 법정 비교 항목이 이율·수수료율·가맹점수수료 등이다. 부가서비스 조건 비교는 공적 공시 항목이 아니다 [확인: KB국민카드 공시이용매뉴얼]. 이 빈자리를 민간 플랫폼이 채운다 [해석] |
| 3. 상이한 조건 비교 수요 | 있음 | 같은 항목도 카드사마다 적용 범위가 다르다(§5-2). 소비자가 PDF를 직접 비교하기 어렵다 [해석] |
| 4. 공개 정보만으로 가치가 있는가 | 비교·설명에는 충분 | 단, 정답 판정(이 결제가 혜택 대상인가)은 가맹점 분류 등 PDF 밖 정보에 의존한다 [확인: 각 PDF에 "카드사 업종 기준에 따라 제공" 문구] |
| 5. 추가되는 관리·표준화 문제 | 큼 | 카드사마다 문서 양식·텍스트 품질이 다르고(KB 띄어쓰기 소실, NH 제어문자·2단), 항목 분류 체계가 다르며(KB는 상하수도를 지방세 하위 항목으로 표기), 확정·가능 표현이 다르다(KB "제외될 수 있습니다"). 신한·우리는 정적 방식으로 PDF를 받지 못했다 |

### 3-3. B안의 핵심 제약

**한 카드사의 정책 변경은 다른 카드사의 정책 변경으로 이어지지 않는다.** 따라서 B안에서 "조건 변경 영향 추적"은 카드사 경계 안에서만 의미가 있다. 카드사 간 연결은 **비교**(같은 개념을 어떻게 다르게 처리하는가)이지 **영향 전파**가 아니다.

### 5-4. 병합 기준과 필요한 속성 [가정: 설계 제안]

| 노드 | 병합 범위 | 필수 속성 |
|---|---|---|
| `ExclusionItem`(예: 선불전자지급수단 충전) | **같은 카드사 안에서만** 병합. 문구 표준화 사전으로 묶음 | `issuer`, `canonical_name`, `raw_terms[]` |
| `Concept`(예: 상품권 구매, PG 재분류) | 카드사 간 공통 개념. **정책이 아니라 분류용** | `name` |
| 조건 관계 `EXCLUDES` | 카드·혜택별 인스턴스 | `scope`(실적/할인/적립/캐시백), `modality`(확정/가능), `document_id`, `page`, `evidence` |

| 방식 | 할 수 있는 것 | 한계 |
|---|---|---|
| SQL(정규화된 테이블) | 공유 항목 조인으로 영향 카드 목록을 낼 수 있다 | **정규화가 끝나면 SQL로도 답이 나온다.** 경로 길이가 가변이거나 관계 유형이 섞이면(실적·할인·적립, 외부 실체) 쿼리가 길어진다 |
| 벡터 RAG | "하나머니" 문구가 있는 청크를 찾는다 | scope(실적/적립)를 구분하지 못한다. VIVA G처럼 다른 표현은 놓친다. 누락 여부를 보장하지 못한다 |
| GraphRAG | 관계 유형·scope·근거 조항이 **명시된 경로**로 답과 근거를 함께 낸다. 가변 길이 탐색, 시각화, MCP 도구화 | 추출·정규화 품질에 그대로 의존한다. 저장소를 바꾼다고 정확도가 올라가지 않는다 |

결론: 이번 프로젝트에서 GraphRAG의 가치는 **"같은 개념을 어디까지 같은 조건으로 볼지"를 관계로 명시하고, 그 경로를 근거와 함께 보여주는 것**이다. 카드 수나 관계 수 자체가 가치는 아니다.
