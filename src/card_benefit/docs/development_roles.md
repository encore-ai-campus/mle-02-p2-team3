# card_benefit 개발 담당과 협업 기준

2인 팀의 담당 범위와 협업 기준입니다. 표기: ✅ 구현됨 · ⏳ 개발 예정 · ❓ 미확정.
폴더·파일 설명은 [directory_structure.md](directory_structure.md), 흐름은 [architecture.md](architecture.md)를 봅니다.

> **분업 방식:** 두 사람은 하나의 파이프라인을 앞뒤로 나눠 맡는 것이 아니라,
> **같은 원천 문서를 서로 다른 기술 방식으로 처리해 파싱·AI 추출·검증을 각자 끝까지 구현**합니다.
> 두 결과는 공통 데이터 계약으로 비교합니다. 하나의 구현으로 반드시 합치는 것을 전제로 하지 않습니다.

## 1. 담당 요약

| 담당자 | 방식 | 현재 폴더 | 처리 범위 |
|---|---|---|---|
| **이현근** | 파일 기반 Python 파싱 + LLM 추출 | `payment_card/extraction/` | 문서 읽기 → 전처리 → 정규식 → LLM 추출 → Python 검증 → 추출 결과 A |
| **김병주** | PostgreSQL 기반 저장·처리 + AI 추출 | `payment_card/ingestion/` | 원본 DB 저장 → SQL 전처리 → DB 데이터 기반 AI 추출 → SQL 정제·검증 → 추출 결과 B |
| **공동** | 공통 데이터 계약, 비교·검증 | (폴더 미정) | 평가 기준, 결과 A·B 비교, 최종 데이터 확정, 향후 Neo4j·GraphRAG |

두 사람 모두 현재 담당 폴더에 Python 코드가 없습니다(폴더 README만 있음). 아래 담당 범위는 모두 ⏳ 개발 예정입니다.

## 2. 이현근 — 파일 기반 Python 파싱 및 LLM 추출

PDF·원천 문서 파일을 Python으로 직접 읽어 처리하는 방식을 독립적으로 구현하고 테스트합니다.

- 기존 `graph-rag` 저장소의 `3_LLM식추출` 학습자료 참고 (Notebook 학습 코드를 Python 소스로 구현)
- PDF 및 원천 문서 파일을 Python으로 직접 읽기 (`src/common/document_reader.py` 재사용 검토)
- 텍스트와 표 데이터 전처리
- 정규식 기반 후보 추출
- Python에서 LLM을 호출해 엔티티·관계 추출
- 추출 결과를 JSON 등으로 구조화 → **추출 결과 A**
- Python 기반 결과 검증 및 오류 처리

## 3. 김병주 — PostgreSQL 기반 데이터 처리 및 AI 추출

데이터 저장·전처리·추출 결과·검증을 PostgreSQL 중심으로 처리하는 방식을 독립적으로 구현하고 테스트합니다.

- PostgreSQL 데이터 모델 및 테이블 설계 (`sql/` DDL)
- 원본 문서에서 확보한 텍스트·메타데이터 등을 PostgreSQL에 저장
- SQL 기반 데이터 전처리 및 정제
- PostgreSQL에 저장된 데이터를 대상으로 AI 추출 기능 구현
- DB 내 AI 함수 또는 외부 LLM 연동 방식 검토
- AI를 이용한 엔티티·관계·조건 데이터 추출 → 결과를 PostgreSQL에 저장 → **추출 결과 B**
- SQL 기반 중복 검사·무결성 검사·정합성 검증
- 원본 데이터와 추출 결과의 연결 및 이력 관리
- 공통 `PostgresDbSession` 과 Named SQL Mapper 활용

**전제와 미확정 사항** ❓
- PostgreSQL이 PDF 자체를 직접 파싱하거나 AI를 기본 지원한다고 가정하지 않습니다. DB에 넣을 텍스트는 DB 밖에서 확보해야 합니다.
- DB에서 AI를 호출하는 방식은 **기술 검증 전까지 미확정**입니다. 검토 후보: `pgai` 등 PostgreSQL 확장, DB 함수에서 외부 AI API 호출,
  Supabase Edge Functions, DB 밖 Python 코드가 LLM 호출만 중계하는 방식.
- 실제 사용 중인 Supabase/PostgreSQL 환경에서 각 후보의 지원 여부를 확인한 뒤 확정합니다.
- Python이 LLM 호출을 중계하더라도, 입력·출력·이력을 PostgreSQL에 두고 SQL로 처리·검증한다면 PostgreSQL 중심 설계 목적은 유지됩니다.
- SQL만으로 검증 가능한 항목과 LLM 또는 사람의 의미 검증이 필요한 항목을 구분합니다([architecture.md](architecture.md) 5절).

## 4. 공동 — 공통 데이터 계약과 비교·검증

**각자의 파이프라인은 독립적이되, 결과를 비교하려면 공통 데이터 계약이 필요합니다.** 아래 항목은 구현 전에 함께 정의합니다. 모두 ❓ 미확정입니다.

| 항목 | 정해야 할 내용 |
|---|---|
| 원천 문서·테스트 데이터 | 두 방식이 같은 문서 집합을 사용 (`data/`) |
| 엔티티·관계 유형 | 유형 목록과 관계 방향 |
| 문서 ID·원문 위치 | 문서 식별자, 페이지·영역 등 위치 표기 방식 |
| 추출 결과 공통 JSON 형식 | 결과 A·B를 같은 형식으로 내보내기 (B는 DB에서 내보냄) |
| 원문 근거 보존 | 추출값마다 근거 원문을 어떻게 남길지 |
| 정상 추출·누락·오탐 기준 | 비교에 쓸 정답 기준과 판정 규칙 |
| 검증 상태·오류 사유 | 상태값과 오류 사유 코드 정의 |
| 비교 기준 | 추출 정확도, 처리 시간, API 비용 등 |

그 밖의 공동 업무: 결과 A·B 비교, 추출 정확도·근거 검증, 최종 데이터 확정 방식 결정, 통합 테스트, 향후 Neo4j·GraphRAG 연동.

## 5. 폴더·파일별 소유와 변경 범위

이미 존재하는 파일 중 담당이 명시되지 않은 것은 모두 **공동**으로 둡니다.

| 경로 | 소유 | 변경 규칙 |
|---|---|---|
| `payment_card/extraction/` | 이현근 | 파일 기반 방식 코드. 자유롭게 변경 |
| `payment_card/ingestion/` | 김병주 | PostgreSQL 기반 방식 코드(전용 `.sql` 포함). 자유롭게 변경 |
| `sql/` (신규 DDL) | 김병주 (테이블 설계) | 운영 DB 적용 전 공동 확인 |
| `sql/schema.sql` (기존) | 공동 | 현재 CLI가 쓰는 `card_product` 테이블. 변경 시 합의 |
| `payment_card/models.py`, `repository.py`, `payment_card.sql`, `main.py`, `__init__.py` | 공동 | 현재 카드 등록·조회 CLI 코드. 어느 쪽 방식에도 아직 속하지 않음. 기존 동작을 깨지 않게 변경 |
| `payment_card/tests/test_payment_card.py` | 공동 | 각자 테스트는 새 `test_*.py` 파일로 추가 |
| `data/` | 공동 | 두 방식이 같은 원천 문서를 쓰도록 함께 관리 |
| `docs/`, `README.md` | 공동 | 자기 방식 문서는 각자 추가 |

공통 JSON 형식 정의와 결과 A·B 비교 코드를 둘 위치는 아직 정하지 않았습니다 ❓.

## 6. 담당자별 입력·출력

| 담당 | 입력 | 출력 |
|---|---|---|
| 이현근 | 원천 문서 파일 (`data/`) | 추출 결과 A (공통 JSON) + 원문 근거 + 오류 정보 |
| 김병주 | 원천 문서에서 확보한 텍스트·메타데이터 (확보 방법 ❓) | PostgreSQL에 저장된 원본·추출 결과·검증 결과·이력, 공통 JSON으로 내보낸 추출 결과 B |
| 공동 | 추출 결과 A·B, 정답 기준 | 비교·평가 결과, 최종 확정 데이터 (향후) |

## 7. 의존성과 통합 방식

```text
원천 문서 (data/) ──┬──▶ extraction/ (이현근) ──▶ 결과 A (JSON) ──┐
                    │                                              ├──▶ 공통 형식 비교 · 근거 검증 (공동)
                    └──▶ ingestion/ (김병주) ──▶ PostgreSQL ──▶ 결과 B (JSON) ──┘
```

- `extraction/` 과 `ingestion/` 은 서로 import하지 않고, 서로의 출력을 입력으로 쓰지 않습니다.
- 두 방식이 공유하는 것은 원천 문서, 공통 데이터 계약, `src/common` 뿐입니다. 따라서 각자 독립적으로 개발·테스트할 수 있습니다.
- `ingestion/` 은 `src/common` 의 `PostgresDbSession` 을 사용합니다. 기존 `CardRepository` 를 재사용할지는 테이블 설계 때 결정합니다 ❓.
- `extraction/` 이 결과 A를 PostgreSQL에 저장할지(비교를 DB에서 할지)는 미정입니다 ❓.

## 8. 향후 확정이 필요한 사항

| 항목 | 상태 |
|---|---|
| 공통 데이터 계약 (4절 전체) | ❓ 공동 합의 필요 — 가장 먼저 결정 |
| 김병주 방식의 원천 텍스트 확보 방법 (이현근 파싱 결과 공유 / 별도 파싱) | ❓ 비교 범위가 달라짐 ([architecture.md](architecture.md) 4절) |
| DB에서 AI를 호출하는 방식과 Supabase 지원 여부 | ❓ 기술 검증 필요 |
| 결과 A·B 비교 코드·정답셋 위치, 비교를 파일에서 할지 DB에서 할지 | ❓ 미정 |
| 최종 데이터 확정 방식 (한 방식 채택 / 결과 병합 / 사람 승인) | ❓ 미정 |
| `ingestion/` 폴더 이름 | ❓ 검토 의견만 있음 ([directory_structure.md](directory_structure.md) 9절) |
| `run_offline_tests.py` 에 card_benefit 테스트 포함 여부 | ❓ 미정 (루트 스크립트 변경 필요) |
| Neo4j 적재·GraphRAG 검색 | ⏳ 향후 공동 |
