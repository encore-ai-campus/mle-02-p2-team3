## 0. 개정 이유 (기존안과 달라진 점)

| 항목 | 기존안 | 개정안 | 이유 |
|---|---|---|---|
| 핵심 질문 | 왜 이 카드가 추천됐는가 | **조건 하나가 바뀌면 무엇을 다시 봐야 하는가** | [과제 매핑표](과제_매핑표_10.29.md)의 확정 핵심 시연(공유 조건 변경 → 영향 추적)과 PPT 스토리를 일치시킨다 |
| 1차 사용자 | 불분명(고객/마케팅) | 카드사 **내부**: 상품 기획·준법·상담 | 고객 대면 추천·광고의 준법 부담을 피하고, 실제 업무 문제에 맞춘다 |
| 판단 과정 | 독립 축 | 영향 분석·판정 결과의 **근거 경로** | 근거 표시는 RAG의 기본 요건이라 단독 차별점이 되기 어렵다 |
| 오답 분석 | 독립 축 | 엔진을 **믿을 수 있는 이유**(검증 장) | 도입 동기가 아니라 신뢰 근거로 쓴다 |
| 마케팅 | 수식어·의도별·기간별 문구 노출 | 문구를 그래프의 `Copy` 노드로 두고 **약관 정합성·재심의 대상**으로 관리(제안) | 문구 노출은 기존 CMS로 가능하다. 실무 부담은 문구와 약관의 일치 관리다 |
| 판정 | 적합/추천 | **적용 / 미적용 / 판단 불가(사유)** 3상태 | 근거가 부족할 때 답하지 않는 것이 금융권 신뢰의 핵심이다 |

## 1. 핵심 메시지

**"조건 하나가 바뀔 때, 다시 봐야 할 카드·혜택·조항·문구를 근거와 함께 찾아주는 하나카드 약관 조건 엔진."**

마지막 장 메시지:

> **정답을 말하는 AI보다, 놓치는 조건과 답할 수 없는 지점을 먼저 알려주는 AI.**

## 2. 첫 장 질문

> **"상품권 구매 실적 제외 조항이 바뀌면, 하나카드 몇 개 상품의 어떤 혜택과 안내 문구를 다시 봐야 합니까?"**

- 근거: ONE PICK STYLE·PLAY·BT·에너지 더블 4종 모두 전월실적 산정에서 상품권 구매를 제외한다 [확인: `card_scope_comparison_gpt_review.md` 3절].
- 같은 '상품권'이라도 카드·혜택마다 **실적 제외 / 혜택 제외 / 적립 제외**로 범위가 다르다 [확인]. 이 차이가 질문을 어렵게 만든다.

## 3. 추천 PPT 흐름 (10장)

| # | 장 | 보여줄 내용 | 상태 |
|---|---|---|---|
| 1 | 문제 질문 | 위 첫 장 질문 | — |
| 2 | 업계의 문제 정의 | 신한카드 2026-09-09 발표: 환각·일관성 부족·복합 조건 누락·정책/규정 미반영을 해결할 조건 구조화 AI 엔진 개발 착수 [확인]. 상품설명서의 부가서비스 유지·변경 고지 조항 [확인] | — |
| 3 | 왜 어려운가 | 실제 PDF 사례: 상품권의 범위 차이, STYLE·PLAY 제외 조항의 문자 단위 동일, 표 자동 추출 실패(STYLE·PLAY 표 0개, BT 행 병합) [확인] | — |
| 4 | 해결 구조 | `Card → Benefit → Condition → Clause`(+ 제안: `Copy`) 그래프, 이중 추출 교차 검증 | ⏳ |
| 5 | **시연 1** | 3상태 판정 + 근거 경로 | ⏳ |
| 6 | **시연 2 (핵심)** | 조건 변경 → 영향 카드·혜택·조항 목록 | ⏳ |
| 7 | **시연 3** | 오답 전후 비교 + 해결하지 못한 사례의 판단 보류 | ⏳ |
| 8 | 검증 수치 | 골든 질문 결과, 가능하면 일반 RAG와 비교(불리한 항목도 공개) | ⏳ |
| 9 | 확장 제안 | 문구 정합성 검사, 상담 채널 연동, 마케팅 분리 원칙 | 제안 |
| 10 | 한계와 마지막 메시지 | 문서 최신성 미확인, 수작업 보정, 소규모 데이터의 SQL 대비 우위 없음 | — |

M0~M9 산출물 증빙(전처리 전후, 스키마, 프롬프트, 적재 건수, Cypher, 검증 기록)은 각 장 하단 또는 부록에 둔다. 본문은 **제안형 흐름**, 증빙은 **기술 부록**으로 나눈다.

## 4. 핵심 시연 3개 (예상 · 미검증)

### 시연 1 — 3상태 판정과 근거 경로

| 질문 (가상) | 기대 판정 | 근거 경로 (예상) |
|---|---|---|
| "STYLE로 편의점 CU 결제하면 ONE PICK 캐시백 받나요? 전월실적이 필요한가요?" | **적용**, ONE PICK은 실적 무관 | Card(STYLE) → Benefit(ONE PICK) → Condition(실적 조건 없음) → Clause(1쪽) |
| "STYLE로 상품권을 사면 ONE MORE 대중교통 실적 10만원에 포함되나요?" | **미적용**, 실적 제외 | Card → Benefit(ONE MORE 대중교통) → Condition(전월실적 10만원) → EXCLUDES(상품권 구매) → Clause |
| "○○ 가게가 편의점 혜택 대상인가요?" | **판단 불가**, 사유: 가맹점 업종 분류는 카드사 기준이며 PDF 밖 정보 | 경로가 Merchant 분류 단계에서 끊김 → 사유 표시 |

- 혜택 단위 실적 조건(ONE PICK 실적 무관 / ONE MORE 10만원)을 **카드 전체 조건으로 확대하지 않는 것**을 보여준다.

### 시연 2 — 조건 변경 영향 추적 (핵심)

- 가상 변경: "상품권 구매 실적 제외 조항 변경을 가정"
- 기대 출력: 영향 **검토 후보** 카드·혜택·조항 목록
  - STYLE, PLAY: ONE MORE(대중교통·놀이공원) 실적
  - BT: 인천공항 라운지 실적(50만원)
  - 에너지 더블: 일상생활 서비스 실적(40만원 구간)
  - BIG TICKET처럼 **실적 무관 혜택은 영향 대상에서 제외**되는 것도 함께 보여준다
- 같은 질문을 **Neo4j Browser의 Cypher**와 **MCP 도구 응답**으로 실행해 결과가 일치하는지 보여준다.
- 결과는 자동 정책 변경이 아니라 **사람이 확인할 검토 목록**이다. 실제 공동 관리 정책 여부는 [가정].

### 시연 3 — 오답 전후

- 대표 오류 유형 후보: 혜택 제외와 실적 제외 혼동, 혜택 단위 조건의 카드 전체 확대, `상품/선불전자지급수단` 같은 원문 문구의 임의 정규화.
- 동일 질문·동일 자료로 개선 전후의 답변, 근거 일치, 조건 누락을 비교한다.
- **해결하지 못한 사례 1건은 "판단 보류"로 처리한 모습을 그대로 보여준다.**

## 5. 오답 사례 공개 원칙 (기존안 유지 + 보완)

1. PPT에는 대표 2~3건만 공개하고, 전체 목록·재현 절차는 저장소 문서로 연결한다.
2. 실제 약관과 실행 로그로 재현된 것만 '실제 오답'으로 제시한다. 2일차 말까지 실제 오답을 확보하지 못하면 '가상 시나리오'로 표기한다.
3. GraphRAG가 항상 정답이라고 주장하지 않는다.
4. **추가:** "전부 고쳤다"보다 "어디서 멈추는지 안다"를 보여준다. 미해결 1건을 판단 보류로 공개한다.

## 6. 마케팅 기능의 재배치 (제안 기능)

기존 세 가지 문구(카드 고유 수식어, 검색 의도별 문구, 기간별 캠페인)는 **삭제하지 않고 역할을 바꾼다.**

| 기존 | 개정 | 구현 여부 |
|---|---|---|
| 카드 고유 수식어 노출 | `Copy` 노드로 저장, `CLAIMS → Benefit` 연결 | 여유 시 가상 문구 5개로 시연 |
| 검색 의도별 문구 | 문구 속 주장(예: "커피 할인", "실적 무관")을 약관 혜택·조건과 대조해 **조건 병기 누락·과장 경고** | 제안 |
| 기간별 캠페인 문구 | 혜택 조건이 바뀌면 **재심의가 필요한 문구 목록**을 영향 분석 결과에 포함 | 제안 (시연 2의 확장) |

### 객관성 보호 원칙

1. **판단 먼저, 문구는 나중에:** 판단 결과를 확정한 뒤 마케팅 레이어를 조회한다. 마케팅 데이터는 판단 입력으로 쓰지 않는다.
2. **순위 불변 테스트:** 마케팅을 켜고 끈 두 경우의 판단·순위 결과가 같음을 자동 테스트로 확인한다(구현 시 시연).
3. **조건부 노출:** 약관으로 확인된 혜택이 있는 카드에만 관련 문구를 연결한다.
4. **수치 차단:** 문구에 할인율·한도 등 수치가 있으면 그래프 값과 대조하고, 대조 실패 시 노출하지 않는다.
5. **표시 분리:** 문구는 [광고] 라벨로 판단 영역과 분리한다.
6. 모든 문구는 PPT용 **가상 문구**이며 하나카드 공식 문구가 아니다. 실제 적용 시 카드사 준법심의를 거친 문구만 사용한다.

## 7. MVP와 제안 기능 구분

| 구분 | 범위 |
|---|---|
| **MVP (3일 구현 목표)** ⏳ | 하나카드 2~3종(STYLE·PLAY + BT 또는 에너지 더블) · A/B 파이프라인 독립 추출 → 공통 JSON 비교 → 불일치 목록 · 정규화 · Neo4j 적재(근거·조항 ID 보존) · Cypher 3개(혜택 조회 / **영향 추적** / 판정 경로) · 3상태 판정 · 골든 질문 15~20개 · MCP 도구 1~2개(컷라인 준수) |
| **여유 시** ⏳ | 가상 문구 5개를 `Copy` 노드로 넣어 영향 추적에 포함 · 일반 RAG 기준선 비교 |
| **제안만** | 관리자 승인 UI · 기간 캠페인 운영 · 검색 의도 문구 노출 · CTR·A/B 테스트 · 고객용 채널 · 타사 비교 · 이미지 표 OCR · 개인화 추천 |

`file_pipeline`(이현근)과 `db_pipeline`(김병주)은 **병렬 독립 구현**이다. 발표에서는 "두 방식의 결과가 어긋나는 항목을 사람 검토 대상으로 분류할 수 있다"는 교차 검증 관점으로 설명하되, 처음부터 의도한 설계라고 과장하지 않는다.

## 8. 예상 반론과 답변 준비

| 반론 | 준비할 답변 |
|---|---|
| 카드사의 정본은 PDF가 아니라 내부 상품 DB다 | PDF는 고객에게 **고지된 계약 문구**다. 내부 DB와 고지 문서의 불일치를 감사하는 용도로 가치가 있다 [가정: 내부 시스템 구조 미확인] |
| 카드 3종이면 SQL로 된다 | 맞다. 같은 질의를 Cypher와 SQL로 나란히 보여주고, 노드 유형(조항·문구·채널)이 늘어날 때의 질의 차이로 설명한다. 소규모 성능 우위는 주장하지 않는다 |
| 신한이 이미 비슷한 걸 개발한다 | 차별점이 아니라 **업계가 인정한 문제**라는 근거로 쓴다 |
| 표 추출이 자동인가 | 기본 표 추출은 대부분 실패했고 수작업 보정이 들어간다고 공개한다 |
| 고객에게 추천하면 규제 문제는 | 이번 범위는 내부 도구다. 고객 대면 추천·광고는 금융소비자보호법상 권유·광고 규율 검토가 필요하다 [해석, 준법 확인 필요] |
| 문서가 최신인가 | 시행일·현재 유효 여부·재배포 조건은 미확인이며, 문서 해시와 버전을 함께 표기한다 |
