## 1. 핵심 메시지

**"AI 서비스는 여러 개여도, 카드 혜택의 판단 기준과 근거는 일관되게 관리되어야 합니다."**

**구체적 문제 해결:** "조건 하나가 바뀔 때 다시 검토해야 할 카드·혜택·약관 조항을 근거와 함께 찾아주는 카드사 공통 AI 판단 엔진."

### 카드사 도입 논리 — 검색 서비스가 아닌 재사용 가능한 엔진

- **정확성:** 비정형 상품설명서의 혜택·실적·제외 조건을 적용 범위와 함께 구분하고, 검증된 근거를 제공한다.
- **추적성:** 답변·판단 불가의 사유, 관련 원문, 가상 조건 변경 시 영향 검토 대상을 추적한다.
- **재사용성:** 동일한 조건 조회·판단 서비스를 내부 업무 AI, 자사 앱·상담 AI, 제휴된 외부 AI에 **API 또는 MCP 어댑터**로 제공할 수 있도록 설계한다.
- **도입 명분:** 개별 채널마다 별도 약관 판단 로직을 만드는 대신 공통 관리 계층을 둔다는 제안이다. 단, 기존 카드사 상품 DB·규칙 엔진을 대체한다고 주장하지 않고 **공개 약관의 비정형 조건 해석·근거 검증을 보완**하는 용도로 설명한다.
- **현재 입증 범위:** 여러 채널의 실제 비용 절감, 오답 감소, 최신성 보장, 카드사 도입 수요는 실측·검증되지 않았다. 이번 프로젝트는 **엔진의 정합성 및 로컬 MCP 재사용 시연**까지만 검증 목표로 삼는다.

마지막 장 메시지:

> **정답을 말하는 AI보다, 놓치는 조건과 답할 수 없는 지점을 먼저 알려주는 AI.**

> **카드사 공통 판단 기준을 관리하고, 필요한 AI 채널에 동일한 근거를 공급하는 구조.**

## 2. 첫 장 질문

> **"상품권 구매 실적 제외 조항이 바뀌면, 하나카드 몇 개 상품의 어떤 혜택과 안내 문구를 다시 봐야 합니까?"**

- 근거: ONE PICK STYLE·PLAY·BT·에너지 더블 4종 모두 전월실적 산정에서 상품권 구매를 제외한다 [확인: `card_scope_comparison_gpt_review.md` 3절].
- 같은 '상품권'이라도 카드·혜택마다 **실적 제외 / 혜택 제외 / 적립 제외**로 범위가 다르다 [확인]. 이 차이가 질문을 어렵게 만든다.

## 4. 핵심 시연 3개 (예상 · 미검증)

### 시연 1 — 3상태 판정과 근거 경로

| 질문 (가상) | 기대 판정 | 근거 경로 (예상) |
|---|---|---|
| "STYLE로 편의점 CU 결제하면 ONE PICK 캐시백 받나요? 전월실적이 필요한가요?" | **적용**, ONE PICK은 실적 무관 | Card(STYLE) → Benefit(ONE PICK) → Condition(실적 조건 없음) → Clause(1쪽) |
| "STYLE로 상품권을 사면 ONE MORE 대중교통 실적 10만원에 포함되나요?" | **미적용**, 실적 제외 | Card → Benefit(ONE MORE 대중교통) → Condition(전월실적 10만원) → EXCLUDES(상품권 구매) → Clause |
| "○○ 가게가 편의점 혜택 대상인가요?" | **판단 불가**, 사유: 가맹점 업종 분류는 카드사 기준이며 PDF 밖 정보 | 경로가 Merchant 분류 단계에서 끊김 → 사유 표시 |

- 혜택 단위 실적 조건(ONE PICK 실적 무관 / ONE MORE 10만원)을 **카드 전체 조건으로 확대하지 않는 것**을 보여준다.

### 시연 2 — 조건 변경 영향 추적 (핵심)

- 가상 변경: "상품권 구매 실적 제외 조항 변경을 가정"
- 기대 출력: 영향 **검토 후보** 카드·혜택·조항 목록
  - STYLE, PLAY: ONE MORE(대중교통·놀이공원) 실적
  - BT: 인천공항 라운지 실적(50만원)
  - 에너지 더블: 일상생활 서비스 실적(40만원 구간)
  - BIG TICKET처럼 **실적 무관 혜택은 영향 대상에서 제외**되는 것도 함께 보여준다
- 같은 질문을 **Neo4j Browser의 Cypher**와 **MCP 도구 응답**으로 실행해 결과가 일치하는지 보여준다.
- 결과는 자동 정책 변경이 아니라 **사람이 확인할 검토 목록**이다. 실제 공동 관리 정책 여부는 [가정].

### 시연 3 — 오답 전후

- 대표 오류 유형 후보: 혜택 제외와 실적 제외 혼동, 혜택 단위 조건의 카드 전체 확대, `상품/선불전자지급수단` 같은 원문 문구의 임의 정규화.
- 동일 질문·동일 자료로 개선 전후의 답변, 근거 일치, 조건 누락을 비교한다.
- **해결하지 못한 사례 1건은 "판단 보류"로 처리한 모습을 그대로 보여준다.**

## 5. 오답 사례 공개 원칙 (기존안 유지 + 보완)

1. PPT에는 대표 2~3건만 공개하고, 전체 목록·재현 절차는 저장소 문서로 연결한다.
2. 실제 약관과 실행 로그로 재현된 것만 '실제 오답'으로 제시한다. 2일차 말까지 실제 오답을 확보하지 못하면 '가상 시나리오'로 표기한다.
3. GraphRAG가 항상 정답이라고 주장하지 않는다.
4. **추가:** "전부 고쳤다"보다 "어디서 멈추는지 안다"를 보여준다. 미해결 1건을 판단 보류로 공개한다.

## 6. 마케팅 기능의 재배치 (제안 기능)

기존 세 가지 문구(카드 고유 수식어, 검색 의도별 문구, 기간별 캠페인)는 **삭제하지 않고 역할을 바꾼다.**

| 기존 | 개정 | 구현 여부 |
|---|---|---|
| 카드 고유 수식어 노출 | `Copy` 노드로 저장, `CLAIMS → Benefit` 연결 | 여유 시 가상 문구 5개로 시연 |
| 검색 의도별 문구 | 문구 속 주장(예: "커피 할인", "실적 무관")을 약관 혜택·조건과 대조해 **조건 병기 누락·과장 경고** | 제안 |
| 기간별 캠페인 문구 | 혜택 조건이 바뀌면 **재심의가 필요한 문구 목록**을 영향 분석 결과에 포함 | 제안 (시연 2의 확장) |

### 객관성 보호 원칙

1. **판단 먼저, 문구는 나중에:** 판단 결과를 확정한 뒤 마케팅 레이어를 조회한다. 마케팅 데이터는 판단 입력으로 쓰지 않는다.
2. **순위 불변 테스트:** 마케팅을 켜고 끈 두 경우의 판단·순위 결과가 같음을 자동 테스트로 확인한다(구현 시 시연).
3. **조건부 노출:** 약관으로 확인된 혜택이 있는 카드에만 관련 문구를 연결한다.
4. **수치 차단:** 문구에 할인율·한도 등 수치가 있으면 그래프 값과 대조하고, 대조 실패 시 노출하지 않는다.
5. **표시 분리:** 문구는 [광고] 라벨로 판단 영역과 분리한다.
6. 모든 문구는 PPT용 **가상 문구**이며 하나카드 공식 문구가 아니다. 실제 적용 시 카드사 준법심의를 거친 문구만 사용한다.

## 6-1. MCP 연동: 하나의 조건 엔진, 여러 AI 창구 (과제 범위 · 미구현)

**사업적 문제 정의:** 고객이 카드사 앱이 아닌 외부 AI에서 카드 혜택을 물을 수 있다. 이때 카드사는 외부 AI의 답변·추천 순위·브랜드 문구 표시를 직접 통제하기 어렵지만, **공식 상품 조건과 출처를 조회할 수 있는 도구**를 제공할 수 있다. 이는 카드사의 **정확한 정보 공급**에 관한 제안이지, 외부 AI 답변의 노출 통제권을 확보했다는 뜻이 아니다.

**핵심 메시지:** "외부 AI의 답변 형식은 통제할 수 없어도, AI가 조회할 수 있는 카드사 조건·원문 근거는 관리할 수 있다."

### 자사 AI와 외부 AI는 무엇이 다른가?

**공통점:** 같은 카드사 판단 엔진을 호출한다면 조회한 혜택·조건·원문 근거의 **구조화 결과는 동일하게 제공**할 수 있다. 자사 AI도 MCP를 사용할 수 있지만, 내부 API를 직접 호출해도 된다.

| 구분 | 카드사 자체 앱·AI | 외부 AI 클라이언트(연동 허용 시) |
|---|---|---|
| 조건·근거 조회 | 공통 엔진의 동일 서비스 사용 가능 | 동일 엔진의 MCP/API 조회 가능 |
| 답변·화면 구성 | 카드사가 직접 설계·운영 | 외부 플랫폼이 결정 |
| 자사 캠페인·브랜드 메시지 표시 | 승인·노출 정책을 자체 관리 가능 | 도구로 필드를 제공해도 표시 보장 불가 |
| 다른 회사 상품 비교 | 서비스 범위·보유 데이터에 따라 다름 | 외부 AI가 다른 정보원과 결합할 수 있음 |
| 최신 조건 사용 | 시스템과 운영 절차를 통제 가능 | 도구 호출·캐시·요약에 따라 달라질 수 있음 |

**따라서 둘은 별도 판단 엔진이 아니라 같은 엔진을 쓰는 서로 다른 고객 접점**이다. MCP를 만들었다는 사실만으로 카카오 등 외부 플랫폼의 정식 연동이나 자사 브랜드 노출이 확보되는 것은 아니다.

### 기술 구성 및 역할 구분

```text
로컬 MCP 지원 AI 클라이언트 (예: Claude Desktop)
  → MCP 서버 (얇은 도구 어댑터)
  → 기존 GraphRAG 서비스 / Neo4j Cypher 조회
  → 카드·혜택·조건·약관 근거 및 검토 후보 반환
```

- **GraphRAG:** 비정형 약관에서 추출·검증한 관계를 탐색하고, 조건·적용 범위·근거를 설명한다.
- **MCP:** 기존 조회 함수를 AI 클라이언트가 호출할 수 있게 연결한다. MCP 서버에 별도 약관 판정 로직을 중복 구현하지 않는다.
- **외부 서비스 실제 연동:** 로컬 MCP 호출 시연과 카카오 등 외부 플랫폼의 실제 서비스 연동은 다르다. 외부 연동은 플랫폼의 지원 방식, 보안·인증·승인·배포 정책 확인이 필요하며 **이번 범위에 포함하지 않는다**.

### 아키텍처 개념(구현 전)

```text
                    카드사 공통 조건·근거 조회 서비스
                    (GraphRAG / Neo4j / 필요 시 PostgreSQL)
                               │
                      동일한 서비스 함수 재사용
                    ┌──────────┴───────────┐
                    │                      │
             내부 API 어댑터          MCP 서버 어댑터
                    │                      │
           자사 앱·내부 업무 AI       로컬 MCP 지원 AI
                                     (Claude 등)
```

자사 API + MCP 양쪽 시연이 시간상 어렵다면 **기존 Cypher/서비스 함수 결과와 로컬 MCP 도구 응답의 일치**를 검증하는 것만으로 MVP 범위를 한정한다. 이는 실서비스 다중 채널 운영을 입증하는 것이 아니다.

### 최소 도구 및 시연 계획

| 우선순위 | MCP 도구(안) | 호출 대상 | 시연 내용 |
|---|---|---|---|
| **필수 후보 1** | `get_card_benefits(card)` | 카드별 혜택·조건·원문 근거 조회 | 로컬 AI에서 카드 질문 → MCP 호출 → 근거 포함 결과 반환 |
| **가능하면 2** | `find_affected_by_condition(condition)` | 기존 조건 변경 영향 Cypher 조회 | 변경 가정 → 영향을 검토할 카드·혜택·조항 목록 반환 |
| 후속 | `explain_judgment(card, benefit)` | 판단 경로 설명 | 조건 적용 범위와 출처 경로 노출 |

**시연 검증:** 같은 데이터·조건으로 Neo4j Browser의 Cypher 결과와 MCP 도구의 구조화된 반환값을 대조한다. 외부 LLM이 도구를 호출하지 않거나 응답을 요약·변형할 가능성이 있으므로, **MCP 응답 일치**와 **최종 자연어 답변의 정확성**은 별도 평가한다.

**컷라인:** 기존 [과제 매핑표](과제_매핑표_10.29.md)대로 M8 검증이 3일차 오전까지 끝나지 않았다면 MCP 도구는 `get_card_benefits` 1개만 구현하고 나머지는 후속 과제로 남긴다. **PDF 추출·관계 정합성·오답 검증보다 MCP를 먼저 구현하지 않는다.**

**마케팅 문구와의 관계:** 카드사가 승인한 문구를 도구 응답의 별도 필드로 제공하는 방안은 *여유 시/제안*에 해당한다. 플랫폼이 표시해 준다는 보장은 없다. 약관 사실과 광고를 혼합하지 않으며, 문구 자체 저장·캠페인 운영은 PostgreSQL/CMS 기능이다.

## 7. MVP와 제안 기능 구분

| 구분 | 범위 |
|---|---|
| **MVP (3일 구현 목표)** ⏳ | 하나카드 2~3종(STYLE·PLAY + BT 또는 에너지 더블) · A/B 파이프라인 독립 추출 → 공통 JSON 비교 → 불일치 목록 · 정규화 · Neo4j 적재(근거·조항 ID 보존) · Cypher 3개(혜택 조회 / **영향 추적** / 판정 경로) · 3상태 판정 · 골든 질문 15~20개 · **기존 조회 재사용 MCP 도구 1~2개 + 로컬 AI 클라이언트 호출 검증**(컷라인 준수) |
| **여유 시** ⏳ | 가상 승인 문구 별도 필드 제공 및 `Copy` 노드 5개 영향 추적 · 일반 RAG 기준선 비교 |
| **제안만** | 실제 카카오 등 외부 AI 플랫폼 연동 · 관리자 승인 UI · 기간 캠페인 운영 · 검색 의도 문구 노출 · CTR·A/B 테스트 · 고객용 채널 · 타사 비교 · 이미지 표 OCR · 개인화 추천 |

`file_pipeline`(이현근)과 `db_pipeline`(김병주)은 **병렬 독립 구현**이다. 발표에서는 "두 방식의 결과가 어긋나는 항목을 사람 검토 대상으로 분류할 수 있다"는 교차 검증 관점으로 설명하되, 처음부터 의도한 설계라고 과장하지 않는다.

## 8. 예상 반론과 답변 준비

| 반론 | 준비할 답변 |
|---|---|
| 카드사의 정본은 PDF가 아니라 내부 상품 DB다 | PDF는 고객에게 **고지된 계약 문구**다. 내부 DB와 고지 문서의 불일치를 감사하는 용도로 가치가 있다 [가정: 내부 시스템 구조 미확인] |
| 카드 3종이면 SQL로 된다 | 맞다. 같은 질의를 Cypher와 SQL로 나란히 보여주고, 노드 유형(조항·문구·채널)이 늘어날 때의 질의 차이로 설명한다. 소규모 성능 우위는 주장하지 않는다 |
| 신한이 이미 비슷한 걸 개발한다 | 차별점이 아니라 **업계가 인정한 문제**라는 근거로 쓴다 |
| 표 추출이 자동인가 | 기본 표 추출은 대부분 실패했고 수작업 보정이 들어간다고 공개한다 |
| 고객에게 추천하면 규제 문제는 | 이번 범위는 내부 도구다. 고객 대면 추천·광고는 금융소비자보호법상 권유·광고 규율 검토가 필요하다 [해석, 준법 확인 필요] |
| 문서가 최신인가 | 시행일·현재 유효 여부·재배포 조건은 미확인이며, 문서 해시와 버전을 함께 표기한다 |
| MCP가 있으면 외부 AI의 답변을 통제하나 | 아니다. 카드사가 **구조화된 조건·근거를 제공**할 수 있을 뿐, 외부 AI가 도구를 사용하거나 특정 문구를 노출할지는 통제하지 못한다 |
| 자체 AI와 외부 AI가 같은 MCP를 쓰면 차이가 없지 않나 | **판단 서비스는 공통**이다. 다른 것은 답변 구성·화면·광고 표시 권한, 접점과 추가 정보원이다. 자사 AI는 MCP 없이 내부 API를 써도 된다 |
| 카드사가 왜 별도 AI 검색 서비스 대신 엔진을 도입하나 | **여러 AI 채널이 재사용하는 약관 조건·근거 관리 계층**이라는 가설이다. 운영 가치·중복 감소·오안내 감소 효과는 검증 대상이며, 카드사 기존 시스템과의 통합 전제도 미확인이다 |
| MCP를 위해 별도 판단 엔진을 만드나 | 아니다. 기존 GraphRAG 서비스/Cypher를 호출하는 얇은 인터페이스이며, 단순 정보 조회 자체는 SQL로도 가능하다 |
