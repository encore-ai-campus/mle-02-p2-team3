# 카드 혜택 GraphRAG — 프로젝트 목적 및 MVP 범위

- 기준일: 2026-11-01
- 권장 저장 위치: `src/card_benefit/payment_card/PROJECT_SCOPE.md`
- 상태: 프로젝트 범위 및 설계 판단 기준(실제 코드·DB 변경 지시 아님)

## 1. 프로젝트 핵심 컨셉

이 프로젝트는 **카드 발급 전 사용자가 자신에게 맞는 카드를 고를 수 있도록 돕는 근거 기반 카드 혜택 검색·비교 GraphRAG**를 구현한다.

카드사 공식 상품설명서 PDF에 흩어진 혜택, 조건, 제외, 한도, 예외 규정을 구조화하고, 카드 간 비교 또는 복합 조건 질의에 대해 **원문 근거와 함께 설명**한다.

**핵심 검증 질문:** 카드 상품설명서의 복잡한 조건과 예외를 관계로 구조화하면, 일반 벡터 RAG에 비해 카드 선택·비교 질문에 더 정확하고 근거 있는 답변을 제공할 수 있는가?

> Neo4j 자체를 사용한다는 사실은 GraphRAG의 효과를 입증하지 않는다. 실제 질문·답변 품질과 근거 일치로 비교·검증한다.

## 2. 사용자 및 데이터 전제

- 현재 MVP는 **회원 계정, 실제 소유 카드, 개인별 카드 이용 이력, 결제 내역, 최초 카드 사용 등록일 등의 개인 정보가 없는 상태**를 전제로 한다.
- 사용자가 질문에서 제시하는 관심사(예: 대중교통, 카페, 전월 실적 부담, 혜택 우선순위)는 **해당 질문의 탐색·비교 조건**으로 사용할 수 있다.
- 카드사 공식 상품설명서의 **상품 정책 정보**를 대상으로 답한다.
- 정확히 확인되지 않은 혜택 적용 여부나 계산 규칙은 임의로 확정하지 않고 원문·불확실성을 명시한다.

## 3. MVP 포함 / 제외 범위

| 구분 | 포함 여부 | 설명 |
|---|---|---|
| 카드 혜택 검색·비교 | 포함 | 서로 다른 카드의 혜택, 조건, 한도, 제외 규정 비교 |
| 사용자 질문 기반 카드 후보 탐색 | 포함 | 질문에서 제공된 희망 혜택·조건을 기준으로 후보 제시 |
| 전월 실적·신규 등록 예외의 설명 | 포함 | 특정 상품의 정책 조건과 예외를 정확히 설명 |
| 복합 조건·관계 탐색 | 포함 | 혜택 → 자격·예외·제외·한도·근거 연결 |
| PDF 원문 출처 제시 | 포함 | 답변의 근거가 되는 문서·페이지·인용 연결 |
| 실제 개인별 전월 실적 집계 | 제외 | 결제 이력이 없음 |
| 개인의 카드 등록일 기반 혜택 판정 | 제외 | 개인 등록일이 없으며 판정 엔진이 목적이 아님 |
| 개인별 캐시백 정산·한도 소진 계산 | 제외 | 실거래 데이터·사용 횟수 없음 |
| 조건 실행용 날짜 계산 handler/완전한 규칙 엔진 | MVP 필수 아님 | 정책을 설명하는 데 필요한 조건 의미 보존이 우선 |
| 임베딩·벡터 검색 | 후속 검토 | 초기 관계 탐색 이후 추가 가능; 비교 실험에 필요하면 도입 |
| 원문 주변 문맥 확장 검색 | 후속 구현 가능 | 단, **원문·근거 위치 정보 자체는 현 단계에서 보존 및 검증** |

## 4. 확정된 기본 데이터 흐름

`공식 PDF → LLM 멀티모달 추출 → PostgreSQL 중간 데이터 → 원문 대조·검증·승인 → V6 확정 데이터 → Neo4j 관계 구성 → GraphRAG 검색·답변`

### 각 구성 요소의 책임

- **LLM:** 비정형 PDF의 혜택, 계산 구간, 한도, 예외·제외 조건과 근거 후보 추출. 추출값은 오류 가능성이 있는 후보 데이터로 취급.
- **PostgreSQL V6:** 중간/확정 데이터 저장 및 관계형 정합성 검사. 문서 근거의 연결, 정책·혜택·한도 참조와 변환 시 의미 손실을 검증. 형식 검증 통과만으로 업무 의미의 정확성이 증명되지는 않음.
- **Neo4j:** 검증된 카드·혜택·조건·예외·근거 간 관계를 탐색해 복합 질문에 관련 후보를 찾아주는 역할.
- **GraphRAG/LLM 답변:** 탐색된 관계와 PDF 근거를 함께 사용해 비교·설명하며, 확인되지 않은 조건은 단정하지 않음.

## 5. ONE PICK STYLE — AND/OR 사례의 설계 원칙

대중교통 ONE MORE 혜택의 **전월 실적 자격**은 원문 검토에 근거해 다음과 같이 표현한다.

```text
(전월 실적 10만원 이상) OR (최초 카드 사용 등록일부터 다음 달 말일까지의 유예 기간에 해당)
```

여기에 별도로 버스·지하철 대상, 시외·고속버스 및 철도 제외, 공통 제외, 월 한도 등의 정책을 연결한다. 전월 실적 산정 제외 항목은 실적 합계의 정의에 속한다.

- **이 OR 관계는 실행용 규칙 엔진을 만들기 위해서만 필요한 것이 아니다.** 카드 선택·비교 질문에서 예외 조건을 잘못 설명하거나 잘못 필터링하지 않기 위해 정확히 보존한다.
- 사용자의 실제 카드 최초 사용 등록일이나 결제 이력 없이도 **'신규 등록 시 실적 유예가 있는가?'**라는 상품 규정 질문에는 답할 수 있다.
- V6 조건 JSONB가 OR 표현을 허용하고 `fn_valid_cond_expr` 형식 검증에 통과한 것은 확인되었다. 그러나 해당 조건의 **실행 가능한 handler 계약**까지 입증한 것은 아니며, MVP에서 개인별 유예 기간 판정 handler는 필수 구현 대상으로 두지 않는다.
- 조건의 예외 범위, 제외 대상 및 원문 근거가 틀렸다면 JSON 형식 통과 여부와 무관하게 보완해야 한다.

## 6. 대표 사용자 질문

- “전월 실적 부담이 적으면서 대중교통 혜택이 있는 카드는?”
- “신규 발급 후 실적이 없어도 대중교통 혜택을 받을 수 있는 카드가 있어?”
- “대중교통 캐시백 5%라고 하는데 어떤 교통수단은 제외되나요?”
- “A카드와 B카드의 혜택 조건과 월 한도는 어떻게 달라?”

이 질문들은 **상품 선택·비교를 위한 정책 설명**이다. 개인별 승인/정산 결과를 보장하는 판정은 범위에 포함하지 않는다.

## 7. 현재 진행 단계와 진입 기준

### A7-1 — 매핑·근거·의미 검토(현재)

- 실제 1페이지 추출 후보: 혜택 4건, 카드 조건 4건, 근거 30건.
- 주요 금액·횟수 일치는 검토했으나 근거 누락, 중복된 문구의 표 행 연결, 규칙 중첩, `1인 1매`, 정책 적용일 등 미해결 쟁점이 있다.
- 대중교통 실적 조건의 AND 오류는 발견되었고, 원문 의미에 따른 OR 수정안을 문서화했다.
- **A7-1에서는 확정 업무 테이블에 INSERT하지 않는다.**

### A7-2 — 수동 시험 적재(별도 승인 후)

- 원문 근거, 조건 의미, 필수 정책값의 미해결 항목을 확인한 뒤 실행.
- 수동 SQL 및 ROLLBACK을 통해 V6의 표현력·참조 정합성·SQL 게이트 검증을 수행.
- 특정 오류를 SQL 게이트가 자동으로 발견했는지, 사람의 PDF 대조로만 발견했는지 **구분하여 기록**.
- 결과를 근거로 V6 유지·단순화와 Neo4j 변환 방식을 재판단.

## 8. 향후 검색 및 평가 원칙

1. **관계 중심 검색을 먼저 검증:** 카드 → 혜택 → 조건/예외/한도 → 원문 근거.
2. **원문은 반드시 추적 가능:** PDF/페이지/청크/근거 위치를 이용하여 원문 의미를 재확인할 수 있어야 함. 주변 문맥을 앞뒤 20글자 등으로 확장하는 조회 기능 자체는 나중에 구현할 수 있음.
3. **임베딩은 독립적인 후속 선택:** 필요시 벡터 검색을 추가해 관계+벡터 하이브리드 GraphRAG로 확장.
4. **비교 실험:** 동일한 카드 자료, 질문 세트와 평가 기준에서 GraphRAG와 일반 벡터 RAG를 비교. 조건·예외 누락, 잘못된 적용 판단, 근거 정확도, 답변 일관성 등을 관찰.

## 9. 변경 및 협업 원칙

- 이 문서는 **프로젝트 범위에 대한 기준 문서**이며 실행·DB 변경 승인이 아니다.
- V6 DDL/DBML, 기존 DB, 유료 API 호출, Git Commit/Push는 별도 승인 없이 변경하거나 실행하지 않는다.
- `file_pipeline`은 팀원 소관이므로 임의 수정하지 않는다.
- Service / Repository / SQL Mapper 구조와 기존 미커밋 변경 사항을 보호한다.
- 새로운 패키지·폴더·추상화를 MVP 범위 확인 없이 추가하지 않는다.
