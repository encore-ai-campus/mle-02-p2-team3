# Git pull · commit · push 문제 해결

## 현재 상태

- 현재 브랜치: `main`
- 로컬 전용 커밋: 2개
- 원격 전용 커밋: 15개
- 작업 트리: clean
- 원인: 로컬과 원격 `main`이 서로 다른 커밋을 가지고 있어 분기됨
- `git pull`은 통합 방법을 지정하지 않아 중단됨
- 로그의 `for-each-ref`, `git status`는 VS Code가 상태를 확인한 기록이며 오류가 아님

## 해결 순서

1. 저장소와 변경 상태 확인

   ```bash
   git status
   git log --oneline --graph --decorate -10
   ```

2. 작업 트리가 깨끗한지 확인
   - `working tree clean`이면 다음 단계로 진행
   - 수정 파일이 있으면 커밋하거나 임시 보관
   - 현재 기록된 상태는 clean

3. 원격 변경을 먼저 반영하고 로컬 커밋을 재적용

   ```bash
   git pull --rebase origin main
   ```

4. 충돌이 발생하면 파일을 수정한 뒤 계속 진행

   ```bash
   git status
   git add <해결한-파일>
   git rebase --continue
   ```

   - 중단하고 원래 상태로 돌아가려면 `git rebase --abort`
   - 충돌 해결을 마칠 때까지 push하지 않음

5. 동기화 결과 확인

   ```bash
   git status
   git log --oneline --graph --decorate -10
   ```

6. 원격 브랜치로 push

   ```bash
   git push origin main
   ```

## 커밋이 작성자 오류로 실패할 때

- `fatal: no email was given and auto-detection is disabled`는 현재 저장소에 작성자 정보가 없다는 뜻
- 저장소에만 이름과 이메일 설정

  ```bash
  git config user.name "LEE"
  git config user.email "<GitHub에 등록한 이메일>"
  ```

- 설정 확인

  ```bash
  git config --get user.name
  git config --get user.email
  ```

- `--global`은 모든 저장소에 적용하므로, 특정 저장소만 설정할 때는 생략

## 주의

- `git reset --hard`나 강제 push(`git push --force`)는 로컬 또는 원격 커밋을 잃게 할 수 있으므로 사용하지 않음
- rebase가 성공한 뒤 push가 거부되면 `git status`와 원격 변경을 다시 확인
- 이 문서는 일반적인 복구 절차이며, 저장소의 보호 규칙에 따라 `main` 직접 push 대신 작업 브랜치와 PR을 사용해야 할 수 있음
