# M1 — 전처리 전후 추적 예시

이 문서는 M1의 문서 인덱스 → 페이지 추적 → 청킹 흐름을 설명한다. 아래 전후 예시는 **합성 데이터**다. 예시 식별자와 값은 실제 문서나 실행에서 얻은 것이 아니며, PDF 문구·청크 본문·실제 처리 결과를 포함하지 않는다.

## 입력과 출력의 연결

현재 `doc_index`는 원본 목록과 PDF를 대조해 문서 인덱스를 만들고, 대표 문서에 대해 페이지별 추적 JSON을 생성한다. `doc_id`는 PDF SHA-256 앞 16자리다. 페이지 추적에는 페이지 번호, 페이지 텍스트, 품질 정보가 기록된다. `chunking`은 이 추적 정보를 입력으로 사용해 페이지별 연속 범위를 청크로 나누고, 각 청크에 페이지 안의 1부터 시작하는 `start_pos`와 끝 문자를 포함하는 `end_pos`를 기록한다.

다음은 **구조를 보여 주기 위한 가상 한 페이지 사례**다. 실제 PDF의 문장, 숫자, 표 내용이나 OCR 산출물을 옮긴 것이 아니다.

| 단계 | 합성 예시의 형태 | 추적 필드 예시 |
|---|---|---|
| 전처리 전 입력 | PDF 한 쪽에 제목 영역, 표 영역, 설명 영역이 있다고 가정 | 문서 자체에는 파이프라인 식별자가 아직 부여되지 않은 상태 |
| 문서 인덱스 | 문서 행이 인덱스에 등록됨 | `doc_id=0123456789abcdef` (가상), `file_path`는 실행 환경의 원본 위치를 가리킴 |
| 페이지 추적 | PDF에서 얻은 해당 쪽 텍스트와 페이지 메타데이터가 추적 JSON에 연결됨 | `page_no=3` (가상) |
| 청크 1 | 이 93자 가상 페이지는 현재 구현의 4,000자 기준 이하이므로 페이지 전체가 한 청크가 됨 | `chunk_id=0123456789abcdef-p0003-c01`, `page_no=3`, `start_pos=1`, `end_pos=93` |

`start_pos`와 `end_pos`는 각 페이지 텍스트 기준의 문자 위치이며 양 끝을 모두 포함한다. 따라서 위 합성 예시의 범위는 겹치거나 비지 않는다. 현재 구현은 4,000자 이하인 쪽을 하나의 청크로 두며, 긴 쪽은 최소 400자 이후에 발견된 제목 위치를 분할점으로 사용할 수 있다. 실제 입력에서 청크 경계와 개수는 페이지 텍스트 길이 및 분할 규칙에 따라 달라지며, 위의 숫자는 실행 기록이 아니다.

## 전처리 전후를 읽는 방법

- **전처리 전:** 페이지에는 사람이 읽는 순서의 제목·본문·표가 함께 있을 수 있다. PDF의 레이아웃에 따라 텍스트 추출 순서가 시각적 읽기 순서와 다를 수 있다.
- **전처리 후:** 페이지 텍스트는 `doc_id`와 `page_no`로 문서에 연결된다. 청크는 원문 페이지에서 잘라낸 연속 범위이며, `chunk_id`와 위치 필드로 원래 페이지 구간을 가리킨다. 이 기록은 내용의 의미가 맞다고 보증하지 않는다.
- **제목:** 청킹 구현은 긴 페이지에서 PDF 페이지의 줄과 표 영역을 바탕으로 제목 위치를 찾는다. 청크에 제목 메타데이터가 붙을 수 있고, 제목 위치는 분할 경계 결정에 사용된다. 짧은 페이지는 제목 탐색을 생략할 수 있다.
- **표:** 표 영역은 제목 위치 탐색에 활용된다. 인덱스의 표 추출 점검은 페이지 글자와의 일치 신호를 계산하는 용도다. 표를 일반 문장으로 재해석하거나 셀의 의미를 자동 보장하는 단계로 간주하지 않는다. 행·열 관계가 불분명하면 별도 점검 대상으로 남긴다.
- **OCR:** 인덱스가 OCR 필요(`ocr_needed=Y`)로 분류한 이미지 PDF는 현재 `doc_index.batch`의 일반 추적 대상에서 제외되며 건너뜀 사유로 보고된다. 따라서 이 경우 이 파이프라인이 OCR을 수행했다고 기록하면 안 된다. 별도의 승인된 OCR 결과를 사용한다면 쪽별 텍스트와 위치 정합성을 확인한 뒤 처리 경로와 도구를 실제 실행 메타데이터에 적는다.

## 페이지 재결합 점검

청킹 구현은 각 페이지에 대해 청크 범위가 페이지 텍스트를 빠짐없이, 겹침 없이 재구성하는지 확인한다. 확인 조건은 개념적으로 다음과 같다.

```text
페이지 텍스트 = 해당 페이지 청크 범위를 원래 순서대로 이어 붙인 텍스트
```

위 합성 예시에서는 `page_no=3`의 1–93 구간이 가상의 페이지 텍스트 전체가 되어야 한다. 실제로는 `check_pieces`가 페이지의 0 기반 슬라이스를 이어 붙여 같은지 검사하고, 저장되는 `start_pos`는 1 기반·끝 포함 규약으로 기록한다. 빈 페이지에는 청크가 없어야 한다. 이 문서의 합성 예시 자체는 파이프라인에 넣어 실행한 테스트나 실측 검증이 아니다.

## 팀 작성란 — 실제 선정 문서 실행 메타데이터

아래 항목은 팀이 대표 문서를 확정하고 승인된 실행을 마친 뒤 실제 산출물과 대조해 채운다. 미확인 값은 추정하지 말고 `미기록` 또는 `미실행`으로 둔다. 원문, OCR 전문, 청크 본문, API 키, 로컬 절대 경로는 적지 않는다.

| 필드 | 팀 기록 |
|---|---|
| 대표 문서명 / 발행 기관 | 미기록 |
| 공식 출처·URL 및 문서 버전/게시일 | 미기록 |
| 이용·제출 가능 범위 확인자와 확인일 | 미기록 |
| 인덱스 실행일 / 도구 버전 또는 커밋 | 미실행 |
| 실제 `doc_id` (필요 시 SHA-256 전체값은 비공개 작업 폴더에 보관) | 미실행 |
| 처리 쪽 수 / 성공·건너뜀·실패 건수 | 미실행 |
| OCR 필요 여부 및 사용했다면 도구·검토 상태 | 미확인 |
| 선택 표본의 `chunk_id`, `page_no`, `start_pos`, `end_pos` | 미실행 |
| 페이지 재결합 점검 결과 및 확인한 표본 수 | 미실행 |
| 처리 결과 위치 (저장소 밖의 작업 폴더임을 확인; 실제 경로 대신 보관 위치 유형만 기록 가능) | 미실행 |
| 팀 검토자 / 검토일 / 보완 사항 | 미기록 |

실제 문서 처리와 표본 확인 전까지 M1의 합성 설명은 제출용 전처리 흐름 예시일 뿐, 선정 문서의 실행 증거가 아니다.
