# 부분 완료 과제의 완료 전환 실행계획

작성일: 2026-11-09  
범위: 카드 상품설명서 도메인, 기존 `payment_card/file_pipeline` 구현 재사용, 제출 산출물은 `src/lee_file_pipeline/`에 정리.

## 목표

M0–M9의 각 항목을 실제 증거로 채워 과제 제출 가능 상태로 만든다. 기존 추출·그래프 구현은 손대지 않고, 문서·검토표·비본문 실행 요약을 이 폴더에서 연결한다. 양식 작성만으로 완료 판정하지 않는다.

## 실행 원칙

- 실제 문서 본문·페이지 텍스트·청크·인용문 및 원문을 포함한 LLM 출력은 저장소에 두지 않는다. 처리 결과 파일은 저장소 밖의 승인된 작업 폴더에 둔다.
- 출처·버전·이용 범위는 공식 출처 및 팀 확인으로 채운다. 확인 전에는 미기록으로 둔다.
- 실제 LLM 호출, DB/Neo4j 접속, Browser/Streamlit 실행은 사용자·팀이 허용된 환경에서 수행한다. Codex는 코드·문서 계약, 안전한 메타데이터, 오프라인 요약과 제출 문서를 정리한다.
- 정확도 수치는 정답 표본·판정 기준·분모·계산이 기록된 경우에만 낸다.
- 기존 코드나 기존 이력 문서의 수정이 필요해지면 수정하지 않고 해당 파일과 충돌을 보고한다. 제출 산출물은 이 폴더에만 추가한다.

## 단계별 실행

### 0. 공통 실행 기준 확정 — M0

**담당:** 팀이 대표 문서와 과제 제출 범위를 확정하고, Codex가 저장소에 이미 있는 비본문 메타데이터를 대조해 기록한다.  
**현재 산출물:** [`M0 데이터 선정 기록`](docs_작업기록/M0_데이터선정_기록.md).  
**작업:** 대표 문서 1건과 그래프 질문 2–3개를 선택한다. 공식 제목·발행 기관·URL·게시/개정일·파일 형식·기준일·이용/공유 범위·선정 이유·포함 범위·민감정보 점검을 채운다. 기존 하나카드 파일럿을 대표본으로 쓸 수 있지만, 현재 제출 버전으로 쓰는지는 팀이 확인한다.  
**완료 조건:** 메타데이터 각 값에 출처가 연결되고, 출처에서 확인한 사실과 팀이 결정한 범위가 구분된다. 이용 허가를 공개 다운로드 사실만으로 추정하지 않는다.

### 1. 전처리 결과를 제출용으로 연결 — M1

**담당:** Codex가 기존 `doc_index/`·`chunking/`의 필드와 알고리즘을 문서화한다. 팀원이 대표 문서에서 표·페이지 구조 및 추적 결과를 확인한다.  
**관련 자료:** [`문서 인덱스`](../card_benefit/payment_card/file_pipeline/doc_index/README.md), [`청킹`](../card_benefit/payment_card/file_pipeline/chunking/README.md).  
**작업:** `doc_id`, `chunk_id`, `page_no`, `start_pos`, `end_pos`의 연결, 제목·표·OCR 처리 기준, 청크 재결합 확인 절차를 정리한다. 전후 예시는 합성 입력으로 보여 주고 실제 문서 처리 근거는 페이지/청크 ID·건수·검토일 같은 비본문 정보로 기록한다.  
**완료 조건:** 선택 문서의 실제 위치 추적을 팀이 확인했고, 합성 예시와 실제 처리 사실을 명확히 구분했다. 원문이나 청크 본문은 제출 폴더에 없다.

### 2. 스키마와 실제 프롬프트 실행본을 연결 — M2·M3

**담당:** Codex가 기존 스키마·프롬프트와 설명 문서의 관계 방향·필드를 대조한다. 팀은 제출할 실행본(run)을 선택해 모델·일자·코드 버전과 prompt fingerprint를 기록한다.  
**현재 산출물:** [`추출 계약`](extraction_혜택추출/과제_추출-계약.md).  
**작업:** `Benefit`, `Condition`, `Limit`, `Target` 추출 계약과 Card/`OFFERS`의 그래프 조립 책임을 구분한다. 실제 사용하는 `build_prompt(chunk)` 소스 경로, 스키마 버전, 프롬프트 규칙을 run 식별자와 연결한다. prompt hash/fingerprint는 실행 메타데이터에서 확인하고, 청크 본문이 결합된 전체 prompt는 저장소에 덤프하지 않는다.  
**완료 조건:** 발표 자료의 개체·관계 방향이 실제 코드와 일치하고, 제시한 실사용 prompt source·fingerprint·model·실행일이 같은 run을 가리킨다. run metadata가 없으면 M3는 source 확인 완료, 실실행본 연결 미확인으로 남긴다.

### 3. 재현 가능한 추출 run과 요약 — M4

**사전 조건:** M0–M3가 고정되고, 팀이 승인한 문서 인덱스·청크 위치·모델·새 저장소 외 작업 폴더를 지정한다.  
**담당:** 팀이 실제 `--execute`를 수행한다. Codex는 실행 절차와 비본문 결과 요약 양식을 정리한다.  
**현재 실행 안내:** [`추출 계약의 재현 절차`](extraction_혜택추출/과제_추출-계약.md#재현-안내).  
**기록할 값:** run ID, 기준 코드 커밋 또는 코드 스냅샷 식별, 문서/청크 입력 식별자, 선택 청크 수, model, 실행일, 결과·파싱·검증·실패 건수, 그래프 CSV 생성 여부 및 외부 경로.  
**완료 조건:** 팀이 새 작업 폴더에서 실행해 결과와 검증 요약을 보유하고, 제출 문서에서 해당 run을 재현할 수 있다. 이 단계만으로 의미 정확도는 주장하지 않는다. 원문이 포함된 결과는 저장소 밖에 둔다.

### 4. 사람 검토로 대표 ID를 확정하고 관계 endpoint 갱신 — M5

**사전 조건:** M4 run을 하나 고정하고, 같은 run의 추출 노드·관계 ID를 기준으로 한다.  
**담당:** 팀의 문서 검토자/스키마 담당자가 사람 판정을 한다. Codex는 허용된 비본문 ID와 합성 데이터의 매핑·endpoint 검사만 지원할 수 있다.  
**현재 양식:** [`그래프 검증 안내의 M5 표`](graph_그래프/과제_그래프-검증-안내.md#m5--중복-개체-검토와-대표-id-결정).  
**작업:** 동일 유형 내 정규 표기 후보를 만들고, 유사도는 후보 생성에만 쓴다. MVP 검토안은 통합 후보 2–3쌍과 유사하지만 별개인 대조 1쌍 이상이다. 범위·표본 수는 팀이 확정한다. 검토자는 `통합/유지/보류`, 대표 ID, 근거 위치 참조, 이유 코드, 검토자·일자를 기록한다. 승인된 대표 ID를 관계의 양 endpoint에 적용한 뒤 중복 edge·자기 루프·유형 불일치·끊긴 endpoint를 집계한다.  
**완료 조건:** 실제 문서에서 검토한 사례, 판정자와 근거 위치 참조, 결정 이유, endpoint 치환 후 검사 결과와 미해결 보류 건수가 모두 기록된다. `normalize_values.py` 또는 챗봇 서브그래프 dedupe가 있다는 이유로 완료 처리하지 않는다.

### 5. Neo4j 매핑·적재·출처 재실행 확인 — M6

**사전 조건:** M5 대표 ID 결정이 적용된 하나의 그래프 CSV run, 승인된 로컬 Neo4j 운영자 및 실행 대상 확인.  
**담당:** Codex는 코드·CSV/Cypher의 오프라인 구조를 검토한다. Neo4j 운영자는 Browser에서 대상 확인, 최초 적재, 동일 입력 재실행과 결과 확인을 한다.  
**현재 양식:** [`그래프 검증 안내의 M6 표`](graph_그래프/과제_그래프-검증-안내.md#m6--neo4j-매핑과-적재).  
**작업:** `Fp*` 라벨·`FP_*` 관계, 고유성 제약·`MERGE`, endpoint, 근거의 문서 해시·쪽·위치·상태 연결을 확인한다. 라벨별 노드 수·관계 유형별 수·근거 상태·누락·중복·CSV 대비 차이를 기록한다. 같은 입력을 두 번 적재해 중복 증가가 없는지도 확인한다.  
**과거 차이:** 2026-11-06 기록은 CSV 근거 24,066행과 Neo4j `FpEvidence` 23,970개의 차이 96개를 미해결로 둔다. 코드의 evidence ID 중복 제거는 조사 후보일 뿐 원인 결론이 아니다. 해당 과거 CSV가 남아 있고 오프라인 집계가 허용될 때만 중복 키·제외 건수를 분석한다. 과거 파일이 없으면 과거 수치를 새 run과 억지로 대조하지 않고 새로운 기준선을 기록한다.  
**완료 조건:** 운영자가 최신 run의 적재/재실행 결과와 출처 연결 표본을 기록한다. 96건은 근거가 없으면 미해결로 명시하고, 현재 그래프 검증과 구분한다.

### 6. 실제 Cypher 결과와 시각화 증거 — M7

**사전 조건:** M6에서 현재 run 적재를 확인하고 대표 카드/대상 ID를 정한다.  
**담당:** 팀의 Neo4j 운영자·시연 담당자가 질의 실행과 캡처를 한다.  
**현재 양식:** [`그래프 검증 안내의 M7 표`](graph_그래프/과제_그래프-검증-안내.md#m7--cypher-조회와-시각화).  
**작업:** ① 카드의 혜택·조건·한도·대상, ② 특정 대상의 혜택, ③ 대표 근거 위치 추적 질문 중 2–3개를 선택한다. 기존 `queries.cypher`에서 해당 질의를 실행하고 결과 개체·방향을 해석한다.  
**완료 조건:** 각 질문에 Cypher, 실행 시점/run 식별, 비본문 결과 요약, 관계 방향 해석, 실제 Browser 캡처 위치가 연결된다. 문서의 예시 쿼리나 과거 적재 건수를 새 실행 결과처럼 쓰지 않는다.

### 7. 원문·트리플·정규화·그래프 정합성 판정 — M8

**사전 조건:** M4 run, M5 매핑, M6 적재를 고정하고 문서·청크·트리플 표본과 검토자를 정한다.  
**담당:** 실제 문서 검토자와 그래프 담당자가 공동 판정하고, 구현 담당자가 오류를 조치한 뒤 재확인한다.  
**현재 양식:** [`그래프 검증 안내의 M8 표`](graph_그래프/과제_그래프-검증-안내.md#m8--원문·트리플·그래프-수동-대조).  
**작업:** 작은 대표 문서라면 해당 문서의 결과 관계 전수를 검토하는 방안을 우선 고려한다. 표본이 크면 문서 구간·관계 유형 기준과 분모를 미리 고정한다. 주어/관계/목적어 및 방향, 근거 위치의 관계 지지 여부, 누락·중복·오병합, 스키마 허용성, canonical endpoint, 그래프 적재 여부를 대조한다. 오류는 원인·조치·동일 기준 재검토를 기록한다.  
**완료 조건:** 검토 기준·표본 수·분모·판정 결과·오류 유형·수정·재확인·미해결이 남는다. 실제 라벨과 계산법이 없으면 정확도율은 기재하지 않는다. 보고서에 원문 인용문을 넣지 않는다.

### 8. 전체 재현 시연과 팀 회고 — M9

**사전 조건:** M0–M8 자료 링크가 준비되고 미완료 단계가 표시되어 있다.  
**담당:** 팀 전원이 맡은 단계와 앞뒤 입출력 계약을 설명하고, 시연 진행자가 화면과 실행 흐름을 묶는다.  
**현재 양식:** [`M9 시연·회고 틀`](docs_작업기록/M9_시연_회고_작성틀.md).  
**작업 순서:** 문서 선정 → 전처리·추적 → 스키마·프롬프트 → 추출 → 개체 정규화 → Neo4j 적재 → Cypher·시각화 → 원문 검증·오류 조치 → KPT.  
**완료 조건:** 실제 시연 증거 위치, 담당자별 설명 구간, 각 단계의 입력·출력 연결, 개인 기여, Keep/Problem/Try와 후속 담당·기한을 기록한다. 미실행 화면이나 팀 회고를 대신 만들어 적지 않는다.

## 의존 관계

```text
M0 문서·질문 확정
  → M1 전처리·원문 추적 증거
  → M2/M3 스키마·실사용 프롬프트 연결
  → M4 실제 실행 run
  → M5 사람 판정 및 canonical endpoint
  → M6 Neo4j 적재·출처·재실행 검증
  → M7 Cypher 결과·시각화
M4 + M5 (+ M6 그래프 판정) → M8 원문 정합성 검증
M0–M8 증거 → M9 통합 시연·KPT
```

## 다음 실행 라운드 — M0 고정부터 제출 증거까지

### 라운드 목표와 범위

다음 라운드의 목표는 후보 카드 문서 하나를 기준으로 M0–M9 증거를 같은 run 계보에 연결하는 것이다. 현재 저장소에서 직접 확인한 기준점은 `5ce52f1`이며, 기존 브랜치에는 이 과제와 무관한 미커밋 변경도 있다. 작업은 `src/lee_file_pipeline/`의 제출 안내와 기록물에 한정하고, 기존 `file_pipeline/`, 일반 문서, 이력 파일은 수정하지 않는다. 원문·청크·전체 프롬프트·실제 추출 JSON·비밀 값은 저장소에 복사하지 않는다.

**기준 run 연결:** `M0 문서 버전 → M1 doc_id/chunk_id → M4 팀 기록 ID·결과 지문 → M4 graph exporter ID → M5 승인 매핑 SHA/버전 → M6 import ID → M7 query 기록 → M8 검토 표본 → M9 시연 증거`를 외부 lineage manifest로 잇는다. CLI는 M4 팀 기록 ID를 받지 않고, graph exporter는 `fp_load_runs.csv`용 ID를 `result_dir` 이름과 시각에서 자동 생성한다. M5 변환 뒤에는 별도 M6 import ID를 정해 `fp_nodes.csv`/`fp_edges.csv`의 `run_id`에 기록한다. Neo4j Cypher는 `fp_load_runs.csv`를 run 노드로 적재하지 않으며, Evidence 노드에는 `run_id`가 없으므로 연결된 node/edge ID로 추적한다. 동일한 정규화 스냅샷을 재실행할 때는 동일 M6 ID와 hash를 쓰고, mapping/내용이 바뀌면 새 M6 ID와 별도 격리 대상 DB를 사용한다. 값이 없는 단계는 ID를 지어내지 않고 `미실행`으로 남긴다.

외부 lineage manifest에는 최소한 `m4_record_id`, M4 입력 인덱스/청크 SHA-256, M4 코드 버전, `m4_export_run_id`, 승인된 mapping SHA-256/버전, `m6_import_run_id`, M6 CSV manifest hash, 생성 Cypher SHA-256, 격리 DB의 비밀이 아닌 별칭, 실행 시각, M7 query ID를 연결한다. 같은 M4 결과를 다시 적재할 때 기존 M6 ID를 재사용할지 새로 발급할지 혼합하지 않는다. 이 과제안은 같은 바이트의 동일 스냅샷 재실행에만 같은 ID를 재사용하고, 입력·매핑·출력이 바뀌면 새 ID를 발급한다. 기존 `Fp*` 그래프에 신규 ID를 덧씌우지는 않는다.

| 3 | **M2/M3 계약·실행본 고정** (M0 질문 확정; M1 입력 식별 가능) | Codex 정적 대조; 스키마·추출 담당 승인 | [추출 계약](extraction_혜택추출/과제_추출-계약.md)의 개체·관계 필드와 `Card/OFFERS` 경계를 확인. 실행할 코드 버전/스냅샷, 모델, 입력 지문 기록 방식을 결정. 실제 프롬프트 전문은 보관하지 않음. | 발표 설명의 유형/방향이 코드와 일치. `prompt_sha256`은 청크별 프롬프트 지문으로만 사용하고 코드·전체 실행 ID와 혼동하지 않음. M4 run ID와 모델/코드/입력 식별이 연결될 준비가 됨. |
| 4 | **M4 사전 계획·실행** (M0–M3 Gate 통과) | 팀의 승인된 LLM 실행자; Codex는 안전한 요약 연결 | 원본 인덱스를 수정하지 않는다. 저장소 밖 `input/`에 대표 문서 1행만 담은 `documents.csv`(이 파일 자체를 `--index-csv`로 사용)와 대표 상품-문서 연결만 담은 `product_docs.csv`를 둔다. `chunks/` 바로 아래에는 `<doc_id>.chunks.json` 한 개만 둔다. 입력 세 파일의 해시와 필터 규칙을 기록한다. `run_pilot` 적격 행은 `canonical=Y`, `ocr_needed≠Y`, `doc_role∈{product_guide,web_capture,brand_service}`, `card_type∈{credit,common}`이어야 한다. 주의: `--count 1`은 문서 1개가 아니라 청크 1개를 뜻한다. 문서 전체를 처리하려면 chunk 파일 안의 실제 chunk 수를 먼저 확인하고 그 수만큼 `--count`를 지정한다. 계획 모드는 선택 ID를 출력하지 않으므로, 계획 요약의 `indexed_documents=1`과 `selected_chunks=기대 chunk 수`인지, 준비한 chunk 파일 하나가 그 문서 ID인지 사전 확인한다. 이 격리 구성이면 CLI의 선택 가능한 청크가 그 문서에서만 온다. 계획 통과 후 비어 있는 외부 `WORK_DIR`에서 실행하고 실행 뒤 `selected.json` ID를 원래 chunk 파일 ID와 대조한다. [M4 기록](extraction_혜택추출/과제_실행-재현-기록.md)에 팀 기록 ID, exporter 생성 ID, 코드/입력 지문, 모델·temperature(미지정이면 `None`), 일시, 요청/선택/완료 수, 파싱·객체·스키마·실패 집계와 외부 산출물 위치를 기록한다. | 적격 필드가 모두 맞고 계획 모드의 유일한 입력 문서가 M0 대표본이며 선택 청크 수/예상 토큰이 승인 범위인지 확인한 뒤에만 실제 호출. 결과·요약·자동 점검이 같은 run에 속하고 집계마다 분모가 있음. 실패·부분·검토 필요 결과를 숨기지 않음. `summary.json`/결과 파일이 원문을 포함할 수 있으므로 외부에 둠. 자동 점검은 의미 정확도 증거가 아님. |
| 5 | **M5a 사람 ER 판정** (M4 결과 고정) | 문서 검토자 + ER/그래프 담당 | 동일 유형·동일 카드 안의 표기 변형 후보와 유사하지만 별개인 대조쌍을 선정한다. 사유 코드 목록/버전·판정 규칙을 먼저 고정하고 `통합/유지/보류`, canonical ID, 근거 위치 참조, 판정자·일자를 [M5 표](graph_그래프/과제_그래프-검증-안내.md#m5--중복-개체-검토와-대표-id-결정) 또는 외부 검토표에 기록한다. 기존 CSV 검증기는 그룹·scope·member/canonical 일관성은 검사하지만 유형/속성 호환성을 보증하지 않으므로, 사람 검토와 추가 호환성 검사가 필요하다. | 표본 수·선정 기준·그룹별 판정·미결 건수가 명확함. 근거 부족, 문맥 충돌, 검토자 불일치는 보류. 이름 유사성만으로 자동 병합하지 않음. 초기 병합 범위는 `within_card` + `SAME_AS_STRONG`로 한정하고 across-card `SIMILAR`는 병합하지 않음. |
| 6 | **M5b 승인 매핑·endpoint 재연결 도구** (M5 판정 승인) | 그래프 데이터 담당 구현; 독립 검토자 확인 | 현재 `export_files`는 canonical mapping을 입력받지 않고, `entity_links_loader.validate_links`는 CSV를 검증/매핑 제안할 뿐 graph CSV를 바꾸지 않는다. 기존 `graph/load.py`는 CSV를 주어진 그대로 PostgreSQL 테이블에 적재하는 기능이며 Neo4j 적재기가 아니다. 따라서 구현 시 기존 `file_pipeline`을 수정하지 않고 `src/lee_file_pipeline/graph_그래프/entity_resolution.py` 같은 독립 adapter에서 승인 mapping을 새 출력 폴더로 적용한다. 입력은 원본 `fp_load_runs.csv`, `fp_nodes.csv`, `fp_edges.csv`, `fp_evidence.csv`, 승인 mapping CSV다. Neo4j 변환 CSV 폴더에는 허용된 네 개 `fp_*.csv`만 두고, mapping/edge ID 대응표·전후 집계·hash manifest는 형제 `audit/` 폴더에 둔다. mapping은 타입/카드 범위·핵심 속성 일치, canonical 실존, 중복 그룹·순환 부재를 확인한 뒤 적용한다. node evidence의 `node_id`, 모든 edge endpoint, duplicate edge collapse 뒤의 `edge_id`를 함께 재연결한다. 노드 alias와 원 ID는 감사표에 보존하며 canonical의 핵심 속성을 자동 덮어쓰지 않는다. 원 CSV는 보존한다. | `fp_load_runs.csv`의 run ID를 새 M6 import ID로 발급하고, `fp_nodes.csv`/`fp_edges.csv`의 run ID 및 노드/edge 행수를 일치시킨다. dangling endpoint·유형 위반·중복 ID/edge·self-loop·근거 미연결을 전후 수로 기록하고 각 예외를 격리/사유화. canonical 충돌, 타입/카드/핵심 속성 불일치, 여러 edge가 하나로 합쳐지며 근거 대상이 모호한 경우 출력하지 않고 사람 판정으로 되돌린다. |
| 7 | **M6a CSV/Cypher 정적 검증** (승인된 M5 출력) | 그래프 exporter 담당 + 독립 검토자 | 새 run 디렉터리에서 노드/관계/근거 CSV, 파일별 행 수·SHA-256 manifest, 생성 Cypher와 오프라인 endpoint 검증 요약을 만든다. 모두 저장소 밖에 둔다. 기존 `graph/load.py`의 CSV 검증 함수는 PostgreSQL loader용 CSV 구조 검사이며, 실제 DB 적재에 쓰지 않는다. Neo4j Browser용 스크립트는 `graph/cypher_export.py`가 만들고 `fp_load_runs.csv`를 Neo4j의 run 노드로 적재하지 않는다. 따라서 run lineage는 외부 manifest/로그와 CSV node/edge의 `run_id` 속성으로 연결한다. | CSV↔manifest 일치, 허용 라벨/방향/고유성/MERGE 및 근거 연결 확인. 변환 후 `fp_load_runs.csv`의 node/edge 행수, `fp_nodes.csv`/`fp_edges.csv`의 `run_id`, 네 CSV의 열 규칙이 맞음. Cypher 입력 폴더에 임의 CSV가 섞이지 않음. 출력이 기존 추출 결과를 덮어쓰거나 공유 DB 초기화 명령을 포함하면 중지. |
| 8 | **M6b Neo4j 적재·멱등성 확인** (M6a 검토 통과, 운영자 승인) | 로컬 Neo4j 운영자 + 확인자 | 정규화 전/이전 `Fp*` 데이터와 ID가 충돌하지 않도록 별도 비어 있는 로컬 DB/격리 인스턴스를 우선 사용한다. 이 환경이 없으면 MERGE만으로 기존 duplicate/member 노드를 삭제하지 못하므로 Browser 적재 전에 중지하고 운영자와 대상 전략을 정한다. 승인된 대상에서 적재 전 기준 건수/스크립트 해시를 기록한다. 같은 normalized snapshot과 같은 `run_id`의 동일 스크립트를 1차·2차 실행하고 라벨/관계별 수, endpoint, 근거 위치 표본을 조회한다. | 같은 입력 재실행 전후 중복 증가 없음, CSV 대비 차이 설명, 대표 근거 대상 일치가 기록됨. ID가 같은데 속성이 다른 CSV를 같은 run으로 재사용하지 않는다. 대상·기존 ID 충돌·근거 건수 차이 원인이 불명확하면 재실행/삭제 금지 후 중지. Fp 외 데이터 무변경 확인. 2026-11-06의 96건 차이는 과거 수치로 분리. |
| 9 | **M7 실제 질의·시각화** (M6b 통과) | Neo4j 운영자·시연 담당 | M0 질문 중 실제 연결이 있는 2–3개 질의를 골라 [M7 표](graph_그래프/과제_그래프-검증-안내.md#m7--cypher-조회와-시각화)에 실행 시각·시간대·run ID·질의/매개변수·비본문 행 요약·방향 해석·캡처 위치를 남긴다. 기존 쿼리의 발급사/대상 고정값은 교체한다. 질의의 노드/관계에 `$m6_run_id` 조건을 포함하고, 불가능한 결과는 반환 ID의 `run_id` 속성을 별도 조회해 현재 스냅샷 여부를 증명한다. `queries.cypher` 5번은 위치 필드를 반환하지 않으므로 전용 근거 조회를 사용한다. | 질문에 맞는 schema와 값으로 새로 실행하고 반환된 노드·관계가 M6 import ID와 일치함을 확인. 캡처에 비밀 접속정보·원문·청크 본문 없음. |
| 10 | **M8 사전 등록·원문 대조** (M4/M5/M6 run 고정; M7과 병행 가능) | 독립 문서 검토자 + 그래프 담당; 오류 수정 담당 별도 지정 | 조회 전에 표본 선정 기준·시드·검토자를 고정한다. 분모는 세 층으로 별도 보고한다: (1) M4 원 추출 관계 수와 실패/빈 청크 수, (2) M5 변환 후 고유 관계 수 및 merge/collapse/보류 수, (3) M6 적재 후 확인 관계 수. M4 relation ID→M5 canonical edge ID→M6 확인 ID 대응표를 사용한다. 소규모 파일럿은 원관계 전수 검토를 우선하고, 규모가 크면 관계/유형/페이지 구간별 표본 설계와 크기를 기록한다. 주어·관계·목적어·방향, 근거 직접 지지, 정규화·오병합, 스키마, endpoint·누락·중복을 [M8 표](graph_그래프/과제_그래프-검증-안내.md#m8--원문·트리플·그래프-수동-대조)에 판정한다. | 세 모집단/분모를 혼합하지 않고 검토 판정·오류 유형·원인·조치·동일 기준 재검토·미해결 건수가 모두 있음. 정답 라벨 없이 정확도율을 쓰지 않음. 그래프 수정이 생기면 영향받은 M7 질의를 다시 실행하고 캡처 갱신. |
| 11 | **M9 통합 시연·회고** (M0–M8 링크 및 미완료 표시 확인) | 팀 전체; 발표 담당 통합 | 동일 run을 사용해 문서/범위→전처리 ID→스키마/프롬프트 식별→추출→ER 판정→적재→질의/캡처→검증/오류 조치를 순서대로 시연한다. [M9 작성 틀](docs_작업기록/M9_시연_회고_작성틀.md)에 run/log ID, 증거 위치, 팀원별 입력·출력 설명과 실제 개인 기여를 기록하고 전원이 KPT를 작성한다. | 실행 증거와 팀원 역할/기여의 근거가 연결되고 Keep/Problem/Try에 담당·기한·수용 조건이 있음. 리허설하지 않은 화면·팀 회고는 비워 두거나 미실행으로 표기. |

### 병렬 진행과 권장 일정

M0 결정을 기다리는 동안 문서 담당은 M1 체크 절차를, M8 검토자는 오류 코드/표본 선정안을, 발표 담당은 역할표와 시연 순서를 준비할 수 있다. M0 미확정 상태에서 실제 PDF 처리, M4 호출, M5 대표 ID 판정, M6 적재는 시작하지 않는다. M7 질문 선택은 M6에서 확인된 노드 ID와 연결 경로를 사용한다.

| 권장 일정 | 핵심 작업 | 종료 관문 |
|---|---|---|
| 1일차 오전 | Go/No-go 0, 대표 문서·질문·공유 범위·역할 확정 | M0 통과 또는 보류 사유 확정 |
| 1일차 오후 | M1 처리·위치 표본 확인, M2/M3 계약과 실행본 식별 고정 | 문서/청크 ID 및 스키마·모델·코드 버전 연결 |
| 2일차 오전 | M4 계획 모드 검토 후 승인된 실제 추출, run 요약 | 동일 run의 출력·검증·prompt 지문 기록 |
| 2일차 오후 | M5 사람 판정·매핑/endpoint 검사, M6 CSV/Cypher 정적 확인 및 운영자 적재 | 승인 매핑 및 Neo4j 1·2차 적재 비교 |
| 3일차 오전 | M7 질의·캡처, M8 원문 표본 검토·오류 조치·재확인 | 실제 결과와 검증 기록 연결 |
| 3일차 오후 | M9 end-to-end 시연·전원 설명·KPT, 제출 링크 점검 | 미완료 범위·후속 작업까지 표시한 제출본 |

일정은 3일 진행 권장안이며, 승인·권한·LLM 대기·오류 수정에 따라 늘릴 수 있다. 하루가 끝났다는 이유로 다음 Gate를 건너뛰지 않는다.

### 실행자별 세부 체크리스트

#### M0–M4 입력과 run

1. M0 기록에서 대표 `doc_id`, 전체 SHA-256, 대표 상품명/상품 키, 수집 파일과 공식 출처 확인 방법을 한 건으로 고정한다. 제출 대표본 버전을 기존 후보에서 바꾸면 이유와 새 hash를 적는다.
2. 원본 자료는 열람 권한이 확인된 외부 로컬 경로에서 유지한다. 제출본에 원문이 필요한지와 별도로 실행자료의 접근 권한·삭제/보관 책임자를 정한다.
3. M1 실행자는 기존 인덱스 행과 `<doc_id>.chunks.json`의 `doc_id`, `doc_sha256`, 청크 ID를 맞추고, 페이지별 위치 추적을 샘플 또는 전수로 확인한다. OCR 필요 여부와 표 읽기 순서 문제를 기록한다.
4. 외부 run 입력 폴더는 최소한 다음 구조를 갖춘다. `documents.csv`는 `--index-csv` 입력이자 graph exporter가 읽는 문서 메타데이터 파일이다. 별도 index CSV 파일명을 쓰면 부모 폴더의 `documents.csv`도 같은 행/내용으로 유지한다. 입력 CSV는 원본에서 복사해 대상만 필터링하며 저장소 안 원본을 고치지 않는다.

   ```text
   <RUN_ROOT>/input/documents.csv        # 단일 대표 doc 행, --index-csv로 전달
   <RUN_ROOT>/input/product_docs.csv     # 대표 문서와 확정 카드의 연결 행
   <RUN_ROOT>/chunks/<doc_id>.chunks.json
   <RUN_ROOT>/m4/                        # 새롭고 비어 있는 --work-dir
   ```

5. `documents.csv` 필터는 대표 문서 1행, `product_docs.csv`는 M0에서 확정한 카드 연결만 남긴다. 문서가 여러 카드와 연결된 것으로 표시되면 적용 근거가 확인될 때까지 해당 문서의 `OFFERS` 적재를 멈춘다. 파일별 row count와 SHA-256을 외부 manifest에 기록한다.
6. 계획 모드에서 `indexed_documents=1`, 선택 청크 수가 기대 수와 같음, 예상 토큰이 팀 한도 이하인지 확인한다. `--count`는 chunk 개수다. 선택 청크가 0개, 기대 수와 다름, 대표 doc ID/해시 불일치, token 한도 초과, 작업 폴더 재사용이면 실행하지 않는다.
7. 승인 후 실제 실행한다. 외부 `selected.json`의 ID 집합이 입력 chunk 파일의 ID 집합에 속하는지 확인하고, 문서 수·선택/완료/실패 수·분모·모델·temperature·코드 식별자·결과 지문을 M4 양식에 옮긴다. `prompt_sha256`은 결과별로 확인하고 고유 지문 수와 총 결과 수를 기록한다.

**M4 명령 템플릿** (경로·표본 수·모델은 팀이 정한다. 아래는 실행하지 않은 예시다.)

```bash
INDEX_CSV="<RUN_ROOT>/input/documents.csv"
CHUNK_DIR="<RUN_ROOT>/chunks"
WORK_DIR="<RUN_ROOT>/m4"
COUNT=10  # 실제 문서의 전체 청크 수로 바꾼다.
MODEL_NAME="<APPROVED_MODEL>"

UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit \
  uv run --locked --no-sync python -m payment_card.file_pipeline.extraction.cli pilot-run \
  --index-csv "$INDEX_CSV" --chunk-dir "$CHUNK_DIR" --work-dir "$WORK_DIR" \
  --count "$COUNT" --model "$MODEL_NAME"
```

계획 출력과 비용/토큰 범위를 승인한 뒤 동일 경로·옵션에 `--execute`를 추가한다. 이 명령의 `COUNT`는 처리할 청크 수다. `$WORK_DIR`는 저장소 밖이어야 하며 plan-mode에서 만들어진 `plan.json` 외에 기존 결과나 graph CSV가 있는 작업 폴더는 재사용하지 않는다.

현재 CLI에서 `--temperature`를 생략하면 `None`이 전달된다. 팀이 값을 고정하기로 하면 계획·실행 명령 둘 다에 `--temperature "$TEMPERATURE"`를 추가하고, 정하지 않으면 M4 기록에 `None (옵션 미지정)`이라고 남긴다.

#### M5 정규화와 M6 매핑

1. M4 결과를 고정한 뒤 node CSV에서 동일 유형·동일 카드 범위의 후보 그룹을 만든다. 판정표에는 `group_id`, `scope`, `link_type`, `kind`, `canonical_node_id`, `member_node_id`, 판정/사유 코드, 근거 위치 참조, 검토자·일자를 둔다. `within_card` + `SAME_AS_STRONG`만 병합 후보로 받고 `across_cards` + `SIMILAR`는 검색상 유사 연결로 남긴다.
2. 검토자는 각 group에서 canonical ID가 실제 member 중 하나인지 확인하고, 서로 다른 `node_type`/카드/의미 속성이 섞이면 보류한다. CSV validator 성공은 이 의미 판정을 대신하지 않는다.
3. M5 변환기는 원본 그래프 CSV를 읽기 전용으로 두고 별도 output directory를 만든다. member 노드를 canonical로 치환하고 모든 edge endpoint를 갱신한다. 치환으로 같은 edge가 중복되면 대표 edge ID를 결정하고 이전 edge ID→대표 edge ID 대응표를 저장해 관계 근거를 재연결한다. node evidence의 `node_id`도 canonical로 갱신한다. `fp_evidence.csv`를 Neo4j로 보낼 때 Evidence ID는 `cypher_export.py`가 갱신된 `node_id`/`edge_id`와 근거 위치로 다시 계산한다. 매핑을 설명할 수 없는 근거는 삭제하지 말고 격리/미해결로 집계한다.
4. 새 CSV는 기존 `load.validate_csvs`가 요구하는 column/schema를 유지한다. 결과표에 변환 전후 node/edge/evidence 행수와 고유 ID 수, dangling endpoint, endpoint 유형 오류, 중복 관계/ID, self-loop, 미연결 근거 수를 기록한다. 실패 건을 억지로 0으로 만들거나 원본을 덮어쓰지 않는다.
5. M6a에서 생성한 `load.cypher`와 CSV hash/행수 manifest를 독립 담당자가 대조한다. 스키마 라벨·방향·제약·`MERGE`가 같은 CSV run에서 생성됐는지 확인한다. 이 단계는 오프라인 파일 검토이며 DB 상태 확인이 아니다.
6. 운영자는 M6b 실행 직전 DB 대상(로컬 인스턴스·프로젝트명), 기존 Fp 라벨별 건수, 다른 데이터 보존 여부, import script hash를 확인한다. 대상이 예상과 다르거나 정리/reset이 필요해 보이면 중지하고 담당자 판단을 요청한다. 동일 입력 1차·2차 적재 후 라벨/관계/근거 수, 대표 위치 연결, Fp 외 데이터 변화 여부를 기록한다.

**M6 Cypher 생성 템플릿** (M5 변환 CSV를 검토한 뒤 운영자가 실행. 여기서 실행하지 않았다.)

```bash
CSV_DIR="<RUN_ROOT>/m5/neo4j-import"
OUTPUT_CYPHER="<RUN_ROOT>/m6/load.cypher"
UV_CACHE_DIR=/tmp/uv-cache PYTHONPATH=src:src/card_benefit \
  uv run --locked --no-sync python -m payment_card.file_pipeline.graph.cypher_export \
  --csv-dir "$CSV_DIR" --output "$OUTPUT_CYPHER" --lang ko
```

이 명령은 Cypher 파일을 생성할 뿐 Neo4j에 접속하지 않는다. 운영자는 생성 스크립트·CSV hash·대상 DB를 상호 확인한 뒤에만 Browser에서 적재한다. `graph/load.py --execute`는 PostgreSQL 적재 경로이므로 Neo4j 적재 절차와 혼동하지 않는다.

#### M7–M9 질의·검증·시연

1. M7 각 질문은 고정한 M0 표현을 그대로 따라야 한다. `queries.cypher`의 카드 필터 `우리`와 대상 `커피`는 샘플 값이므로 선택된 카드/대상 값으로 바꾼다. 첫 번째 쿼리의 `FpIssuer`는 현재 exporter가 생성하지 않으므로 대표 질문으로 쓰지 않거나 미지원 사유를 밝힌다. 질의 ID, Cypher 파일/절, 파라미터, 실행 시각·시간대, run ID, 반환 행수와 비본문 결과 요약을 기록한다.
2. 카드 혜택 질의는 카드→혜택→조건/한도/대상 방향을 설명한다. 근거 위치 질의는 노드/edge ID에서 `doc_sha256`, `page_no`, `start_pos`, `end_pos`, `quote_status`를 조회한다. `queries.cypher`의 ambiguous 예시는 근거 위치 증거로 대신 쓰지 않는다.
3. M7 캡처는 실행 직후 화면을 새로고침/재질의해서 만든다. 화면에 원문·인용문·청크 본문, API key, 접속 비밀번호·비밀 URI가 없어야 한다. 저장소 밖 접근 통제 폴더에 두고 저장소 기록에는 파일 경로/ID만 남긴다.
4. M8 검토 계획은 결과를 보기 전에 고정한다. 모집단은 고정된 M4 run의 전체 relation 목록이며, 소규모 파일럿은 전수 검토를 우선한다. 청크별 빈 추출도 선택/제외 여부를 분모와 함께 남긴다. 각 판정은 `근거 없음/누락/방향 오류/중복/오병합/스키마 위반/적재 누락/위치 불명확/기타` 등 오류 코드를 사용한다.
5. 원문 검토자는 로컬 승인 문서를 보며 ID·쪽·위치로 확인하고 원문 내용은 기록표/캡처에 옮기지 않는다. 구현 담당은 수정 후 동일 표본/규칙으로 재확인하고 수정 전후 카운트를 기록한다. 정확도율은 정답 판정 라벨과 분모를 별도로 구성한 경우에만 계산한다.
6. M9 리허설에서는 모든 팀원이 자기 담당 구간과 앞뒤 단계 인터페이스를 각자 설명한다. 진행자 1명이 전체 발표를 맡더라도 다른 팀원이 설명할 순서를 실제 시연에 포함한다. 발표 순서는 M0→M1→M2/M3→M4→M5→M6→M7→M8이며, 막힌 단계는 숨기지 않고 현재 상태·다음 조치를 말한다.
7. 리허설 직후 전원이 Keep/Problem/Try를 작성한다. Try에는 담당자, 기한, 완료 판정 조건을 채우고 개인 기여는 해당 팀원이 한 작업과 확인 가능한 증거를 근거로 작성한다.

**M7 질의 명세(계획 템플릿):** 모든 패턴에서 `FpIssuer`를 사용하지 않고, 현재 `FpCard/FpBenefit/FpCondition/FpLimit/FpTarget/FpEvidence`와 `FP_*` 관계를 사용한다. Card/Benefit/Target 및 관계 row마다 `$m6_run_id`를 확인한다. 기존 쿼리 파일의 샘플 값은 그대로 쓰지 않는다.

| query_id | 입력 파라미터 | 패턴/방향 | 반환할 비본문 필드 |
|---|---|---|---|
| Q1 card-benefit | `$m6_run_id`, `$card_id` | `(Card)-[FP_OFFERS]->(Benefit)`; optional `Benefit→Condition/Limit/Target` | 카드·혜택·관계 ID, 관계 유형, 결과 행수 |
| Q2 target-benefit | `$m6_run_id`, `$target_id` 또는 승인된 대상명 | `(Benefit)-[FP_APPLIES_TO/FP_EXCLUDES]->(Target)`; 가능하면 역으로 `(Card)-[FP_OFFERS]->(Benefit)` 연결 | 대상·혜택·카드 ID, 적용/제외 구분, 결과 행수 |
| Q3 evidence-location | `$m6_run_id`와 `$node_id` 또는 `$edge_id` | 노드는 `FP_HAS_EVIDENCE`; edge는 관계 ID로 연결된 `FpEvidence.edge_id` 속성 조회 | `doc_sha256`, `page_no`, `start_pos`, `end_pos`, `quote_status` |

각 query에 대해 결과 노드와 관계의 `run_id`가 `$m6_run_id`와 같은지 확인한다. Evidence 자체에는 run_id가 없으므로 Q3는 확인된 node/edge ID에 부착된 근거인지도 대조한다. 실제 질의 결과가 0행이면 캡처를 성공 화면처럼 쓰지 말고, 파라미터/대상 ID와 그래프 내 연결 부재를 구분해 원인을 기록한다.

### 라운드 완료 판정

- M0 결정 기록이 통과하고 M1–M4 실제 증거가 같은 대표 문서/run을 가리킨다.
- M5 사람 판정과 승인 mapping이 근거·endpoint 검증 결과로 연결된다. 기존 `entity_links.sql` 초안이나 챗봇 중복 제거 기능만으로 M5를 완료 처리하지 않는다.
- M6 현재 run의 CSV/Cypher·Neo4j 적재·동일 입력 재실행·근거 표본 결과가 있다. 과거 적재 수치는 현재 상태로 섞지 않는다.
- M7 실제 질의 결과와 M8 판정표, 수정 뒤 재확인이 동일한 run 계보에 연결된다.
- M9 실제 시연, 팀원별 설명/기여, KPT가 기입된다. 증거가 없는 과제는 완료로 바꾸지 않는다.

### 서브 에이전트 실행 묶음

작업을 실제로 착수할 때는 파일 충돌을 막기 위해 아래 묶음별로 맡기고, 한 파일에 두 구현자가 동시에 쓰지 않는다.

1. **Agent A — M5 변환기:** M5 판정표를 입력받는 `src/lee_file_pipeline/graph_그래프/entity_resolution.py` 구현. 기존 `file_pipeline`은 수정하지 않는다. mapping CSV 검증, canonical 적용, 모든 edge endpoint 치환, edge 중복 collapse 및 ID 대응표, node/edge evidence 재연결, 격리 처리, 네 개 Neo4j CSV와 별도 audit manifest 생성을 맡는다. 사람 판정 결과를 자동 생성하거나 미승인 merge를 적용하지 않는다.
2. **Agent B — M5/M6 독립 리뷰어:** Agent A와 다른 에이전트가 입력 열·허용 scope·canonical/type/card/property 제약, 원본 보존, ID/run lineage, CSV 열·개수·endpoint·evidence 참조와 생성 Cypher를 읽기 전용으로 검토한다. 불일치가 있으면 A가 수정하고 B가 재검토한다.
3. **Agent C — M7/M8 제출 연결:** M0 질문을 `Q1 card-benefit`, `Q2 target-benefit`, `Q3 evidence-location`에 대응시키고 query 템플릿·분모 설명·캡처 체크리스트를 산출물 폴더 문서에 준비한다. 기존 쿼리의 고정 `우리`/`커피`와 미지원 `FpIssuer`를 일반 질문처럼 쓰지 않는다.
4. **통합 담당:** C0–C8 증거의 run 계보와 링크를 맞추고 M0–M9 상태표를 갱신한다. 팀이 제공하지 않은 실행 증거를 채우지 않는다.

Agent A의 산출물은 M5a 사람 판정이 승인되기 전 실제 CSV에 적용하지 않는다. Neo4j 실제 실행은 Agent B나 Codex가 하지 않으며 운영자가 진행한다. 구현 검증에 필요한 테스트 추가/실행은 별도 요청 범위로 두고, 그 전에는 이 계획 문서에서 실행했다고 표시하지 않는다.

## 현재 단계와 다음 행동

계약·검토 양식은 이 폴더에 준비되어 있다. 다음 실작업은 **M0 대표 문서의 공식 메타데이터와 이용/공유 범위를 팀이 확정**하는 것이다. 그 뒤 M1 처리 표본과 M4 run을 같은 문서에 맞춘다. 실제 LLM·Neo4j 실행과 원문 판정은 이 저장소 작업자가 대신하지 않는다.

`M0`, `M4`, `M5`, `M6`, `M7`, `M8`, `M9`는 실자료·사람 판정·외부 시스템 결과가 필요한 단계다. 그 증거가 이 폴더에 연결되기 전까지는 부분 완료/미실행으로 유지한다.
